# 踩坑记录

> 本文档整理本项目开发全程踩过的坑，按「现象 → 根因 → 解法」组织。
> 每个坑都是真金白银的时间换来的，希望后来者少走弯路。

## 一、架构设计坑

### 1.1 DDR 带宽共享导致画面细线撕裂
- **现象**：背景读与显示读共享 DDR 时，画面出现周期性细线撕裂。
- **根因**：分时复用不是简单时间片轮转——批处理完整性、切换条件严格性、burst 长度匹配任何一个细节都会在 60fps 高速流水中被放大。
- **解法**：消隐期双帧整帧读架构。利用 HDMI 场消隐期（4.26ms）将当前帧+背景帧（672000 拍）从 DDR 整帧读出并差分，显示期 DDR 完全归还显示读与采集写。三路严格分时仲裁（ser_arbiter），每个状态服务完整 burst，批未完成绝不切换，超时保护 256 拍强制切换防死锁。
- **教训**：FPGA 架构选择的正确性远重要于局部代码优化；带宽分配要在架构设计阶段算清楚。

### 1.2 前景标记漏写一行
- **现象**：上板发现前景标记 ERAM 漏写一行。
- **根因**：流水线排空窗口不足一个时钟周期——帧尾排空时序与 ERAM 写使能错位。
- **解法**：对照仿真波形逐拍比对，修正排空窗口。
- **教训**：FPGA 调试不能靠试错，必须依靠可观测、可复现的验证手段（仿真波形）。

### 1.3 fg_init 判据永远到不了
- **现象**：整帧读 700 行应写满 22400 字，原判据 22920 永远满足不了 → fg_init 恒 0 → 涂白/外接框全灭。
- **根因**：判据数值与真实写入字数不符（拍数换算错误）。
- **解法**：判据改 22080，背景检测恢复。
- **教训**：涉及「计数达到才置位」的状态机判据，必须用仿真确认计数器实际轨迹。

## 二、工具链坑

### 2.1 TD 的 DDR 参数真载体是例化参数，不是参数文件
- **现象**：改 ddr2 相关参数文本文件后编译，行为毫无变化。
- **根因**：PH1P35 的 DDR 参数真正生效位置是 ddr2.v 的例化参数；文本参数文件无效。
- **解法**：改 DDR 参数必改 ddr2.v 例化；改完必查 phy 日志确认（如 SYN-8411 数量与历史一致）。
- **教训**：工具生成的封装文件里「哪个文件才是参数真源」必须先验证再改。

### 2.2 GUI 保存会清掉 ddr2 引用
- **现象**：TD GUI 里手动保存工程后，编译报错/行为异常。
- **根因**：GUI 保存会重写工程文件，清掉 ddr2 引用等关键条目。
- **解法**：GUI 操作后对比 .al 关键条目（ddr2、CompileOrder）；必要时从备份恢复。
- **教训**：工程文件（.al）是「活文件」，GUI 会重写；改动后 diff 验证。

### 2.3 杀 TD 编译必须按 PID
- **现象**：两个工作区并行编译（命令行 + GUI），按进程名全杀会误杀另一个会话的编译。
- **根因**：同名 td 进程多实例并存。
- **解法**：taskkill /F /PID <具体PID>，绝不按进程名全杀。
- **教训**：多工作区并行是常态，杀进程前先确认 PID 归属。

### 2.4 TD 工程路径必须全英文
- **现象**：工程目录含中文（如「框」字）下板失败。
- **解法**：下板前工程目录改英文名；GitHub 仓库名同理用英文。

### 2.5 iverilog 与 TD 语义差异
- **现象**：Scharr 幅值取反 `~x[11:0]` 在 iverilog 仿真里全白，TD 上板正确。
- **根因**：iverilog 在部分表达式上下文存在 12 位位宽推断 bug（位宽上下文错误）。
- **解法**：改 XOR 掩码 `x ^ 12'hFFF`，两工具语义一致。
- **教训**：仿真与综合结果不一致时，先怀疑工具语义差异，用无歧义写法绕开。

### 2.6 裸 python3 是 ARM 工具链的
- **现象**：WSL 里 python3 装包报 SSL 错误/缺库。
- **根因**：PATH 里的 python3 是 ARM 交叉工具链自带 python（无 SSL）。
- **解法**：用 /usr/bin/python3 建 venv 装包（pip 走清华源）。

### 2.7 CompileOrder 必须连续且唯一
- **现象**：从 .al 删文件条目后留下编号空洞，TD 行为异常。
- **解法**：删除条目后把 CompileOrder 重排为 1~N 连续。
- **教训**：.al 是 XML，程序化改（正则删除 + 重排），改完验证连续性与顶层模块声明。

## 三、Verilog 语言坑

### 3.1 声明初值与复位值不一致
- **现象**：Sobel 阈值复位后显示 128（预期 512）→ 边缘全白+噪。
- **根因**：寄存器声明 `= 512` 与复位分支 `<= 128` 不一致，复位后取的是复位分支的值。
- **解法**：两处统一。
- **教训**：声明初值和复位分支必须成对检查——这是隐蔽性极高的坑，仿真里初值路径不同还不一定暴露。

### 3.2 隐式 1bit 线
- **现象**：数码管显示「1FFFE」垃圾，按键调了不显示。
- **根因**：wire 声明被注释吞掉，变成隐式 1bit 线，高位全截断。
- **解法**：声明拆行；全工程 iverilog 语法检查能捕获（隐式线警告）。
- **教训**：改代码后跑一次全工程语法检查，比肉眼查快且可靠。

### 3.3 带 initializer 的 wire 必须「先声明后使用」
- **现象**：TD 报错（时序依赖）。
- **解法**：联动块（先声明后使用）放在例化块之前。
- **教训**：TD 对声明顺序有额外要求，与 iverilog 宽松语义不同。

### 3.4 流水线延迟连锁改动
- **现象**：改了某模块流水线级数，下游对不齐 → 数据/valid/坐标错位。
- **教训**：改任何模块流水线延迟，必须连锁改下游所有对齐（打拍数、地址延迟、tvalid 链）；改完 grep 核对所有引用点。

## 四、算法工程坑

### 4.1 阴影抑制误滤目标内部
- **现象**：白墙背景下手内部暗区被误判为阴影滤掉 → 涂白稀疏、填充填不满。
- **根因**：相对色度容忍判据在低色度背景（白墙）上容忍仅 4~5，手内部（亮度低于墙面、AWB 后色度不升）完全满足阴影特征。
- **解法**：v3→v2 单向回退（场景门控 s_bg≥12 前置），最终为演示涂白完整性干脆全删阴影抑制（纯差分判据），接受影子涂白。
- **教训**：算法增强必须有针对性测试场景；「看起来更智能」的判据往往带出误滤，取舍要按实际演示效果定。

### 4.2 canny 边界断续虚线
- **现象**：左边界 4 列断续虚线、右边界 1 列擦不掉。
- **根因**：边界屏蔽只挡前 3 组（h_cnt 3~318），卷积链左邻居依赖实际扩散到第 4 组附近。
- **解法**：边界屏蔽扩为左 5 组右 2 组，实测校准。
- **教训**：卷积链的邻域扩散范围要实测，不能按理论模板半径拍脑袋。

### 4.3 阈值窗口被高增益噪声挤压
- **现象**：阈值稍高啥也看不见、稍低背景白噪声多。
- **根因**：曝光/增益处于极端状态，高增益噪声压过阈值窗口。
- **解法**：两级高斯级联（≈5×5 核）压噪 ~1.7 倍 + 阈值步进细化（11bit 域步进 16）。
- **教训**：调阈值体验差的根因可能在链路噪声，先压噪再谈阈值。

### 4.4 阈值跟随自动调节不如手动（用户实测结论）
- **现象**：二值/边缘阈值跟随亮度联动调节，实测效果不好（尤其边缘）。
- **决策**：回退为纯手动（I_auto_en=0），Sobel 阈值初值 48（实测甜点），保留 AE 重采背景联动。
- **教训**：联动方案好不好，只有上板实测才知道；「自动化」不是目的，效果才是。

## 五、调试方法论（经验总结）

1. **仿真先行**：每个算法模块改动先 iverilog/verilator 仿真验证，再综合下板。全程建立了 10+ 套 testbench 回归体系。
2. **验三连**：每次编译必查——真编译（exit 0 + bit 时间戳）、时序全绿（SWNS/HWNS）、SYN-8411 与历史一致（固有告警数量变了说明 DDR 配置被动了）。
3. **波形证据链**：疑难问题保存波形截图与现象照片，形成可回溯的证据链。
4. **大改动先写文档存档**：跨会话接力文档（迭代清单.md）记录每个版本的决策、验证结果与待办，下一个会话直接接手。
5. **参数真源先验证**：工具生成的工程文件、IP 封装里哪个参数真正生效，改之前先验证。
