# SC500 摄像头分辨率切换（720P↔1080P）与黑屏排查

板子资料（含 SC500 数据手册 SC500CS_数据手册_V1.8.pdf）：`D:\Users\user\Desktop\FPGA比赛\板子资料\HX1P35A_Contest_202606\4_芯片手册\SC500摄像头\`。查摄像头分辨率/帧率/寄存器先翻这本手册（用户偏好官方一手文档，不要从博客抄）。

## SC500 手册关键事实

- 命名口径：1080P（1920×1080）= 2K/FHD；1K = 720P（1280×720）——按横向像素数叫。
- Full Size FHD：1920×1080 @ **30fps**（1080P 只有 30 帧，没有 60）
- Crop HD：1280×720 @ 60fps
- **自动曝光统计模块必须跟着像素数重审（2026-10-27 用户发现 1080P 沿用 720P 自动调节不合适）**：720P→1080P 像素 2.25 倍，两处残留：①brightness_stat 累加器 28 位（720P 上限 2.35 亿够）在 1080P（5.29 亿）溢出回绕 → 扩 30 位；②右移 20 的「≈除像素数」缩放（720P 921600≈2^20 成立）在 1080P（2073600≈2^21）下统计=真实×1.98 → 自动曝光误判过亮压暗画面一半 → 改右移 21。改分辨率后凡是「除以像素数」类的统计/缩放，位宽和右移位数都要按新像素数重核（tb 用满灰度帧验溢出：全 255 帧 O_avg 应≈252）。
- 500 万像素传感器；MIPI 2 lane 输出
- MIPI 关键寄存器：3018 = lane 数量、3031 = 输出数据模式（raw8/raw10，接收端 uial2axis 位宽须一致）、3650 = MIPI LP 驱动、3652/3654 = 相位延时、3800 = group hold 控制（0X 打包/1X 打包完/6X 立即生效/4X 延迟生效）、3e08/3e09 = 曝光上限
- **像素阵列结构（错位/边距排查的源头依据）**：像素阵列 2600H×1952V，Active Array 2592H×1944V，Active Border = 四边各 4 列/4 行（dummy 像素）；手册 2.4.1 读取顺序图、2.4.2 输出窗口表。输出窗口寄存器默认值：宽 {0x3208,0x3209}=0x0a20=2592、高 {0x320a,0x320b}=0x0798=1944、列起始 {0x3210,0x3211}=0x0008=8、行起始 {0x3212,0x3213}=0x0008=8（默认跳过阵列左侧 8 列 dummy）。**720p60 例程实际 crop 配置（uics500reg_720p60.v）**：宽 0x0500=1280、列起始 0x0200=512——crop 起点在有效区内部，行数据 100% 拍摄像素、行首无前瞻/边距数据。打包层也无 padding：RAW10 每行 1280×10bit=12800bit=100×128bit 整除，ISP 输出 240×128bit/行整除。排查「错位/异常是否来自传感器数据源头（行首有多余数据）」时：先 pdftotext 手册 grep 阵列/窗口表，再 grep 例程寄存器文件里 0x3208/0x3209/0x3210/0x3211 的实际值算 crop 窗口。

## 官方 1080P 参考例程（黑屏排查的零成本对照工具）

板子资料自带官方 1080P 直出例程：`HX1P35A_Contest_202606\2_Example\32_cs500_mipi_hdmi\`（VTC 2200×1125、像素时钟 75MHz、MIPI→ISP→HDMI 直出无 DDR 帧缓存），**其 td/test_Runs/best_result/test.bit 是编译好的官方 bit，可直接下板对照**（同板同管脚）。官方例程的存在意味着：

- 配套显示器必然认 1080p30（75MHz）时序——「显示器不认 30Hz」不能作为第一嫌疑，除非连官方 bit 都不显示。
- 官方 uics500_cfg/uics500reg.v 是厂商验证过的 1080P 寄存器表——工程里改分辨率手写的表用它逐条对照。
- 官方例程无 DDR 帧缓存，工程加了 DDR 乒乓后黑屏，差异范围 = DDR 读写链 + 手写寄存器表，两处分别对照。
- **官方 bit 的 device 可能对不上用户的板**：板子资料是竞赛板包（HX1P35A，芯片 PH1P35A），用户的主板是 PH1P35——官方预编译 bit 固化的是 PH1P35A，下载报「The default bit is not match with the device」。报这个错别折腾下载工具，直接放弃官方 bit 对照、改走「寄存器表 diff + 自己工程编译验证」（同板同管脚只对同芯片型号成立）。

## 切换分辨率要动的参数层（720P↔1080P 全清单）

工程里改分辨率不是改一个参数，六层都要对齐（**权威清单 = lab_ex1 的 uics500reg_1080p30.v 头注释**：uicfg 实例、uial2axis、ISP、DDR 帧尺寸、VTC、hdmi_mixer、hdmi_tx 全部切换，漏一处 = 黑屏/分屏/错行/DDR 帧不同步）：

1. **摄像头寄存器表**：uicfgcs500_720p.v 内 `u_init_table` 例化的是 uics500reg_1080p30 还是 uics500reg_720p60——两套完整寄存器表同目录共存，切换 = 改例化名。两表的头注释互指，默认只把一个加入工程源文件列表。
2. **PLL 像素时钟**（.params_PLL.txt 的 CLK4_REQUEST_FREQ）：720p60 = 74.25MHz；1080p30 = 74.25MHz（分频不变）；1080p60 = 148.5MHz。改频率要走 TD GUI IpTool 重新生成 IP（命令行改参数文本 + 删 db 全量重编都刷新不了，见 td-commandline-build.md）。
3. **VTC 时序**（design_top_wrapper 的 uivtc 例化）：720p60 = 1650×750；1080p30 = 2200×1125 @74.25M；1080p60 = 2200×1125 @148.5M。
4. **ISP 链路行参数**：uial2axis 的 IMG_WIDTH/IMG_HEIGHT、demosaic line_buffer 的行缓冲参数、isp_top 内部 IMG 参数——720P 硬编码 1280/720 的地方全部要改成 1920/1080，漏一处 = 行结构错乱。
5. **hdmi_mixer 的 IMG_WIDTH/IMG_HEIGHT** 例化参数。
6. **DDR 帧尺寸**：bg_read.v 的 FRAME_CNT_128（720P=172800 / 1080P=388800）和对应计数位宽（S_rd_total 18 位→19 位防 388800 溢出）——**即使模块当前被 I_bg_en 禁用也是潜伏雷**（禁用只是不触发读，帧尺寸写错会在启用后错行）。切分辨率时全工程 grep 帧字数常量（172800 / 388800 / 0x2A300 / 0x5EE80）一处不落，video_in/video_out 是纯地址递增/读窗口直通、无帧尺寸参数可跳过。
7. **像素数相关的统计/计数类模块（最易漏，实锤 bug 层）**——分辨率切换时全工程 grep「像素数」出现在注释/常量里的模块逐个重算：
   - **累加器位宽**：一帧灰度总和 = 像素数×255。720P 921600×255≈2.35 亿（28 位够）；1080P 2073600×255≈5.29 亿 > 28 位上限 2.68 亿 → **溢出回绕、平均亮度统计乱掉**（brightness_stat 的 r_sum 28 位扩 30 位）。
   - **平均值的右移缩放位数跟像素数的 2 次幂级走**：sum>>N 近似÷像素数，720P 921600≈2^20 用 >>20（统计=真实×0.88 可接受）；1080P 2073600≈2^21 必须 >>21——沿用旧 N 时统计=真实×1.98，自动曝光闭环把画面当「比实际亮一倍」往下压，画面整体偏暗一半。**任何「sum>>N 求平均」的模块切分辨率后 N 必须重算。**
   - **曝光上限 AE_MAX = 2×帧长-10 跟帧长走**：720P 帧长 2000 → 3990；1080P 帧长 1127 → 2244。
   - **调节周期帧数不变时实际间隔随帧率变**：每 40 帧调节在 720P 60fps 下 0.67s、1080P 30fps 下 1.33s——响应慢一倍属预期，实测闭环正常可保持不动。

## 1080P 黑屏排查顺序

0. **传感器不出流的排查要「先验灯、再对照恒高版」**：LED4 亮（I2C 表写完）+ LED3 灭 ≠ 传感器卡死——**先 grep LED 驱动条件里每个信号是否有驱动**：tvalid_act 判定 `I_tvalid && O_tready`，顶层 O_tready（S_ISP_O_tready）曾悬空=TD 综合成 0 → LED3 从始至终恒灭，把排查带偏成「传感器卡死」；诊断灯条件里的悬空 wire 比灯本身更先要查。**XSHUTDN 复位脉冲是反面教训**：给恒高的 O_cam_rst 加「配置完成拉低 1ms → 拉高等 6ms → 写 I2C」的复位脉冲后传感器反而不出流（复位后 I2C 恢复等待不足、前几条寄存器写失败 → 配置不完整），而主线「O_cam_rst 恒 1」版本热下载一直正常。**规则：加传感器复位脉冲前先对照已验证的恒高接线版本（直接下板主线 bit）；若确需复位脉冲，复位后到 I2C 的等待取 50~100ms 而非手册最小值 4ms**。手册上电时序（数据手册 V1.8 图 1-6/1-7）：XSHUTDN 拉低 T4≥1ms、拉高后 T5≥1ms、EXTCLK 有效 T6≥4ms 才能 I2C；官方例程 O_cam_rst 恒 1、上电仅 5.3us 就写 I2C 也能工作（官方 demo 靠断电上电）。

1. **先看 LED 组合语义——但读灯前先 grep 顶层 O_led 当前接线**（诊断 patch 复用 LED 后语义会漂移，LED4 曾从「摄像头配置完成」改成「写 FIFO 满锁存」，用户记忆的语义可能过期）：LED4 灭 = 寄存器没写完/I2C 问题；LED4 亮 + LED3 灭 = 配置写进去了但传感器没流数据 → 嫌疑在寄存器表内容（分辨率/流启动/MIPI 配置）而非接线；两灯都亮 = 数据在流、写侧在写，问题在写 DDR 之后的链（DDR 读/显示）或显示器。
2. **显示器问题的精确判据**：不认时序 = 连 OSD 都不显示（无信号）；OSD 文字/logo 正常但视频区黑 = 显示器没问题、时序没问题，问题在视频数据链（HDMI 链全好）。换显示器对照：OSD 出来了说明原来那台不认该时序；OSD 出来后视频仍黑则显示器因素排除。
3. **官方 bit 对照**：下板官方例程 test.bit（见上节）——出画面 = 硬件/板子/摄像头全好，问题 100% 在工程改动（寄存器表或 DDR 链）；官方 bit 也黑 = 硬件问题，省一次白编译。
4. **寄存器表 diff 法**：把工程手写的分辨率表与官方 uics500reg.v 逐条对比（sed 提取 `16'hxxxx, 8'hxx` 排序后 comm/diff）。**脚本解析坑：case 的 default 行（`{16'h0000, 8'h00}`）不是表条目、同一地址写两次会被「唯一地址」计数漏掉**——提取条数与 REG_SIZE 对不上时先按 case 实际枚举索引数（REG_SIZE-1）。两个疑点按优先级：①工程表「多写的寄存器」比「值不同」更可疑——官方验证过的表不写某寄存器说明默认值即可用，工程多写很可能写错（实例：3018=MIPI lane 数、3031=输出数据模式、3650=MIPI LP 驱动、3652/3654=相位延时，全是 MIPI 物理层配置，写错任一都可能让传感器不出流）；②「值不同」的寄存器按手册逐条核对默认值与位含义。确认后把表对齐官方编译验证。
5. **对齐官方的操作坑**：case 序号表（case(REG_INDEX) 枚举）**不能只删条目**——删掉的序号无匹配分支，REG_DATA 保持 reg 旧值 = I2C 重复写上一条；正确做法是整表文件替换（cp 官方 uics500reg.v 覆盖），然后对齐三处：①模块名改回工程例化的名字（u_init_table 例化的模块名）——官方文件 module 名与文件名不一致（uics500reg.v 里 module 声明是 uics500reg），忘了改会报 `HDL-8007 ERROR: <模块> is a black box`；②REG_DATA 位宽对齐工程的 wire（官方声明 [31:0]、工程例化接 [23:0]——改成 [23:0]，否则仿真告警、TD 靠截断混过去）；③REG_SIZE 按官方表条数自动带出，不用手动改。替换前 cp 备份原表。
6. **数码管计数截断是假象**：写计数 18 位寄存器在 1080P 溢出截断（388800 mod 262144 = 126656 = 0x1EEC0）——不是数据坏，见 ddr-debug-bisection.md 计数位宽条。
7. **写 0 + 画面冻结的二分之一刀：把数码管 debug 源从写计数换成读计数**（顶层 seg_data 一行，{13'd0, S_dbg_rd_cnt}）——读计数 5EE80 = 读在跑/DDR 活（断点在写批触发条件）；读计数 0 = DDR 全停（校准失败/命令接口死）。一次编译同时带「修诊断灯 + 切换读计数显示」两个二分探针，下板一趟定位所有断点，省 45 分钟。
7b. **黑屏区显示「多份一模一样的图/像第一帧」= DDR 残留数据，不是摄像头只出一帧**：写停（写计数 0）后读侧轮转乒乓旧块，旧帧内容被重复显示成多份。判读前先看写计数和读计数，别先下「传感器只工作一帧」的结论。**DDR 内容跨复位/跨 bit 重下载持续（FPGA 复位不清 DDR，仅断电清）**：用户报「显示的是下载这一版之前的图（如主线 720P 边缘检测旧图）、复位没用」正是此因——残留画面不能作为「新 bit 没生效」的证据，判新 bit 生效看数码管/LED/新观测。
7c. **「左 1/3 实时画面 + 右 2/3 黑/白闪」的判读**：读计数≈整帧（5EE80）而画面只铺 1/3 → 写量不足。写计数 5EE80=满帧（问题在行结构/地址）；写计数≈1FA40（1/3）=传感器数据率或写批速率不足。**先查写批速率/读占空（读批是否占满仲裁把写饿死）再动表；表的方向是「对齐官方例程 1080P 原版」而非按 Full 模式参考删 PLL——1080P 删 PLL 覆盖 = 传感器不出流（实测写 0）**。表内容对不齐时逐条与官方 uics500reg.v diff（方法见第 4 条）。
7d. **「黑、白、画面三种内容轮闪」= 4 块乒乓只有 1 块被写**（wp 卡 0、读指针 rp 每帧轮转看到 3 块空/旧+1 块实时）。wp 递增的三个门控逐一查：I_display_pause、I_mipi_rx_error（顶层接没接恒 0）、S_frame_start 帧开始下降沿（tuser 链经 demosaic/awb 直通到 data96_128 的 awb_O_tuser_128 才是 O_tuser）。
7e. **写 0 的三信息排除法**：写计数 0 + FIFO 满锁存 0 + LED3 亮（ISP tvalid 恒 1）同现时，对写批四条件（水位≥批长、!读忙、!FIFO 复位、!跳帧屏蔽）逐一排除——满锁存 0 直接排除「读忙恒 1」和「跳帧屏蔽恒 1」（这两种 FIFO 会涨满、full_flag 必置 1），候选收敛到「FIFO 恒复位（tuser 恒 1）」或「水位攒不够」。**加帧开始锁存位（once-latch）后进一步区分：fs_latch=1 直接排除 tuser 恒 1**（恒 1 时 S_frame_start 下降沿永不触发、锁存位不可能置 1）。板载实测读数 80000000 = {fs_latch=1, 满锁存=0, 写累计=0}：满锁存 0 再排除「rd_busy 恒 1」和「masked 恒 1」（这两种都会让 FIFO 涨满置满锁存）；停写批曾按「帧开始高频打断写批」假说怀疑并删除，删除后写累计仍 0（下板复现）→ **停写批已排除，别重复删停写批实验**。剩余候选：FIFO 写侧没进数据（we 恒 0/demosaic 之后 O_tvalid 链断）或水位攒不够（FIFO 复位窗口/上游 valid 节律异常）。**该案已结（2026-10-27）：真凶 = isp_top 抄漏 algo_valid 驱动行**（分支工程无驱动变体，见 sim-passes-board-fails.md 第 0 条）——帧开始锁存 1 + 写累计 0 + FIFO 满 0 的组合最终指向「ISP 输出 tvalid 恒 0」，用「LED 诊断点从 ISP 输入逐级前移到 ISP 输出」+ demosaic 1080P 独立仿真排除后，grep 对照主线实锤。**教训：写 0 类排查到「数据链没进 video_in」层级后，先 grep 各环节 valid 信号的驱动存在性（例化引用有、驱动无 = 抄漏），再逐模块仿真，别倒过来白仿一轮。**tuser 链源头沿 csi_unpacket FS 检测 → raw10 打拍 → uial2axis（tuser = vcnt==0 && hcnt==0）→ demosaic 延迟 → awb 直通 → data96_128 打拍逐级查。仿真三档对照（恒 0/恒 1/行频）可离线实锤（方法见 sim-debug-methodology.md 对照激励二分）。
7f. **数码管诊断档位改语义后，下板说明按板上物理拨向写**：板上 SW4「拨下」= I_sw[3]=1（低有效，与代码注释直觉相反）——用户习惯性拨下想看摄像头数据时，看到的是 case 分支（前 4 位恒 FFFF 的曝光/增益档）或旧语义档位，误判成「写计数 0」。改 seg 显示源后下板说明必须写「拨上/拨下各显示什么」，并让用户报 8 位数码管从左到右的全部数字而不是笼统的「0」——{满锁存, 12'd0, 写计数[18:0]} 的前 4 位同时含 full_latch 和写计数高 3 位，可直接判读。
7. **行结构残留**：video_out/hdmi 解包按 128bit 字与行宽的整除关系（720P 行 = 240 字、1080P 行 = 360 字）——批长 240 与行宽无关可保留，但任何「每行固定 N 批」的假设要重算。
8. **帧率不匹配**：摄像头 30fps vs 显示 60fps 时，若 FIFO 无重复帧处理会读空——先确认显示时序频率与输入帧率的关系再下板。

## Motorola 量产内核驱动 = SC500CS 权威寄存器参考（比官方例程表更权威）

SC500CS 曾是 Motorola 手机量产摄像头，内核驱动就是官方量产配置：

- 源码：GitHub `MotorolaMobilityLLC/kernel-mtk`，路径 `drivers/misc/mediatek/imgsensor/src/common/v1/mot_ellis_sc500cs_mipi_raw/ellis_lce_sc500csmipiraw_Sensor.c`（GPL-2.0）。raw.githubusercontent 直连慢/超时（校园网）时改走 jsDelivr CDN：`https://cdn.jsdelivr.net/gh/MotorolaMobilityLLC/kernel-mtk@<commit>/<path>`。

- **驱动权威事实（与官方例程表逐条 diff 后的差异都要按这些判）**：
  - **36EB/36ED/36FA/36FB/36FC 五条「PLL 覆盖」的删留按模式区分（实测血泪）**：Motorola 参考是 **Full 模式（2592×1944）** 的表——Full 模式删这五条（量产驱动不写、寄存器缺席用复位默认）。**1080P 模式必须保留官方例程表的这五条**：实测从 1080P 表删掉后传感器直接不出流（写计数 0），官方例程的 PLL 覆盖是 1080P 的必需配置。**跨模式套用参考表结论前，先确认参考表是哪个分辨率/模式——Full 模式结论不能直接套 1080P。**
  - **36E9/36F9 是 bank（页）切换寄存器**：写 80 开页 → 写页内寄存器 → 写 04 关页。读表结构先识别 bank 边界，不要把页内寄存器当平铺。
  - **0103=01 也是 stream off**（与 0100=00 同写）；**开流收尾顺序恒为 0100=01 之后紧跟 302D=00**——工程表结尾是 0000=00 的要对齐；302D 只写一次 00，中间写 302D=20 的删掉。
  - **模式切换（预览/捕获）时序：0100=00 关流 → mdelay(10) → 0100=01 开流 → 302D=00**。初始化表本身连续写无此要求（表首 0100=00、表尾 0100=01 与量产 sensor_init 同构），但「关流后立即开流」在切换场景是稳定出流的隐患。
  - **I2C 初始化延时实测结论（2026-10-27）**：官方例程 8 位计数器 10.7us 是验证过能出流的值；改成 Motorola 参考的 5ms（120000 拍）后实测同样写 0（传感器不出流）。SC500 上电到 FPGA 配置完成的时间已天然满足 T6，不必额外等 5ms——跨工程照抄延时也会踩坑。
  - **VTS（320E/320F）决定帧率**：Full 30fps 的 VTS=2000（官方例程旧表 VTS=3000 → 只有 ~20fps）；1080P 表 VTS=1127 是 1080p30 正确值；720p60 表（uics500reg_720p60）VTS=1000 是 60fps 正确值。HTS=320C/320D（Full 模式 1600）。**验证实际帧率 = grep wrapper 例化的 sensor 初始化表模块名（u_init_table 例化 uics500reg_1080p30 还是 uics500reg_720p60）+ 该表 VTS 寄存器值——注释写 60fps 不一定等于实际配置**。
  - 通用现象佐证：量产工程文档明确「下载新 bit 后要 reset/power-cycle 摄像头」——热下载后传感器需要重新初始化才能应用新寄存器表，FPGA 复位键重跑 I2C 即等效复位。

## 主线仿真实锤的 video_in 修复的移植边界（停写批在 nogrant 已回滚）

1. **帧开始强制停写批（S_frame_start_d1）在 nogrant 1080P 已回滚，且不是写 0 的元凶（实测排除）**：停写批在位时写累计 0；删除停写批后下板写累计仍 0（80000000 复现）——停写批排除。「帧开始频率高于写批完成时间（240 拍 @66.67M ≈ 3.6us）→ 停批+计数清零 → 写批永远完不成」只是未实锤的假说，不要当结论引用。**跨工程/跨分辨率同步修复后必须下板重验，不能标「已同步」了事**。排查「写 0/写不足」优先查会持续门控的改动（FIFO 复位、masked、rd_busy、水位、we 有效链），脉冲型改动（停写批）先按无害处理、有实锤再升级。
2. **O_fifo_full_latch 满锁存诊断**（保留，移植无副作用）：采集 FIFO 的 full_flag 锁存到复位，数码管最高位显示——1=FIFO 满过溢出丢字（「写不准」的实锤，帧残缺直接证据），不用再靠写计数猜。
3. **写 0 的三标志组合判读**（帧开始锁存 + FIFO 满锁存 + 写累计计数，一次编译带三个观测）：满锁存 0 排除「rd_busy 恒 1」与「masked 恒 1」；帧开始锁存 1 + 写累计 0 = 帧开始活着但写批死（停写批/水位/FIFO 复位三选一）；帧开始锁存 0 + 写累计涨 = tuser 链断但写批照跑（wp 不递增 = 轮闪根因）。写累计必须自由累计（不依赖帧开始锁存显示），否则帧开始一断显示恒 0、与「写批死」无法区分。

## 操作坑（改 Verilog 源）

- **patch 工具改 .v 文件时不要在 new_string 里写 `\t` 转义表示 tab**：JSON 转义层会把 `\t` 按字面反斜杠+t 写进文件（`assign O_cam_rst \t= 1'b1;`），TD 报 HDL-8007 syntax error。写真 tab（复制原文里的制表符）或空格。改完 grep 字面 `\\t` 残留再编译，别浪费一次 45 分钟的编译。
- **诊断 patch 收工前必须全量恢复**：根因修复 + 下板验证通过后，把诊断性改动（复用 LED 的语义、seg 的调试档、为观测新增的输出端口/锁存位）全部还原成功能语义——LED 恢复 {cfg_done, 数据活动, 模式码}、数码管恢复按模式显示功能值；**恢复基准 = 主线同段代码（主线禁改，永远是可用参照）+ 会话里自己的 patch 记录反推**。有长期价值的诊断端口（如 O_fifo_full_latch）保留但顶层接线注明「暂不显示」，而不是整体删除。清理完先 grep 各诊断信号名（frame_start_latch/isp_out_valid_latch 等）确认全文件残留为零，再启动编译。
- **删端口后必查端口列表尾逗号**：从 output 列表删除最后一个端口时，前一个端口行的逗号会残留（`output reg O_fifo_full_latch,` 后直接 `);`），iverilog 报 Superfluous comma in port declaration list——单文件 `iverilog -tnull` 语法检查秒抓，别带病进 45 分钟编译。
