# DDR 视频帧缓存 + 多路访问仲裁（PH1P35 竞赛项目实战）

本次会话（2026-10-20）在安路 PH1P35 上把「运动检测背景减除」从全分辨率 DDR 背景读一路调试，核心成果是**自写 DDR 多路访问仲裁器**。以下按「类级知识」组织，避免下次重踩。

## 1. DDR 单路 AXI 多路访问的标准做法：优先级 + 饿死超时仲裁器

**背景**：安路合封 DDR 是「单路 AXI」接口，官方 lab_ex 例程只用「一路写 + 一路读」的显示帧缓存，**官方没提供多路仲裁参考**。竞赛项目要加「第三路背景读」，必须自写仲裁。

**症状**：三路（video_in 写 + video_out 读 + bg_read 读）用「组合逻辑互相避让」（写避让读、读避让写、背景读避让写读）+「地址复用写优先」，结果是**随机闪烁 + 周期性错位带**（读写指针竞态 + 低优先级饿死）。

**根因**：组合逻辑「互相避让」存在「同时触发竞态」（地址被覆盖）+ 没有调度器导致「低优先级饿死」。

**正确做法（本次验证）**：

```
1. 各路不互相避让，只上报「请求」（req = 突发有效电平）
2. 顶层仲裁器按优先级发「grant」（时序逻辑，互斥，无竞态）
3. 各路在 grant 时真正读写 DDR（使能/计数/地址都 grant 门控）

优先级：显示读无条件最高（显示不能断，req_rd 时无条件 grant，不参与饿死超时）
        写/背景读：正常写优先，饿死超时轮转（谁等待超时谁强制 grant）

饿死超时：每路一个等待计数器，请求且没被 grant 时 +1，被 grant 时清零，
          计数 >= 阈值(WR=100/BG=200) 时该路「饿死」，强制 grant。
```

**关键代码结构**（顶层）：

```verilog
wire req_rd = S_vo_rd_req;  wire req_wr = S_vi_wr_req;  wire req_bg = S_bg_req;
reg grant_rd, grant_wr, grant_bg;
reg [7:0] wr_wait_cnt, bg_wait_cnt;
always @(posedge clk) begin
    wr_wait_cnt <= (req_wr && !grant_wr) ? wr_wait_cnt+1 : 0;
    bg_wait_cnt <= (req_bg && !grant_bg) ? bg_wait_cnt+1 : 0;
end
always @(*) begin
    grant_rd=0; grant_wr=0; grant_bg=0;
    if (req_rd)            grant_rd=1;   // 显示读无条件优先
    else if (req_wr && wr_wait_cnt>=100) grant_wr=1;  // 写饿死
    else if (req_bg && bg_wait_cnt>=200) grant_bg=1;  // 背景读饿死
    else if (req_wr)       grant_wr=1;
    else if (req_bg)       grant_bg=1;
end
assign S_ddr_user_wr_en = S_vi_ddr_wr_en && grant_wr;
assign S_ddr_user_rd_en = (S_vo_ddr_rd_en && grant_rd) || (S_bg_rd_en && grant_bg);
assign S_ddr_user_addr  = grant_wr ? S_vi_wr_addr : grant_rd ? S_vo_rd_addr : grant_bg ? S_bg_addr : 0;
```

**各路改动**：删掉「互相避让」输入，加 `O_xx_req`（=突发有效）+ `I_xx_grant`（grant），突发使能/计数/地址递增全部 `& grant` 门控。这样 grant=0 时该路「暂停」（计数地址冻结），grant=1 时继续。

**踩坑**：`grant_*` 的 `reg` 声明必须放在「信号声明段」（例化连接之前），否则例化连接里第一次出现会「隐式声明 wire」跟后面的 `reg` 冲突，报 `already implicitly declared` CRITICAL-WARNING。

**反模式（踩过）**：第一版把「饿死超时强制」排在「正常优先级」之前（`if(req_rd&&rd_starved)…else if(req_wr&&wr_starved)…else if(req_rd)…`），结果写/背景读一饿死超时就**抢占显示读**，显示读断流 → 出现「暗带错位」。正确做法：显示读 `req_rd` 时**无条件 grant 放第一个 if**，饿死超时只用于写/背景读、且放 `else if` 里（只在显示读空闲时才轮转）。饿死超时（starvation timeout）是给低优先级端口兜底的，绝不能让它反过来饿死高优先级端口。

## 2. 闪烁排查的错误链（从表象到根因的完整路径）

1. 横白线（18 根均匀）→ **解包 D 丢失**：`bg_read` 读侧 `re=1'b1` 直读把「3/4 拍有效」读成「4/4 拍」，`data_128bit_to_96bit` 的 `S_cnt` 每拍 +1、第 4 个 96 位（D）丢不出来 → 改读侧 re 为「独立 3/4 节流计数器」（`rd_cnt!=0`，每 4 拍读 3 拍）。
2. 白线消但「上下移动花屏」→ **DDR 半速**：板载 SIT9121 差分晶振（100MHz，K5/L5）被闲置，DDR ref_clk 接 50M 晶振 C4 → 整个 DDR 半速（内存 533Mbps + usr_clk 66.667M）。IPUG035 手册「4:1 标准」= usr_clk 133.3M。
3. ref_clk 改 100M 差分晶振（`PH1P_LOGIC_IBUF_DIFF` 差分转单端）→ 内存 1066Mbps 满速。
4. **满速 1066 花屏**：SWNS +0.007ns 贴边（usr_clk 133.3M 下 MC IP 内部 7.493ns 路径）→ 降内存速率 800Mbps 稳定。
5. **帧同步对齐失败（已回退）**：用「背景帧开始」动态对齐当前帧（FIFO + 读指针对齐），引入循环依赖×2、打包相位错位（竖分割）、解包 S_cnt 无帧复位（花屏）等一堆问题。
6. 禁用背景读后「原样+灰度+二值+边缘」跑通 → 坐实背景读（第三路整帧访问）是闪烁唯一根因，显示链路两路本身稳定。
7. 自写仲裁器 → 随机闪烁消失，但暴露「60 帧周期错位带」（帧率差，见 §5）。

## 3. DDR 时钟配置（半速 / 满速 / 降速）

**半速检测**：`.params_ddr2.txt` 里 `PH1P_REF_CLK=100.0`（期望 ref_clk 100M），但顶层 ref_clk 接 50M 晶振 → VCO 只有一半，整个 DDR 半速。**合封 DDR 标称 1066Mbps（DS1300），ref_clk 应为 100M 差分晶振（K5/L5，SIT9121 LVDS）**。

**满速花屏 → 降 800Mbps 的参数**（改 `ddr2.v` + `.params_ddr2.txt` + `.m_params_ddr2.txt` + `Design.xml` 四个文件同步）：

| 参数 | 1066Mbps | 800Mbps |
|---|---|---|
| tCK | 1876 ps | 2500 ps |
| CL | 7 | 6 |
| CWL | 6 | 5 |
| PLL0_FBKCLK_DIV | 32 | 24 |
| PLL1_REFCLK_FREQ | 133.3 | 100.0 |

（VCO = ref_clk × FBKCLK_DIV/REFCLK_DIV；800Mbps 时 usr_clk 100M，SWNS 裕量 2.5ns 稳定。）

**半速→满速 1066Mbps 回改（2026-10-21 实测成功，时序全绿 SWNS 259ps）**：
- `ddr2.v`：只改 `PLL0_REFCLK_FREQ` 50.0→100.0（tCK 1876 / CL 7 / CWL 6 / FBKCLK_DIV 32 / REFCLK_DIV 3 已经是满速值不用动——半速当时是「ref_clk 接 50M 晶振」实现的，tCK 参数没跟着改）。
- 顶层：加差分端口 `I_ddr_ref_clk_p`/`I_ddr_ref_clk_n`，加 `PH1P_LOGIC_IBUF_DIFF #(.DIFF_TERM("TRUE")) u_ddr_ref_clk_ibuf`（`.i_p/.i_n/.interm_disable(1'b0)/.o(S_ddr_ref_clk)`），DDR wrapper 的 `.I_sys_clk` 接 `S_ddr_ref_clk`。
- `pin.adc`：`I_ddr_ref_clk_p=K5 / I_ddr_ref_clk_n=L5`，**IOSTANDARD 是 `LVDS18`**（不是 LVDS/LVDS33/DIFF_SSTL15！K5/L5 在 BANK11 是 DDR bank，SIT9121 LVDS 晶振经 R254=100R 上拉 1.5V 适配）。
- `timing.sdc`：`create_clock -name ddr_ref_clk_100m -period 10.000 [get_ports I_ddr_ref_clk_p]`。
- **反查精确配置的方法**：grep 之前满速综合日志 `syn_1/run.log` 的 `RUN-1002 start command "set_pin_assignment ..."`，直接翻出当时的端口名/IOSTANDARD/引脚，不用猜。

## 4. 128↔96 打包解包的 S_cnt 帧复位

`data_96bit_to_128bit`（打包）的 `S_cnt` 在 `I_96b_valid=0`（消隐）时归 0；`data_128bit_to_96bit`（解包）的 `S_cnt` 原来**从不复位**（上电相位随机），导致解包输出像素序列错乱 → 花屏。修复：解包的 `S_cnt` 在 `I_128b_frame_start`（背景帧开始）时归 0，跟打包的消隐归 0 对应。3 个 128 位 = 4 个 96 位（最小公倍数 384），一帧 172800 个 128 位是 3 的倍数所以帧末自动回 0。

## 5. 帧率对齐（genlock）：HDMI 75M vs 74.25M

**现象**：仲裁器修好随机闪烁后，暴露「每隔约 60~100 帧，一段长方形暗带（比正常暗、非花屏）从上往下滚、复位到上方」。

**根因**：主 PLL 的 `clk4` 请求 74.25MHz（720p60 标准），但 `.params_PLL.txt` 里 `VCO_FRACTIONAL_ENABLE=0`（小数分频关闭），VCO 只能用整数倍（1500M=50M×30），`clk4=1500/20=75MHz`（不是 74.25）。HDMI 帧率 = 75M/(1650×750)=60.6fps，摄像头 60fps，差 1% → 写指针（跟摄像头帧开始）和读指针（跟 HDMI vsync）相位每帧漂移 → 读写指针错位带周期滚动。

**解决（三条路，实测结论）**：
- ❌ 开 PLL 小数分频：安路 PLL 的 `SDM_FRAC` 是正小数（0~2^24-1），只能让 VCO 往上走，到不了 1485M（比 1500M 小），74.25M 配不出来。
- ❌ 改 H_FrameSize 1667（让 75M 对应 60fps）：显示器黑屏不认（HDMI 时序对消隐严格，后肩 +17 也不认）。
- ❌ **读指针独立 + 互斥锁跳帧**（Intel 白皮书「帧缓冲解耦」思路，见 §7）——**已证伪**：下板出现「撕裂带（从左到右无规律闪）+ 黑带中间白点」，回退到「读指针 = 写指针 + 2」。
- ✅ **最终结论：帧率差根本不是根因**。下官方例程（lab_ex1，也用 75M）做基线对比发现「一切正常」——错位带/闪烁是**我们工程自己的改动**（背景读/仲裁器/读指针独立）引入的，不是帧率差。**教训：先下载官方例程做基线对比，再折腾自己的改动**（详见 §7 反转）。

## 6. 安路 PH1P 原语（TD 本地模板库）

- **LVDS 差分输入转单端**：`PH1P_LOGIC_IBUF_DIFF`（端口 `i_p/i_n/interm_disable/o/o_p/o_n`，参数 `DIFF_TERM`）。模板在 `TD_6.2.1/template/verilog/Device-Primitive/PH1P/I,O/ph1p_i_o.v`。
- 差分输出 `PH1P_LOGIC_OBUF_DIFF`，双向 `PH1P_LOGIC_IOBUF_DIFF`。
- **K5/L5 是 DDR I/O 引脚（ddrio，BANK11 的 IO_L1P_11/IO_L1N_11，VCC_1V5）**，IBUF_DIFF 的 DIFF_TERM 片内端接不生效（报 `can't config diff term` CRITICAL-WARNING）——但 DDR ref_clk 裸跑能锁住，不影响功能。
- **K5/L5 的 IOSTANDARD = `LVDS18`**（不是 LVDS/DIFF_SSTL15，从综合日志 `set_pin_assignment I_ddr_ref_clk_p LOCATION = K5; IOSTANDARD = LVDS18;` 反查的精确值）。晶振 SIT9121AI-2B1（100MHz LVDS），板端端接：R254=100R（N 上拉 VCC_1V5）、R256=1K（P 下拉 GND）、R262=100R/NC（差分端接未焊，靠 IBUF_DIFF 的 DIFF_TERM）。**满速 ref_clk 全套改动**：顶层加 `I_ddr_ref_clk_p/n` 端口 + `PH1P_LOGIC_IBUF_DIFF`（实例名 `u_ddr_ref_clk_ibuf`，DIFF_TERM="TRUE"）+ pin.adc 加 K5/L5 LVDS18 + timing.sdc 加 `create_clock ddr_ref_clk_100m`（100M，源 I_ddr_ref_clk_p）。
- **满速 1066 的时序关键路径在 hdmi_mixer（不是 DDR）**：禁用背景读只剩两路时，SWNS 最差路径 = hdmi_mixer 第 323 行 Logo 地址计算 `S_logo_addr = (S_y_2d-LOGO_Y)*160 + (S_x_2d-LOGO_X)`，`*160` 用 DSP 乘法器 + 14 级逻辑 + fanout 367，路径 12.8ns、SWNS 仅 104ps（clk2 HDMI_PIXEL_CLK）。加裕量三招：`*160` 改移位加法 `(<<7)+(<<5)`、Logo 地址打拍、削 fanout（复制寄存器）。⚠️ 之前的「MC 内部 7.493ns 贴边」是三路时的记录，两路时关键路径实际在 hdmi_mixer。

## 7. 读指针独立 + 互斥锁跳帧（⚠️ 早期不完整版证伪；完整三件套见 §11）

> ⚠️ **两度反转（最终结论见 §11）**：早期这套「读指针独立 + 互斥锁」下板后出现「撕裂带 + 黑带白点」，一度回退。但会话末尾定位到——**早期失败是因为漏了「写指针打 2 拍」**（互斥锁拿未同步的写指针判断，又撞了写指针更新）。**完整三件套（读指针独立 + 写指针打 2 拍 + 互斥锁）才是正解，已用 iverilog 仿真验证逻辑正确**（读写指针零冲突、跳帧次数精确等于帧率差，见 §11）。本节的代码是「漏了写指针打拍」的不完整版，完整版在 §11。
> 结论链：官方例程（lab_ex1，**实测 1066M 满速**——diff 官方 ddr2.v 得 tCK=1876/usr_clk 133.3M，非半速，见 §17.8；无背景读、读指针=写指针+2）下板**一切正常** → 帧率差可接受、不是根因 → 错位带是「我们工程改动」（背景读/仲裁器/800Mbps）下的采样竞争 → 「读指针独立」的跳帧反而引入撕裂带。
> **铁律：改「帧同步 / 读指针 / 时钟」这类底层机制前，先下载官方例程做基线对比，否则方向可能整个错。**

**现象**：帧率差（HDMI 60.6 vs 摄像头 60fps）导致「错位带（暗带）滚动 + 错位带下方闪烁」。暗带本身可接受，但**闪烁不可接受**（动态、演示时明显）。

**根因**：读指针 `O_video_out_rp = 写指针 + 2`，**绑定在写指针上、在摄像头帧开始（100M 域）更新**，而 video_out 在 HDMI vsync（另一个异步事件）才采样——帧率差一漂移，采样和更新撞车 → 读写指针错位 + 读写竞争闪烁。

**标准解法（Intel 白皮书原话）**：帧漂移（frame drift）导致「output video frame to jump or roll over sporadically or continuously」，解法是「**add a video frame buffer to decouple the input and output**」——读和写完全独立，互斥锁保证不冲突，冲突时**跳帧**而不是错位。

**实现**：

```verilog
// video_in：删「读指针 = 写指针 + 2」的 case 映射，改成直接输出写指针
assign O_video_in_wp = S_video_in_wp;

// video_out：读指针独立维护 + 互斥锁跳帧
reg [1:0] S_video_out_rp;
always @(posedge I_ddr_clk or negedge I_rst_n) begin
    if (!I_rst_n)
        S_video_out_rp <= 2'd2;                    // 初始错开 2 块（写指针从 0 开始）
    else if (S_video_frame_start) begin
        if ((S_video_out_rp + 2'd1) != I_video_in_wp)  // 追不上写指针
            S_video_out_rp <= S_video_out_rp + 2'd1;   // 则 +1
        // else 跳帧：保持当前块，重复读一帧
    end
end
// 选缓冲区用 S_video_out_rp（替代原来的 I_video_out_rp）
```

**效果**：读指针的「更新」和「采样」都在 HDMI vsync 这**同一件事**上，永远无竞争、无闪烁；帧率差导致的「读追上写」变成「每 ~100 帧跳 1 帧」（肉眼无感），替代了错位带滚动。

**关键洞察（踩坑，含反转修正）**：
- ~~读指针「绑定写指针」是错的~~ **反转**：「读指针 = 写指针 + 2」是官方例程的稳定方案，配合仲裁器够用；「读指针独立 + 互斥锁跳帧」反而引入「水平撕裂带 + 黑带白点」（读写竞争），已回退。**两个异步帧源（摄像头帧 / HDMI vsync）本就不同步，靠「帧缓冲 + 互斥锁」隔离，而不是靠改读指针更新时机。**
- 「跳帧」理论比「错位带」好，但「读指针独立」的跳帧实现引入了新的撕裂带，得不偿失——底层机制改动前先下官方例程做基线对比。
- 业界参考：Microchip DDR AXI4 Arbiter（先到先服务+低通道号优先）、SmartFusion2 Arbiter（round-robin）、ARM DDR 控制器（优先级 + `CFG_STARVE_TIMEOUT_P` 饿死超时）。

## 8. 时间片轮转 vs 优先级仲裁器 + 最终结论（三路无法根除）

**优先级仲裁器的隐患**：显示读无条件优先 + 写/背景读在显示读空闲时「见缝插针」，写/背景读可能在显示读的突发中间插入、打断显示读节奏 → 出现「左右撕裂带」。

**时间片轮转（用户提出，本次验证）**：固定时间片 240 拍（跟写/读突发长度一致），三路轮流「写→显示读→背景读→写」，每路在自己时间片内独占、互不中途插入。

```verilog
reg [7:0] tslot_cnt;  reg [1:0] tslot_sel;   // 0=写 1=显示读 2=背景读
always @(posedge clk) begin
    if (tslot_cnt >= 239) begin tslot_cnt<=0; tslot_sel <= (tslot_sel==2)?0:tslot_sel+1; end
    else tslot_cnt <= tslot_cnt+1;
end
wire grant_wr=(tslot_sel==0); wire grant_rd=(tslot_sel==1); wire grant_bg=(tslot_sel==2);
// grant 由时序 tslot_sel 决定，无「见缝插针」，各路使能/计数/地址仍 grant 门控
```

**效果**：时间片轮转**解决了左右撕裂带**（无见缝插针），但**上下错位带 + 下面闪烁还在**——那是读写指针的「帧错位」（帧率差/跳帧/采样竞争，见 §5/§7），跟时间片/仲裁无关。

**跳帧影响读写指针相位**：自动曝光每 10 帧调节一次、调节后跳 3 帧（`video_in` 的 `r_skip_cnt`），跳帧时写指针不动 → 读写指针相位偏移。用户观察到「不同曝光增益值闪烁方式不同」（指向跳帧），但「刚下载就闪」又说明跳帧不是初始原因（跳帧要运行几秒后才触发）。验证跳帧是否元凶：`r_skip_cnt <= 3'd3` 改成 `3'd0` 禁用跳帧下板看错位带消不消。

**最终结论（铁律）**：PH1P35 合封 DDR 是**单路 AXI**，**两路访问（写+显示读）稳定，三路（加背景读）无论优先级仲裁还是时间片轮转都只能缓解、无法根除竞争错位**。官方例程（1066 满速两路，实测见 §17.8）是稳定基线。**竞赛项目做运动检测背景，正解是背景走片内 ERAM（320×180 降采样，前景 4×4），显示帧缓存才用 DDR 两路**——别再在 DDR 三路上耗。

## 9. 真正的根因：读数据分发没隔离（⚠️ 推翻「三路无法根除」的结论）

> ⚠️ **本会话最后一刻才定位到的真 bug**。上面「三路无法根除」的结论是**错的**——之前仲裁器、时间片、跳帧、打拍全在「时序/控制」层面找，而真正的 bug 在「数据路由」层面。

**现象**：三路（写 + 显示读 + 背景读）下，「大部分帧好、偶尔几帧坏」的错位带 + 闪烁。用户关键观察：「显示底色正常，能显示手/天花板」，只有局部错位带——说明污染是「局部几拍」不是「整帧」。

**根因**：`video_out` 和 `bg_read` 两个读 FIFO 的 `.we`（写使能）都**直接接共享的 `I_ddr_user_rd_valid`**，没按「读命令来源」隔离。DDR 读有延迟（约 40 拍），背景读时间片发出的读命令、数据延迟到显示读时间片才返回，此时 `I_ddr_user_rd_valid=1`，背景数据就漏进了显示读 FIFO（反过来显示读数据也漏进背景读 FIFO）。这就是「偶尔几帧坏」的精确来源——污染只发生在时间片切换边界的延迟返回那几拍。

**粗暴隔离踩坑**：第一版把 `.we` 直接门控当前 `grant`（`I_ddr_user_rd_valid && I_rd_grant`），**导致花屏**——显示读时间片末尾发出的读命令，数据 40 拍后返回时已切到下一时间片、`I_rd_grant=0`，这 40 拍显示读数据被丢掉 → 显示读 FIFO 读空 → 花屏。

**正确隔离（标签 FIFO，最终正解）**：⚠️ grant 打固定拍是**错的**（40/67/16 拍全试过都花屏）——因为 DDR 读延迟**不固定**（CAS latency + bank 切换 + 刷新都会变），固定拍根本对不齐。正解是**读命令标签 FIFO**：读命令发出时把「来源标签」（显示读=1/背景读=0）压入 FIFO，读数据返回时弹出标签，标签就是这条读数据的归属：

```verilog
// 顶层：读命令标签 FIFO
reg rd_tag_fifo [0:63];         // 1=显示读，0=背景读
reg [5:0] rd_tag_wptr, rd_tag_rptr;
always @(posedge clk) begin
    if (S_ddr_user_rd_en) begin                // 读命令 → push 来源
        rd_tag_fifo[rd_tag_wptr] <= grant_rd;  // 显示读时间片=1，背景读=0
        rd_tag_wptr <= rd_tag_wptr + 1;
    end
    if (S_ddr_user_rd_valid) rd_tag_rptr <= rd_tag_rptr + 1;  // 读数据 → pop
end
wire rd_tag = rd_tag_fifo[rd_tag_rptr];        // 当前读数据归属（1=显示读）
// video_out .we = I_ddr_user_rd_valid && rd_tag
// bg_read   .we = I_ddr_user_rd_valid && !rd_tag
```

**核心洞察**：读数据的「归属」由「读命令的来源」决定。DDR 读命令和读数据**顺序严格一致（先发先回）**，所以标签 FIFO 按「读命令顺序」压、按「读数据顺序」弹，天然对齐——**读延迟无论多少拍、固不固定，都不影响正确性**。这是 Microchip 官方「读数据 ID 路由」（RAC routes read data by Read data ID）的软件等价实现。⚠️ 反面教训：grant 打固定拍（移位寄存器）只在读延迟固定时才对，而 DDR 读延迟是变的 → 花屏。**多路读共享一根读数据总线时，正解是「读命令来源标签 FIFO」，不是「grant 打拍」。**

**教训**：一直在「时序/控制」层面（仲裁器/时间片/跳帧/打拍）找，而 bug 在「数据路由」层面（读数据分发）。遇到「偶尔坏几帧、底色正常」的现象，优先查「共享数据总线是否按来源隔离」，而不是继续调时序。判断「读延迟多少拍」之前，先想「能不能用顺序一致的标签 FIFO 绕开延迟」。

## 10. 标签 FIFO 之后的剩余坑（上电时序 + 时间片切碎 + 跳帧加大）

标签 FIFO 解决「读数据污染」（长方形黑屏消失）后，还陆续踩了三个坑，都是**「数据路由」之后的「边界/时序」问题**：

### 10.1 上电时序：S_init_calib_complete 必须门控系统复位（紫色花屏）

**现象**：标签 FIFO 后下板出现「大面积横线花屏 + 下面彩色花点（红蓝绿底白）+ 手/脸变紫」——**紫色 = R+B，G 通道丢失 = 数据字节错位**。关键线索：**按键复位后紫色消失、画面正常**。

**根因**：`S_init_calib_complete`（DDR 初始化校准完成信号）在顶层声明、从 DDR IP 引出，但**从头到尾没有任何地方用它**——上电时 DDR 还没初始化校准完，读写命令就发出去了 → 读数据错乱（字节错位 → 紫色）。按键复位后 DDR 重新初始化、时序对齐，紫色消失。

**修复**：系统复位同时等 DDR 初始化完成：
```verilog
assign S_rst_n = S_pll_lock && S_init_calib_complete;  // 上电等 DDR 就绪再读写
```
**教训**：DDR 有独立的初始化校准流程（比 PLL 锁定晚），`init_calib_complete` 必须参与复位链/读写使能门控，否则上电初期读写是「在未就绪的 DDR 上读」→ 数据错乱。现象特征「按键复位后正常」= 上电初始化时序问题，不是运行期逻辑 bug。

### 10.2 时间片轮转切碎显示读数据（持续闪烁/紫色扫屏线）

**现象**：标签 FIFO + 时间片轮转下，即使 S_rst_n 修好上电时序，运行中仍「持续闪烁 + 紫色扫屏线」。用户观察纠正：「一直在闪」而非「每隔 N 帧」（帧号跳太快、肉眼把持续闪烁误判成周期性）。

**根因**：时间片轮转每 240 拍硬切一刀，显示读的**连续读数据流在时间片边界被切断、字节错位**。标签 FIFO 只保证「谁的数据」没错（归属对），但**数据本身被时间片切碎了**（字节错位 → G 丢失 → 紫）。

**结论**：时间片轮转适合「各路的访问天然可分段」的场景，**不适合「显示读这种必须连续读」的数据流**——硬切导致字节错位。**正解回到优先级仲裁（显示读无条件优先、连续读不切碎）+ 标签 FIFO**。这是「优先级仲裁 vs 时间片轮转」的最终取舍：
- 优先级仲裁：显示读连续（不切碎），但写/背景读「见缝插针」可能打断显示读的突发节奏 → 撕裂带（标签 FIFO 隔离后撕裂带主要是「污染」，已由标签 FIFO 解决）
- 时间片轮转：无见缝插针，但**切碎连续数据流** → 持续闪烁/紫色（更严重）
- **最终方案：优先级仲裁 + 标签 FIFO**（显示读连续 + 读数据隔离，两头都对）

### 10.3 跳帧数（⚠️ 已纠正：两路 DDR 下 3 帧够，7 帧是三路竞争时期的误判）

**早期结论（已纠正）**：曾以为「跳 3 帧盖不住异常帧、要改 7 帧」，当时观察到「每隔 10 帧闪几帧」误判成异常帧泄漏。

**纠正（2026-10-21，用户指正）**：那个「每隔 10 帧闪几帧」其实是**三路 DDR 竞争的撕裂闪烁**，不是异常帧泄漏。摄像头切曝光的异常帧其实 ≤3 帧，**两路 DDR 下跳 3 帧就盖得住**。跳 7 帧是过度修正——多冻结 4 帧（117ms vs 50ms），是「改曝光卡顿」的元凶。两路下用 `r_skip_cnt<=3'd3`。

> ⚠️ **2026-10-21 反转（用户纠正）**：「跳 3 帧盖不住异常帧、改 7 帧」这个结论是在「三路 DDR 竞争」的乱背景下得出的——当时的「每隔 10 帧闪几帧」其实是**三路撕裂的闪烁**，被误判成「异常帧泄漏」。回两路后实测：摄像头切曝光的异常帧 ≤ 3 帧，跳 3 帧本来就够，跳 7 帧是「错误背景下的过度修正」，白白多冻结 4 帧（117ms vs 50ms，肉眼可感的卡顿）。**教训：在「有并发竞争/撕裂」的背景下观察到的现象，不能直接归因于当前调的参数（跳帧数），要先隔离背景（回两路）再判断——这是「先下官方例程基线对比」铁律的变体。**

### 10.4 读延迟概念澄清（别再混淆）

「DDR 读延迟」（读命令到首个读数据）≈ **CAS latency + PHY/MC 流水线 ≈ 十几拍**（800Mbps 下 CL=6 + 流水线约 10 拍）。而 motion_detect 的 `DELAY=55 拍` 大头是**读突发攒数据 + 跨时钟域 FIFO**，不是 DDR 读延迟。把 55 拍当读延迟去「grant 打拍」是错的（40/67/16 拍全花屏）。**凡是要「对齐读命令和读数据」，用标签 FIFO（顺序一致天然对齐），不要试图打固定拍匹配读延迟。**

## 11. 读写指针竞争的最终正解：完整三件套 + 仿真验证（推翻 §7 证伪）

标签 FIFO 解决「读数据污染」后，还剩下一个独立问题：**读写指针的跨时钟域竞争**。

**诊断线索（关键）**：用户观察「**卡顿的那一帧反而是好的**」——跳帧时写指针、读指针都**不动**、画面正常；非跳帧时读写指针**更新**、画面花屏。这直接锁定根因：花屏 = 读写指针更新（摄像头帧开始）和采样（HDMI vsync）两个异步事件的竞争，跟数据路由无关。

**根因**：读指针 `O_video_out_rp = 写指针 + 2`，绑定写指针、在摄像头帧开始更新，而 video_out 在 HDMI vsync 才采样。帧率差让相位漂移，采样撞上更新窗口 → 采到错值 → 读错缓冲区 → 花屏。「打 2 拍」隔离亚稳态没用，因为语义层面的「更新时机 vs 采样时机」本身就是错位的。

**完整三件套（正解，仿真验证）**：

```verilog
// video_in：删「读指针 = 写指针 + 2」，输出写指针
assign O_video_in_wp = S_video_in_wp;

// video_out：
// ① 写指针打 2 拍（互斥锁判断用稳定值，避免撞写指针更新）
reg [1:0] S_wp_1d, S_wp_2d;
always @(posedge clk) begin
    S_wp_1d <= I_video_in_wp;  S_wp_2d <= S_wp_1d;
end
// ② 读指针独立（HDMI vsync 自己 +1，更新和采样同拍无竞争）
// ③ 互斥锁跳帧（读追上写则保持，重复读一帧）
reg [1:0] S_video_out_rp;
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) S_video_out_rp <= 2'd2;          // 初始错开 2 块
    else if (S_video_frame_start)
        if ((S_video_out_rp + 2'd1) != S_wp_2d)  // 追不上写指针
            S_video_out_rp <= S_video_out_rp + 2'd1;
        // else 跳帧：保持当前块
end
```

**早期失败根因**：§7 那版只做了②③、漏了①（写指针没打拍），互斥锁拿「未同步的写指针」判断、又撞写指针更新 → 撕裂带。**教训：跨时钟域的「互斥锁/比较」逻辑，两个输入都必须同步（写指针打拍 + 读指针独立），只同步一边不够。**

**仿真验证（iverilog，无需编译下板半小时）**：读写指针竞争是纯逻辑，可写 testbench 快速验证——写指针周期 1000 拍（模拟 60fps）、读指针周期 990 拍（模拟 60.6fps 帧率差 1%），断言「读写指针永不相等（错开≥1）」，统计跳帧次数。结果：202 帧跳 2 次、零冲突，跳帧次数精确等于帧率差（202×1%≈2），证明逻辑闭环。**这是「先仿真验证逻辑、再下板验证硬件交互」的正确顺序**——读写指针这类纯逻辑的改动，别每次编译半小时下板试。

**教训汇总（数据路由 → 边界时序 → 读写指针竞争的完整排查链）**：遇到「底色正常但偶尔坏几帧/闪烁」→ 先查「共享数据总线是否按来源隔离」（标签 FIFO）；隔离后还花屏 → 查「上电 DDR 是否就绪」（init_calib_complete 门控）；还闪 → 查「时间片是否切碎连续数据流」（显示读必须连续，用优先级仲裁）；最后「卡顿帧好」→ 查「读写指针跨时钟域竞争」（完整三件套）。

## 12. 格雷码同步 + 降半速（会话最终结论，修正 §11 的二进制打拍）

### 12.1 写指针打拍必须用格雷码（§11 三件套的第四件）

**症状**：§11 完整三件套下板后**仍撕裂**。用户追问「读写指针竞争没法用打拍解决吗」→ 点破关键：**打拍能解决亚稳态，但 2 位指针「二进制直接打拍」会采到中间态错值**。

**根因**：写指针是 2 位（4 块乒乓，0→1→2→3→0）。二进制下「3→0」是 `11 → 00`，**两位同时翻转**。打 2 拍时若采在翻转瞬间，两个 bit 的亚稳态可能一个采新值一个采旧值 → 采出 `01`/`10` 这种**根本不存在的中间值** → 互斥锁拿错值判断 → 撕裂。单 bit 打拍只解决「亚稳态的 0/1 不确定」，解决不了「多 bit 同时翻转采到非法中间态」。

**正解（异步 FIFO 指针同步的标准做法）**：格雷码相邻值只变 1 位，打拍采到翻转瞬间时中间态只会是「旧值」或「新值」（都合法），绝不会有错值。

```verilog
// video_in：写指针输出转格雷码
assign O_video_in_wp = S_video_in_wp ^ (S_video_in_wp >> 1);   // bin→gray

// video_out：格雷码打 2 拍后转回二进制再给互斥锁
reg [1:0] S_wp_1d, S_wp_2d;
always @(posedge clk) begin S_wp_1d <= I_video_in_wp; S_wp_2d <= S_wp_1d; end  // 格雷码打拍
wire [1:0] S_wp_bin;
assign S_wp_bin[1] = S_wp_2d[1];                    // gray→bin（2 位）
assign S_wp_bin[0] = S_wp_2d[1] ^ S_wp_2d[0];
// 互斥锁用 S_wp_bin（不是 S_wp_2d）
```

格雷码映射（2 位）：0→00、1→01、2→11、3→10（3→0 是 `10→00` 只变 1 位）。**教训：跨时钟域传「多 bit 指针/计数器」时，二进制直接打拍会采到非法中间态，必须格雷码（相邻值只变 1 位）。**

### 12.2 屏幕撕裂本质 + 降半速是最终解

**现象**：格雷码 + 三件套都上了，下板**仍撕裂**（滚动带更像撕裂不是花屏）。逻辑仿真（读写指针 202 帧零冲突、标签 FIFO 33183 条零错位）全对，说明不是逻辑 bug。

**搜 Intel 官方文档《Framebuffer Driven LCD Display Design Example》确认本质**：

> screen tearing = 「屏幕显示一半新数据、一半旧数据」，根源是「在显示画到一半时更新画面」。标准解决是 **Vsync（等垂直消隐期才更新）** + **帧同步（每帧清空 FIFO、重置计数器）**。

对照：乒乓 + 读写指针错开 2 块就是「近似 Vsync」，但**摄像头 60fps vs HDMI 60.6fps 帧率差 1%**，让这个「近似 Vsync」的相位一直在漂移，漂到读写撞车就撕裂。真正的 Vsync 需要摄像头和 HDMI 帧率严格 genlock（改时钟架构），复杂且风险高。

**最终决定：降半速 533Mbps**（当时以为跟官方例程一致——**2026-10-22 diff 官方 ddr2.v 实测官方是满速 1066（tCK=1876/usr_clk 133.3M），「官方=半速」是误记**；时序宽松、读延迟稳定，撕裂消失）：

| 参数 | 800Mbps（降速前） | 533Mbps（最终） |
|---|---|---|
| ref_clk | 100M 差分（K5/L5） | 50M 单端（C4，I_sys_clk） |
| tCK | 2500 ps | 1876 ps |
| CL / CWL | 6 / 5 | 7 / 6 |
| PLL0_FBKCLK_DIV | 24 | 32 |
| PLL0_REFCLK_FREQ | 100.0 | 50.0 |
| PLL1_REFCLK_FREQ | 100.0 | 133.3 |

带宽 8.53G（半速）够三路（有效 4G + 开销约 6G）。**降速回退要同步改 4 个文件**（ddr2.v + .params_ddr2.txt + .m_params_ddr2.txt + Design.xml）+ 删 K5/L5 引脚约束 + 删 SDC 的 ddr_ref_clk_100m + 顶层删 IBUF_DIFF、ref_clk 改回 I_sys_clk。⚠️ 回退 ddr2.v 参数时小心：`PLL0_REFCLK_DIV(3)` 不能删（它是 REFCLK_DIV），`PLL1_REFCLK_FREQ` 位置在 PLL0 参数之后、别重复。

**铁律（贯穿全场）**：改「帧同步/读指针/时钟/仲裁」这类底层机制前，**先下载官方例程做基线对比**——会话中途一度在「帧率差」上耗了多轮（开小数分频、改 H_FrameSize、读指针独立），最后下官方例程发现「一切正常」才反转。逻辑层（读写指针、标签 FIFO）能用 iverilog 写 testbench 快速验证（几分钟），比每次编译半小时下板快得多，先仿真再下板。

## 13. 降半速后仍撕裂 → 最终方案：消隐期读 + 降采样到片内 ERAM（本会话最终结论）

> ⚠️ **§12.2「降半速是最终解」被推翻**：降半速 533Mbps 后下板**仍撕裂**；读指针回退到官方例程「读指针=写指针+2」也**仍撕裂**。坐实「读写指针」根本不是撕裂的根源，之前 §11/§12 在读写指针上耗的功夫方向偏了。

**搜索 Microchip DDR Read IP 文档确认本质**：DDR Read IP 是「读一行」为单位，`read_en_i` 持续整个水平分辨率时间才完成一行读，读数据是**连续**的、中间不被别的通道打断。而我们的显示读是「读 240 停、FIFO 快满停」，背景读**见缝插针**插进来，把显示读的连续数据流**切碎** → 撕裂。

**核心矛盾（最终定论）**：只要背景读和显示读在「同一段时间」共用 DDR 单口，显示读的连续数据流就一定会被切——不管优先级仲裁（见缝插针切突发）还是时间片轮转（时间片边界切碎，读延迟跨时间片返回）。

**最终正解：错峰（消隐期读）**：

```
显示期间（画面显示）：DDR 只给显示读用，数据流连续 → 不撕裂
消隐期（画面空白）：DDR 给背景读用，把背景读出来
```

**死结（必须降采样才能落地）**：消隐期读出的背景整帧 22Mbit 要「存到有效期间用」，但片内 ERAM 只有 2.16Mbit、FIFO 只有 64Kbit，都放不下整帧 → 必须**降采样**（读背景时缩小到 320×180 ≈ 0.69Mbit 存片内 ERAM，前景 4×4 块）。DDR 里仍存全分辨率背景（满足「DDR 该用」），只是读出来时缩小。

**存储 vs 访问的澄清（用户反复确认，务必讲清这两件事是两码事）**：
- DDR **存储够**：512Mb，背景 22Mbit + 4 块乒乓 88Mbit = 110Mbit，绰绰有余。背景 + 采集画面「一起存 DDR」完全没问题。
- 瓶颈是**单口访问**：单路 AXI 一次只能读/写一路，三路（写+显示读+背景读）抢口——这是「能不能同时读」的问题，不是「能不能存」的问题。
- FIFO（w128_d512_fifo，512×128bit=64Kbit）是「跨时钟域过路小缓冲」，从来不是「存背景」用的；背景一直存 DDR，FIFO 只是边读边减的流水过渡。

**降低帧率的辅助作用（用户问过）**：60fps→30fps 让消隐期变长、背景读更从容；但「背景整帧缓冲」死结还是要降采样解决，且降帧率让画面卡顿（比赛演示不划算）。降帧率不能「让时间片轮转更好错开」——时间片切碎是机制问题，跟帧率无关。

## 14. 消隐期读 + 前景标记片内（全分辨率 1×1，2026-10-21，推翻 §13「降采样」）

> ⚠️ §13「降采样到片内 ERAM 320×180」被推翻：用户开发者想到——减背景的**结果（前景标记）只有 1bit/像素**，1280×720×1bit = **0.92Mbit**，片内 ERAM 2.16Mbit 放得下，**全分辨率 1×1 前景可行**，不需要降采样。

### 14.1 消隐期时间预算（§13/§16 的「消隐期 12.83ms」是错的）

文档《当前状态与下一步.md》第十六节写「消隐期 12.83ms」——那是**有效显示时间**，不是消隐期。从 uivtc 参数实测（H_FrameSize=1650、V_FrameSize=750、HDMI 像素钟 75M）：

```
帧周期 = 1650×750 = 1237500 像素 @75M = 16.5ms
有效显示 = 1280×720 = 921600 像素 @75M = 12.29ms
消隐期 = 315900 像素 @75M = 4.2ms   ← 实际只有 4.2ms
```

读两帧（当前帧+背景）数据量固定 = 345600 个 128bit（一帧 172800）。usr_clk = DDR_SPEED/8（PLL0 的 C0 输出）：

| DDR 速率 | usr_clk | 读两帧时间 | vs 4.2ms 消隐期 |
|---|---|---|---|
| 半速 533Mbps | 66.67M | 5.18ms | ❌ 读不完 |
| 800Mbps | 100M | 3.46ms | ✅ 够（余 0.75ms） |
| **满速 1066Mbps** | 133.3M | **2.59ms** | ✅ 够（余 1.6ms） |

### 14.2 前景标记 ERAM 精确深度（省 EMB，用户经验强化）

前景标记 = 921600 bit。用 **40bit 宽 × 23040 深**（ERAM 最大位宽 512×40 配置，单块深 512）：

- 深度 = 921600/40 = **23040**，块数 = 23040/512 = **45 块**（精确整除，零浪费）。
- ⚠️ **IP 深度参数直接填 23040，不要填 2 的幂 32768**（32768/512=64 块，白白浪费 19 块 ERAM）。
- 这是「深度精确设置省 EMB」原则（§2 的「57600 深省 3 块」）的极端案例：信息量 921600bit = 45 块×20480bit 完全匹配。
- 前景标记 ERAM 是双口（消隐期 DDR 域写、有效期间 HDMI 域读），40bit 打包：每拍比较得 4bit，累积 10 拍=40bit 写 1 地址。

### 14.3 DDR 满速 1066Mbps 精确配置（K5/L5 = LVDS18，补 §6）

半速→满速的**最小改动集**（tCK 1876/CL7/CWL6/FBKCLK_DIV32 等参数已是满速值，只差 ref_clk）：

### 14.4 时序关键路径定位方法（读 final_timing.rpt，别先入为主）

满速编译 SWNS 104ps 全绿（NUM_FEPS=0），但「最差路径」不在 DDR、在 **HDMI_PIXEL_CLK 域**。定位方法：

1. 读 `phy_1/final_timing.rpt` 的 **Clock Summary**（每时钟域的 SWNS/HWNS）：满速下 `HDMI_PIXEL_CLK(75M) SWNS 0.104ns` 是最差，而 `usr_clk(133.3M) SWNS 0.165ns` 反而更松。
2. 找该域的 **Max Paths**：最差路径 = `u_hdmi_mixer/mult0_syn_59`（DSP 乘法）→ `S_osd_color_reg[5]`，源头是 hdmi_mixer.v 的 `S_logo_addr = (S_y_2d-LOGO_Y)*LOGO_W + (S_x_2d-LOGO_X)`（`*160` 用了 DSPMULT，14 级逻辑，net 延迟 52%、fanout 367）。
3. 加裕量三招：`*160` 改移位加法 `(x<<7)+(x<<5)` 甩 DSP；Logo 地址计算打拍拆路径；复制寄存器削减 fanout 367。

**加裕量实测效果（2026-10-21）**：三招上去后 HDMI 域 SWNS 104ps→**383ps**（3.7 倍），全局最差转移到 `usr_clk(133.3M)` 域 **259ps**，路径在 DDR MC IP 内部（`u_alc_mc_top/page_ctrl` 的 txn_fifo，net 延迟占 76%）——**加密 IP 改不了，满速下 259ps 是物理极限，别再试图优化 DDR 内部时序**。这也说明「满速贴边」的旧印象是错的（三路竞争时才贴边，两路下时序宽裕，全绿无违例）。

⚠️ **铁律：时序最差路径 ≠ 功能故障点**。满速下「最右列花屏」时序全绿（NUM_FEPS=0），且最差路径（Logo 颜色，左上角）位置跟花屏（最右列 x=1279）对不上——花屏根因更可能是跨时钟域亚稳态或行末尾 FIFO 边界逻辑，不是 setup 违例。定位显示瑕疵根因时，先查「半速时是否也存在」：半速有=逻辑 bug（修 video_out 解包边界）、满速独有=跨时钟域/亚稳态（降 800 对症）。

## 15. 显示链路瑕疵修复（算法切换格雷码 + 帧率差现象映射 + 自动曝光，2026-10-21）

### 15.1 算法切换的异常像素 = 多 bit 模式选择信号二进制打 2 拍

- 现象：切换算法（灰度↔二值↔边缘↔原样）时，切换帧中间几列出现异常像素（白点/黑点），下一帧消失。
- 根因：`algo_mode`（3 位模式选择，0~3 循环）二进制直接打 2 拍，切换瞬间（如灰度 001→二值 010，bit0/bit1 同时翻转）采到中间态 000/011，MUX 选错算法。
- **诊断关键线索**：不只「延迟跳变」的切换会闪（原样/灰度/二值 0 拍 ↔ 边缘 8 拍），**「同延迟」的切换也闪（灰度↔二值都 0 拍）**——这坐实是「二进制打拍中间态」，不是「延迟跳变」。
- 修复：`gray = bin ^ (bin>>1)` 转格雷码打 2 拍再转回二进制。⚠️ **isp_top（算法 MUX）和 hdmi_mixer（OSD 算法名）两处各自独立同步同一信号，都要改，漏一处仍闪**。
- ⚠️ **2026-10-21 反转（用户下板实测：格雷码同步没修好，仍闪）**：格雷码只解决「跨时钟域打拍的中间态」，但**格雷码转回二进制后，二进制值切换时仍会变多位**（灰度 001→二值 010 变 bit0+bit1 两位），case 组合 MUX 对「多 bit 同时翻转」仍产生毛刺。用户补充的精确规律锁死根因——**「原样→灰度不闪，其余切换都闪」**：原样 000→灰度 001 只变 1 位（不毛刺），灰度 001→二值 010 变 2 位（毛刺），二值↔边缘/边缘↔原样还有 0↔8 拍延迟跳变。**最终修法：数据/valid/algo_mode 统一打 8 拍对齐 sobel 的 8 拍延迟，寄存器输出无毛刺无错位**（sobel 内部已 8 拍不额外打，awb/gray/binary 打 8 拍，algo_mode 格雷转二进制后再打 8 拍）。核心洞察：**格雷码只解决「同步采样」问题，不解决「MUX 毛刺」和「延迟不一致」问题，这是三件独立的事——格雷码 ≠ 消除毛刺，多 bit 组合 MUX 的毛刺要靠「寄存（打拍）选择信号 + 数据」解决**。

### 15.2 帧率差撕裂的精确现象映射（§5 补充）

- 现象：满速两路下「最右列 / 画面下部约 1/3 花屏 + 一闪一闪」（周期约 100 帧），上部 2/3 正常。
- 根因：读写指针漂移读上「半写帧」——摄像头 60fps vs HDMI 60.6fps 差 1%，读写指针相位每约 100 帧漂 1 帧，漂到「读追上写」时读到「上面已写、下面还没写」的半写帧 → 下面 1/3 花屏，下一帧漂移错开 → 闪一下。
- genlock 修不了（§5 已证两条路都不通），接受（偶发、只占画面下部 1/3、比赛演示肉眼难察觉）。半速三路竞争时被撕裂盖住，满速两路干净才暴露。

### 15.3 自动曝光「移动小白点」= 持续调节的异常帧

- 现象：移动摄像头（亮度持续变）有白点噪声，静止无；跳帧数 3 还是 7 都治不了。
- 根因：移动时亮度持续变化 → 自动曝光持续调节 → 异常帧一波接一波，跳帧盖完这波漏下波。
- 修复：调慢调节频率（brightness_stat 的 `r_frame_cnt` 从 5 位/20 帧 改 6 位/40 帧），减少调节次数、少产生异常帧。代价是亮度响应慢一点。
- ⚠️ **2026-10-21 反转（调慢频率没修好，真根因是光源频闪，不是异常帧）**：40 帧调节频率下小白点仍在。用户关键实验锁死根因——**「固定增益 80（手动，曝光也固定）后，有光源还闪、无光源不闪」**：此时曝光/增益都不动、跳帧也不触发，白点却还在，彻底排除「增益跨档位 + 曝光异常帧」。真根因：**教室长 LED 灯（交流整流 100Hz 频闪）+ SC500CS 滚动快门逐行曝光，曝光时间 <10ms 时把灯的亮暗周期采样进去，灯在画面里的几个像素明暗闪烁 = 白点**。这是物理现象非代码 bug，跳帧/调慢频率/增益锁定全无效。解决：①现场换非频闪光源（DC 恒流 LED，首选）；②曝光下限 AE_MIN 从 2 拉到约 2424（曝光 >10ms 覆盖频闪周期，代价亮光过曝 + 运动模糊）。**调试方法论：用「固定某个变量」（固定增益）做隔离实验排除根因，比反复猜测改参数快得多——尤其当「有 X 就闪、无 X 不闪」这种强相关现象出现时，直接锁定 X 本身**。

### 15.4 验证方法：位序/打包这类纯逻辑用 iverilog 真实 RTL，别用 Python 复现

- 用户明确纠正「为啥要用 Python 模拟，不能仿真吗」——验证打包/解包位序这类逻辑，用 iverilog 例化真实 RTL（`data_96bit_to_128bit` + `data_128bit_to_96bit`）跑往返，比 Python 重新实现可靠（复现容易引入位序/时序错误，结果「全反序」对不上「画面正常」就是复现错了）。
- 实测「96→128→96」往返无损（真实 RTL 320 个 96bit 零错误，带行消隐也零错误），坐实打包和 128→96 解包正确，把花屏范围缩到 video_out 的 128→24 解包。
- 配套：`w128_d512_fifo` 是 `OUTREG_EN="NOREG"`，但 ram_infer 的 `read_b` 用非阻塞 `dob_tmp <= memory[addr]`，**NOREG 下 dob 实际有 1 拍延迟**（re 后 1 拍 dout 有效），testbench 模拟读时序时别当成 0 拍组合输出。

## 16. 两路 DDR 下的显示瑕疵（读满即停 + 跳帧卡顿，2026-10-21）

禁用背景读（两路写+显示读）后，显示链路仍有三个瑕疵，逐个定位：

### 16.1 video_out 读地址越界 → 「读满即停」（⚠️ v1 失败，v2 锚点见下）

- **现象**：最右列 + 画面下部约 1/3 每帧闪的花屏（最右列密集白点 + 漂红黄点 = 越界读空隙的未初始化 DDR 随机值）。
- **根因**：`video_out` 读地址只在 `S_video_frame_start` 复位到缓冲区基址，之后 `+8` 无限递增，**没有「读满一帧 172800 个 128 位就停」的保护**。读触发用 `wrusedw`（写侧）而 FIFO 读在 HDMI 侧，跨时钟域反馈 2~3 拍延迟 → 帧尾多读，读地址越过本帧缓冲区，读到「空隙/下一块」的未初始化或旧数据。
- **v1（已证伪）**：加 18 位帧内读计数 `S_frame_rd_cnt`，在 vsync（S_video_frame_start）清零、读触发加 `<172800`。下板失败：**vsync 比 HDMI 有效显示早一个消隐期**，DDR 读先跑满 172800 硬停、FIFO 空了 HDMI 侧还在读旧值 → 上面 2/3 黑灰横线（比原问题更糟）。「读满即停正好落在读突发边界」也是错的——锚点错位后读满落在突发中间。
- **v2（⚠️ 下板仍失败、最终撤销，见 §17.2）**：帧开始锚点改用 **`I_video_rd_en` 上升沿**（HDMI 有效显示窗口，跨时钟域打 3 拍到 DDR 域）——与 HDMI 读侧天然同一时刻。消隐期读触发自动停（frame_rd_cnt 保持上一帧的 172800）。**失败根因：锚点的 3 拍跨域同步让 DDR 读比 HDMI 读恒定晚 3 拍 → 每行前 3 像素读旧值、行尾 3 像素错位（= 老师「每行前 3 个数丢」）。最终撤销读满即停，读触发回到官方同款自然停（官方验证过无此问题）。**
- **读满即停必须截断进行中的读突发**：只门控读触发不够，读突发 240 个连续进行、读满落在中间时剩余 239 个照读（仿真实测多读 239 越界）。修法：读使能加 `frame_rd_cnt < 172800` 门控 + 读突发状态机在 `>=172800` 时强制清 `S_ddr_rd_valid`。
- **关键数据**：一帧 128 位数 = 1280×720×96/128 = 172800；读地址每次 +8；缓冲区基址间隔 7000000，一帧地址范围 1382400，乒乓块之间有空隙，越界读到的是空隙未初始化数据。
- **教训**：读地址这类「帧内连续递增」计数器必须有「帧边界停止」保护，但**帧边界的锚点必须与消费侧（HDMI 读）同源**——用 vsync（生产侧）做锚点差一个消隐期，用有效显示窗口信号做锚点才对。显式帧内计数到满即停是确定性兜底，不依赖水位反馈时序。

### 16.2 跳帧卡顿 → 手动模式不跳帧、自动模式才跳

- **现象**：手动按键调曝光/增益时画面卡顿。
- **根因**：每按一次键（长按每 500ms 一个 tick）都触发一次「跳 3 帧」，跳帧 = 画面冻结 3 帧 = 50ms，连续按键就连续跳帧累积卡顿。跳帧本意是盖「曝光/增益切换瞬间的异常帧」，但把冻结副作用带给了每次手动调节。
- **修法**：video_in 的跳帧触发（`ae_done_rise`）加「自动模式」条件——手动模式不跳帧（用户主动调，短暂 1 帧花屏比连续卡顿可接受），自动模式跳帧（后台偶发调节，冻结无感）。需把 SW3/自动标志引入 video_in。
- **按键调节完整链路**（排查时摸清，留档）：KEY2加/KEY3减 → debounce → key_hold 长按 500ms tick → ae_set 手动更新 r_ae_set（曝光步进 100）/r_ag_set（增益步进 1）→ 拉 O_ae_req → uicfgcs500 I2C 写摄像头寄存器 → 拉 O_ae_cfg_done → video_in 跳帧。SW3 低=自动（亮度闭环，按键无效）、高=手动（按键调）。**关键：跳帧的「冻结」副作用对「用户主动的连续手动调节」最刺眼，而对「后台偶发的自动调节」无感——同一个保护机制，两种模式要区别对待**。

## 17. 最右列 3 像素噪点攻坚（§16 的延续）

§16.1 的「读满即停 v2」和本节反复修复后，最右列 3 像素宽异常条（白/灰/彩色点、位置固定、帧间闪烁）最终定位到**帧尾 FIFO 读空**。以下按主题记录，避免重踩。

### 17.1 官方双向互斥只恢复一半不够：写避让读缺失

- 官方 lab_ex1 的 video_in 写触发条件是 `fifo_rd_num>=240 && !I_video_out_rd_busy`——**官方是双向互斥**（读避让写 + 写避让读）。本工程只恢复了「读避让写」（修好全画面白点），「写避让读」半边缺失 → 写命令在读数据延迟返回（约 40 拍）期间插入，写数据上总线暂停读数据流 → FIFO 写间隙 → 读穿噪点。
- **铁律：恢复「官方同款」时要 diff 完整的触发条件，别只挑记得的那半**——官方 video_in 写触发和 video_out 读触发各带一个避让条件，两个都要对齐，只恢复一个方向仍会残留异常。

### 17.2 读满即停锚点的跨域同步拍数 = 数据流恒定错位拍数（撤销 v2）

- v2 的帧开始锚点 `I_video_rd_en` 上升沿在 DDR 域打 3 拍同步 → DDR 读比 HDMI 读**恒定晚 3 拍** → 整条数据流错 3 拍：每行前 3 像素读旧值（丢）、行尾 3 像素读到下一行头（错位条）。老师意见「每行前 3 个数丢」与此完全吻合。
- **规则：任何「帧/行开始锚点」跨时钟域同步引入的延迟拍数，会原样变成数据流的恒定错位像素数**。锚点同步 N 拍 = 错位 N 拍。要么锚点与消费侧同源同域，要么别用人工锚点——官方自然停（FIFO 水位触发）根本没有锚点，也就没有错位。
- 3 像素错位肉眼验证不了（LOGO 对齐实验看不出），所以「画面是否左移 N 像素」的实验对 N≤3 无效——锚点同步拍数要从代码直接数，别指望下板看出。

### 17.3 tick 级行为仿真：节拍/水位问题不必例化真实 RTL

- 验证「自然停下帧尾会不会读空、多读多少」：用纯整数 tick 模型（读触发阈值、写忙周期、HDMI 每 16 tick 读 3 个、vsync 复位 FIFO 10 拍）在 iverilog 里跑 4 帧即可复现精确数字——**每帧多读 240 个（帧尾多一个完整读突发越界读空隙，被 vsync 的 FIFO 复位清掉，无害）+ 每帧恒定 HDMI 读空 3 拍**。
- **规则：读空/越界/多读少读这类「节拍与水位」问题，行为级 tick 模型几分钟就出精确数字，比例化完整 RTL 或编译下板快一个数量级**。先把数字仿出来（读空几拍、多读几个），再决定修法。
- ⚠️ **模型的保真度决定结论对错：DDR 读延迟必须进模型**。无 40 拍延迟的模型给出「每帧恒定帧尾读空 3 拍」的结论，加了「读命令入队 40 拍后数据才写 FIFO」的移位队列模型后，读空全跑到**帧头**（帧开始 FIFO 空 + 40 拍供给滞后），帧尾不读空——「3 像素 = 帧尾读空」被自己推翻。**凡模型结论与下板现象冲突或过于巧合时，先检查模型缺了什么真实环节（延迟、写忙相位、复位），再信结论**。
- 阈值扫描（300→297~220）和突发长度扫描（236~244）都**消除不了读空**——读空是供给节奏与消耗节奏的相位锁定（结构性），改触发参数只改变读总数、不改变相位。别在阈值/突发长度上耗。

### 17.4 帧尾读空 = 固定位置噪点的标准机制（⚠️ 结论已被带延迟模型部分推翻，见 §17.3 反转）

- 机制链（无延迟模型下的假设，带 40 拍延迟模型已推翻「帧尾」位置）：帧尾 DDR 读供给晚于 HDMI 消耗 → FIFO 读空 → dout 保持最后写入值 → 保持值随场景变化。表现四件套：**位置固定**、**帧间闪烁**（值随场景变）、**颜色随场景变**（白/灰/彩色）、**宽度 = 读空拍数**（3 拍读空 = 3 像素条）。
- **现象→根因推理链**：位置固定 = 恒定错位/固定路径；帧间闪烁 = 值随数据或时序偶发；官方无 + 自己工程有 = 自己的改动引入。这条链能快速排除「传感器坏列」「时序违例」等方向（传感器坏列官方也会有；纯时序违例位置不会锁死帧尾）。
- 阈值微调（300→320）**无效**——读空的相位错位是节奏性的，改触发阈值不改变供给和消耗的节奏结构。别在阈值上耗。

### 17.5 数码管 debug 计数器：内部计数下板直读

- 验证「读写指针碰撞/少读」假设的零成本手段：目标模块加「每帧计数值锁存输出」（vsync 锁存 + 复位），顶层数码管用闲置拨码开关（SW4）切换显示源（拨上 = debug 计数 hex，拨下 = 原显示内容）。期望值换算好再下板（一帧 172800 个 128 位 = 0x2A300；自然停预期 0x2A3F0 = 多 240）。
- **规则：数码管/七段显示是现成的 debug 通道，用闲置开关切显示源即可把任意内部计数下板直读，比示波器/ILA 快**。改动前先算好「正常值」和「异常值」的对照表，读码即结论。
- **开关编号约定：代码 `I_sw[3:0]` 对应板丝印 SW1~SW4**（I_sw[3]=SW4 背景采集、I_sw[2]=SW3 曝光模式、**I_sw[1:0]=SW2/SW1 组合 = S_mode 4 档模式选择（sw_mode.v：mode = sw[1:0] 打两拍），不是空闲**）——给用户描述拨码开关时必须用板丝印编号（「拨 SW1」），不要用代码位号（「拨 SW0」），用户会纠正（板上只有 SW1~SW6 丝印）。二分定位/调试开关优先复用「某模式档下才生效」的 AND 组合（如模式 3 + 开关位），不占用既有功能档。
- ⚠️ **数码管段码表未必含 A~F**：seg7 模块若只做 0~9 的 BCD 段码，hex 计数值里的 A/F 位会灭——0x2A3F0 显示成「2 3 0」（用户报数时只剩 2/3/0 三个数字，按「A、F 缺失」反推原值）。**已给 seg7 补全共阳 A~F 段码**：A=8'h88、b=8'h83、C=8'hC6、d=8'hA1、E=8'h86、F=8'h8E（0 点亮、dp 恒灭，与既有 0~9 表同风格）。
- **已下板实测：SW4 读帧计数显示 0x2A3F0 = 173040 = 172800+240**，坐实「自然停」每帧多读一个完整读突发（帧尾 240 个越界读空隙，被 vsync 的 FIFO 复位清掉，无害）——与 tick 行为模型（§17.3）数字精确一致，模型可信。

### 17.6 修复候选（状态记录）

- 显示侧整体延迟 N 拍（数据 + de + vsync/hsync + OSD 坐标统一打拍），把读空的 N 拍挪到消隐期——画面内容不变（整体延迟），显示不再读空。延迟拍数要覆盖读空的最大拍数（偶发帧可能大于恒定值）。⚠️ 前提是「读空发生在帧尾」——带 40 拍延迟模型显示读空在帧头，此方案需重新评估。
- 读数据 + valid + 标签同步打 1 拍（打断 DDR 读数据 → FIFO 长路径修时序）——**已下板，最右列仍在，不解决 3 像素**。usr_clk 域时序本来就够（SWNS 1.256ns），打拍方向错了。

### 17.7 时序贴边 = 「位置固定 + 帧间闪烁」的最强候选（当前方向）

- 所有读路径修复（双向互斥、读满即停撤销、读数据打拍）下板后最右列 3 像素仍在，且 FIFO IP、video_out/video_in 逻辑与官方逐行 diff 一致、usr_clk 域 SWNS 1.256ns 足够——读路径基本排除。
- **像素域（MIPI_RX_BYTE_CLK 16.67ns）SWNS 仅 462ps 贴边**，最差路径 = demosaic 的 line buffer 读地址（addrb 行尾回绕 319→0 的比较+MUX）+ canny 的 dir_4p 方向寄存器。
- **症状→违例映射**：addrb 行尾回绕偶发违例 → 读地址错 → 读邻组数据 → 行尾最后一组的 3 个像素错（位置固定在行尾 = 最右列）；违例偶发（462ps 裕量随温度/电压漂移）→ 帧间闪烁；读到邻组数据 → 颜色随场景变。BPC 旁路后该路径仍在（demosaic 是 ISP 第一级），所以旁路无效——全对得上。
- **修复方向：demosaic 的 addrb 回绕打 1 拍**（把 `addrb <= rd_en ? (addrb==319 ? 0 : addrb+1) : addrb` 的比较+MUX 拆两级寄存，路径减半）。line_buffer_demosaic 是官方 IP 但 BPC/canny 复用，改一处全链路受益。
- **方法论**：官方无 + 自己工程有的持续固定位置异常，读路径 diff 一致后，查「像素域时序报告的最差路径是否恰好落在异常位置的数据流上」——时序贴边的症状特征 = 位置固定 + 帧间闪烁 + 值随场景变，与逻辑 bug（恒定错值）区分看「值是否随场景变」。
- ⚠️ **此假设已被推翻：时序最差路径会随布局漂移**。同一 RTL 再次编译后，最差路径从 demosaic addrb（462ps）漂到 canny dir_4p（1.057ns），demosaic 路径不再贴边——而最右列 3 像素仍在。**规则：不能凭单次编译报告的最差路径坐实「时序贴边是根因」；报告路径消失（布局变了）而现象还在 = 该路径不是根因**。贴边结论要在同一 bit 流上「违例路径恰好位于异常位置的数据流 + 下板现象随温度/电压可复现」双重成立才算。

### 17.8 官方 lab_ex1 速度真相：1066M 满速，不是半速（2026-10-22 diff 坐实）

- diff 官方 `ph1p35_ddr/ddr2/ddr2.v` 与本工程：官方 **tCK=1876 / CWL=6 / CL=7 / PLL0_FBKCLK_DIV=32 / PLL1_REFCLK_FREQ=133.3** = **1066Mbps 满速**；本工程 800M 参数（tCK=2500/CWL5/CL6/DIV24/100.0）**反而比官方慢**。
- ⚠️ **usr_clk 频率更正（官方时序报告坐实）**：官方 1066 配置的 usr_clk **实测 15ns = 66.67M，不是 133.3M**（官方 final_timing.rpt 里 `usr_clk period=15.000000`）。`PLL1_REFCLK_FREQ=133.3` 是 **PLL1 参考时钟参数 = DDR_SPEED/8**（pll1.v 头注释 `REFCLK : DDR_SPEED/8`），不是 usr_clk 频率。**规则：查 usr_clk 实际频率看时序报告的 period，别把 REFCLK_FREQ 参数当 usr_clk 频率。**

- **校验报错链与对应修法**（Design.xml 只存电气参数 84 个 referenceId，**IO 规划类参数（ADC File Path、PLL Location、RefClk Location）不存 Design.xml**，重新打开向导时是默认值，跟工程对不上）：
  1. 「adc constraint file does not exist」→ 界面 IO Planning 区的 **ADC File Path 点 Browse** 选 `ddr2/src/adc/ddr2.adc`（IP 目录自带），不是主界面 Add Source；ADC File Path 留空也会报「please enter a valid path」。
  2. 「ddr_addr constraints is less than the design requirements」→ DQ Bytes / DRAM Type 与位宽不配套（x8 比 x16 多要地址线，adc 里 ddr_addr 根数对不上）——按工程实际改 DQ Bytes=2 + DRAM Type=x16。
  3. 填了 adc 还报「ddr_dqs_p[0] used pin X0Y33Z2 is an invalid pin name」→ IO 规划参数（PLL Location 下拉只有 BANK32 没得选等）和 adc 的实际内容冲突——**正解是打开官方工程（lab_ex1，完整生成过）的向导，把官方界面参数原样抄过来**，别在默认值上硬调。
- **教训：拷贝官方工程改出来的工程，IP 重新生成时向导参数会全部回到默认值（IO 规划类参数根本没存下来），逐项核对 = 对照 Design.xml（电气参数）+ 官方工程向导（IO 规划参数）**。

**用户沟通偏好（多轮攻坚必用）**：连续多轮「改→编译→下板→还在」后用户会说「折腾太多搞不清状况」——此时**先停手给一张状态地图**（根因是什么/卡在哪/手头有几份工程各是什么状态/下一步动作对照表），把混乱收拢成一张表，再继续；用户对「接下来干什么」的全局位置感优先于细节进度。

### 17.15 最终根因：DDR ref_clk 接线错晶振（参数文件无辜，§17.11 机制全推翻）

- **真根因（2026-10-23 锁定）**：官方 lab_ex1 的 DDR ref_clk 接 **C4 的 I_sys_clk（50M 板载晶振，与 u_PLL 共用）**；本工程当年接成 **K5/L5 100M 差分晶振（IBUF_DIFF 差分转单端）**。PLL 倍频系数由 IP 配置固定 → **输出 = 实际输入 × 固定倍率**：喂 50M → usr_clk 66.67（官方时序报告 clk1 实测值）；喂 100M → 133.33。§17.11 的「REF_CLK 参数 50→100 修复」机制是错的——参数文件两边 md5 全对齐后仍 133.33，错的从来不是参数，是顶层接线。
- **铁律：硬核 IP 输出频率不对（2 倍/半频）时，先 diff 顶层「时钟源接线」对照官方例程，再查参数文件**——三个位置：① IP 例化端口接法（官方 `.I_sys_clk(I_sys_clk)` 直连 vs 本工程接 IBUF_DIFF 输出 `S_ddr_ref_clk`）② pin.adc 引脚（C4 50M 单端 vs K5/L5 100M 差分）③ sdc 时钟约束（官方无 100M ref_clk 的 create_clock）。倍频系数固定，输入频率决定输出——为「刷新参数」在 GUI IpTool 上耗一整天（§17.14 坑表）是白折腾。
- **定位实验（决定性）**：官方工程删 *.db 全量重编 = 66.667、本工程同样全量 = 133.333，而两边 ddr2 目录 md5sum 递归全一致 → 差异必在 ddr2 目录之外 → 顶层三处 diff 一击命中。「参数文件对齐」必须用整文件 md5 验证（`find . -type f | sort | xargs md5sum` 两边 diff）——sed 单点改值不算对齐，本工程 .params 与官方曾「值看着全对」但 md5 仍不同（IO_VOL 1.8 vs 1.5 等残留差异），md5 一致才是文件级判据。
- **修复**：删顶层 IBUF_DIFF + `I_ddr_ref_clk_p/n` 端口、DDR wrapper `.I_sys_clk` 接回 `I_sys_clk`、pin.adc 删 K5/L5、sdc 注释 ddr_ref_clk_100m。⚠️ **删最后一个端口时前一行要删掉尾部逗号**（`ddr_dqs_n,` → `ddr_dqs_n`），否则 `)` 前多逗号报 HDL-8007 语法错误、白跑一轮编译。
- **TD GUI 关闭时可直接编辑 .al 管 IP 引用**：IP_FILE 段落内 `<File Path="../src/hdl_source_ip/ddr2/ddr2.xml">` 块（FileInfo 含 UsedInSyn/UsedInP&R/BelongTo/CompileOrder 四个 Attr）。GUI Remove 过的 IP，启动编译前先 `grep -n ddr2 <proj>.al` 确认引用在，否则 elaborate 缺模块白跑 26 分钟。
- **裁剪复制填充保底方案的规律**：hdmi_mixer 右列复制填充（S_last_col_data 锁存 + x≥N 输出锁存值）下板 3 像素→1 像素，是「覆盖边界与 bug 实际位置差 1 拍」的铁证；残留宽度 = 覆盖边界与 bug 位置的错位量，放大覆盖（x≥1264 锁存 1263）验证错位拍数——但若放大到 16 列仍残留细竖线（覆盖扩大、残留不缩小），伪影不在数据列位置而在显示时序，转 DE 消隐裁剪（§17.16）。
- **GUI 参数读取技巧**：IpTool 界面参数用 `tesseract <截图路径> out -l eng` OCR 直读（参数名大多是英文，中文界面也能出关键参数行），不用逐项问用户。「ADB File Path」等界面参数名以 OCR 原文为准。

### 17.16 66.67M 真正生效后：频率相关的第二 bug（grant）+ 伪影细分到「显示时序」（2026-10-23）

- **官方接法（C4 50M）全量重编后 clk1 终为 66.667，但下板出现与之前完全不同的大面积异常**：下 1/3 白色花屏+红绿蓝点、上 2/3 灰黑交替横线。**判读规则：频率变量改变后现象形态剧变 = 新异常由频率本身触发**——133.33M 时画面基本正常只有最右列、66.67M 反而大面积坏，说明超频时代「恰好工作」、官方频率才暴露的东西，首要嫌疑是**自写的 grant 仲裁（时序敏感）**。官方 66.67M 无此异常 → 差异在 grant 门控。修复 = 撤销 grant 全直连官方同款：`S_ddr_user_wr_en/rd_en` 只 `&& S_init_calib_complete`、地址按「写使能优先」选、video_in/video_out 的 `I_wr_grant/I_rd_grant` 接 `1'b1`。
- **写帧计数下板实测 0x2A300 = 172800 精确一帧 → 写侧（打包+写突发+计数）完美，「写侧提前结束/少写」假设彻底排除**——数码管 debug 计数器的价值：把「数量级」的猜测变成「精确数字」的判决。
- **数据覆盖 vs 显示时序伪影的区分（数据覆盖压不掉的伪影在显示时序）**：右列复制填充 3 像素→1 像素→放大到 16 列（x≥1264、锁存 1263）仍残留 1 条细竖线——**覆盖扩大而残留不缩小时，伪影源不在 DDR 数据链，而在显示时序（DE 边沿附近）**。**激进裁剪 = DE 消隐**：`O_hdmi_de <= S_video_de_3d && (S_x_2d < 12'd1264)`——把右缘直接送进消隐区，显示器根本不显示，比覆盖数据彻底一个量级（数据覆盖只是「坏像素换好像素」，消隐是「让像素不存在」）。
- 多份工程并行（分析/crop/nogrant）时 **patch 前先确认路径落在哪一份**——本次把 DE 消隐改进了正在编译的分析份又撤回重改 crop 份；编译中改 RTL 有 elaborate 读到中间文件状态的风险。
- **用户偏好：编译期间要求「预估编译完后的现象及其可能」**——给出带概率的预估表（各现象 × 概率 × 对应下一步行动），而不是只报「编译中」。
- **最终下板判决（2026-10-23，两个 bug 闭环，画面干净）**：66.667M（C4 50M 官方接法）+ 撤销 grant 全直连 → 最右列伪影、灰黑横线、白花屏全部消失。完整因果链：①接线错 100M 差分晶振 → 133.33M 超频 → 眼图边缘位错误 → 最右列 3 像素伪影；②133.33M 恰好掩盖了 grant 仲裁的时序问题，回官方 66.67M 才暴露 → 灰黑横线+白花屏；③撤销 grant（官方直连互斥）→ 显示链路 = 官方频率 + 官方架构，完全正常。**铁律：频率变量改变后「恰好工作」的逻辑可能在新频率下崩——修复一个频率问题后必须整链重验，别假设其他模块与频率无关。**

### 17.17 主线带宽方案 B（usr_clk 翻倍）+ 1080p30 版本知识

**主线消隐期读的带宽预算方法**：「消隐期读当前帧+背景帧逐像素比较、前景标记存片内 ERAM」的前提是消隐期能读完两帧。预算 = 两帧 128bit 个数 ÷ usr_clk vs 消隐期时长（帧周期 − 有效显示），把每个组合算成一张表再拍板，不要凭感觉选时钟方案：720p 两帧 = 345600 个 128bit、消隐 4.2ms → 66.67M = 5.18ms ❌ / 100M = 3.46ms ✓ / 133.33M = 2.59ms ✓✓；写侧独立验证（写需求 10.5M beat/s，帧周期内可用写窗口换算后远超需求）后确认写从来不是瓶颈。

**方案 B（⚠️ 已下板证伪——只翻 CLK0_DIV 也校准失败）**：改 `ph1p_ddrphy_pll0.v` 的 `localparam CLK0_DIV = CLK2_DIV*4 → *2`（CLK1_DIV/CLK2_DIV 不动）确实让 usr_clk 66.67→133.351M（时序报告坐实翻倍成功），内存仍是 1066Mbps——但下板**仍黑屏 + 写帧计数 0 + init_calib_complete 不拉高**。坐实机制：**MC↔PHY 的 DFI 接口是同步接口，MC 在 dhi_clk（usr_clk 133.35M）域、PHY 在 ctl_clk（66.67M，PLL0 clk1 经 MLCLK 缓冲）域，改比例把 1:1 打成 2:1 → 命令/数据采样错位 → 校准训练失败**。IPUG035 的「4:1 只支持」不适用这个 IP 版本——官方/米联客都跑 8:1 且 4:1 实测起不来。**铁律：dhi_clk（usr_clk）= ctl_clk = 内存 CK 三者 1:1 锁死、比例永不能动；要 usr_clk 快只有整体等比超频（VCO 缩放、所有时钟同比涨）一条路——用户历史 1660 超频正常显示的机制在此（超频可以、改比例死路；历史配置记忆是第一手证据，先问用户再反推）。**⚠️ **动 PLL0 任一路分频前必读 ph1p_ddrphy_clk_top.v 的连线，确认这路时钟接的消费者**——PLL0 四路拓扑（ph1p_ddrphy_clk_top.v 实测连线）：**clk0 → PLL1 参考 → usr_clk（dhi_clk，两级级联，usr_clk 不是 PLL0 直接输出）；clk1 → PH1P_PHY_MLCLK1 缓冲 → ctl_clk（PHY 控制/DFI 接口时钟）；clk2 → PH1P_PHY_MLCLK2 缓冲 → ddr_clk（内存时钟）；clk3 → cfg_clk**。**「CLK1_DIV 同步改」是错的（已下板坐实翻车）**：CLK1_DIV 翻倍 = 内存 CK 翻倍 = 内存 1066→2133 超频、且 CK 与 PHY 数据时钟关系破坏 → DDR 校准失败 → init_calib_complete 恒 0 → S_rst_n（含 calib 门控）不释放 → 黑屏 + 写帧计数 0。只有 CLK0_DIV 能翻（usr_clk 与内存 CK 分频独立）。这是「官方同款接法」与「主线带宽需求」的折中——**官方 lab_ex1 自己就跑在 usr_clk 66.67M（CLK0_DIV=16 即 ×4），「照抄官方」和「4:1 标准」是两件事，主线要 4:1 是消隐期带宽逼出来的**。⚠️ 此改法会改掉 IP 底层 RTL 的 localparam（TD 重新生成 IP 会覆盖回来），且 usr_clk 翻倍后 MC IP 内部最坏路径要重新看时序。**验证协议三步（每步都过才算数）**：①编译完先看 final_timing.rpt 的 clk1 是否翻倍（没翻 = 改动没进编译，白下板）②看 usr_clk 域 SWNS（MC IP 内部路径改不了，看工具布局给不给过）③下板验画面正常。

- **「黑屏但有 OSD Logo + SW4 debug 计数全 0」= DDR 校准失败的判据**：Logo/OSD 走 HDMI 域独立复位（S_hdmi_rst_n），不受 DDR 校准门控；而 video_in/video_out 在 DDR 域被 S_rst_n（pll_lock && init_calib_complete）挂起 → 写帧计数恒 0 + 读 FIFO 空黑屏。看到这个组合直接查 DDR 校准/复位链（改了什么时钟参数），不用往数据链查。**同场景的「自动曝光还在调节」= 采集链路活着的判据**：曝光统计走像素域（MIPI 域）、不经 DDR 也不受 S_rst_n 门控——黑屏时曝光值还能动，说明摄像头→MIPI→ISP 全链正常，故障被压缩到 DDR 域（校准/复位/时钟），不要往采集链查。

**1080P30 版本知识（_video_base 源码快照）**：SC500CS 支持 1920×1080@30 直出（寄存器表 uics500reg_1080p30.v：HTS=0x0B24、VTS=0x0467、MIPI 时序 0x4837=0x21）。**启用 1080p30 必须全链路切换**（uicfg 实例/uial2axis/ISP/DDR 帧尺寸/VTC/hdmi_mixer/hdmi_tx 全部 1920×1080），只换寄存器表会黑屏/分屏/错行。_video_base 是**无工程壳的源码快照**（HDMI 74.25M 标准 1080p30、DDR 已是官方 50M 接法免修复），落地要套一份现有工程的壳。1080p30 的消隐期带宽另算：一帧 = 388800 个 128bit、两帧 @133.33M = 5.83ms vs 消隐 5.4ms ❌——1080P 主线比 720P 更紧张，别直接套 720p 结论。

- **多份工程副本同步同一修复**：每份都要过「顶层接法 + pin.adc + sdc」三处改动（清单见 §17.15），改完 `grep -rn "I_ddr_ref_clk|S_ddr_ref_clk" src/` 确认残留只剩注释行，再清缓存全量重编、每份独立验证 clk1——**同步代码 ≠ 同步编译结果，每份都要过时钟报告**（实测同步修复的两份 clk1 各自验证为 66.667 才算完成）。

Design.xml 另加 `PH1P_DDR_SPEED` 1066.00→1600.00、`PH1P_SPEED_BIN` → DDR2-1600。**usr_clk = 内存/16（8:1）：1600 → 100M**。⚠️ **时间类参数（tCK/CL/CWL）按「绝对时间保持」缩放，不是按周期数**；频率类参数（FBKCLK_DIV/CLK3_DIV/REFCLK_FREQ）按比例缩放，**CLK2_DIV 例外保持 2**。**等比缩放后必查 final_timing.rpt 的时钟表全貌（clkN 列表），不只 clk1**：ddr_clk 266.667 = 内存半速 533（CLK2_DIV 错改 3 的露馅信号）、ddr_clk 800 = 内存 1600 正确；ctl_clk/ref_clk/usr_clk 各域频率逐行核对，比值不对（如 ddr_clk 与 ref_clk 比值变了）直接查分频参数。验证协议同 §17.17 三步（先看 clk1 是否 100、再看 SWNS、下板验画面正常）。

**带宽预算 tick 模型（主线开工前必跑，几分钟出精确数字）**：行为级整数 tick 模型（usr_clk tick 计拍 + 读延迟 40 拍 + 突发间隙 8 拍/240 拍突发）算出：100M 下消隐期读两帧 = 357160 tick = **3.572ms < 4.212ms ✓**（余 0.64ms）；写侧需 1.786ms、可用窗口 11.2ms ✓（余 527%）。**模型数字先做量级 sanity check**——帧周期 16.5ms = 1.65M tick @10ns，单位换算错 1000 倍（可用窗口算出负数）立刻露馅；模型脚本在 scripts/bw_budget_tick_model.py，改分辨率/速率直接改顶部常量。

**sdc 时钟组漏网坑（1600 实测）**：等比缩放后时序报告里 DDR 域时钟的**名字会变**——66.67M 配置下报 `usr_clk`，100M 配置下同一根信号报成 `ref_clk`（clk1: 100.000 ref_clk，usr_clk 名从时钟表消失）。sdc 的 `set_clock_groups -asynchronous` 若只列 usr_clk/ddr_clk，ref_clk 漏出异步组 → MIPI→DDR 域的跨域同步链（video_in 帧开始第一级打拍）被当真路径检查 → hold 违例 SWNS -1.571ns 全盘变红。修复（实测两轮才成）：**用通配符 `u_ph1p35_324_ddr_wrapper/u_ddr2/*` 匹配整个 DDR 域**——第一轮枚举五时钟名（usr_clk,ddr_clk,ref_clk,ctl_clk,mcu_clk）整条 `set_clock_groups` 命令 fails（log CRITICAL-WARNING）：**get_clocks 组内只要有一个不存在的时钟名（1600 下 usr_clk 已消失），整条命令被拒、一个组都不生效**。通配符对任何配置都稳（时钟名再变也不怕）。**规则：改 DDR 速率后核对时钟表全貌时，同时检查 sdc 的 get_clocks 匹配是否还覆盖所有 DDR 域时钟名——时钟改名让旧约束失效是隐蔽坑；枚举时钟名时先确认每个名字在当前配置下真的存在（时序报告 clkN 列表为准），拿不准就用通配符；违例路径若落在「跨域同步链第一级」，先查时钟组漏网，别急着改 RTL。**

**跨域 hold 违例的物理评估**：电平展宽信号（宽度 ≥ 多个源时钟周期）+ 3 拍同步链的第一级 hold 违例可接受——亚稳态由后续打拍消化，MTBF 远大于设备寿命，不必为它改 RTL；单周期脉冲跨域才是真危险。sdc 异步组豁免是这类同步链的正确处理方式，不是掩盖 bug。

## 18. 消隐期读落地：错峰读源的隔离铁律 + 流水实现坑（bg_read 状态机）


§13/§14 的「消隐期读」方案落地实现（bg_read 状态机：行块交替读两帧 → 双 FIFO → 3/4 节流弹 → 128→96 解包 → 逐像素比较 → 40bit 攒字写 ERAM）时，首版下板花屏。以下四条铁律覆盖全部根因。

### 18.1 消隐期读源的返回接收必须加时间窗口隔离（标签 FIFO 的互补方案）

- 现象：花屏+闪烁+画面内容「位置左右上下乱跳」= 叠加涂白乱画（标记数据错乱），视频本体没坏。用户直觉「数据读早了/一直刷新无用数据」方向正确——是 bg_read 把别人的数据当自己的在刷新。
- 根因：bg_read 的 `I_ddr_user_rd_valid/rd_data` 直连公共返回线（与 video_out 共享），显示期 video_out 的读返回被 bg_read 当自己的数据收进 FIFO → 状态机/标记全乱 → init 被误拉高 → 叠加用垃圾标记涂白。
- 修法：bg_read 内部加「接收窗口」`S_accept_ret`——消隐触发时开、显示期开始时关；FIFO 写使能和返回路由计数全部 `&& S_accept_ret`。显示期 video_out 的返回物理上仍在线上，但被窗口挡住。
- **规则：多路读共享返回总线时两种隔离手段**：① 读命令来源标签 FIFO（读交错进行的场景，§9）；② 时间窗口使能（严格错峰读的场景）。错峰读用窗口比标签简单可靠；窗口开关必须与读命令真正有效的时间严格对应，宁可晚开早关。

### 18.2 贴线预算的错峰读必须带「期界强制停止 + 清场」

- 读两帧纯数据时间贴着消隐期预算（3.45ms vs 4.2ms）时，实机 ready 波动/写忙/刷新会让跨期风险真实存在。bg_read 必须有「显示期开始」脉冲输入（de 恢复上升沿跨域打拍）：
  1. 立即停读（rd_active<=0）；
  2. 关接收窗口（§18.1）；
  3. 清场：两 FIFO 复位、解包复位（清 pending D）、攒字器/弹控制/帧头标记全部复位，防残余污染下一消隐期。
- **设计取舍铁律：错峰读「宁可标记作废，绝不干扰显示链路」**——读不完时该帧标记丢弃（init 不拉、画面干净），比「读完但跨期抢带宽花屏」好一个量级。
- 完成标志 init 必须由「写完最后一字」判定（写满 23040 字的地址条件），不能由「读命令发完/返回收完」判定——被污染的数据流能骗过后者。

### 18.3 行块交替读 → 3/4 节流 → 128→96 解包流水的实现坑（仿真全抓，编译前必过）

1. 读总数清零逻辑错误会读不停——读满停条件用 `(cnt==TOTAL-1) && rd_en && ready` 精确判定最后一拍发出。
2. 完成标志判定时机：读完 ≠ 写完，init 在「最后一字写入」拉高。
3. 行弹不能用「FIFO 水位>=N」当持续条件（弹 1 个就 <N 立即停）→ 行内弹计数（S_row_pop_cnt）弹满 240 对再复位。
4. 行尾无缝衔接会吞解包 pending D（下一行第一个输入占掉空洞拍）→ 行弹之间强制留 1 拍空洞（S_row_gap）。
5. 解包 valid 必须接 FIFO 的 valid 输出（与 dout 同拍、均延迟 1 拍），不能接弹使能信号（re 当拍数据还没出来，数据流错位 1 拍：帧头数据垃圾、帧尾丢数据）。
6. 写忙打断读返回时行尾 FIFO 可能空拍拒弹丢数据 → 行内弹加双 FIFO 水位门控（cur/bg 都 >=1 才弹），数据晚到后继续弹，行边界不错乱。
7. 帧头复位（frame_start）要提前到弹拍（数据拍前 1 拍），否则复位拍撞上数据拍、cnt=X 吞掉第一个输出。

### 18.4 流水线仿真调试的逐步收敛手法

- 层次引用打印：iverilog 支持 `u_bg_read.S_xxx` 直接打印模块内部信号，不用在 RTL 加 debug 端口。
- 现象→统计逐步收敛：总数差 2 → 按行统计每行输出数（定位差在哪行）→ 打印输出序列看 A/B/C/D 相位 → 检测「有输入无输出」事件 → 定位帧头/帧尾/行界。别从「感觉可疑的地方」改起。
- 两路同步性用异或统计（curV ^ bgV）：异或=0 说明两路同步、问题在共同输入链；异或>0 说明两路错位——一个统计直接把搜索空间砍半。
- TB 数据图案位序必须与 RTL 位序约定一致（96bit [95:72]=像素3、[23:0]=像素0），构造反了会出现假 FAIL（错位差值模式实为 TB bug）——仿真 FAIL 先排除 TB 自身图案/计数口径，再怀疑 RTL。
- 现象判读：「画面内容位置乱跳」优先查叠加数据源（标记 ERAM 数据从哪来、init 是否误拉高），别往视频本体链路查——视频本体坏是整帧花，叠加坏是局部乱跳。

### 18.5 读不完跨期的判据 + 分帧读正解

- **「读不完跨期」三件套判据（下板现象直接判定，别在别处耗）**：①画面内容对但**整体水平平移**、平移量每帧随机（=闪烁）——显示读帧头被消隐期读尾返回干扰；②**功能永远无效**（前景标记 init 永不拉、无涂白）——每帧读都被显示期打断、标记作废；③加了期界强制停止（§18.2）后行错位消失、只剩水平平移——干扰从「整帧」收窄到「帧头」，坐实是跨期残留。
- 因果链：读量纯数据时间贴着消隐期预算（如 3.45ms vs 4.2ms）时，实机 DDR 刷新/命令背压波动使实际读时长超预算 → 每帧读不完被打断 → 两条后果同时出现（标记作废 + 帧头干扰）。**纯数据时间预算「够」不等于实机够，贴线（<20% 余量）就要按「读不完」设计。**
- **分帧读正解**：每消隐期只读「半帧 cur + 半帧 bg」（数据量减半、余量翻倍），读满翻半帧选择（S_half_sel），奇偶消隐期交替读前/后 360 行；ERAM 写地址按半帧起点（0 或 11520）；init 由「两半都写完最后一字」判定。检测率降为帧率一半，全分辨率不变。
- 半帧选择只在「读满拍」翻转；读没满被打断**不翻**、下帧重读同半（写地址在期首/期界回半帧起点）——保证标记空间和帧内容永远同半对齐，不串半。
- **攒字器/写地址的期首置位与写递增必须同一 if-else 链**（置位分支优先），否则同拍非阻塞双赋值、递增覆盖置位 → 首字地址错 1。凡是「事件拍置基值 + 常规拍递增」的计数器，都写成 if-else 优先级结构。
- 诊断路径：功能无效（无涂白）先查「完成标志 init 是否从未拉高」（= 读/写从未完整完成一轮），坐实后再谈读量/预算，别先怀疑比较或叠加逻辑。
- **二分定位开关（消隐期读这类后加功能定位干扰源的首选）**：顶层把功能触发信号加软件门控（如 `I_blank_trig_eff = S_blank_trig && !(S_mode==N && I_sw[x])`，用数码管模式档 + 空闲开关组合，避开已有用途），一次编译同时产出「功能启用/禁用」两种状态，下板拨开关对比即可砍半搜索空间——比「改代码禁用功能 → 编译 → 下板 → 再改回来」省两轮编译。开关组合选择：优先「仅在某模式档下生效」的 AND 组合（本工程 SW1/SW2 已用作模式选择，二分开关最终用 S_mode==3 这一档本身 = 禁 bg，无冲突）；硬件丝印与代码位号映射见 §17.5。

### 18.6 写拍吞读命令 → 标签 FIFO 压弹错位（§9 标签方案的隐藏前提，三轮下板才定位）

§9 的标签 FIFO 有一个**没有明说的前提**：「压标签的拍 = DDR 实际执行读命令的拍」。任何优先级抢占（写优先）只要在该拍**没有同拍门控读使能**，前提就被打破，标签全链错乱。

- **现象判据（数码管双计数一眼定位）**：消隐读计数读满（正常）+ 显示读每帧计数暴跌到正常的 ~1/7（如 2A300 → 5000~6000）+ 画面撕裂但**撕裂线被前景标记正确涂白**（标记/比较系统正常，坏的是显示数据路由）。机制：标签错位后 video_out 误收背景读数据 → FIFO 水位虚高 → 读触发骤减 → 读不足 → 画面靠残留数据错乱显示（撕裂、内容左右漂移、功能标记全错）。
- **根因链**：video_in 写批第 1 拍，第三路读（bg_read）的「写忙避让」接的是**寄存器电平信号**（天然晚 1 拍）→ 该拍 bg 读命令照发 → 顶层 en=1、标签 FIFO 压入 1 个标签 → DDR 写优先执行写、读命令被吞、永远无返回 → 弹少 1 拍 → 错位 1 拍**累积**（FIFO 深度 64 很快溢出）→ 之后所有读返回标签全错。
- **修复三件套（写拍精确门控，三处缺一不可）**：
  1. 顶层读使能同拍门控写：`S_ddr_user_rd_en = (vo_en || bg_en) && !S_vi_ddr_wr_en`——写拍 en=0 → 标签不压 → 压弹永远匹配；
  2. video_out 的读 grant 改接 `!S_vi_ddr_wr_en`——vo 内部「命令计数 + 地址递增」在 vo_en 拍发生，必须与 DDR 实际执行同步，否则计数多算、地址错位；
  3. 第三路读的避让改接**组合写使能**（写拍精确），替换寄存器 busy 电平（宽信号晚 1 拍）。
- **铁律：撤销 grant 直连 OR 模式下，共享标签 FIFO 的「压」必须与 DDR 实际执行读严格同拍——任何优先级抢占都要在同拍门控读使能。拍级精确的避让必须用组合信号；寄存器信号（busy/valid 电平）天然晚 1 拍，只适合「写批整体避让」不适合「写拍精确互斥」。**
- **连带的恶性循环要认识**：显示读不足 → rd_busy 持续为 1 → video_in 的「写避让读」条件（!rd_busy）长期不满足 → 采集写停 → DDR 帧内容坏 → 显示读读到坏帧——现象会自我放大，定位时从「读计数异常」这一环切入，别在写侧/采集侧打转。
- **串行仲裁（ser_arbiter）时代的同款回归（2026-10-28 实锤）**：撤销 grant 全直连（§17.16）时把上面三件套一并撤了（顶层 rd_en 无 !wr_en 门控、vo grant 直连 S_vo_grant、bg 无写避让端口）——当时 bg 未启用画面正常，bg 启用后写拍同拍冲突回归。ser_arbiter 轮转下的新变体机制：video_in 写命令打 1 拍（`O_ddr_user_wr_en <= S_fifo_rd_en`），写批 valid（=仲裁 I_vi_busy 源）降拍后写命令仍发 1 拍 → 仲裁已切 VO/BG → 写命令尾拍与读命令同拍 → DDR 写优先吞读命令、标签 FIFO 照样压入 → 压弹错位。每帧 720 个写批 = 720 次错位累积 → 画面整体错位 + cur/bg 内容错位（静止水管涂白）+ bg 读计数错乱读不满（数码管 FC00/FC88 交替）。修复四件套：① 顶层 rd_en 加 `!S_vi_ddr_wr_en`（标签压同步关）；② vo 的 I_rd_grant 接 `S_vo_grant && !S_vi_ddr_wr_en`（vo 计数/地址与执行同步）；③ bg_read 加 I_video_in_wr_busy 端口接 S_vi_ddr_wr_en（读使能门控）；④ 仲裁 I_vi_busy 展宽接 `(S_vi_wr_req | S_vi_ddr_wr_en)`（wr_en 打 1 拍的尾拍溢出 valid 窗，展宽从源头防写读同拍）。**铁律：撤销/回退架构改动时，对照历史修复清单逐条核对是否被一并回退——「回退时某功能未启用所以没暴露」是最典型的回归陷阱；回退后 grep 顶层读写使能行的门控条件，与历史修复记录比对，别信「代码看着顺眼」。

### 18.6b ⚠️ 机制修正：真根因是「标签 FIFO 深度 < 命令 FIFO 在途数」（官方 RTL 坐实）

- 「写拍吞读命令」机制在官方架构下**不成立**：`mc_to_user_interface`（TD 生成的用户接口转换层，88 行 RTL）把读写命令都压进 155 位宽、**512 深**的命令 FIFO（`S_fifo_wr_en = wr_en | rd_en`），MC 按序弹出执行——**命令永不丢**，写拍只是让读命令排队晚发。查证方法：直接读 `src/hdl_source_clean/mc_to_user_interface.v`（公开 RTL，比搜文档快且是一手资料；网上搜不到这种内部实现细节）。
- **O_ddr_user_ready = ~命令 FIFO 的 afull**（官方注释原文：ready 拉低后还能再写 8 个）——ready 语义是「命令队列背压」，不是「DDR 空闲」。
- **真根因**：第三路读消隐期连续灌命令 → 512 深命令 FIFO 充满 → video_out 读命令排在队尾 → 返回延迟 = 队列 512 + MC 内部 ≈ 550+ 拍；而标签 FIFO 按「官方注释读延迟 40 拍」只做了 64 深 → **溢出 → 压弹错位 → 数据路由全乱**。判据：数码管显示读计数暴跌到正常的 1/7~1/30（2000~6000 vs 2A300），消隐读计数读满——且「写拍门控」修复后读数反而更低（命令更慢、队列更深）。
- **铁律：标签 FIFO 深度 ≥ 最大在途读命令数 = 用户接口命令 FIFO 深度 + MC 读延迟**。第三路连续读接入共享通道前，先读转换层的命令 FIFO 深度（PH1P = 512），标签 FIFO 按 ≥1024 设计；两路时代「读延迟 40 拍 → 64 深」的旧经验在有连续灌队的新路后失效。
- 「写拍精确门控」三件套（§18.6）保留——无害且让压弹更稳，但单靠它修不好本 bug，别再按「写拍吞命令」修。

### 18.7 帧边界复位撞进行中的读批 → 画面卷绕（vsync 强制停批 + 复位覆盖在途）

- 现象：画面不闪、无随机撕裂，但内容整体「卷绕」错位（视野右边缘绕到屏幕左边，屏幕左边出现一条图像边界竖线；手从右伸入视野会先从屏幕内竖线处出现、再从左边界绕出）。错位量 ≈ 读批剩余拍数（读批 240 拍，撞点位置决定错位量，约 0~240 拍）。
- 机制链：vsync 帧开始复位读地址时，video_out 的读批可能正读到一半 → 地址复位后，读批剩余命令用「帧头地址」读帧头数据、跟在帧尾批后面混进 FIFO → 显示顺序 = 帧尾 + 帧头 = 卷绕。第三路读加入后改变读批节奏（水位触发被干扰），读批撞 vsync 从「几乎不」变「常撞」。
- 连带的第二层竞态：FIFO 复位 10 拍覆盖不了 40 拍读在途——帧开始时读批若在途，复位结束后在途返回写进新 FIFO、混入帧头。
- 修复两件套：① vsync 帧开始强制停读批（`S_ddr_rd_valid <= 0`，读批剩余丢弃无损——本就该被 FIFO 复位清掉）；② FIFO 复位时长延长到 ≥ 读在途延迟（10 → 50 拍），复位期间 we 无效、在途返回全部丢弃。
- **规则：帧/行边界锚点复位地址或清 FIFO 时，必须先停掉进行中的读批，且复位时长 ≥ 读在途延迟拍数——「锚点复位」与「读批在途」是竞态对，第三路读改变读批节奏后从潜伏变爆发。**
- **⚠️ 写侧同款竞态（读侧修完卷绕仍在时才定位）**：video_in 的写批（攒 240 写 240）同样没有「帧开始强制停」——第三路读挤占命令通道使写批变慢，写批跨过帧开始拍时，写地址已复位到新帧头，帧尾批残余数据写到新帧头 → DDR 帧内容 = 帧尾+帧头卷绕。修法与读批对称：`if(S_frame_start) S_ddr_wr_valid <= 1'b0`（帧开始强制停写批，尾批残留由 FIFO 帧复位清除，丢一行尾数据比整帧卷绕强）。**帧开始停批判定若直接吃跨域打拍后的组合脉冲（如 `~extend_3d & extend_2d`），该组合路径进状态机可能 hold 违例（实测 -49ps，fix_hold 修不掉）——把脉冲再打 1 拍用（S_frame_start_d1），hold 压力转成 setup（本工程 setup 余量 176ps 足够），停批晚 1 拍无实质影响（新帧数据还没到）。****铁律：「帧边界停批」对读写两批对称成立——显示链路一侧修好、现象仍在时，先查另一侧（写批）有没有同款竞态，别假设写侧天然安全。**
- **「画面整体偏色（如偏红）+ 肤色/白色区域变绿」= R↔G 字节交换 = 帧头相位错位的字节级表现**，与卷绕同源：跨帧写错位让 128 位流的帧头相位错，解包时像素组边界错位，RGB 字节串位（白 FFFFFF 三通道同值不受通道重排影响，纯通道重排解释不了白变绿——只有「相位错位导致字节串位」能）。修好跨帧停批后色偏应随卷绕一起消失，不必单独查色链。

### 18.8 消隐检测的边沿脉冲要防重入（电平抖动二次触发）

- 现象：读计数比读满值多出一段（如 2A5D0 = 172800+720）——跨域电平检测（de 连续低 N 拍）在电平抖动/毛刺时产生第二个上升沿，二次触发把读计数清零重读，残余读量累加到显示值。
- 修复：读状态机的触发与所有「期首清零」都带激活保护——`if(I_blank_trig && !S_rd_active)` 才清零/置位（读总数、返回路由计数、帧头标记、写地址、攒字器、debug 计数逐个加），激活期内对重复触发免疫。
- **规则：跨域电平检测生成的「期开始」脉冲接状态机时防重入——所有期首清零统一走「触发且未激活」条件，不要只防触发拍、漏掉各处期首清零点。**

### 18.9 命令队列排队延迟 → 采集 FIFO 溢出丢字（卷绕+色偏最终根因，⚠️ 修正 §18.7）

- **现象判据**：卷绕+色偏「稳定不随机」（错位量固定 ≈ 几十字）；多轮机制修复（vsync 停读批 / FIFO 复位 50 拍 / 帧开始停写批 / blank_trig 防重入）下板**现象完全不变**——修复没打中根因。二分开关（模式 3 禁用 bg_read）画面完全正常 → 元凶锁定 bg_read 的 DDR 活动。
- **根因链（最终坐实）**：bg_read 消隐期连续读 172800 拍，命令灌满 mc 命令 FIFO（512 深）→ video_in 写批命令排在 bg 命令后，执行延迟 500+ 拍 → 传感器在显示消隐期持续输出，采集 FIFO 在写批延迟期间继续攒字 → **溢出丢字（几十字）** → 写进 DDR 的数据流整体前移 → 帧内容环形错位（卷绕）+ 128 位组边界错位（RGB 字节串位 = 偏红/肤色绿）。
- **写侧 FIFO 溢出预算模型（第三路读接入前必算）**：最坏写批排队延迟拍数 × 采集字率 < FIFO 深度 − 攒批触发水位。本工程：500+ 拍 × 0.67 字/拍 ≈ 348 + 正常水位 240 = 588 > 512 溢出。命令 FIFO 排队不丢命令、数据保序，但延迟效应全压在写侧 FIFO 上。
- **修复两件套**：
  1. **突发节流（参数设计铁律：停窗排空量 ≥ 读窗灌入量）**：连续读改「读 N 拍 + 停 N 拍」循环（burst 计数 0~2N-1 循环，写忙时不推进）——停窗让命令队列排空、写批命令低延迟插入、采集 FIFO 不溢出。⚠️ **N 的选择决定成败**：命令队列稳态水位 ≈ 读窗灌入量 N（停窗只能排空读窗灌入的量），写延迟 ≈ N + MC 延迟。首版 240/240 下板**无效**——停窗排 240、读窗灌 240，队列仍 ~512 恒满，写延迟仍 540 拍，溢出依旧。**128/128 已下板证伪（现象依旧，仍只有模式 3 正常）——「排队延迟 → 写侧 FIFO 溢出」假设整体排除**，突发节流方向放弃、勿再调 N。节流参数算术（停窗排空量 ≥ 读窗灌入量）本身正确，但下板证明溢出不发生在写侧 FIFO，转查「读侧互误收」（§18.12）。**判据：N 要满足「写延迟 N+40 拍 × 采集字率 + 攒批触发水位 < FIFO 深度」**，且节流后有效读窗口（消隐期 − 写批占用）÷ 2 ≥ 读满所需拍数，两项都要验算；预算模型成立不代表实机成立，下板确认前别把候选当结论。
  2. **写避让信号用「写请求电平」**（= 写批进行中 = S_ddr_wr_valid，video_in 现成输出 O_wr_req），不是「写命令拍」——写批期间第三路读完全让位，写命令畅通。写命令拍门控只保证「写拍不吞读命令」，保证不了「写批不被排队延迟」。
- **⚠️ 修正 §18.7 的连带结论**：「帧开始停写批修好色偏」不成立——跨帧停批是必要防护（防帧尾批写进新帧头），但不是本现象的根因；色偏与卷绕的真正根因是命令排队导致的写侧 FIFO 溢出丢字。
- **规则：多路共享 DDR 命令队列时，任何一路「连续长读」都必须突发节流（读 N 停 N）**，否则写命令排队延迟让写侧 FIFO 溢出丢字——丢字 = 数据流前移 = 内容卷绕 + 字节相位错。连续读灌满队列的延迟效应是隐形的（命令不丢、数据保序），症状体现在写侧 FIFO 溢出后的数据流错位，定位从「写命令排队延迟 × 采集率 vs FIFO 余量」预算模型入手。
- **「修复多轮现象完全不变」的信号**：同一现象下多轮机制修复都无效时，说明没打中根因——立即用二分开关（禁用可疑路，§18.5）下板砍搜索空间，别继续在同一层机制上叠加修复。禁用档位下「功能失效」是设计预期（如模式 3 禁 bg 后背景检测必然无效），不构成新问题。

### 18.10 显示链路二分诊断的判读规则（黑屏/错位定位通用）

- **禁用开关生效后，数码管计数显示的是「切换瞬间冻结的旧值」**——每切一次模式/开关，冻结值不同（切换时刻计数跑到的进度不同），是正常现象，不代表被禁模块还在运行。判读规则：切到禁用档后「盯着看数值变不变」——不变 = 已冻结（禁用生效）、持续变 = 禁用失效（查门控条件/开关极性/跨域）。
- **「插着线黑屏但显示器不提示无信号，拔线几秒后才显示无信号」= HDMI 同步已建立**：时序/VIC/像素时钟正确，显示器在正常接收但数据全黑 → 问题在数据链路（采集/ISP/DDR 读），别继续查 HDMI 参数。真 HDMI 链路故障（时序错/VIC 错）显示器会直接提示无输入。
- **曝光值拉爆（远超当前分辨率的上限）= AE 拿不到有效图像**：AE 在无数据下不断拉曝光——这是采集链路断（传感器配置失败/MIPI 无数据/ISP 无输出）的旁证，和「写计数为 0」互相印证。1080p30 的 AE 上限 = 2×VTS-10（1127×2-10=2244），720p 是 3990，判读前先按当前分辨率算对上限。
- **LED 位编码做配置状态诊断**：把「摄像头寄存器配置完成」信号接到 LED 某一位（如 O_led = {cfg_done, 1'b0, S_mode}），比数码管档位更直观——LED 位诊断：配置完成位亮 = 配置完成（问题在 MIPI/ISP）、灭 = I2C 配置失败（查时钟分频/引脚/寄存器表）。诊断改动要小、不破坏既有功能位。⚠️ **描述 LED 前先核对 pin.adc 位序和板丝印的对应**：`O_led = {cfg_done, ...}` 的 cfg_done 在最高位 O_led[3]（本工程 D6 = 丝印 LED4），口说「LED1 亮」会误导用户——位序以 pin.adc 的 set_pin_assignment 为准，不确定就让用户报「亮的是哪个位置的灯」。扩展用法：**数据活动诊断**——把 ISP 输入 tvalid 展宽（约 0.9 秒计数器，valid&&ready 时置满、否则递减）接 LED 另一位，下板一眼区分「MIPI→ISP 无数据」还是「有数据但后面断」，比等写计数诊断快一轮。
- 720p60 与 1080p30 的**像素时钟相同（都是 74.25M 标准钟）**，有效像素率不同（1280×720×60=55.3M vs 1920×1080×30=62.2M 像素/s，差 12.5%）——MIPI 物理层速率自适应、参数 diff 一致，切 1080p 时 MIPI 层不用动，只改寄存器表 + 全链路尺寸参数；「黑屏无 OSD/logo」时先查加密 HDMI IP 的例化传参（例化参数覆盖 .enc 默认值，查 .v 实际传参行，不能只看 .enc 声明），VIC 不对显示器拒显。

### 18.11 分辨率切换（720p→1080p）黑屏的静态审查清单 + 编译并行规则

- **配置完成（cfg_done=1）但画面黑时的静态审查清单（逐项过，全对再下板二分）**：① 寄存器表长度由 REG_SIZE 自动获得（例化表模块名对了就不会截断）——确认 uicfgcs500 内部例化的表是 1080p 表且行宽/行高/HTS/VTS 四项寄存器（0x3208~0x320F）完整；② MIPI RX wrapper 参数（LANE_NUM/BYTE_NUM/DPHY 位置）与 720p 版 diff 一致；③ CSI/RAW10 解包层是协议驱动（DT/包长），无分辨率写死，不用改；④ ISP 各例化（demosaic/awb 的 IMG_WIDTH/IMG_HEIGHT）与坏点/中值/Sobel/Canny 的行计数回绕上限都要查——**行缓冲 reg 数组宽度 [0:319]→[0:479] 这类易漏**；⑤ 数据/valid 对齐链是纯移位无行计数，不用改；⑥ AE 上限按新分辨率重算（2×VTS−10）。静态审查找不到 bug 时，别继续猜——下板用「写计数 + 数据活动 LED」二分（§18.10）。
- **TD 编译并行规则（实测）**：不同工程目录可并行跑 td_commands_prompt（无 license 冲突）；**同一目录绝不允许并行**（旧 shell 会拉起第二个 td 打同一个 db，编译结果互相破坏）。「两个版本在编译」的报错先 kill 所有 td/td_commands/cmd 进程再重启干净一轮。

### 18.12 读侧互误收窗口 + 时间隔离（当前方向，待下板验证）

- 节流证伪后的新分析：卷绕+色偏的量级 ≈ 几十字误收（如 34 字 ×5.33 ≈ 181 像素卷绕，且 34 mod 3 = 1 → 解包相位错 1 个 96bit → RGB 字节串位 = 偏红/肤色绿）。**通用规则：任何使 128bit 数据流丢/多 N 个字、且 N mod 3 ≠ 0 的机制，都会在卷绕之外额外产生字节相位错色偏**——两个症状同源，不必分查色链。
- 两个互误收重叠窗口（标签机制逻辑自洽但无时间兜底）：① video_out 帧尾读批（显示期末发出）的在途返回在消隐期头 ~300 拍落地，bg_read 的接收窗口（blank_trig 即开）误收 vo 返回 → 比较数据污染 → 检测无效（init 永不拉/涂白错）；② bg 消隐期读返回若标签有隐藏错位（如 1024 深 reg 数组组合读被综合器变同步读）进 vo FIFO → 显示数据混入 bg 读出的帧内容 → 卷绕+色偏。
- 修复（时间隔离兜底，标签之外的独立防线）：
  1. video_out 加 I_disp_win（= !消隐电平，DDR 域）：FIFO 写门控 `we = rd_valid_d1 && rd_tag_d1 && I_disp_win`——消隐期 bg 返回即使标签错也不进 vo；vo 自己的帧尾批返回被拒无损（vsync 的 FIFO 复位本来就会清掉它）。
  2. bg_read 读启动延迟 ~600 拍（blank_trig 后计数再置 rd_active）：vo 帧尾返回先落地，bg 的读/收窗口都不与其重叠；消隐期预算要减掉延迟量重算。
- 规则：多路读共享返回总线时「标签路由」和「时间窗口」是两道独立防线——标签按命令顺序路由（数据保序前提），时间窗口按错峰时刻隔离。标签逻辑自洽 ≠ 实现无错，深 FIFO 的组合读综合行为也要怀疑。错峰两路的「在途返回尾」落在对方窗口的拍数要算清，用延迟启动/提前关闭错开。
- ⚠️ **下板证伪（2026-10-25）**：窗口隔离两件套下板后画面**更乱 + 闪烁严重 + 显示器下方一部分黑屏**，已整体回退。机制：① I_disp_win 用「消隐电平的反」（!S_blank_s3）做显示期窗口是**粗糙边界**——场消隐电平在显示期末行就拉高，把 video_out 帧尾读批的在途返回也拒了 → 帧尾行数据丢 → 下方黑屏；② bg 读启动延迟 600 拍挤压读窗口、加剧读不完。**规则：时间窗口门控的边界必须比「被保护的在途返回窗口」更紧——用粗糙的消隐电平反相做门控会误伤帧尾批，窗口边界要精确算（消隐电平生效拍 vs 帧尾批返回落地拍），算不清就别上窗口门控。**
- 回退后回到「节流 128 + 标签加深」基线，新增「写不准」直接实锤诊断：video_in 采集 FIFO 的 full_flag 锁存到 LED 高位（`O_led = {S_fifo_full_latch, 模式位}`，锁存到复位）——下板判据：LED 满标志位亮 = 采集 FIFO 确实溢出丢字（写侧坐实，继续治写）；灭 = 写侧干净（全力查读侧路由）。**规则：多轮机制修复无效、在「写不准 vs 读不准」之间反复时，先给写侧加满标志锁存诊断再下板——一次下板就把假设二分，比继续叠加修复快。**
- **搜索核查结论**：公开资料（Bing 中英文两轮）对「多路读返回时间重叠污染」无直接命中案例，通用原则 = 乒乓多缓冲 + 读数据 ID 路由 + 独立读写通道（FDMA 类架构），与本工程已有设计一致——此类深水 bug 无公开捷径，靠二分开关 + 实锤诊断下板定位。

### 18.13 窗口边界跨域问题 + DDR 域自同步窗口状态机（已实现 + 仿真验证，下板待验）

- **S_blank_hdmi 检测链事实（架构，现已退役）**：场消隐 = de 连续低满 1650 拍才拉高（开窗晚 1650 拍）、de 高立即拉低——**边界不对称**；再跨域 3 拍进 DDR 域（上升沿 = bg 读启动、下降沿 = 停读）。bg 读的启停时刻完全由 HDMI 域信号跨域决定，每次复位后两域相位漂移 → bg 窗口与 vo 读批的相对位置漂移 → 症状每次下板不完全一样。
- **「闪烁复现」的因果坐实**：窗口隔离版把 !S_blank_s3（跨域信号）直接门控 vo 收数，闪烁立即复现——跨域抖动直接灌进显示读。**规则：跨域信号（未同步稳定的电平）绝不能直接门控消费侧数据通路；回退门控后闪烁消失 = 坐实。**
- **用户架构直觉（已采纳）**：三个时钟域角色分明（摄像头域连续采集写、DDR 域搬运+处理、HDMI 域消费显示），DDR 读写应有「明确的窗口期」——对应 C 工程原则「明确变量表明、边界清楚」。窗口边界不该由跨域检测决定，应由 DDR 域本域信号判定。主显示链（采集→算法→显示流水并发）不要改成分阶段串行——算法在像素域边到边就处理完、不过 DDR（灰度/二值/Canny 在 isp_top 的 AWB+BPC 之后，四路并行 MUX 选一），「窗口期」思想精确落在 DDR 这个共享资源上。
- **S_ddr_win 窗口状态机（已实现）**：2 位显式状态变量——WIN_DISP（显示窗口：vo 读+vi 写互斥，bg 完全禁止）/ WIN_BLANK（消隐窗口：bg 读+vi 写互斥 bg 避让写批）。切换全部由 DDR 域本域信号判定：
  ```verilog
  // vo 读请求连续空闲计数（显示期读批间隙几十~几百拍 < 2000 拍阈值不误判；空闲计数到 2047 封顶防溢出）
  if(!S_vo_rd_req) S_vo_idle_cnt <= (S_vo_idle_cnt==11'd2047)? S_vo_idle_cnt : S_vo_idle_cnt+1;
  else            S_vo_idle_cnt <= 11'd0;
  case(S_ddr_win)
    WIN_DISP : if(S_vo_idle_cnt==11'd2000) S_ddr_win <= WIN_BLANK;  //vo 连续空闲 2000 拍=消隐窗口开
    WIN_BLANK: if(S_vo_rd_req)             S_ddr_win <= WIN_DISP;   //vo 请求恢复=立即关窗（1~2 拍停 bg）
  endcase
  // bg 启停 = 窗口切换沿的单拍脉冲（prev 打 1 拍 + 沿检测），DDR 域零跨域
  wire S_blank_trig_new =  (S_ddr_win == WIN_BLANK) && !S_win_prev;
  wire S_disp_begin_new = !(S_ddr_win == WIN_BLANK) &&  S_win_prev;
  // 二分开关保留：S_blank_trig_eff = S_blank_trig_new && !(S_mode==2'd3 && I_sw[0])
  ```
  退役清单（一并删干净，别留悬空）：S_de_low_cnt/S_blank_hdmi 检测块、S_blank_s1~3 跨域链、S_disp_begin_s1~3 跨域链、S_blank_trig 旧声明、video_out 的 I_disp_win 端口及其顶层接线。S_hdmi_de 本身独立存在（VTC 驱动、hdmi_mixer 消费），删检测块不影响它。
- **窗口状态机必过仿真（8 场景全 PASS 才编译）**：抽出状态机写独立 tb 验证——①显示期读批间隙（240 读 80 停循环 12 轮）不误判；②空闲 2000 拍准时进 BLANK；③blank_trig_new 严格单拍；④vo 请求恢复 1~2 拍内回 DISP；⑤disp_begin_new 严格单拍；⑥模式 3+开关二分门控生效；⑦BLANK 期 vo 抖动 1 拍立即关窗（设计预期行为：宁可 bg 少读不干扰显示）。**规则：状态机/窗口/仲裁这类纯时序逻辑，抽出独立 tb 跑 iverilog 几分钟验证全部边界场景，比编译半小时下板试错快一个数量级。**
- **FIFO 满标志 LED 下板实锤（写侧溢出的直接证据）**：video_in 采集 FIFO 的 full_flag 锁存到 LED 高位（`O_led = {S_fifo_full_latch, 模式位}`，锁存到复位），实测 LED 常亮 = 上电以来满过至少一次 = 写侧溢出真实存在 → 窗口状态机保留「bg 避让写批」规则。⚠️ **锁存型诊断的粒度限制**：常亮只能证明「满过」（含初始化瞬态），不能区分「初始化期满过一次」还是「bg 活动期持续溢出」——判读时要配画面现象（稳定错位 = 持续机制、仅上电期错 = 瞬态）下结论，别把「常亮」直接当「持续溢出实锤」。**规则：多轮机制修复无效、「写不准 vs 读不准」反复摇摆时，先加满标志锁存 LED 一次下板二分假设，别继续叠加修复。**
- 状态机改动点备忘：S_vo_idle_cnt 用 11 位（2000<2048）；复位后初始 WIN_DISP（上电即有显示期，bg 等第一个消隐窗）；窗口进出脉冲用 prev 打拍+沿检测（组合比较当前状态和 prev），不用跨域边沿检测。消隐窗开窗延迟 = 显示期末 vo 把 FIFO 填满的最后几批（几百拍）+ 2000 拍判定 ≈ 3000 拍。⚠️ **预算口径别按「4.2ms 消隐期」算**——那是「场消隐+行消隐汇总」（见 §18.14 精确数字），BLANK 窗口实际只有场消隐段 ~64690 拍。

### 18.14 vsync 预读批打断窗口 + 800 拍屏蔽窗 + 真实场消隐预算（仿真坐实）

- **现象**：窗口状态机版下板——错位仍在 + 画面下方叠加一层花屏。用户质疑状态机是否写成功、要求仿真——仿真立刻抓出真问题。
- **根因（tb 坐实）**：vsync 后 video_out 的**预读批**把 BLANK 窗口拦腰打断。vo 读批触发是纯水位触发（空位 ≥300 即水位 ≤211），**没有 de 条件**——vsync 后 FIFO 复位 50 拍让水位归 0 → 必然触发预读批（灌 240 字到水位 240 > 211 停，**只 1 批不是 2 批**）→ S_vo_rd_req=1 → 窗口状态机误判「显示期开始」立即回 DISP → BLANK 窗口只活了 ~1 万拍 → bg 读不满 → ERAM 半残 → 叠加花屏。
- **修复**：vsync 跨域打 3 拍 + 上升沿脉冲 → `S_vsync_hold_cnt` 800 拍屏蔽窗（脉冲置 800、每拍递减）；`S_vo_req_eff = S_vo_rd_req && (S_vsync_hold_cnt == 0)`——屏蔽窗内预读批视为空闲（不重置空闲计数、不触发回 DISP），de 恢复后真正的读批（屏蔽窗外）正常关窗。
- **规则 1：用「vo 请求活动」判定窗口的状态机，必须认识 vo 的「消隐期合法活动」形态**——vsync 后 FIFO 复位引发的预读批是消隐期内必然发生的，不是显示期开始。窗口状态机要按 vo 行为模型的全部形态设计屏蔽，否则窗口被「自己人」打断。
- **规则 2：仿真模型必须按真实行为建模——先读 vo 读批触发条件代码（水位阈值）再写 tb**。预读批数 = 1（240 拍，水位 240 > 211 不再触发）；给 2 批（读/停循环 804 拍 > 屏蔽窗 800 拍）会假 FAIL。模型给多了比给少了更误导。
- **真实帧时序精确数字（720p60：HTS 1650、VTS 750，HDMI 75M，DDR 域 100M）**：帧周期 = 1237500 像素 = 1667250 拍；有效显示 = 921600 像素；**场消隐 = 30 行 = 49500 像素 = 66690 拍（0.67ms）**；行消隐汇总 = 750 × 370 = 277500 像素 = 373973 拍；**vo 空闲总时长 = 场消隐 + 行消隐汇总 ≈ 4.4ms**。§14.1 的「消隐期 4.2ms/315900 像素」是**汇总值不是场消隐**——行消隐（498 拍/行@100M）是碎片化 vo 空闲，2000 拍连续阈值把它们过滤在 BLANK 窗口外。
- **vsync 脉冲触发（非窗口状态机）的读窗口更小**：VTC 的 vsync 高 5 行（vcnt 726~730）、上升沿在 730 行末 → 到帧末仅 20 行 = 44000 拍 @100M，比场消隐（66690 拍）还小 1/3。bg 读「读满才停」的设计让读不满自动跨显示期继续（仲裁轮转下与 vo 分享带宽），窗口大小只决定读满耗时——**读计数应持续增长，恒 0 = 启动链断，不是窗口小**。
- **预算后果**：BLANK 窗口 = 66690 − 2000 判定延迟 ≈ **64690 拍 < 分帧读 172800 拍** → 每消隐读不满半帧、跨 3 个消隐累计读完 → 检测率掉到 ~10fps（全分辨率不变）。2000 拍阈值成立性：显示期读批间隙 ≈ (水位差 451−211)/消费率 0.74 ≈ 324 拍、行消隐 498 拍，都 < 2000 不误开；场消隐 66690 拍必然开。**帧率优化方向：行消隐也纳入 bg 窗口（498×750 ≈ 37 万拍能补回 30fps 预算），但 bg 读批 240 拍会跨行界拖进显示行，需读批压缩或行级窗口切换，未实现前别承诺帧率。**
- **规则 3：窗口/分时预算必须按「窗口真实可用时长」核算，不是按理想消隐期**——「消隐期够读满」的判断要先分清「场消隐」「行消隐」「汇总」三个口径，再减去开窗判定延迟和预读屏蔽，剩下的才是 bg 实际可用窗口。贴线预算（<20% 余量）一律按「读不满」设计（§18.5 分帧读的既有规则）。

### 18.15 标签路由失效实锤 → 窗口分流（症状内容判读法，标签路由退役）

- **症状内容判读法（用户观察直接锁死根因）**：窗口状态机版下板后画面下方花屏的**内容 = 背景采集的图片**、SW4 重采背景花屏内容跟着更新、花屏内有竖线错位——混入画面的数据内容可辨识时直接指向数据来源（背景块 BG_BASE 的数据进了 vo 显示 FIFO = bg 读背景块的返回被 vo 错收），不必再猜时序机制。**规则：显示画面混入「另一路读的数据内容」（背景图片/其他帧内容）时，坐实共享返回总线的收数门控失效——下一步只查「谁的返回进了谁的 FIFO」，不要再在命令排队/节流/窗口边界上叠加修复。**
- **标签路由失效教训**：rd_tag（1024 深 reg 数组组合读）的压弹相位在综合器行为/边界拍存在隐藏错位风险，且多轮「时序层」修复（节流/停批/窗口边界）都打不到数据路由层。窗口状态机建立（S_ddr_win 显式窗口）后，**收数分流直接用窗口取代标签**：vo 的 `we = rd_valid_d1 && disp_win_d1`（I_disp_win = S_ddr_win==WIN_DISP——显示窗口收、消隐窗口一律拒收；vo 帧尾批在途返回被拒无损，vsync 的 FIFO 复位本来就要清它）。时间窗口天然把两路分通道，是 FDMA 类架构「每通道独立读数据 FIFO + ID 路由」的简化等价（搜索核查米联客 FDMA 确认此为标准做法）。
- **bg 侧对称误收**：vo 的 vsync 预读批 240 拍命令（纯水位触发、顶层 vo 优先于 bg 进 mc 队列）会插进 bg 的读返回序列 → bg 误收污染。修法：bg 的读使能 + 收数门控（S_accept_ret 的**全部使用点**：读使能、返回计数、cur/bg 两 FIFO 的 we）都 `&& !I_vsync_hold`（顶层屏蔽窗电平）——**停读停收，不是只停收**：只停收会打断返回序列的帧头对齐（S_ret_mod 错位），停读让序列整体跳过屏蔽段、帧头检测自洽。
- **标签电路退役手法**：先只改收数门控、压弹电路保留（无消费者时 TD 综合优化掉，无副作用），下板验证窗口分流成功后，再删干净 rd_tag FIFO 及压弹逻辑——不要一次删电路+改门控两个变量。
- **规则：共享返回总线的多路读，分流手段按「错峰程度」选**——严格错峰（窗口状态机保证）用时间窗口（简单可靠）；交错读用标签 FIFO（§9）。两者都上时窗口是独立兜底防线。标签逻辑自洽 ≠ 综合实现无错，深 FIFO 组合读的时序行为也要怀疑。

### 18.16 窗口一刀切饿死采集链 → 回退标签门控 + 标签同步读钉死延迟（黑屏教训）

- **现象**：窗口分流版下板——不闪烁了但**全屏黑屏**，数码管显示「7800 多 + 0」、LED4 常亮。
- **数码管判读先于一切**：判读数码管数值前必须先确认当前 S_mode 对应的显示内容（本工程模式 0/1 显示曝光/增益，7808 ≈ 曝光拉满上限 7916、0 = 增益）——「7800 + 0」是 AE 拉满信号，不是读计数。**规则：黑屏 + AE 拉满 = 采集链饿死（写不进 DDR），先查「谁把写批饿死」，别在显示链查。**
- **根因（窗口收数一刀切的副作用）**：vo 收数门控纯显示窗口把「帧尾读批的在途返回」（显示期末发出、消隐期头落地）也拒了，且 BLANK 窗口里 bg 连续读挤占 mc 命令队列 → 写批命令排队 → 采集 FIFO 溢出（LED4 实锤）→ 写不进 DDR → AE 拉满 → 黑屏。
- **决策回退（用户问「标签能解决错位吗」的最终答案）**：标签是**事后补救**（数据已在总线上靠门控分流，依赖「标签路径与数据路径严格同拍对齐」这一条脆弱前提）；窗口是**事前隔离**（两路时间上不重叠）。但窗口收数的正确边界必须是「显示窗口 || 在途拖尾窗」——在途拖尾窗 = vo 自己的读批 valid 打 ~400 拍移位（覆盖 mc 延迟+排队），全同域、不依赖综合器行为。**一刀切显示窗口必饿死采集链，未实现拖尾窗前先用标签门控**。
- **标签错位的精确修复（显式同步读钉死延迟）**：1024 深 reg 数组的 `assign rd_tag = fifo[rptr]` 组合读，TD 综合器可能寄存器化（+1 拍）→ 标签与 rd_valid_d1 错 1 拍 → 消隐期 bg 返回被 vo 误收。修法：
  ```verilog
  reg rd_tag_sync;
  always @(posedge clk) rd_tag_sync <= rd_tag_fifo[rd_tag_rptr];  // 显式同步读，延迟钉死 1 拍
  // vo 内：rd_valid 打 1 拍（rd_valid_d1），标签不再打拍
  // we = rd_valid_d1 && rd_tag  —— 两条路径同拍对齐，与综合器行为无关
  ```
  **规则：跨路径对齐的信号（标签 vs 数据）绝不依赖综合器对组合读的处理——显式同步读把延迟钉死，再让两条路径打相同拍数。组合读「语义 0 拍」但实现可能 1 拍，这是深 FIFO 标签错位的头号隐藏源。**
- **钉死标签延迟后，收数两侧的数据路径打拍数必须一致配平**：vo 侧 rd_valid 打 1 拍（rd_valid_d1）配 rd_tag 对齐；bg_read 侧若仍用 rd_valid（0 拍）直配 rd_tag，bg 侧标签系统性错 1 拍 → 每批 240 拍边界丢 1 个真数据、误收 1 个邻居数据（批内正确，约 1/240 污染，不足以完全失效但标记内容错位）。修标签对齐时把「所有消费者」列出来逐一核对打拍数，别只改一侧。
- **锁存型 LED 诊断的判读限制（§18.13 的补充坐实）**：FIFO 满标志锁存「常亮」只能证明上电以来满过一次（含初始化瞬态），不能证明持续溢出——判读必须配画面现象（黑屏+AE 拉满 = 持续饿死；画面正常+灯亮 = 仅上电瞬态）。锁存诊断只适合「是否发生过」，不适合「是否正在发生」，后者要用带递减的实时指示（如数据活动展宽计数器）。

### 18.17 标签同步读对齐下板无效 → 三级优先级战略 + 副本验证法（2026-10-25 当日状态）

- **负结果（已下板坐实）**：显式同步读钉死标签延迟（§18.16）后下板**现象基本不变**——模式 3 正常、其他模式错位+花屏依旧。数码管 3F840（模式 0/1 的曝光/增益档）与模式 3 下的 2CF（=719，切换瞬间冻结值，§18.10 判读规则）都不指向读计数。**规则：修了标签路径对齐而现象纹丝不动 = 标签链条（压弹/对齐/同步读）整体自洽，误收另有通道——停止在标签上叠加修复，转查「地址污染」**（vo 读命令拍错用 bg 地址读回 BG_BASE 背景块内容，同样能造成「花屏=背景图片」且对标签修复免疫）。
- **卷绕 180 像素 ≈ 33 字的新机制分析（候选，未下板验证）**：帧尾读批在途残余命令（vsync 帧开始强制停批时已发出的 ~33 个）的返回被 bg 残余命令在 mc 队列里排队拖后、落到 FIFO 复位 50 拍之后 → 混进新帧 FIFO → 卷绕。修复候选：复位窗 50→300 拍 / 帧开始同时强制停 bg 读批（bg 残余停止灌队列）/ 帧头屏蔽窗（帧开始后 300 拍内 vo 拒收）。**机制要点：帧开始只停 vo 不停 bg，bg 残余命令把 vo 在途返回拖出复位窗——「复位时长 ≥ 读在途延迟」的旧经验（§18.7）在多路排队下要把「对方残余命令的排队时间」也算进在途。**

### 18.20 最终判决：三路并行门控整体放弃 → 回退 BRAM 320×180 降采样（2026-10-25 晚定稿）

**读优先三件套下板负结果（最后一轮 DDR 方向实验）**：① vo 读批触发删写忙避让 ② 顶层写让路 vo 读批 ③ I_rd_grant 恒 1——下板**更严重**：模式 3 出现等间隔横黑线。机制：读写命令交织打断读数据流 → 周期性丢行 → 等间隔黑线；这正是官方 video_in 注释警告的镜像坑（官方靠双向避让避免交织）。三件套整体回退。**规则：双向避让（写批触发看 !读忙、读批触发看 !写忙）是官方两路稳定的根基，破坏它必出交织伤；「读优先」只能通过仲裁顺序实现，不能通过删避让实现。**

**网上三篇同赛道实战文章的共同结论（搜索核查，支撑最终判决）**：① CSDN「DDR仲裁、多输入源拼接」（FPGA 大赛作者）——固定优先级**串行状态机仲裁**，每路一次 burst 轮流服务，「一次 burst 吐出 256 而我只要 128 会造成 DDR→FIFO 时序和数据位的错乱」（= 色偏+卷绕同类病），修法是数据计数强制对齐；②「八通道 DDR 读写防冲突」——仲裁粒度从一笔请求提高到小批量（连续几笔再切方向）、**burst 边界不可打断**、读返回乱序用 ID 映射+每通道独立返回 FIFO；③「FPGA 视频 4 分屏」——写/读各一套串行状态机 + 多选器结构（只有选中路与总线通信），8 通道共享单路 DDR 实战验证。**结论：单路 DDR 多主的标准工程解 = 串行状态机仲裁（任何时刻总线只服务一路、burst 原子、返回落地才切换）；「三路并行使能 + 门控/标签/窗口」的并行架构天然带交织/在途拖尾/返回错乱，修一处冒一处。**

**用户最终决策（时间账优先）**：DDR 三路方向连续一周未收敛（16+ 项门控/仲裁/标签/窗口改动全部下板无效），放弃全分辨率 DDR 背景读，**回退到已验证稳定的 BRAM 320×180 降采样背景减除**（前景 4×4 块，边缘锯齿是已知代价）。决策逻辑：比赛时间 > 分辨率执念。**规则：连续多轮「改→编译→下板→现象不变」且已排除完数据路由/仲裁/时序各层后，果断降复杂度回退已验证方案——稳定可演示 > 完美未收敛。**

- 加：I_frame_start（vsync 打拍脉冲）触发读一帧、I_bg_grant（时间片门控 en）、I_rd_tag（收数门控——`we = rd_valid && !I_rd_tag`，S_accept_ret 退役）、O_bg_rd_busy。
- **批边界**：每 240 拍（S_rd_seg_cnt==239 的 en 拍）置 batch_gap 1 拍 → `O_bg_rd_busy = S_rd_active && !batch_gap` 降 1 拍 → 仲裁切走。下一轮时间片继续下一批，读总量由 S_rd_total 封顶。
- **⚠️ 删端口后必须 grep 全部使用点**：残留 I_blank_trig/I_disp_begin 引用会让 TD 打开工程直接报 `PRJ-8644 Failed to analyze source file(s)`（HDL-8007 not declared），编译 4 秒就死——删端口/改名后全文件 grep 旧名，别靠逐个替换。

**带宽账（串行不亏，设计时先算）**：每轮 720 拍各服务 240 字；bg 一帧 172800 字 = 720 轮 × 5.4μs = 3.9ms < 16.7ms 帧周期 → 60fps 全帧检测；vo 供率 240/720×133M = 44M 字/s = 显示需求 17.4M 的 2.5 倍。

**新 .v 文件注册 TD 工程 + patch 工具的转义坑**：新文件（如 ser_arbiter.v）必须加入 `.al` 工程的 `<File Path="...">` 条目区（复制相邻条目格式，CompileOrder 递增），TD 不自动扫目录。**patch 工具会把 & 转义成 &amp;（UsedInP&R → UsedInP&amp;R）破坏工程文件**——patch 后立即 `grep -c 'amp;R' xxx.al` 检查，误转义用 `sed -i 's/UsedInP&amp;R/UsedInP\&R/g'` 恢复。

**多工程并行编译规则（实测）**：不同工程目录（主线 vs 副本）可并行编译；**同一 prj 目录绝不允许两个编译并存**——杀掉旧编译后必须确认 `ps aux | grep td_commands_prompt | grep -v grep | wc -l` 为 0 再启动新的，否则共用 Runs 目录互相破坏。后台多编译时用启动顺序/elapsed 区分哪条链属于哪个工程。

**仿真先行纪律（用户点名批评「开始编译了仿真发现 bug」）**：新模块/改模块必须先 iverilog 跑通 testbench 再启动编译。行为仿真配套坑：① TD RAM 原语（ram_8eb6fbd14703）iverilog 没有，写同名行为模型（同步双口 1 拍读延迟）且 mem 数组上电初始化=0，防 X 经比较链污染全部检查点；② testbench 的 tlast 每行尾都拉高、tuser 帧首拍与行数据隔离（帧首后一拍空拍）、line 计数在 tuser 拍清零；③ 检查点失败加层次监控（$display 打 DUT 内部信号）定位，别靠猜；④ RAM 写日志（$display 每次 we）能一眼看出「地址 0 没写」这类时序坑。

**execute_code 改文件的坑（Python 重放改动时必踩）**：hermes_tools.read_file 的 content 带「行号|」前缀，直接 join 写回会污染整个文件；改文件用 Python 原生 open。frozen 备份是 CRLF，重放字符串替换前先统一 LF、写回再转回 CRLF——old_string 带 \n 而文件是 \r\n 时 replace 静默失败（不报错但不匹配），先 replace('\r\n','\n') 再替换。

### 18.22 串行版下板后续：副线检测无效果的根因 + 阈值调试配置 + 帧差法标准做法（2026-10-25 晚）

**副线（BRAM 兜底版）「背景检测没有、其他正常」的直接根因**：motion_detect 例化后输出信号没人接——算法 MUX（isp_top 的 `case(algo_mode)`）没有模式 4 分支、algo_mode_sel 的 ALGO_NUM 只有 4 档（0~3 循环）。新算法模块两条配套改动缺一不可：① MUX 加新档位分支（数据 + valid/tlast/tuser 三路同步选）；② 模式选择器的档数 localparam 同步扩（ALGO_NUM 4→5）。**规则：新增算法模块后，先 grep 它的输出信号名在 MUX/例化处有没有消费者——例化成功 ≠ 上屏，输出悬空是「功能无声无息地没有」的头号原因。**

**阈值按键 + 数码管显示是运动检测的标准调试配置**（搜索到的多篇实战文章共识，用户也明确要求「sw12 显示阈值」）：KEY2/KEY3 长按调阈值（0~120、步进 10、初始 40），数码管在检测模式优先显示当前阈值；阈值经验区间 = 背景差分像素差值集中在 30~80，40 起步安全。实现模板：motion_threshold_set（复制 threshold_set 改范围/步进/初始值 + I_enable = algo_mode==N）；阈值从模块参数改输入端口（motion_detect 的 THRESHOLD localparam → I_threshold[7:0]）；顶层 bin2bcd 一份 BCD + 数码管 case 之外用 `if(algo_mode==N) seg_data = ...` 覆盖（优先级高于 S_mode 诊断显示）。

**帧差法/背景减除的标准读法（搜索三篇实战文章的结论，主线「没读对」诊断的对照基准）**：
- 掩码法：两帧灰度存同一地址高低位（SDRAM DQM 掩码交替写高/低 8bit），读出一次同时拿两帧、「相同行场同步时序、数据天然对齐」；帧标志在场同步翻转决定写高/低位。
- 非掩码法：通道读使能 = 写使能但落后一帧——读写地址同一流天然同步。
- 主流架构：背景模型存**片内 RAM**（bg_model 模块 rd_addr/wr_addr/bg_data），采集像素流水线边到边和背景值比较（单周期减法+比较器），DDR 只做帧缓存不参与背景读；背景选择性更新（前景不更新、背景点 bg += (pix-bg)>>4，学习率 1/16）。
- **对照结论：DDR 版 bg_read 从 DDR 读「当前帧+背景帧」做差是非主流自创架构——标准做法是采集流分流一份给检测流水线 + 背景存片内。** 主线「读的是背景、错位竖线=采集右边界」这类内容可辨识的错位，按 §18.15 判读法直接指向数据来源路由。

**主线二分诊断的变体（bg 读的帧级禁用）**：串行版现象与并行门控版一模一样时，做「bg 读仅模式 3 使能」二分——`I_frame_start = vsync_pulse_ddr && (algo_mode跨域打2拍 == 3'd3)`，模式 0/1/2 时 bg 完全不读。判据：画面恢复 = bg 参与仍是病根；现象不变 = 病根在写侧或 vo 自身，下一刀切写批 grant。**规则：功能触发脉冲（frame_start/blank_trig）加模式门控做二分，比删模块/删例化省两轮编译；算法模式跨域只打 2 拍（慢信号电平），不参与时序敏感路径。**

**编译时长估算（用户纠正过拍脑袋）**：TD 增量（源码未动）一轮 ≈ 25 分钟出 bit（SYN 约 1 分钟走工程配置 + PHY 约 23 分钟）；全量重编（大改）≈ SYN 25~30 分钟 + PHY 15~25 分钟 ≈ 45~55 分钟。报预估按这个口径，别往一小时以上估。杀 WSL 侧启动的编译：`ps aux` 里的 PID 是 /init 包装进程，`taskkill.exe /F /PID <该PID>` 会报「找不到进程」——用 WSL 的 `kill -9 <pid>` 杀。/mnt/e 下 `ls -l` 加 `| awk '{print $6,$7,$8}'` 看 bit 文件时间戳确认产出时间。

### 18.23 串行仲裁下 bg 读挤垮显示读 → 双阈值水位门控 + 帧开始无条件清场 + 读地址递增（2026-10-26 闭环）

**现象（bg 读启动成功后）**：SW4 拨下直接花屏、手伸进无涂白，但 bg 读计数正常读满、fg_init 拉高——读链全通、显示链被挤垮。

**花屏根因（时间片账 + 触发水位账）**：bg 读满 172800 拍需跨进显示期，串行仲裁下 bg 批（240 拍）连续读把 vo 份额压到 ~50% < 显示消耗需求；且 vo 读触发水位只有 30（过度读修复时代的值）——vo 触发后要等当前 bg 批剩余 + WR 批最多 ~480 拍（消耗 270 字）> 30 字缓冲 → 显示 FIFO 打穿 → 花屏。

**修复（双阈值水位门控，自适应无窗口信号）**：
1. vo 触发水位 30→200（扛住 bg 批 240 拍的等待消耗；批后 200+240=440<512 不溢出、>200 不重触发）。
2. bg_read 读使能加 `I_vo_fifo_level >= 300` 门控（video_out 引出等效水位 = FIFO水位+在途）：vo 缓冲充足 bg 才占时间片、vo 快空 bg 自动让路（busy 也加同门控让仲裁跳过 BG 不浪费时间片）。**消隐期 vo 不消耗水位自然高 → bg 自动全速，无需窗口信号。**
- **规则：多路共享 DDR 时旁路通道（bg 读）的读使能挂「主显示 FIFO 水位高阈值」门控，与主通道「低水位触发读」形成双阈值错峰——上阈值和下阈值之间留缓冲带（如 200/300），带宽自适应分配且显示永不饿。**

**白线错位根因 2（读不满帧跨帧错乱）**：bg 读按「读满才翻半帧/清 active」设计，若某帧读不满（窗口被挤/仲裁饿），`I_frame_start && !S_rd_active` 的 mod 复位条件不成立 → S_ret_mod 跨帧累积 → cur/bg 分界错乱 → 标记数据错位（实机「静态白线飘、手成密集线不成块」）。
**修复（帧开始无条件清场 300 拍）**：I_frame_start 拍无条件复位 mod/计数/攒字器（写地址回半帧起点，读不满帧 half_sel 未翻 → 重写同半帧）；FIFO 复位 300 拍清残余 + 解包复位清 pending + 弹链复位（节流相位/行弹计数/行尾空洞）；清场期停读（rd_en/busy 门控）。读满帧清场无害（FIFO 已弹空，仅延迟启动 3µs）；读不满帧清场丢弃半行残余、新帧从头读。
- **规则：分帧读状态机的一切「帧开始复位」都写成无条件（不挂 active 条件）——读不满帧时 active 不降，条件复位会让跨帧残留把下一帧数据路由全毁；「读满才翻转」的半帧/指针状态配上无条件清场才是自洽的。**
- **读地址必须逐命令递增（第三个真 bug，实机白线的直接根因）**：行块读状态机的地址 = base + 行偏移 + 行内字偏移，行内字偏移每个命令拍 +8（128bit 字 = 8 个 32bit 字地址）——只按「每行 + 一行量」推进而忘了行内递增，一行 240 个命令全部发同一地址、读回 240 个相同字，比较数据全错。旧仿真只验「读计数」不验「数据-地址对应」是这类 bug 能活过多轮的原因；验证法（地址编码数据 + 层次引用比对解包输出）见 ddr-debug-bisection.md。
