# 多路并行开发与融合工作流（三路 fork 目录 → 主线合并）

## 并行开发期

- 主线 `cp -r` 出 N 份独立目录（含 .git，同源 fork），各路在自己的 git 仓库里开发、编译、下板、commit
- **每个目录放一份任务书**：任务目标 + 背景情报（关键模块/禁改清单/编译纪律）+ 验收标准 + 「融合时注意」清单。任务书是跨会话情报的载体（会话之间不直接通信，靠文档交接）
- **资源红线要提前定并写成「三路增量叠加」**：各路报告自己的增量时别只看「增量 < 本地余量」——融合时所有增量叠加，N 路各自都小于余量不代表总和小于余量。主会话给每路发预算（slice +N 上限），要求每路从 phy_1/*.phy.area 报实测增量
- 每路交付文档结构（用户偏好）：简介（数据流图）→ 模块思路+真实源码片段 → 资源演进表 → 用法演示步骤 → 验证记录（tb+编译三连+下板）→ 文件清单 → 📷占位 → 已知边界

## 已验证版本必须 commit（硬规则）

每个「下板验证通过」的代码状态必须立即 git commit——否则继续开发会把已验证版本覆盖掉，融合时只能从文档参数手工重建（本次实祸：均匀三段下板验证后未 commit 就改整帧读，git 历史里只有验证前的非对称版和未验证的整帧读版，只能拿文档参数重建）。融合只融「已下板验证」的 commit，未验证的新方案留给下一轮。

## 融合步骤（主线会话执行）

1. 收集各路交付文档 + git log，确定每路的**验证过版本**对应 commit
2. 文件按冲突度分级处理：
   - 单路独改文件（如 video_in.v）：直接 cp
   - 两路同改文件（如 bg_read.v：A 路加数据源 mux、B 路改读状态机参数）：以一路为基底 + 另一路的 diff 手动 patch（区域不重叠可叠，重叠要逐块合并）
   - 三路同改文件（wrapper 例化）：以主线为基底，把每路的例化接线差异逐条 patch 进
   - **挂接类模块适配新分段几何时重算所有几何常量**：两半帧版的统计模块（bbox_stat 按「A 半 0~5887 / B 半过滤 addr<5888」去重）挂到三段版数据源后，去重阈值必须按新分段重推（段 N 干净起点 = 段首字 + 重叠行数×每行字数：B1 段 7680+8×32=7936、B2 段 15360+8×32=15616），分组锁存组数、合并树、半帧选择位宽同步升级——只改端口不动几何 = 交界区重复统计的隐错
3. 批量文本替换一律 **assert 检查**：`old in s` 断言替换串存在（替换串必须含目标行的完整谓词，纯片段会匹配错行），返回后再 grep 新值验证——替换静默失败是本工作流头号事故源。**向 always 块中间插入时锚点选「完整语句」而非「块内行」**：用块内两行做锚点、插入文本自带 `end/end` 闭合，会与原块闭合重复出双份 end（iverilog syntax error 暴露）；正确做法是锚点选块后一条完整 assign/例化语句、插入文本不含任何闭合符
4. 工程文件登记新源：.al 用 `../src/...` 路径、.prj 用 `../../../src/...` 路径（prj 文件在 Runs/syn_1/ 更深一层）；CompileOrder 取全局最大值 +1（允许空洞，TD 只当排序键）；插入位置看锚点文件条目
5. 语法验证：`iverilog -g2001 -o /tmp/chk -y src -y src/key -y src/isp -y src/isp/data96_128 -y src/ip_source -I src wrapper.v`（-y 目录要含 ip_source 和 hdl_source_ip，否则 Unknown module type 误报）。**已知豁免**：工程原有 `key_pulse (` 隐式例化（无实例名）iverilog 报错但 TD 接受——只认新增的 error
6. commit 前 git status 核对文件数（端口契约/新源登记应有的文件数）——预期不符 = 漏改警报
7. **tb 对照验证移植正确性**：分支交付的 tb（含其 run.sh）把 ROOT 指到主线后跑移植版，与分支原版输出对比——差异即移植错误。tb 的判据盲区要警惕：分支 tb 只检查它关心的量（如每行写满字数），主线特有链路的就绪标志（fg_init 等）不在判据内，tb 全绿 ≠ 实机功能全对。对照发现差异后先改判据覆盖，再修根因（实例：主线 morph 链 DRAM 化后 645 拍 + row_fill 320 拍，DRAIN 排空窗口仍按旧链 644 拍 → 末行写拍 0；bugfix 原版同 tb 末行写满 → 窗口扩到 700 拍修复）
7. verilator obj_dir 等生成物加 .gitignore 排除，已提交的用 git rm --cached 移除

## 融合后参数联动复核（基底分支链结构变更的连带）

分支方案自带的参数全部基于「该分支的链结构/读量几何」——融合进主线后，主线同名链若已改过（DRAM 化、加级、加功能），所有联动参数必须按主线现状重推：①帧尾排空窗口（DRAIN 拍数）≥ 链总有效拍延迟（morph 645 + row_fill 320 直通后，旧 644 排不净末行）②「首轮写满/就绪」地址判据按新读量 cap 重算（整帧读 700 行写满 22400 字，分段读时代判据 22920 永远到不了 → 就绪恒 0 → 叠加使能全灭，实机「检测不出来」；判据应落在新 cap 行数 ×每行字数减余量处）③「读不满整帧作废」语义下，任何依赖写满的就绪链都要有降级路径或按实际写入量放宽。改完跑分支 tb 对照 + 全工程语法 + 编译三连，缺一不可。

⚠️ 注意 SKILL.md 旧结论「全帧读超消隐预算→画面错位」指 720 行全读；终版整帧读 = cap 336000（700 行×480 拍=3.36ms，底部 20 行放弃，显示期完全禁读），消隐期 4.26ms 内读得满，已下板验证细线根治——代价是底部 20 行不涂白（外接框/质心仍完整），勿再按旧结论劝阻整帧读。

## 融合资源账（基线选最优化分支，别用增量叠加）

融合总账 = 「最优化分支的实测总量」+ 其他分支相对同一基线的功能增量。各路报的增量都是相对「旧主线基线」算的——若某一路顺手优化了共享模块（如 morph 移位链 DRAM 化净省 ~460 slice），它的整机总量会低于旧基线，融合后共享模块只有一份（取优化版），旧基线增量全部高估。实例：框版 20,432/96.3% + bug 400 + 去噪 80 的叠加账算出 99.5% 险爆表，实际以优化过的分支为基底融合后 87.85%，余量 2,500+。判据：共享模块（morph/行缓冲）哪路版本最省资源就定哪路为融合基底，其它路只加「自己独有的功能模块」增量。

## 融合时补全跨模式的触发条件

分支实现的模式触发条件往往只覆盖它自己关心的模式（如背景采集触发只写了模式 2/3）——融合时把所有吃同一数据链的模式补齐：任何消费「背景差分/前景标记」的模式（涂白/框/区域填充）都需要背景已采，mode_need_bg 应为「非原样模式全部」，逐模式验证触发清单再编译。

## 背景采集统一设计（交互类功能的定稿模式）

拨码/按键切换会碰动摄像头（手碰硬件）→ 采集背景必须在「画面稳定后」：单一 bg_capture_req 脉冲入口，触发源四合一（上电延迟 2 秒首采 / 曝光值连续 N 帧不变自动重采 / 模式切换边沿延迟 1 秒重采 / 长按按键强制重采），背景 VALID 门控所有检测显示（未采前涂白/框/填充全不显示）。模式选择拨码与采集动作完全剥离。
