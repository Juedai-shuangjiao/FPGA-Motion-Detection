# 背景采集交互：模式触发 + 防抖 + 冷却（已定型）

## 交互设计（用户拍板，勿退回 SW4 上升沿触发）

- SW3/SW4 组合四模式（拨下=1）：00=模式1显示、01=模式2涂白、10=模式3外接框、11=模式4区域填充
- 触发：组合变化后新组合=01或10 → 自动采背景；上电时若已在 01/10 → 上电即采
- 防抖 6 帧（约 100ms，60fps 下）：触发后延迟再采，拨码/手碰导致的摄像头晃动有时间稳住（实锤验证：延迟采集后水管不再涂白；初版 60 帧=1s 用户实测过长——机械抖动稳定不需要 1s，已缩短）
- 冷却 180 帧（3 秒）：一次采集完成后冷却内不重复触发（用户要求「采集不要太频繁」）
- 实现位置：motion_detect.v bg_state 状态机（2'd0 响应 mode_changed && mode_need_bg && !cooling → 2'd1 每帧 tuser 计数防抖 → 2'd2 采一帧后回 2'd0 并启动冷却）
- 模式判定用打 2 拍后的 sw3_d2/sw4_d2 组合；mode_prev 复位 00，上电即模式 2/3 时首拍即触发
- 演示流程：上电模式1 → SW4 拨下进模式2（自动采背景出涂白）→ SW3 拨下进模式4 → SW4 拨上进模式3（自动采背景出框）
- 用户口头报参数时先与代码对照确认再改：用户自己也会记错（曾要求「迟一帧」采集，实为「等一秒」——代码 BG_DELAY_FRAMES=60 帧=1 秒本来就是对的）。参数类需求落地前 grep 常量确认当前值，把「代码里现在是多少」回读给用户核对，别直接照用户说法改
- **帧计数实现的延迟/冷却，「帧数↔秒数」换算必须查传感器寄存器表验证实际帧率，不能信代码注释的 fps 假设也不能凭猜**：注释「60 帧=1 秒(60fps)」曾被怀疑实际是 30fps——最终查 wrapper 例化的寄存器表 uics500reg_720p60（VTS=1000）实锤就是 60fps。用户报「延迟感觉比设计值长」时按此顺序排查：①冷却吞触发——冷却窗口（180 帧=3s）内重复拨码的触发被 `!cooling` 挡掉，体感延迟 = 剩余冷却 + 防抖可达 3~4s（设计上要么新触发打断冷却、要么把冷却帧数缩到与防抖同级）；②体感叠加——防抖 + 采集 1 帧 + DDR 写 + 重读 + 显示管道 ≈ 设计值 +0.3s，属正常；③时序违例丢帧首脉冲——违例路径打在 I_tuser 采样上会丢帧计数变慢（查违例报告路径是否含 motion_detect）。最便宜的帧率验证 = 下板看 OSD 帧号 1 秒走多少（60fps 走 60）

## 关键坑：bg_captured 必须「采过锁存」而非 SW4 电平

- 原实现 bg_captured = sw4_d2（SW4 电平），未拨下时输出全黑——模式 3 下 SW4 拨上会误关前景输出
- 改法：采集帧（bg_capture=1）时锁存 1 保持，复位才清；输出门控 out_4p = bg_captured ? dilate : 0

## 关键坑：bg_read 启动必须门控到「背景已采」

- 现象：下板发现「等一秒采集没实现」——拨 SW 瞬间画面立即出现满屏乱涂白，像防抖没生效
- 机制：防抖只推迟「背景采集」，但 bg_read 检测链在 SW 拨下瞬间就开跑，用上电随机背景差出满屏前景；1 秒后新背景采完涂白才变正确，但视觉上「立即有反应」已构成误判
- 改法：S_bg_frame_start_ddr 增加 && bg_captured 锁存（motion_detect 引出 O_bg_captured → 顶层 DDR 域打 2 拍）——背景采完前检测链不跑，采完后涂白/框以正确背景首次出现
- 通则：任何「延迟触发」类修复都要查消费方是否还挂在旧的立即触发上——延迟了生产者、消费者仍用旧值立即跑 = 修复被架空
- **第二轮坑：bg_captured 永久锁存让延迟「只在首次可见」**——首采过后锁存恒 1，再切模式时 bg_read 立即用旧背景开跑，涂白瞬间出现（内容旧、1 秒后才刷新），用户复测「等一秒采集没实现」。改法：bg_captured 语义改为「本次采集完成」——触发拍清 0（门控关）、采集帧置 1（门控开），每次模式切换都有「干净防抖期 → 涂白出现」的时序
- **第三轮坑：bg_captured 不能在采集帧第一拍置 1，必须在采集帧结束（bg_capture 下降沿）才置 1**——背景帧写满 DDR 需要一整帧（16.7ms），采集帧第一拍就开门会让 bg_read 在下一 vsync 读到「写了一半的背景」，差分满屏乱标记（实机现象：拨码后画面立即出现未采集数据的检测结果）。改法：`if(S_cap_done_prev && !bg_capture) bg_captured <= 1'b1`（下降沿锁存）。通则：任何「采集/写入完成」标志必须在数据完整落盘后置位，「写使能第一拍」永远不等于「写完」
- **涂白叠加使能同样要门控**（hdmi_mixer 的 I_sw4 接 `SW4电平 && bg_captured`）：门控关闭期间 ERAM 旧标记残影会在等待期显示错位涂白——检测链和显示链两个消费方都要挂同一个门控，只挂一个仍能看到旧状态

## 下板误判诊断：三条独立误检源（采集晃动 / 曝光漂移 / 高增益噪声）——延迟采集只治第一条

- 现象：静止高对比度物体（水管/袋子边缘）被误判前景，且重采背景后立刻复现；均匀背景（白墙）零涂白
- 机制：采背景瞬间手碰板子/摄像头 → 背景帧与后续稳定帧整体错位 → 高对比度边缘差超阈值必中；均匀区域错位后差≈0 无感
- 区分实验：白墙（均匀背景）采完零涂白 + 真实场景采完立刻涂白 = 错位实锤；若采完干净、几秒后才慢慢出现 = 自动曝光/反光漂移（另一条排查线：SW3 拨上=自动曝光，代码 I_auto_en(~I_sw[2])）
- **根治法分层（两条源独立存在，防抖只治第一条）**：
  1. 采集瞬间晃动 → 触发延迟防抖 6 帧≈100ms（本文件设计）
  2. 防抖后仍误检（实锤：等 1 秒再采水管还是被框）→ 自动曝光漂移——采背景时曝光值 X、实时帧已调到 Y≠X，整体偏移让高对比度边缘先超阈值。修法：检测模式期间冻结自动曝光（ae_set 的 I_auto_en 改 `~SW3 && ~SW4`，仅模式 1 跑自动 AE，模式 2 从拨下 SW4 那刻起冻结——防抖 1 秒内曝光先稳再采背景）+ 背景差阈值档位 25→40（I_thr_sel 2'b01；手肤色差 ~70 仍检测、水管边缘微小漂移不再中）
  3. 高增益噪声放大（实锤：增益 110 分界——110 以上天花板/水管仍涂白，往下只剩零星噪点）：增益 >110 时传感器噪声被放大，静态高亮区（天花板/水管反光）的噪声波动超差分阈值必中。与前两条独立、延迟采集治不了。**已落地修法（2026-11-02 集成，仿真先行验证 32 项断言全过）**：
     a) **差分阈值随亮度自适应**（自然光噪声对症，零资源）——根因是「亮度高→像素波动绝对值大」，ae_set 的全图平均亮度 avg 查表映射阈值档位：avg<80→25、80~139→40、140~199→60、≥200→80。实现 = wrapper 内联 3 个比较器查表（8bit 慢变信号跨 DDR 域打 2 拍），bg_read 的 I_thr_sel 直接接自适应档（SW 手动档位废弃）。
     b) **块密度过滤**（外接框孤立远点/白点团，bbox_stat 内，约 +400 slice）——画面分 16×9=144 块（80 行×80 像素=2 字宽），帧内计数各块前景点，帧末（fs_pulse）锁存「块点数 ≥5 才有效」的有效图，下一帧统计（min/max/sum/cnt）只收有效块内点。块号派生自拍B锁存字地址（行=字/32 比较链 9 档、列=字%32>>1），块计数在拍C（S_st_en_c 拍、S_wr_addr_b 稳定后），门控在拍D累加器。首帧有效图全 1 默认不滤。
     仿真原型与未集成项（sim/ 目录）：thr_adaptive、blk_density、sobel_adapt_thr（梯度均值×1.5 自适应阈值，CNT_LOG2 参数化计数）、erode_1bit 双级联（吃 2-3px 噪点团、目标须 ≥5×5 才存活）、bg_avg_ema（(4a+b)/5 单帧内存背景平均，差分×205>>10 定点，噪声衰减 5 倍）——morph 双腐蚀/Sobel 自适应/EMA 平均集成待办。
     c) 候选未实现：AE 增益上限锁 110（省事但牺牲低光）；5×5 非对称腐蚀。**阶梯式验证纪律：先零成本阈值抬档（40→60，盯弱对比度手部漏检）→ 不够上非对称 5×5 → 再不够上增益自适应——一步一动、每步下板验证，别一次叠多层改动**
- 诊断树：白墙实验零涂白 = 链路线路正常 → 采完立刻涂白 = 采集瞬间晃动（延迟防抖，已实锤有效）→ 延迟后仍涂白 = 曝光漂移（冻结 AE + 提阈值）→ 仅增益 >110 时涂白 = 高增益噪声（阈值自适应 / 锁增益上限）

## 检测模式下前级算法处理必须冻结（差分对处理图的连锁坑）

背景差分要求「当前帧」与「背景帧」经过完全一致的前级处理——背景采集存的是原样画面，检测期实时帧若被算法切换（KEY 切灰度/二值/Sobel）处理，差分变成「原样背景 vs 处理图」：Sobel 模式全图差分超阈值 = 面积全白，切回原样时数据链路相位失配 = 画面整体左移错位。修法：算法模式切换（algo_mode_sel 的 en）锁到「仅原样模式（SW3SW4=00）」——检测模式（01/10/11）KEY1-3 不切算法，画面保持原样+叠加。通则：差分/比较类检测链的前级参数与处理（曝光/增益/算法模式）在检测期间全部冻结，凡新增一条前级开关都要问「背景采的时候它是什么状态」。

## 模式切换必须帧同步化（KEY 帧中切换 = 持续错位的根治）

按键脉冲随机落在帧中间，任何「改变数据链延迟/结构」的模式信号（算法模式、显示模式三态、fill_en 类）若帧中直接生效，会造成：切换拍撕裂 → 数据链状态机错位 → 画面整体平移且**持续**（再按键或复位才恢复，不是闪一下自愈）。「有概率错位」= 按键时刻与帧相位的随机关系。根治定式：**模式信号在帧开始拍采样应用**——isp_top 的算法模式 `if(bpc_tuser) algo_applied <= algo_mode_2d`（数据/valid/tuser mux 全用 applied 版）；bg_read 的显示模式/fill_en `if(S_fs_d512) 锁存 I_disp_mode/I_fill_en`。效果：切换延迟 1 帧生效（16.7ms 无感）、切换帧干净完整。注意应用点选「数据链源头模块」而不是显示端：切算法在 isp_top（处理链）应用、切显示模式在 bg_read（显示源 mux）应用——两处各自帧同步，一处漏改该处仍会帧中撕裂。

## 显示期多路读互斥（顶部错位实锤）

bg_read 的读门控显示期必须全禁（`S_vo_room = I_disp_win ? 1'b0 : 1'b1`），不能「水位高就放行」：水位满（480）时 bg 批拖尾跨进显示期抢 grant 挡 vo 预读 → 显示 FIFO 二三行断供 → 顶部 1~3 行错位（bg 开才错、静止也错、错位数波动）。完整诊断链与残余丢弃加固见 references/tag-fifo-discard-lesson.md。
