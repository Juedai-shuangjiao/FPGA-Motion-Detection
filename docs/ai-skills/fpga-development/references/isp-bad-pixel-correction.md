# ISP 坏点校正与视频链路图像质量 debug

## 白点/亮点簇诊断链（按顺序排除；⚠️ 官方对照是最强判据，别跳过）

画面固定位置的白点/亮点簇，依次验证：

1. **固定增益（手动模式）看白点还在不在** → 还在 = 排除「自动增益跨模拟档位」和「曝光/增益切换异常帧」
2. **官方例程同场景对照下板（决定性判据，必须先做）** → 同板同传感器同光源，官方无白点 = **坐实白点是本工程改动引入**（传感器坏列/光源频闪这类物理缺陷跟工程无关，官方必然也有）。官方也有 = 才往物理缺陷方向查
3. **对比官方与本工程显示链路的差异** → 白点 = 数据流错误，重点查「被删掉/改掉的官方保护机制」（如写忙避让，见下条）、读数据路由、帧边界越界
4. **降 DDR 速率/改时序参数** → 无效 = 排除时序违例

⚠️ **「位置固定 + 随增益变亮 + 手机摄像头低增益仍可见」三者看似坐实传感器坏列，但都能被「数据流错误」解释**：错误数据的绝对值随增益放大（白点变亮）、错误位置由访问节奏固定、对比度低时肉眼看不见而手机增益放大可见。**这三条不是「物理缺陷」的充分判据——官方同场景对照才是**。实战教训：曾据此终判「传感器坏列」并写 BPC 模块，后用户下载官方 bit 用手电筒照（极端光源）无白点 → 推翻，真根因是写忙避让被删（下条）。光源频闪的特征是整幅/大面积明暗起伏，不是固定 6 组×4~5 列的断续条带。

## 白点/最右列竖线的真根因：删掉了官方的「写忙避让」（仲裁 grant 门控替代不了）

- **根因**：官方 video_out 读触发带 `!I_video_in_wr_busy`（写忙时读触发停），自研工程改「仲裁 grant 门控」时把它删了。**grant 门控只管「读命令能不能发出」，管不住「读数据在 DDR 管道延迟约 40 拍才返回」**——写命令插进来后，写数据上总线（DQ 复用）把读数据返回暂停几拍 → video_out FIFO 写入出现间隙 → HDMI 读穿读旧值 → 固定位置白点 + 最右列竖线。
- **铁律**：DDR 显示帧缓存两路（采集写 + 显示读）就用官方的「写忙避让」（读触发加 !wr_busy），不要用仲裁 grant 门控替代——grant 是「发出」层门控，管不了「读数据返回」层被写打断。仲裁/标签 FIFO 是为「第三路背景读」才需要的，两路时它们不仅多余、还会掩盖避让缺失。
- ⚠️ **避让是双向的**：官方 video_in 写触发同样带 `!I_video_out_rd_busy`（写避让读）。只恢复「读避让写」半边时白点消失但最右列残留异常（写命令在读数据 40 拍返回期间插入、打断读数据流），补上「写避让读」才是官方完整互斥方案。读写忙不同时、交替节奏无死锁，可直接照官方恢复
- 特征对照：白点随增益变亮 = 错误数据绝对值随增益放大；挥手/切算法同一区域 = 访问节奏固定；跳帧数 3/7 都无效 = 跟异常帧无关。恢复 `!I_video_in_wr_busy` 一行后白点即消失（官方验证过的稳定方案）。

## BPC（坏点校正）实现要点

- 位置：demosaic/AWB 之后、算法 MUX 之前——所有算法（原样/灰度/二值/边缘）共享校正，亮度统计也随之变准
- 结构：R/G/B 三通道**独立** 3×3 极值检测，每通道走 2 行 `line_buffer_demosaic`（共 6 块 BRAM）；不要用「灰度检测+RGB 打拍透传」的简化版（见踩坑 3）
- 判据：中心比 8 邻域都大且差 > 阈值 → 亮点坏点，替换邻域最大值；都比小且差 > 阈值 → 暗点，替换邻域最小值；比较用 9 位防溢出（255+阈值超 8 位）
- 只在极值时替换 → 正常像素和边缘不受影响。这与整帧中值滤波有本质区别（中值滤波糊边缘、方向性错误，之前试过失败）
- 4 像素并行，跨组边界：左邻居缓存上一组 g3、右邻居复制 g3（同 canny_top 的 NMS 写法）
- 首行/首末列不校正（lb 首行是垃圾、跨组邻居不可靠）；行 1 起即可校正（行 0 的邻域含 lb 垃圾，但误判时替换值≈邻域最大/最小≈原值，影响小）

## BPC 仿真踩坑（全是行/组对齐错位，下板前必仿）

1. **lb 输出延迟账**：`line_buffer_demosaic` 输出 = 输入打 2 拍（内部 data_d0 1 拍 + BRAM 读 1 拍）的「上一行」；cur（当前行）打 2 拍后与 lb 输出**同组**对齐（时间晚一拍但组号相同，3×3 内容正确）
2. **中心行 up 不要再额外打 1 拍**：多打 1 拍错 1 组（4 像素），坏点进入自己的 8 邻域 → 邻域最大值=坏点自己 → 极值检测失效。仿真表现：坏点残留 1 个、位置偏移一整行
3. **原 RGB 不能只打 N 拍跟随数据流**：lb 输出是「上一行」，RGB 打拍是「当前行」，行错位 1 行使坏点在原样路径透传（输出仍 255）。正解：RGB 三通道也走 line buffer，与检测数据同构，输出取 lb 的「上一行」
4. **定位对齐错位的最快手段**：testbench 层次引用（`tb.u_dut.signal`）打印坏点时刻的 cur/up/up2/有效性信号，比翻输出波形快
5. **行为级模型（initial + for 循环）里模拟时序打拍要用变量交换**：`s3=s2; s2=s1; s1=新值` 再判 `s2 && ~s3` 得上升沿——写成组合赋值（`s2=s1; s3=s2`）会让上升沿永不触发、帧计数不复位，仿真静默失效（读数全 0 / 只读一帧后停）。行为级循环不消耗仿真时间（$finish called at 0 正常）

## iverilog 仿真安路 IP：行为模型桩

安路硬核（PH1P_LOGIC_ERAM 等）iverilog 不认识，写行为模型桩替代：

- **NOREG 模式 = 组合读**（`assign dob = mem[addrb]`，读延迟 = addrb 的 1 拍寄存，在 line_buffer 内部）
- **OUTREG 模式 = 组合读 + 1 拍输出寄存器**（读延迟 2 拍）
- 先查 wrapper 里的 REGMODE_B 参数再写桩；组合 vs 寄存差 1 拍会让仿真里所有对齐判断整体错位
- 桩按 `ram_*.v` 的端口原样定义，参数照抄；仿真例化时同时编译 wrapper + ram + 桩

## BPC 时序收敛（新增组合逻辑重的 ISP 模块后必查）

- **BPC 的 12 路 8 邻域比较树 + BRAM 输出 → gray_convert → 亮度统计累加器，是整条组合长链**：实测把像素域 SWNS 压到 100ps 贴边（温度漂移就偶发违例）。**新增组合逻辑重的模块后必看 final_timing.rpt 的 SWNS 和最差路径**——编译报告里的 End Point/Start Point 直接点名根因，比上网搜「某现象」更有效（网上几乎搜不到「最后一列噪点」这种特例）。
- **修复：模块输出寄存 1 拍打断长路径**（BRAM→组合→新寄存器 一段、新寄存器→下游 一段）。加打拍后总延迟 +1，下游统一延迟对齐的账要重算（本例 bpc 2→3 拍后 isp_top 统一 8 拍不变，因为 canny 输入同为 bpc 后 3 拍，3+8=11 仍对齐）
- **视觉特征区分两个子问题**：偶发的彩色噪点（漂一下红黄点）= 时序偶发违例；固定密集白点 = 数据流固定错误（越界读空隙垃圾）。两者同屏出现要分开定位，别当一个问题治
- **「位置固定 + 每帧亮的点不同（手机录像逐帧看）+ 颜色随场景变（白/灰/彩色）」= 固定路径的偶发时序违例**：违例时值错（亮）、不违例时值对，帧间随机违例 → 闪烁；错值与场景数据相关 → 颜色随场景变。配合 final_timing.rpt 最差路径点名（如 demosaic line buffer 的 addrb 行尾回绕 319→0 的比较+MUX、canny 方向量化函数）直接锁定要打拍的组合逻辑
- **「画面整体左移 N 列、最右列空出来变白」的诊断与排除**：OSD（LOGO/文字）是 hdmi_mixer 里固定坐标画的、不随视频数据走——把 LOGO 与场景垂直参照物（天花板水管）对齐，再下载官方例程看同一对齐关系；官方与本工程一致 = 无左移，最右列是「数据本身的错」。另：丢第一列 = 数据整体左移、最后一列显示下一行第一列（错位的正常数据）；丢最后一列 = 最后一列垃圾（固定高值）——白点固定高值指向丢最后一列
- **patch 替换大代码块后编译报 undeclared**：用 patch 把「含声明 + 赋值」的整块替换成新块时，新块仍引用旧块里的信号（如 tlast_d2）→ 声明被一起删了。替换后 grep 一遍新块引用的 reg 是否都有声明

## 相邻主题 pitfall（同属视频处理链路质量类）

- **多算法切换 MUX 毛刺**：格雷码只解决「跨时钟域打 2 拍采中间态」，不解决「格雷转二进制后选择位变多位（如 001→010 变 2 位）导致的组合 case MUX 毛刺」。修法：所有算法数据/valid/选择信号统一打拍对齐（对齐最慢路径，如边缘检测 8 拍），MUX 用寄存后的选择信号。只变 1 位的切换（000→001）不闪是佐证
- **读满即停的消隐期错位（v1 失败 → v2 锚点，实战验证）**：帧读计数在 vsync 复位、HDMI 读从有效显示开始，两者差一个消隐期——DDR 读先跑满一帧硬停，FIFO 空了 HDMI 侧还在读旧值 → 画面大面积黑灰横线。**v2 正解：帧开始锚点改用 `I_video_rd_en` 上升沿（HDMI 有效显示窗口信号，打 3 拍同步到 DDR 域）**——与 HDMI 读侧天然同一时刻，比「vsync 后延时消隐期」更精确（直接复用现成窗口信号，不用算消隐期拍数）。消隐期读触发自动停（帧内读计数保持上一帧的 172800，不满足 <172800）。
- **读满即停必须截断「进行中」的读突发**：只门控读触发不够——读突发 240 个是连续进行的，读满 172800 恰好落在突发中间时，剩余 239 个照读（iverilog 行为级仿真实测多读 239 个越界）。修法两处：读使能也加 `frame_rd_cnt < 172800` 门控 + 读突发状态机在 `frame_rd_cnt >= 172800` 时强制清 `S_ddr_rd_valid`。仿真验证：一帧读总数精确 172800、地址终点 1382400 不越界；帧尾仅剩约 47 像素的轻微重复（跨时钟域同步 3 拍延迟所致，是「重复」不是「垃圾」，与「越界读空隙垃圾（密集白点+红黄点）」有本质区别）
- **越界读空隙的视觉特征**：读地址越过本帧缓冲区读「块与块之间的空隙」，空隙是未初始化 DDR = 随机值 = 密集白点 + 漂红黄点（彩色噪点说明是随机数据不是单一错误值）
- **跳帧与卡顿**：跳帧=画面冻结 N 帧。手动模式不跳帧（用户主动按键，冻结=卡顿不可接受，短暂 1 帧花屏可接受）；自动模式才跳帧盖曝光/增益切换异常帧（后台偶发，冻结无感）。**跳帧数 3 帧就够**——7 帧是「白点被误判为异常帧盖不住」时期的过度修正，根因（写忙避让）修复后 7 帧只带来挥手卡顿；自动模式跳 3 帧 = 50ms 冻结，现场演示偶发一次可接受
