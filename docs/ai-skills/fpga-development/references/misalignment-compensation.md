# 实机错位补偿实验收敛（FPGACompetition 背景减除链路）

## 模式切换致错位 = 帧同步化修复（与训练/写侧错位并列的第四机制，2026-11-02 实锤）

按键/拨码切换模式后画面「整体平移、颜色正常、持续错位（要再按键或复位才恢复）」、且只在特定切换路径出现（如「检测模式按 KEY4 → 回原样模式再切算法」）——根因是数据链模式信号（算法模式/显示模式/fill_en）在按键拍立即生效，切换拍随机落在帧中间：不同算法路径延迟不同（Sobel 8 拍 vs 直通 0 拍），数据链延迟跳变使下游对齐永久破坏，每帧都错（故持续）。「有概率错位」= 按键时刻与帧相位的随机关系，不是竞争类偶发。判别指纹：只出现在切换动作之后、再切换/复位可恢复、画面内容完整只是平移——与训练失败（同 bit 重下即恢复）、写侧错位（重下仍错）区分。

根治 = 模式应用锁到帧开始拍：`if(帧开始脉冲) mode_applied <= mode_sync;`，数据 mux/valid mux 全用 mode_applied。各模块用自己的帧边界信号（isp_top 用 bpc_tuser、bg_read 用 S_fs_d512、hdmi_mixer 用 vsync），不要跨模块传脉冲。代价 = 切换最多晚 1 帧生效（16.7ms，无感）。附带规则：算法切换使能仅限原样模式（检测模式锁算法=原样，否则背景差分对 Sobel/灰度图做差 → 全图全白）。

## 触发场景
实机显示恒定错位 N 像素（涂白标记与运动目标错开），tb 仿真全绿、RTL 账逐拍对过仍错。错位恒定 = 结构错位，不是数据错误。

## 现象定性四问（动手前先分清错位在哪条链，再选方法）

错位 bug 有两类完全不同的机制群（检测链相位差 vs 显示链字流错位），修法南辕北辙。开工先问用户四个现象问题，映射到错位层：

1. **错位的是涂白标记还是整个视频画面？** 涂白错位、视频正常 → 检测/标记链（bg_read/ERAM/mixer 相位，本文件主战场）；整个视频画面错位、与涂白无关 → 显示链（video_in 写侧/video_out 读侧）。
2. **会自己恢复吗？** 一直错到复位 → 状态机级错位（内容错位写进了帧缓冲、持续存在）；几帧自恢复 → 单帧事件。
3. **整体平移还是撕裂/花屏？** 完整画面整体平移 → 内容相对帧头错位（固定或随机 N 字）；撕裂（上下半不同）→ 帧内读指针切换/半帧拼接；花屏乱码 → 内容全错（块基址/命令路由级）。
4. **平移量恒定还是随机？** 恒定 → 固定结构偏移（常数补偿可根治）；每次复位/调节量不同 → 相位决定（复位/调节时刻与流相位的关系随机）。

**颜色错位是字流错位指纹**：128bit 字 = 5.33 个 24bit 像素（128/24 非整数）——字粒度错位必然把像素边界错开 → RGB 通道错乱；画面平移伴随颜色错位 = DDR 内容相对帧头错位 N 个 128bit 字，错位像素量 = 5.33×N；平移但颜色正常 = 错位是 24bit 像素整数倍（如块基址错 3 字节倍）。「平移距离随机 + 颜色错位 + 不采背景也错」三连 = 写侧 FIFO 丢字/残字混入帧头（video_in），不是 bg_read 链。

## 核心方法论（按顺序执行）

1. 单变量实验 + 多点线性拟合
一次只改一个补偿量（读侧地址环 / 写侧地址偏移 / 组相位），下板记录位移，用实测点拟合线性关系（d = a + b×读补偿 + c×写补偿），解 d=0。实测方向优先：理论推导写 +1 = 内容左移，实机实测 = 右移 40px——方向矛盾时信实测，不按理论外推。

2. 方向与量级必须二次确认
用户目测反馈会左右不分、量级不可靠（「是左错位，分不清一半还是和之前一样」）。拿到现象反馈先追问确认方向+量级，再设计下一轮实验。二分实验方向反了 = 白烧一轮编译（45~55 分钟）。追问时给用户「体感量尺」而非直接问像素数：错位 ≈ 1 根手指宽（1.5cm）= 40px、2 根手指 = 80px；24 寸 1080p 全屏放 720p 画面时 1.6cm ≈ 40px（拿尺子量厘米报数即可换算）；或让用户回忆与历史版本（普通错位版/翻倍版）的视觉对比。半指宽 = 60px = 1.5 字 = 半字分量露头。

2.5 实验量级必须 ≥ 用户可辨阈值
20px（半字）级改动在实机上目测不出（涂白块比 20px 大得多，边缘差 20px 无视觉差异），「没变化」会被误判为「没生效」——tb 已 PASS 的机制也照样被怀疑。设计下板实验时补偿量用 40px（1 字）级：加倍到 40px 后判据变锐利（对齐 / 方向翻转 / 完全不动三选一，都肉眼可辨）。小于可辨阈值的下板实验没有判据价值，不要单独烧一轮编译。

3. 每轮实验预设三分判据
下板前写清三种互斥结果各对应什么路径：对齐 → 收敛；方向翻转/量级翻倍 → 补偿系数定值；不变 → 补偿未生效或不在该链路。

4. 字粒度死胡同 → 半字（组粒度）补偿
读/写地址都是 40px 字粒度。线性解落在半字（20px）时，字粒度补偿无解（挪 1 字位移变 2 字、中点=半字不可达）。半字 = 5 个 96bit 组：
- 前 5 组填 0（S_fg_word <= {4'b0, S_fg_word[39:4]}）= 内容右移 20px
- 丢前 5 组（不攒）= 内容左移 20px
填 0 拍必须仍计入 S_word_cnt（保持 10 组/字结构），否则首字变半字宽、内容全乱。

5. 数码管诊断替代串口
本竞赛板板载 USB-UART 被阉割（FT2232 单通道 WinUSB = JTAG 专用、无串口通道），串口诊断不可行。数码管诊断模式：SW4 拨下低 4 位显示 B 半首字写拍地址——bg_read 锁存 first_valid && first_half 拍的首字写拍地址（O_dbg_first_addr），顶层 DDR 域锁存后跨域打 2 拍进 24M 域，接 seg_data。判读：A 半首字 = 0、B 半 = 5632（0x1600）；写地址补偿 ±1 后相应 ±1。数码管两值闪（差 1 或 0x88）= 首字锁存跨域竞争，主值正确即可，次要问题先放。

6. 改动风险分级：地址「值」低风险，写数据/写拍「时机」高风险
读/写地址值补偿（±1 环）从未引发画面级异常。但改 bg_read 内部写拍时机（如填 N 组 0 让攒满拍提前触发 → 首字写拍提前）属于高风险：bg_read 与视频读共享 DDR 仲裁，DDR 域时序分布一变就可能挤压视频链路（异步 FIFO/DDR 仲裁）的动态时序余量——静态时序报告全绿（SWNS 正）也照样实机画面错位（logo 边界竖线 = 视频帧边界错乱）。判据：画面级异常（视频内容错位/竖线/花屏）≠ 涂白级异常（标记位置），出现画面级异常立即按第 7 条回退，不要继续分析补偿效果。

7. 画面级异常先重下板排除 DDR 训练偶发失败，仍异常再单文件回退
每轮编译前 commit。实机出现画面级异常（而非涂白级），先让用户重新下载同一 bit（或冷启动重上电）：PH1P35 合封 DDR 每次配置后训练校准会偶发失败——形态随机不固定：logo 边界竖线、水平镜像（左边内容跑到右边）、颜色错乱、画面错位但颜色正确等都会出现；复位键同样触发（复位也重新训练，连续复位形态每次都不同 = 随机失败，不是越来越坏）。同一 bit 首次下板错位、重下即恢复 = 训练失败，不是代码问题。**与「训练成功但写侧错位」的判别（第二机制，勿混）**：按键复位时摄像头（外部芯片）没有复位、持续满速出流，而 DDR 重训期（init_calib_complete 前）I_ddr_user_ready=0 → 写批/帧尾排空批全写不出去（排空批 240 拍自结束、计数不依赖 ready）→ 采集 FIFO 溢出丢字 + 残字留存 → 训练完成后帧头地址写进旧残字流 → 错位。错位量 = 训练完成时刻相对摄像头帧的相位 → 每次复位随机 → 与训练失败「同 bit 重下即恢复」不同，此机制持续错位、多次复位碰对齐相位才恢复。判据：重下同 bit 恢复 = 训练失败；重下同 bit 仍错、再复位几次才恢复 = 写侧错位（训练本身成功）。修复方向 = init_calib 上升沿置 pending → 下一次帧尾排空批完成拍清采集 FIFO 指针（残字丢弃、下一帧从空 FIFO 开始、帧头对齐）；时序账：排空批启动 ≈ 帧尾判定后 ~2700 拍（DDR 域）+ 240 + 清窗 ~32 拍 < 帧消隐 4040 拍（实机 49500 拍）→ 清窗不碰新帧头。**训练失败态（画面错位）下的涂白错位数据不作诊断**：DDR 读链相位已乱，涂白跟着错是必然，只看画面完全正常态的涂白数据（移动摄像头等物理动作后「突然画面错位、复位重下都不行」时，Flash 初始程序画面正常即可确认硬件全好，也是训练失败）。重下后仍异常才 git checkout <上一 commit> -- <改动文件> 回退 + 启动回退版编译。判断「哪轮引入的」靠问用户最近一次画面正常的版本号/时间点，diff 两版源码 = 唯一实质改动（往往只有一行参数）。历史教训：「填 10 组 → 画面错位」的因果判断当时只下过一次板即回退，极可能就是训练失败冤枉了填 10 组——旧禁区结论存疑，别当硬规则传给后续实验。

## 消隐地址是唯一有效旋钮（行中发地址实机无效）
网格扫描后期的大发现：读侧「行中发地址」（col 37 拍发 word 还是 word+1）实机完全无差异——(无环 r=-1, w=0) 与 (0,0) 实测同为左 40px。装字内容实际由消隐期锁存的地址决定（行中地址被实机时序吞掉，1 拍延迟账与实机不符）。所以「读补偿」实际只通过消隐拍发地址生效，后续扫描直接以消隐地址为单变量。

消隐地址 → 位移实测映射（d 单位 = 字，负 = 左移）：
- base-1（带环，行首发上一行末字）→ +1（右 40px）
- base（原始）→ -1（左 40px）
- base+1 → -2（左 80px）
- base+2 → -1.5（左 60px，首次半字级，映射非线性：步进变化 -2/-1/+0.5 乱跳）
- base+3 → -1.5（与 base+2 无差异 = 消隐旋钮饱和，有效档位就 base-1~base+2 共 4 档，扫到头了）
映射非线性说明消隐地址与装字时刻有相位关系。**装 0 结构新映射**：消隐装字分支改装 40'd0 后，消隐地址映射整体右移 +1 字（base+3：左 60px → 左 20px）——消隐装字分支对主体有 +1 字贡献（它每拍装消隐地址内容并在行首重显示，掐掉 = 内容右移 1 字）。装 0 结构下 base+3 = 左 20px；实测 base+2 = 右 20px（方向翻转，0 点在 base+2 与 base+3 之间 = 半字位置）→ 消隐地址整数档到头，转连续旋钮：发地址拍位置（col 17/27/37 级，10 拍 = 半字档，0~39 拍连续）与消隐半字混合（消隐期最后 N 拍发目标地址、其余发基准）。**装字拍单变量实测对主体错位无效**（col 19 与 col 39 主体同左 20px），且 col 19 引入右边界 40px 盲区（每行末字内容只剩 20 拍显示窗口 = 行末丢 1 字）——装字拍改动只有副作用无收益，主体补偿只认消隐地址一个旋钮。机制推断：ERAM 读口行为 = 消隐期采样起始地址 + 行内自动递增读（行中发的地址与装字拍全部被吞，仅消隐起始地址决定整行内容偏移）——可验证：查工程 PH1P_LOGIC_ERAM 例化参数是否有自增/突发读选项。**验证走门级网表（明文）**：加密的只是 RTL 源码（IEEE 1735 AES，企业级密钥体系不可硬破解），综合/实现后的产物不加密，从产物反查 IP 真实行为不需要任何破解。最快入口 = `phy_1/FPGACompetition_inst.bid`（明文 XML：`<All_Bram_Infos>` 下每个 INST 块含 name/logic_name/logic_depth/width_a/width_b/working_mode/address_step/mode_type/address_offset——用 python re 提取即可，编译跑到 PHY 阶段时该文件已存在可读，读它不干扰编译）。别考古 TD 的网表导出命令：工程里生成的 export_net.tcl 用 read_db 读 gate.db，而 read_db 不是 td_commands_prompt 的有效命令（报 invalid command name），此路不通。实测结论（本项目）：fg_mark ERAM 45 实例 mode_type=161、address_step=1，与工程里所有 RAM（视频 FIFO、demosaic、awb 延迟线等）完全一致 → IP 就是标准 RAM 行为，无「自增读」等特殊模式参数；「消隐采样+行内自增」式怪异行为不体现在 IP 配置里，根源指向自研 RTL 的地址锁存时序而非黑盒——归因要查到位（黑盒只能绕，自研代码可修可查，这是两种不同的处理路线）。教训：翻网表必须带着明确假设专项 grep（如 ERAM 原语例化参数/模式选项），零散翻找（如当时找 retiming 开关）浪费时间且无结论——实验证据指向哪个假设，就立刻去网表验证哪个假设；「理想行为模型 + 全绿仿真」是加密 IP 项目最大的陷阱，真时序行为只能实机标定 + 网表参数实锤。**第二个明文产物 = 时序报告查时钟域**：`phy_1/FPGACompetition_place.timing`（PHY 阶段可读，明文 4MB）每条路径 End Point 行标注寄存器时钟（`u_fg_mark_eram/.../syn_323.dia[6] ... clock u_ddr2/ref_clk`）——确认模块真实时钟域的最快入口（本项目实锤：fg_mark ERAM 写口 dia 在 DDR ref_clk 域、读口在 HDMI 像素域 = 跨域真双口，设计即如此）。「改常数无效、只有慢变化有效」类现象的机制候选第一查时钟域错配。**行为级仿真扫参数 = 证伪快车道**：加密 IP 跑不了真仿真时，把自研链（地址/装字/移位）在 tb 复刻 + IP 换参数化行为模型（如读延迟 D 拍），扫参数对比实机现象——本例扫 D=0~3 全部零错位 → 「延迟账错 1 拍」假设当场证伪、读侧装字链洗清，省 N 轮 50 分钟编译。实现坑：iverilog 命令行 -P 覆盖 parameter 实测不生效（跑出默认值）→ sed 生成参数变体最稳；采集寄存器必须复位初始化否则全 x；D=0 显式分支避免数组负下标。mem[i]=i 的「内容=地址」观测法直接读出错位方向与字粒度。**装字拍与发地址拍必须同步提前**：只把装字拍提前 20 拍（col 39→col 19）而发地址拍仍 col 37，装字发生在发地址之前 → 装进移位链的是上一字周期的旧地址内容 → 每行内容双重影（实测：主体涂白对齐、同时出现第二段残影涂白，间距 ≈ 屏宽；掐掉 x=0 de 拍的消隐装字分支也消不掉——残影不在消隐分支）。干净半字补偿 = 发地址拍与装字拍**同步**提前（保持相对相位：装字拍 = 发地址拍 + 2 拍，如 col 37→col 17 发 配合 col 39→col 19 装）。只提前装字（发地址不动）→ 装旧地址内容 → 双重影；只提前发地址（装字不动）→ 主体位移变化与装字侧不同（实测 col17 发把 60px 拉到 20px 但没到对齐），同步提前才既补偿又无双影。两旋钮组合 = 消隐粗调（4 档）× 移位链细调（发/装同步提前 N 拍，N=0~39 连续半字档），字粒度补偿无解不再是死胡同。装字拍「提前 40 拍」= 周期整字 = 无差异，有效范围 0~39 拍。

## 补偿贡献相互依赖 → 网格扫描（线性拟合破产后的打法）
多点线性拟合（d = a + b×r + c×w）在新数据点出现时可能破产：实测写 +1 贡献在读 -1 背景 = +1、在读 0 背景 = +2——贡献依赖另一侧补偿值，单线性公式外推必错。此时改枚举网格：读/写补偿各 {-1,0,+1} 共 9 组合，逐点实测填表，在表里找 d=0 或最接近的组合。每个新点都是硬数据，即使预测失败也立刻排除一行/一列。错位恒为 40px 整数倍时「感觉不是整数」= 整字分量逼近 0 后底下藏的半字分量露出（半字分量从头就在，被整字错位掩盖）。主体对齐后残余 20px 级错位用移位链同步提前补（发/装同步平移 20 拍），比消隐地址档位更细。

**决策探针打法**：一轮实验的现象要把下一版从 N 个候选里唯一确定下来（对齐→直接收官；饱和→整数档用尽、转半字混合/拍位置连续旋钮；反向→映射方向定了、下一步唯一），一次编译买「唯一解」的决策信息，而不是每个候选都试烧一遍。明确告诉用户当前是「探针-决策」阶段还是「赌候选」阶段，用户会据此决定等待策略。**用户工作方式（明确要求）**：探针反馈到之前不提前准备下一版代码——「看完现象再编译收官版」「最终版代码不用提前准备，收到反馈再动手」。反馈到了再改代码启动编译。**回滚是最后手段**：排查阶段提出回滚方案会被用户喊停（明确说过「先别着急回滚」）——先穷尽驱动/工具链/环境层的排查（这些层的修复不烧编译、分钟级见效），回滚建议等用户自己提或排查确实穷尽再给；用户主动提「双线并行」时（如 GUI 编译打通 + cp -r 副本盲修补偿同时推进），照做不要劝串行。**用户离开且明确授权预编译时例外**：用户睡觉/离开前说「预测参数提前编译好、回来直接下载」→ 预编译多档候选版本（错位量 N 的 ±档 + 补偿双向，如 DATA_DLY/ADDR_DLY 各 5/10/15），用户回来读数直接烧对应版本，把「等编译 50 分钟」从用户路径里删掉；串行编译多版（同机 >2 工程并行在 8GB 内存有风险），每版参数用 sed 改参数后单独编译，各版 bit 目录/文件名标注参数值别弄混。**用户熬夜问「等编译完看完现象再睡 vs 现在睡、醒了再验证」时的标准建议 = 后者**：现在启动编译 → 去睡 → agent 盯编译完成并做静态三连验证（完成标志/时序 SWNS-HWNS/bit 时间戳）记录在案 → 用户醒来直接下板看现象（编译早完成，现象一样，多睡几小时）；小概率残差也不慌（比赛截止前再修一版 60 分钟绰绰有余）。下板验证必须用户亲手做（硬件动作），agent 只能把「醒来即验」的路径铺好，别建议用户硬熬等编译。**多版本矩阵编译（用户睡觉期间的极限打法）**：①复制工程 N 份（`cp -r` 大目录易超时被杀 → 半成品目录用 `rsync -a --delete 源/ 目标/` 补全；先 `df -h` 查空间，每工程含中间产物 ~2GB）；②每版只改一个补偿参数，覆盖「量 × 方向」网格（如 {无补偿, 读地址±1, col±5, OUT_PHASE 5/10}——方向与已知实机错位相反的版本优先级最低可弃）；③串行编译脚本（bash for 循环：rm db → SYN → PHY → 记录 bit 时间戳 + SWNS/HWNS 到日志），后台跑 + notify；④完成后汇总「版本矩阵表」写入开工手册（每版标注 bit 时间戳 + SWNS/HWNS），用户回来纯烧板验证 15 分钟闭环。**bit 真伪校验**：复制工程自带旧 bit 残留——某版是否真编译过 = bit 时间戳刷新 + SWNS 绿 + 各版 bit 大小一致（完整产物），烧板前按此三项核对，防烧到复制残留的旧 bit。**ls 目录里的 bit 时间戳是 cp 副本的陈旧时间戳、不可信**——判真编译唯一可靠来源是串行脚本日志里脚本自己 echo 的「<版本> bit: <时间>」行（脚本在 PHY 完成后才打），目录 ls 只作参考。杀队列坑：`pkill -f '<脚本名>'` 会匹配到执行 pkill 的 shell 自身命令行（命令文本含该字符串）把自己一起杀死（exit -15）——pkill 前先 `ps aux | grep '[b]uild'` 查真实 PID。坑：杀 Windows 编译进程（taskkill）会被审批拦截——用户睡着无人批时不杀，kill bash 脚本让孤儿编译跑完自灭、新队列与孤儿并行（8GB 内存双编译历史可行）；长时间等待用 date 记录实际时间戳再算进度，凭感觉易误判「卡死」而错杀快完成的编译。**多候选并行编译**：两个候选都要下板时，整工程 cp -r 复制一份（175MB SSD 秒级），A/B 目录各自编译各自参数并行——CPU 争抢使单个变慢（60~70 分钟）但总耗时 < 串行（100 分钟），8GB 内存可承受。复制前若用 rm 清旧备份目录，先向用户说明删除目标（哪怕只是备份目录）——用户对删除命令反应强烈。

## 写侧内容相位 = 固有错位新锁定（读侧洗清后的根因方向）
读侧装字链被仿真证伪无辜后，错位温床移到写侧 bg_read：帧差内容 = cur 流（video_in 直通）与 bg 流（DDR 读出）双 valid 门控比较，内容相位 = bg 流首拍与 cur 流首拍的对齐度（差 1 拍 = 4px、差 10 拍 = 1 字），而写地址按 valid 拍数递增、不校屏幕坐标 → 内容错位原样写进正确地址 → 读出即涂白错位。bg 流首拍对齐无显式机制保证 = 「固有 -1」最可能老家；本链路历史上已抓过两个写侧错位（TD 插拍致左移 1 字、地址递增拍致右移 1 字）= 写侧是错位多发地。验证入口：bg_read 前段 cur/bg FIFO 解包对齐 + video_in 写 DDR 地址约定 + O_dbg_first_addr 数码管诊断。

**下一层温床：写批边界与行首同步（基址/行切约定已排除后的剩余角度）**。video_in 写 DDR 是「FIFO 攒够 240 个 128bit 字写一批、写 240 个停」，批边界与摄像头行首**无同步机制**（只有帧开始 S_frame_start 强制停批，行间无对齐）——行首像素可能落在 128bit 批中间某处，DDR 帧内容相对真实画面整体平移 k 像素；显示路径（video_out）与背景读路径（bg_read）用同一套行切约定所以画面正常，但 bg_read 按「字 0 = 列 0」语义解读背景帧 → 涂白错位 k。k 恒定（每行同样结构，多轮实验错位量一致佐证）且 k 很可能 ≈ 8~10px（一个 128bit 字内部/附近的量级）。修法候选 = bg_read 读背景帧时扣行首偏移（不动 video_in：写批逻辑改动风险大且显示路径依赖现约定）。**传感器数据源头已排除**：SC500CS 手册阵列 2600×1952、Active Array 2592×1944（四边各 4px Active Border），但 720p60 例程 crop 列起始 0x0200=512（有效区内部）、宽 1280——行数据 100% 有效像素、无行首前瞻/边距数据；RAW10 打包（1280×10bit=100×128bit）与 ISP 输出（240×128bit/行）均整除无 padding。「开头有其他数据导致错位」的假设在传感器与打包层证伪，错位只在 FPGA 侧处理链（排查依据见 sc500-resolution-config.md 像素阵列条）。**外部同款案例（搜「相位差调试」的收获）**：Lattice VFB IP 调试笔记（chinaaet）症状原文就是「数据的位置不对，但数据的值正确、画面稳定」根因 = DDR 读写地址映射层错位；iopenv DDR 视频抖动总结 = 读写地址偏移必须一致；netv2-fpga GitHub issue #20 全文（slack2450 报 + bunnie 答）是「overlay 与视频流相位错位」最完整的公开案例：症状=overlay 左缘绕到右缘（整幅平移的极端形态）、每次上电漂移量不同；bunnie 机制=DRAM 一次取一组像素、sync 落在取数前后决定对齐、依赖「初始帧位置 vs DRAM 时序」的运气；官方修法=hdmi_core_out0_dma_line_align_write() 对齐微调寄存器（= 常数补偿）。**漂移 vs 固定的判别价值**：对方错位随 boot 漂移 = 板上 ARM/软件参与初始化、启动时序随机；本工程错位固定 = 纯 FPGA 确定性启动、相位锁死——固定错位一次常数补偿根治，漂移错位才需要对齐寄存器或治本。治本写法参照 MiSTer Arcade-Deco16 的 ddr3_framebuffer：写侧 FIFO 指针在每个 HSync 与写指针重对齐（「returns to empty every line and never drifts」）= 行首重置攒批计数器、行首像素永远落在批起点（本工程 video_in 攒 240 字一批纯计数对齐正是缺这一步）。**批分组嫌疑的自我检验**：若纯粹是「攒批边界与行边界不同步」且读侧按行首对齐，推演结果应是逐行扭斜（每行错位不同），而实测整帧均匀平移——出现均匀平移时批分组只是候选之一，错位同样可能藏在 DDR 帧基址/读侧帧首同步层；常数补偿不依赖此区分（平移量固定则补常数必中），治本改动等波形坐实层归属再动。「值对位置不对」类 bug 优先查 DDR 地址映射/批对齐层，不是数据链路。

**实测闭环（探针版现象收束）**：①消隐装数据 + 删行中装字版 → 只剩行首 40px 涂白（代码逻辑必然：装 1 字只够显示 40 拍）——铁证两点：消隐装字只影响行首 40px（「消隐地址移动主体」并非走消隐装字路径，桥在跨域时序里）；M[base] 装着「手在别处」的内容 = 写侧内容-地址错位实锤。②发地址拍 col 17 与 col 27 实测无差异 = 发地址拍位置旋钮死（行中发地址彻底无效，拍位置 0~39 全废）。读侧旋钮图景收束：行中地址、装字拍、发地址拍位置全部无效，唯消隐地址（整字 4 档 + 半字卡死）——读侧已无旋钮可动，错位只能从写侧修。③DDR 地址约定查证（排除基址错位）：video_in 写当前帧 ping-pong 基址 0/7000000/14000000/21000000，bg_read 读背景帧 IMAGE_BASE_ADDR_4=22382400、S_cur_base 用同一 ping-pong 表，帧首=基址、行内 128bit 递增、行切 +240 字两边严丝合缝。④双 valid 门控丢拍机制：bg 首拍比 cur 晚 N 拍 → 前 N 拍 cur valid 而 bg 不 valid → `(cur_valid && bg_valid)` 门控丢弃 → 比较从 cur[N] vs bg[0] 起 → 内容错位 N×4px。行弹门控（cur 攒满 240 且 bg 非空才弹两 FIFO）是首拍对齐的唯一锚，bg 只要求 ≥1 拍——bg 弹出的首拍是否真是帧首像素无显式保证。⑤剩余闭环路径：bg_read 写侧链路（128bit 打包 → FIFO → 行弹门控 → 128→96 解包 → 比较 → 攒字）行为级仿真锁定「差几拍」，DDR 用行为模型替代；修复 = 显式相位锚（帧同步对齐打拍），仿真验证 + 一次下板确认，不再实机标定。**静态推演有极限**：跨域/深流水时序行为（「消隐装字按理只影响行首却移动主体」这类桥）静态推不出，桥在 IP/跨域时序里——推演卡住时明确向用户声明「静态到此为止，等实测/仿真闭环」而不是继续空转（用户明确担心推理死循环，声明确认边界比硬推更受信任）。**说了要用仿真就必须真搭 tb 跑**：用户会盯着「仿真 vs 静态读代码」的落差，口头承诺仿真却一直读代码分析会被直接指出——要仿真就最小 tb 动手跑（哪怕只能证伪一个假设），静态读代码只能作为仿真前的假设准备，不能当仿真的替代品交付。【10-31 最终收敛】RTL 全链仿真（bg_read 打包解包行弹大 tb）同样锁定不了错位拍数：TD 插拍类实机差异在 RTL 仿真里不存在（仿真按你的账跑永远自洽）；RTL 账 8 处（装字链延迟扫 D=0~3、发地址拍 col 17/27/37、装字拍 col 19/39、打包解包真实模块、DDR 地址约定、帧间清场链、morph 帧同步、位序约定）全部自洽 + 实机恒定错 1 字 → 锁定拍数唯一路 = 实机诊断：①数码管 O_dbg_first_addr（写首字应=half_base，错则写地址链实机时序问题）；②特征帧法（屏幕固定位置放亮块→量涂白位置偏移→直接读出错位拍数）；③锁死后一次修复下板。别再烧全链 RTL 仿真。

## CDC 相位差仿真复现 = 用实机现象间距标定错位拍数（零编译成本的错位量测定）

错位拍数不用实机猜：最小 tb 注入 cur/bg 双流「首拍相位差 N」参数（帧内容 = 竖线图案，mem 内容=位置），扫 N——N=0 时静止竖线帧差为零（零标记）；N>0 时竖线**两侧各出涂白**、间距 ≈ N 拍。机制：错位 N 拍后比较 cur[x] vs bg[x-N]，静止局部特征（竖线/水管）两侧边缘都差非零 → 双涂白；大片均匀区域（白墙/天花板）错位后仍是同值对同值 → 不涂白——「水管涂白而天花板不涂白」正是平移错位的指纹，不是新 bug。**反过来用**：实机「两段残影」的间距 = 错位拍数（本项目实测间距 ≈ 40px = 10 拍 = 1 字）→ 实机 CDC 相位差直接标定，三现象（主体错位 1 字 + 水管涂白 + 两段残影）统一为「bg 流晚 10 拍」一个数。修复聚焦 = 确认 10 拍丢在哪条链（行弹 bg 首字残留 / 标签分路 / 帧同步锚），±N 拍对齐一次修复。

## 补偿迭代不收敛的结构性原因（为什么「凑」凑不出 0）

补偿扫档十几轮不收敛不是运气差，是三个结构性错配：①**粒度不匹配**——实机错位量是拍级（TD 插 1 拍/BRAM 化多 1 拍），补偿旋钮是字级（40px 步进），0 点卡在整字档之间的半字位永远扫不中（半字尝试又引入副作用）；②**旋钮路径被实机行为扭曲**——唯一有效旋钮（消隐地址）的实机路径经过装字竞争，映射非线性、会饱和；③**错位量随编译漂移**——TD 实机化位置每次综合/布局可不同，常数补偿追不上会动的系统。结论：根因修复（显式打拍防护 / 显式相位锚 / 相位敏感链改 TD IP 原语固定延迟）才是收敛正路，继续加补偿旋钮是下坡路。

## 用户痛苦于「原理简单为何这么难」时的解释框架
错位排查长跑中用户会周期性进入痛苦态（「原理就是两张图相减涂白，为什么这么难」）。此时给「工程现实三件套」而非继续堆参数细节：①屏幕上的是图片、FPGA 里是溪流——每拍 4px 流水线，两张图相减 = 两条经过不同延迟链（DDR 仲裁/morph 窗口/跨域同步/ERAM 延迟）的溪流必须同相位对齐，任何一环差 1 拍就是 4px；②TD 工具链是自由的——会吃你的显式打拍（retiming）也会自己插拍，RTL 账与实机网表是两本账；③错位量常卡在非整数拍（如 2.5 拍 = 10px），粗旋钮（字级）修不动、细旋钮测出来无效——这类错位必须上 ChipWatcher 实测，不是能力问题。收尾给路径感：已有实测工具 + 赛后时间表，比空泛安慰有效。

用户问「为什么 N 天还没修好」（痛苦复盘请求）时给四因素框架，每个因素可验证可归因，别让用户把失败归到自己身上：①第一天把 bug 类型判错——逻辑 bug（读代码可修）vs 物理相位问题（必须上板测量），用修逻辑的方法修相位必然空转；②验证回路太长——改一行代码要 50 分钟编译 + 下板肉眼判读，一天只能试 3-4 个猜测；③测量工具晚到——ChipWatcher 是唯一能直接量内部相位的手段，工具链坏的日子全部是盲改；④补偿量级错位——真实错位 8-40px 而盲改全是 1-2px 级，「无效」是力度不够不是方向错。收尾：排错把 100 种可能压缩到 1-2 种，信息论上排除错误答案就是进展，只是这种进展看不见摸不着。

## 同类 bug 复发先 git 考古找先例（修复模式可复制）

「错位 40px」在本工程出现多次、每次机制同族不同处（写地址递增拍 / 标签 FIFO reg 数组被 TD 综合成 BRAM 致读延迟多 1 拍 / bg 流相位）——git log --follow 文件历史里的 commit message 就是先例库：每个先例记录「机制 → 修复模式」，复发时按先例的修复模式（reg 数组/移位链改 TD IP 原语固定延迟）处理，比重新发明快。**验证 reg 数组是否被 TD BRAM 化用 .area 报告**：综合产物 FPGACompetition_gate.area 每实例有 eram/dram lut 列——行缓冲类大 reg 数组 eram=0、dram=0 = 纯寄存器未被 BRAM 化（排除）；eram/dram 非零 = 实机化改变延迟账（嫌疑）。先例铁证：rd_tag_fifo reg 数组被综合成 BRAM → rd_tag 与读返回数据相位差 1 拍 → cur/bg 分路错 → 错位 40px——「TD 实机化改变延迟」不是猜想是已发生过的机制，排查相位类 bug 时优先查这条。

## git 考古「重写引入点」+ 混合版回滚（一次根因级修复）
错位旋钮大战几十个 commit 不收敛时，回头看 git 历史找「错位首次出现」与「最后一次无错位版本」：commit message 里「手部边缘完美/主体对齐」= 好版本，「根因修复」类 message = 重写点。**识别模式**：好版本 → 一次以「根因」名义的结构重写 → 之后几十个纯旋钮 commit（全是补偿尝试、无新功能）= 重写本身就是错位引入点，其根因依据大概率后来被证伪。修复 = 混合版：只回滚那次重写的文件（`git show <好commit>:<路径> > 工程/路径`，先 `git diff <好commit>..HEAD --stat -- <文件>` 确认端口未变、内部改动才安全），保留后续的真修复与诊断代码（写侧三修复、数码管 v4），编译下板。回滚前权衡：好版本之后若有真功能（细线修复/排空批等）不能连带回滚，只回滚重写文件。bg_read 写侧文件尤其不要完整回滚到「完美版」：写侧自身也演进过多轮真修复（写命令拍精确避让、FC88 全链根因、首字诊断锁存），完整回滚 = 拿回已修复的老 bug，只回滚「以根因名义重写」的那个文件（本会话 hdmi_mixer 回滚 e95a12a 实测右错 10px ≈ 混合版 8~9px → 重写非引入点、但 bg_read 保持新版不动的决策正确）。回滚版下板前用最小 tb 预验证好版本的读侧 RTL 语义（模型：ERAM 读延迟 1 拍 + word/col 打 1 拍 + col_d1 对齐 → mark 与写入位置零错位，tb_comb_read 实测首拍对齐），给用户「烧板预期 = 对齐」而非盲烧。**回滚版下板判读（实测闭环教训）**：『最后一次完美版』单文件回滚后错位量与原版同量级（e95a12a 回滚 vs 混合版：右错 10px vs 8~9px）= 那次重写不是错位引入点，『完美』依赖当时全套环境（bg_read/wrapper/时钟域也演进过）——单文件回滚只证明「该文件内结构差异不产生错位差异」，不证明「回滚即修复」，『重写=引入点』推断必须以回滚版实测为准更新。**结构不敏感判据**：多个不同结构版本（历史好版/混合版/重写版）实测错位量几乎相同 = 错位对该层结构不敏感 = 根因在共同组件层（写侧 bg_read 写坐标、跨时钟域相位、wrapper 显示链），别再在结构差异里继续找——本会话最终结论 = bg_read 在 ddr_clk 域写、hdmi_mixer 在 pixel_clk 域读的跨域固有相位差 ~2.5 拍（RTL 仿真天然复现不了，理想模型账永远为零）。**旋钮无效即层排除**：单个参数旋钮改动实测纹丝不动 = 错位不在该旋钮所在的层——无效本身就是定位信息；本会话 col 位选择（字内展开层）+ mark 打拍（显示链层）+ 三种读侧结构全部无效 → 读侧整层排除，错位只可能在写侧内容相位或跨域桥。改动无效不是「再加大参数」的信号，是「换层」的信号。**预读+移位结构（8d8e7da 系）实机自带「每字一列周期性竖条空洞」**：该结构在字边界丢 1 列像素，不可作为交付版本——结构选择上组合直读（96679a3 系）干净无竖条。

## 实机诊断 v4：首字写拍数据数码管（判读表三分支定位错位链）

O_dbg_first_addr 只验写地址链；再加首字写拍数据锁存（bg_read 在首字写拍锁存 S_fg_wr_data_int，数码管第 1 管显低 4 位、第 2 管显地址低 4 位）能把错位链三分支定位：①第 2 管 ≠ 0 → 写地址链实机错（地址时序先例复发）；②第 2 管 = 0、第 1 管 = F（手伸最左 4px）→ 写链全对、错位在读侧；③第 2 管 = 0、第 1 管 = 0（手伸最左）→ 写侧内容错位，错位量 = 手伸入出现 F 时的深度 ÷ 4px。诊断版编译期间把判读表写好交用户，醒来烧板一读数即定位。**判读实验法要点**：①手没伸时数据管 = 0 是正常值（无信息），必须先让用户把手贴最左再读——读数时问清手的位置；②「F 和 0 闪」= 手在 bit0~3 边界帧间微抖，正常，出现过清晰的 F 即判定为 F；③seg7 是 8 位数码管（data[3:0]=第 8 管最右），让用户「从左到右念全 8 位」避免管序歧义——念不全时最关键的两管（地址、数据）没念到会误判方向。

## 显示相位收敛 + OUT_PHASE 旋钮（写链 F 实锤后的落点，待下板确认）
诊断 v4 读数闭环：手伸最左时数据管出现清晰 F（首字数据=F）+ 地址管=0 → 写链（数据/地址/使能）实机全对，错位唯一剩余位置 = hdmi_mixer 输出 shift[0] 到屏幕像素之间的「显示相位」（实机晚 5 拍 = 20px 半字）。新补偿旋钮 = 输出取 shift[N]（OUT_PHASE 参数，`S_fg_mark_comb = ... && S_fg_shift[OUT_PHASE]`）：shift[N] 显示 N 拍前装入的位 = 内容右移 N×4px。tb 语义验证：mark 首次出现拍随 OUT_PHASE 平移 = 参数生效（verilator +PARAM 运行时覆盖无效，sed 重编译参数扫描）；方向最终以实机烧板为准。注意：「消隐地址唯一有效旋钮」是写链怀疑未排除时的中间结论，F 实锤后错位落点移到显示相位，补偿网格按 {混合回滚, 读地址±1, col±5, OUT_PHASE 5/10} 布置。

## 显示链打拍审计 = 显示相位错位的最终落点（根因级定位方法）

错位温床收敛到 hdmi_mixer 后，直接逐条数「各叠加层到 O_hdmi_data 的打拍数」：视频背景链 I_video_rd_data → 1d → 2d → 3d → O_hdmi_data 打 3 拍，前景标记 mark_comb 组合直采零打拍——两层打拍数不匹配 = 相位差 × 4px = 错位（本项目：mark 早 2 拍 = 右错 8px，与实机数像素列吻合）。修复 = 给短链补齐打拍（mark 打 N 拍对齐 video_3d）。**实测判据（10-31 下板）**：mark 显式打 2 拍烧板后错位量纹丝不动（右错 10px 不变）= TD 综合 retiming 在时序余量大时吃掉显式打拍（寄存器重定时），与「TD 插拍」是同一魔鬼两面——显式打拍在 TD 手里不可靠；同期 col 数据选择（改取字里哪一位）实测全部生效（col-2 实测右移 8px）。所以短链补拍必须加 keep/dont_touch 属性防 retiming，否则直接用 col 数据选择补偿（组合选择逻辑 TD 动不了）。「打拍结构改动无效、数据选择改动有效」是判别 TD retiming 是否活跃的实测指纹。**这是 RTL 静态可查的根因**，优先级高于一切补偿实验：先 grep 各层打拍链对齐度，再决定要不要补偿。tb 全链模型（word/col 在 x_2d 域打拍 + ERAM 读延迟 + video 链 N 拍 + mark 链打拍）可验证打拍数，但模型简化会丢 1 拍、趋势存疑时以实机为准。**分析时间 vs 编译时间的口径**：向用户说「N 分钟级工程」必须区分——静态审计（读代码数打拍）是分钟级，编译验证一个改动才是 50 分钟级；混为一谈会被质疑「结论太快不靠谱」。

## col 相位方向规则（实测标定，别自推）

col 相位补偿的方向推导极易搞反（本会话 col-2 按「取左边位=左移」推导、实机实测右移 8px，白烧一轮）。**规则**：取 col+N 的位显示在 col 位置 = 右边内容拿到当前位置显示 = 涂白左移 N×4px（右错用 +N 补）；取 col-N = 涂白右移。RTL 写法（带借位绕回，6bit col）：`col_ph = (col_d1 < 40-N) ? col_d1+N : col_d1-(40-N)`（N=2 即 <38 ? +2 : -38）。方向推导完也只在 tb/实机标定后信——「实测方向优先于理论推导」对 col 相位同样适用。**多旋钮叠加先算总账再动手**：补偿常由多个旋钮叠加实现，动手前把每个旋钮的净贡献列成算式——col 链初始值提前 N（初值写 6'd(40-N) ≡ -N mod 40，比 col_d1+N 带借位绕回更简洁的等价实现，同样实现「视频 x 处查位图列 x-N」）→ 涂白左移 N×4px；涂白条件用 mark_comb（打 0 拍）比 mark_2d（打 2 拍）再早 2 拍 → 再左移 2×4px——总账 = (N+2)×4px，对准实测错位量中间值，不要一个旋钮一个旋钮轮流试。**补偿量必须与实测错位量同量级**：历史 ±1/±2px 级补偿（DATA_DLY/ADDR_DLY±1、col±1/+2）在 8~10px 错位上全部「无效」= 量级错位而非方向错——1~2px 的变化在 8~10px 错位里肉眼不可辨，「没变化」是错觉不是旋钮无效；补偿量直接按波形实测数字打（shiyan 实测 6~11px → 打 8px 中值），残余再用下板反馈微调。用户要求「先想一想之前分析的结果」再动手大改动时，即按已有波形 CSV/根因文档的实测数字设计补偿量，不凭感觉估拍数。错位量 <10px 时必须让用户数像素列（「半指宽=20px」类目测会高估 2~3 倍，20px/40px 级补偿全部过冲）；数得的像素数 ÷ 4px/拍 = 拍数，补偿用 ±1~2 拍档（4/8px）而非半字/整字档。数像素给用户的口径：屏幕上一个小白点 = 1 像素，1 拍 = 4 像素（每拍处理 4 像素），col+N = 只抓 40bit 字的低 4 位，某字低 4 位全 0 不代表该字空（高位 bit 可能有标记）——判「字里有没有标记」用 mark_comb（组合位选择取的是全 40bit 的 I_fg_rd_data[col_d1]），别拿低 4 位调试信号当字内容判据（实测：word0 低 4 位全 0 而 mark_comb 在 col=26 起=1，两者不矛盾）。**跨域抓取前把脉冲信号展宽成电平**：写使能这类 1 拍脉冲从 100M 域打 2 拍到 75M 域再 MARK_DEBUG，会被异步采样丢失（实测 wr_en_2d 全程 0 而 wr_addr 停在非零值——地址走过了但使能脉冲没抓到）——wr_addr 残留非零值是「写侧活动过」的间接证据，但脉冲型信号要么展宽（跨域前拉长到 N 拍电平），要么别当触发/判据信号。

## Eram Editor = 写读两侧一把判定的补充实测工具（GUI 无 CLI，数据走文件转）
ChipWatcher 之外 TD 还自带 Eram Editor（Tools → Debug Tools → Eram Editor）：直接读芯片内 RAM 实例内容存 .txt/.mif/.dat，读出的文件转给 agent 分析（read_file 直接读 txt）。用法：①板子上电 + JTAG 连接（否则 Hardware 栏 = No hardware，先查这两项再点刷新按钮）；②点 ram list 按钮加载工程 Runs 目录的 .bid 文件（如 `phy_1/FPGACompetition_inst.bid`，映射 Instance 名与 ID）；③点 Logic 按钮切到 Logic RAM 界面；④选 READABLE 的实例读数据 → 保存为 .txt。判读：手放画面已知位置静止时读 fg_mark_eram 内容——「标记 bit 实际位置 vs 手实际位置」，内容本身偏移 = 写侧错位（bg_read 攒字/写地址），内容位置对而屏幕显示偏 = 读侧错位，一把判定写/读两侧。ChipWatcher 与 Eram Editor 都无 tcl 命令行接口：调试数据全部走「GUI 导出文件 → 告诉 agent 路径 → read_file 分析」中转（ChipWatcher 波形 = Watch 界面 File → Export Wave Data 存 CSV）。另外两个坑：①不先打开 .al 工程而直接开 ChipWatcher 会进 [read only] 只读模式（信号列表可见但所有设置锁定，Mark Debug 是否生效反而能在信号列表里直接确认）；②带 ChipWatcher 采样核的编译在 PHY start_timer 之后的 bit 生成阶段会静默 40 分钟以上（进程存活、日志无新行 = 正常慢，勿判卡死杀进程——用完成通知等待而非 sleep 轮询）；③**烧录窗口（binWriter/bw.exe）开着就占住 JTAG → ChipWatcher/Eram Editor 全部 No hardware**——调试工具走 hwserver.exe 与 binWriter 不同路，先关掉 TD 的 Download 窗口再连；④命令行编译的工程在 GUI 打开 .al 报「Current flow is out of date」点 Yes 仍是 read only → 用离线调试模式绕过：不打开工程直接开 ChipWatcher 选 phy_1/cw/compiled.cwc（.cwc 与 bit 必须同目录，把 bit 复制进去命名 compiled.bit），只读模式仍可 Watch 下载+设触发+抓波形（触发条件是运行时设置不受只读锁）。下载速度档位与 binWriter 不一致没关系（如 binWriter 5Mbps vs ChipWatcher 6Mbps），选最近档位。完整实操见 references/chiplike-debug-tools.md。用户发 GUI 截图求助「不会用」时：本地 tesseract（chi_sim+eng 语言包已装）OCR 截图文字最快，直接读界面按钮/状态字，比派视觉子代理快。

## ERAM 综合模式验证（读延迟账的实锤入口）

怀疑读延迟账时直接查 TD SYN 日志的 memory 综合报告：实例行标注原语与模式（如 `PH1P_LOGIC_ERAM` + `REGMODE_B=NOREG`）——NOREG = B 口同步读下一拍出数 = 1 拍读延迟（与 RTL 注释对齐则设计假设成立）；报告里 IMPLEMENT=20K(FAST) 指逻辑资源实现而非硬核。此报告是「RTL 延迟账 vs 实机化行为」争议的快速裁决入口，与 .area 报告（查 BRAM 化）互补：.area 查「大 reg 数组是否被 BRAM 化」、memory 报告查「RAM 实例的读写模式/延迟」。grep 关键字：ERAM/REGMODE/working_mode/memory type（Windows 换行先 tr -d '\r'）。

## 本项目时钟域全景（跨域相位排查的清单底稿）
四个时钟域：MIPI 摄像头域（S_csi_rx_clk，SC500CS 数据进 ISP）→ DDR 用户域（I_ddr_clk 100M：video_in 写帧、bg_read 读背景、串行仲裁）→ 视频像素域（I_clk 75M：video_out 显示读、hdmi_mixer 叠加涂白）；I2C 配置域（慢时钟，只配寄存器，与图像无关）。PLL 同源相位固定。
跨域路径按影响层级三分：**内容型**（摄像头→DDR、DDR→视频数据通路走异步 FIFO）不产生列错位；**帧级型**（vsync 打拍、S_fg_init 写满标志等控制信号跨域）错几拍只影响哪帧生效、不影响列对齐；ERAM 双口（A 口 100M 写/B 口 75M 读）读新旧混合只影响内容。**列级错位只可能来自「视频流域内部 data vs de vs x_2d 相位」或「写侧列语义 vs 读侧列语义」**——列错位排查先排除内容型/帧级路径再聚焦这两层，别在无关跨域上耗时间。

## 本项目参数速查（背景减除 ERAM 链路）
- ERAM 字 = 40bit = 10 组 × 4bit/组；96bit 解包拍 = 4 像素 × 24bit（3 个 128bit DDR 字 = 4 个 96bit 拍，相位周期 3 字/行内 240 字整除 3 → 行首相位恒定）
- 帧缓冲 = 23040 字 = 720 行 × 32 字/行（首字地址 = 行 × 32）
- 实测网格（d 单位 = 字，读补偿 r / 写补偿 w）：
        w=-1    w=0    w=+1
  r=+1    ？    -2    -1
  r= 0    ？    -1    +1
  r=-1   -1    +1    +2
  单线性公式 d = -1 - 2r + w 只在 r=-1 列成立；(0,+1)=+1、(r=+1,w=+1)=-1 实测使全表线性破产——写贡献依赖读背景，只能网格逐点实测。

## 环实现不对称：补偿贡献翻倍的机制根源
网格不对称（r=-1 贡献 +2 而 r=+1 贡献 -1）的机制 = 补偿实现里的「环」处理贡献了额外 1 字：读 -1 的实现带环（行首发上一行末字，y=0 环到 23039），环的边界处理多挪 1 字 → 贡献 +2；读 +1 的实现无环（行首发 base+1）→ 贡献 -1 对称。写 -1 同理（首字 0-1=32767 读/写块外 = 隐式丢字）。修法 = 对称化：把负方向补偿的环拆掉（行首发 base-1 不绕环，y=0 行首读块外 = 左上角 40px 无涂白），四系数对称后 d = -1 - r + w 恢复线性，解 d=0 = 无环读 -1 + 写 0。若对称化后仍不齐，穷尽 ±1 网格换 ±2 网格继续（线性外推先试 ±2；错位是线性平移不是环索引，跳 +9 级大补偿只会放大错位）。
- 半字分量出现 = 错位不只字粒度（20px = 5 组 = 攒字器组相位错 5）

## 陷阱
- **主线 bug 未收敛时别并行开新功能（用户拉回过）**：趁编译等待开做比赛新功能（区域填充/外接框等）会被用户叫停「先解决错位」——离场期间的不停工指「主线诊断/仿真的推进」，新功能开发必须等主线收敛，用户会主动排优先级，别自作主张分散精力。等待空档（编译排队/用户睡觉）可以写新功能的「方案设计文档」（只写方案、不动代码、不占编译队列），用户反对的是并行开发代码分散主线，方案文档是收敛后直接开工的准备。**主线收敛后用户会主动规划多路并行**（如「以 B3 为基础复制三份独立目录，三路并行开工，最后融合进一个工程 GUI 编译定稿」）：配合动作 = 收敛版 commit 存档（bit 被 .gitignore 忽略时 git add -f 强制入库）+ 开工前划分各路文件边界（多路都改 hdmi_mixer/bg_read 会打架——外接框/填充在检测链、清晰度在 ISP 预处理链，预先约定各改哪几个文件）+ 每路 cp -r 独立目录各自编译，融合会话统一合并。
- 嵌套 if-else 用 patch 改代码后必跑 iverilog -g2012 -tnull 语法检查（过滤 Unknown module 例化引用）：begin-end 不平衡是高频事故。
- 写 ±1 环补偿有代价，必须预先告知用户：首/末字丢失 = 左上/右下角 40px 无涂白；确认对齐后再优化代价，不要边实验边解释。
- tb 判据要选对观察对象：填 0 / 丢组只影响帧开始后 N 拍（= 帧首行行首）。tb 差异图案若每行行首都有，判「填 0 生效」只能看帧首行首字（期望 data=0），不能拿行 1 首字判——行 1 距帧开始 1280 拍不受影响，其 0x0F 是正常值，会误报 FAIL。
- 填 N 组 0 时 N 凑满一个整字（10 组）会让攒满拍在填 0 期间触发、首字写拍提前——这既是「内容右移 1 字」的正确实现，也是写拍时机漂移的来源（与风险分级第 6 条联动）。
- 双重影/两段涂白的判别：主体涂白对齐 + 第二段残影（间距 ≈ 屏宽）= 装字拍与发地址拍相位错开（装的是旧地址内容），改发地址拍与装字拍同步提前；残影间距 = 手与手腕固定距离 = 两个真实物体（手伸深了手腕也进画面），不是 bug；手静止时残影消失 = 移动滞留（帧差链消退延迟），与移位链无关。判别实验 = 手伸进去静止不动看几段涂白，静止一段 → 移动滞留，静止仍两段 → 双装载。**「两段涂白之间有盲区（手伸在中间不涂白）」= 结构双影的铁证**（移动滞留不会产生中间盲区），出现盲区直接修装字/发地址相位，别再查帧差链。
- 绕环双影（手在左边界 → 右边界出现副本，间距 = 行宽）：消隐装字分支（S_x_2d==0 每拍装 I_fg_rd_data）把上一行末字内容在行首又显示一遍。解法 = 消隐装字改装 40'd0（行首 4px 黑不可见，副本消失）。掐 x=0 的 de 拍（保留纯消隐拍）消不掉——副本在消隐拍装的内容里，必须整体装 0。
- 边界盲区与错位是同一件事：内容整体左移 20px → 最左 20px 内容出屏 → 左边界 20px 不涂白。补掉错位盲区自消，不要把盲区当独立 bug 修。
- 画面错位第二个触发源 = 自动调节（增益/曝光）：与 DDR 训练失败不同，是调节时摄像头输出时序短暂变化 → 视频输入链相位失配 → 错位后无法自恢复（逻辑层，不是物理层）。**机制级定位（代码走查实锤的丢字链）**：自动调节写完 I2C 后 video_in 跳 3 帧（r_frame_masked 屏蔽写）——屏蔽期间摄像头持续灌采集 FIFO（S_fifo_rst 恒 0 不复位）→ 满 512 溢出丢新字 → 恢复帧帧头地址写进旧帧残字 → 错位；按键调节不跳帧（I_auto_en=0）→ 无溢出 → 不错位。**根因级修复方向 = 跳帧改「覆盖写同块」**：不屏蔽写，写指针不动 → 地址每帧复位到同一乒乓块帧头 → 异常帧覆盖写进「显示端不读」的块 → 显示冻结 3 帧但不错位、FIFO 不溢出、排空批照常；比旧规避（渐变调节/演示锁定）彻底。**通用规则：跳帧/屏蔽写必须同时解决采集 FIFO 灌入的去向（覆盖写或显式丢弃），否则恢复帧必错位**。演示流程规避（提前调好增益曝光、演示中锁定不调）仍有效。不开自动调节时「黑屏只有 logo 文字」老 bug 几乎不出现——与自动调节同源：持续寄存器写扰动视频链，轻则相位错位、重则视频数据全丢黑屏（OSD 不经过 DDR 所以存活）；修自动调节（限频 + 消隐期写 + 小步进）可能一并根治黑屏老 bug。
- HWNS 红（hold 违例）≠ 逻辑错误：同一份逻辑两次编译 HWNS 可 +0.020（绿）→ -0.087（红），87ps 在临界路径的布局噪声范围内。画面级异常归因前先查该版 timing 报告：填 10 组版画面错位时 HWNS 全绿 = 逻辑/时序效应；填 5 组版 HWNS 红 = 布局随机 hold 违例（下板可能正常也可能异常，重编译即可换布局）。下板前发现 HWNS 红要预告用户「画面异常可能是 hold 违例不是逻辑」。
- S_drop_cnt 位宽按未来最大参数预留（填 5→10 组从 3bit 扩 4bit），判定条件位宽与声明一致（4'd0 对比 4bit 寄存器）；参数从 5 改 10 只动一行赋值，不必改判定逻辑。

## 人为注入延迟仿真 = 参数化补偿预验证（10-31 收敛打法）
RTL 仿真没延迟、实机有延迟——直接在 tb 里给写数据链人为插 N 拍延迟（data_dly_chain 移位链 + DATA_DLY 参数）就能代替实机延迟：错位 = N/字周期向下取整（字周期 10 拍：插 5 拍 = 半字 20px、插 10 拍 = 1 字 40px），半字档错位的来源 = 实机插拍数在 10~15 拍之间。工程侧配套 = bg_read 加 `parameter [3:0] DATA_DLY` 输出链移位补偿（0~15 拍可选，诊断读数 N → 填 N 编译一次对齐），仿真先扫 N 验证「填 N → 落位回正」再编译下板。**时序报告查实机读延迟拍数**：读侧 ERAM B 口 = 寄存器→组合读→寄存器 = 1 拍（不进关键路径报告即不违例）→ 装字链 D=1 远小于错位阈值（发地址拍后地址保持，D≤39-colS 全对齐）→ 读侧无辜的定量证据。

## 实机路径延迟的定位优先级（最终裁决清单）
RTL 仿真（理想 + 扰动 + 注入延迟）全部自洽后，实机路径延迟（TD 插拍/BRAM 化）只剩实机测量：①数码管锁存首字写拍地址+数据（判读表三分支）；②特征帧法（固定亮块量涂白偏移）；③TD 6.2 无明文网表导出命令（gate.db 加密、cmd 文档无 netlist 项），网表级仿真不可行。verilator 提速：`apt-get download verilator && dpkg -x verilator_*.deb ~/verilator_local` + `VERILATOR_ROOT=$HOME/verilator_local/usr/share/verilator` + 直接调 `~/verilator_local/usr/bin/verilator_bin`（Perl 包装器在非标准布局下找错路径）；参数扫描 sed 改参数重编译（verilator `+PARAM=VALUE` 运行时覆盖实测不生效——被常量折叠，三档扫出同一结果；sed 重编译 5 秒内）；坑：未定尺寸大数字要 `64'd` 前缀、数组 for 循环内用阻塞赋值（verilator 不支持非阻塞）。

## 编译中间产物预判实机插拍数（时序报告 Logic Level 判读法，实测验证）
TD 插拍 = 多出来的流水级。实测验证过的方法：①`final_timing.rpt` **只列关键/违例路径**（slack 最紧的子集）——目标链不在报告里 = slack 宽松 = TD 无插拍动机（寄存器→寄存器 1 级路径 10ns 周期下 1.9ns 到达，slack 巨大）。②路径段落自带流水级数：`Logic Level : 1 ( ERAM=1 )` = 起点寄存器直连 ERAM 组合口、无 LUT 无插拍；「clk2q 1.642ns + net 0.232ns = 1.874ns 到达 vs 周期 10ns」直接算 slack。③路径语法：`Begin Point : <reg>.clk`、`End Point : <pin>.dia[i]`；某寄存器只作 Begin Point 出现 = 其 D 端路径不在关键子集 = 该链无插拍。④`.bid` 只含 `<All_Bram_Infos>`（无 FF 实例清单），数 FF 预判插拍数此路不通；寄存器总账用 `syn_1/FPGACompetition_gate.area` 的 seq 列对照 RTL 账（bg_read 7481 与 morph 644 拍延迟链账相符 = 无异常）。⑤TD 报告是 Windows 换行：先 `tr -d '\r'` 再 grep，否则匹配不到。⑥网表命名 `_syn_N` 后缀是 TD 惯例不是插拍级数，别误读。预判结论只作缩小候选，最终以实机数码管读数为准。**反用例（本会话核心战果）**：8d8e7da 曾以「TD 插拍」为由重写读侧引入错位，时序报告判读证明读侧 D=1 拍无辜 → 「哪次重写的依据后来被证伪，哪次重写就是错位引入点」——git 考古判引入点时优先查「以根因名义做的重写」。
