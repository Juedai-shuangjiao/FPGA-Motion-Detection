# 视频显示 FIFO 读穿（underflow）与读触发阈值设计

## 规则

1. **显示读触发阈值（等效水位 = FIFO 水位 + 在途读数据数）不能低于「写批遮挡期间的消费量」**。写批 B 拍期间的消费量 = B 拍 × 消费速率。1080p30 @usr_clk 100M：写批 240 拍（2.4us）× 消费 13.92M 字/s ≈ 33 字。阈值 30 < 33 → 水位被写批压穿到 0 → FIFO 空读（输出保持旧值）→ 行内字流错位 + 128 位解包相位错乱 → 撕裂带/斜线/黑线/闪烁。
2. **阈值取 FIFO 半满附近**（Lattice 官方 Video Frame Buffer IP 标准：低于半满触发、读到半满）。512 深取 240~256：批后落地水位 ≈ 阈值+批长−批内消耗 ≈ 447 ≤ 510 不溢出；写批遮挡最坏水位 = 阈值−33 > 0 结构上不可能读穿。
3. **读触发机制的供给上限恒等于消费速率 × 1.0005**（批间死区 = 批长 − 读批期间消费量，与 usr_clk、批长都无关）。分辨率/帧率升级前先算消费速率是否顶到上限：720p60 消费 10.37M 字/s（余量 34%）、1080p30 消费 13.92M 字/s（余量仅 0.05%）。阈值低（如 30）在消费有富余时无害、顶到上限时必然翻车——**分辨率切换后必须重新审读触发参数，不能沿用**。
4. **帧级撕裂与 FIFO 级读穿是两层独立防线**：帧级靠 3/4 帧乒乓（读写指针差 2 帧，Gowin/Lattice 官方同款）；FIFO 级靠半满水位触发。诊断时先排除帧级（乒乓正常）再查 FIFO 级。
5. ARM QoS 官方文档：显示控制器这类实时主设备在延迟窗口内得不到服务会 FIFO under-run → screen image break up——读穿致画面碎裂是业界公认机制，不是玄学。
6. **异步 FIFO 的占用计数（wrusedw/rdusedw）是跨域同步链输出，延迟 2~3 拍，不能用于「防下溢」类实时门控**（2026-10-26 bg 行弹弹 X 实锤）：行弹速率（3/4 节流 ≈0.75 字/拍）高于写速率（≈0.55 字/拍）时弹链必然追尾，门控靠「计数≥1 才弹」暂停——但计数反映的是 2~3 拍前的读指针，追尾时晚 2~3 拍才见空 → 每行多弹 2~3 字 → 弹空读出未初始化 X → 比较全错 → 宏观上标记乱涂（白线飘、手成线不成块）。修复：模块内维护本地实时计数（写口径与 FIFO we 完全一致、弹口径与 re 一致、同拍写弹相消 `cnt <= cnt + hit - re`），门控用本地计数。同拍相消时注意算术表达式（`cnt + hit - re`）比 if-else 分支干净，且计数在弹拍不可能为负（门控保证 ≥1 才弹）。
7. **双阈值错峰（消费者触发阈值低 + 生产者门控阈值高）在「无消费时段」会冻出死锁带**（2026-10-26 消隐期 bg 饿死实锤）：显示期末水位若落在两个阈值之间（如 269：vo 不触发读批（>200）、bg 被门控（<300）），场消隐期 vo 不消耗 → 水位冻结 → 双方都不动，干等整个消隐期直到下一显示期消费把水位压到触发阈值才解。修复：生产者门控必须带「消费活动窗口」条件（de 电平跨域打拍：显示期才做水位门控、消隐期直接放行）——消隐期生产方全速安全（消费方不消耗），还能把消隐窗口利用上。**凡用双阈值错峰的场合，门控侧必须考虑消费暂停期，不能假设「水位自然回落」**。

## 帧头残余丢弃（discard）与标签计数脆弱性（顶部错位根因，2026-11）

1. **帧尾残余按「返回标签=1（vo）」递减丢弃计数 = 脆弱设计**：多读源（vo 预读 + bg 整帧读）交织时，标签压弹错位（bg 残余误带 vo 标签）→ discard 误减提前归零 → 后续 vo 残余漏丢写进显示 FIFO → 新帧第一批数据被旧帧尾污染。实机特征：顶部 1~3 行错位（第一行 100% 错、二三行按批边界周期错），只在副读源开启时出现——关背景检测立即正常。
2. **健壮实现 = 帧头锁存标签 FIFO 的 wrusedw（已压未弹 = 全部在途命令数 vo+bg），之后每落地一个数据减 1（不看标签）**；DDR 保序保证前 N 个落地 = 全部在途残余，数学完备、标签错位免疫。细节：锁存打 1 拍（等 wrusedw 反映最后一个命令的更新延迟）；标签仍保留用于 FIFO 写使能归属门控（bg 数据不进显示 FIFO）。
3. **修复验证分两层**：先核心数学对比 tb（旧 vs 新实现同场景，错位标签数 k 参数扫描 0~30——旧实现污染 k 字、新实现恒 0），再完整链路 tb（命令队列 + 标签 FIFO 压弹 + 返回延迟链 + 错位注入 20/100）。两层都绿才改 RTL，别只跑一层就下板。
4. 判读辅助：水位满 ≠ 数据对——先用水位消耗速率与显示理论速率自洽（0.18/拍 ≈ 320 字/1650 拍）排除供给问题，再锁定数据内容/标签归属。

## 诊断路径

- 现象：斜线撕裂 + 固定几条黑线 + 锯齿 + 帧间闪烁 → 第一嫌疑读穿（FIFO 空读旧值 → 行内错位 + 解包相位错）。
- 判据：读计数正常（= 帧字数）、写计数正常、DDR 带宽有余（读写合计 << usr_clk 拍数）→ 排除带宽问题，查读触发水位。
- 验证：Python tick 模型（几百行，快速定量）或 iverilog 行为仿真（真 video_out.v + 异步 FIFO 桩 + 40 拍返回延迟链 + 写批遮挡模型）跑新旧阈值对比读穿次数。两套都跑过：阈值 30 → 每 3 帧读穿 616 次（Python）/ 82 次每 3.3ms（iverilog）；240 → 6 次，13.7 倍差。

## 行为仿真桩的坑（iverilog 写 tb 时）

- 异步 FIFO 桩的占用计数不能分两侧各维护（读侧看不到写入 → empty 恒 1）：单一计数在写侧维护，读使能打 2 拍同步回写侧；empty 用计数打 2 拍到读侧。
- 计数要饱和：FIFO 空时 re 不减，否则 0−1 回绕 1023（水位看似满，触发条件永不满足，仿真假死锁）。
- DDR 返回延迟模型用「N 级移位寄存器延迟链」（en 打 N 拍 = valid、数据同步延迟 N 拍），不要用「队列计数 ≥ N 才弹」——后者会剩 N 个字永不返回，在途计数卡 N，触发条件被卡死（假死锁）。
- 所有仿真 reg 给初值，否则 X 在首拍经组合逻辑污染计数器，之后永远 X。

## 相关事实（nogrant 1080P 实测）

- 1080p30 实际时钟：usr_clk 100M、内存 800Mbps（TD 报告 clk1 名 = ref_clk 实为 usr_clk 看 fanout 判别；.params 里 1600 组文本改了但没 Regenerate 不生效——TD IP 参数固化教训）。
- 1080P debug 帧计数需 19 位（388800 = 0x5EE80 > 18 位上限 262144，截断值 0x1EE80 会误判写侧异常）。
- 1080P 背景地址用 28000000（块 3 = 21000000~24110399；720P 时代的 22382400 = 块3+720P帧大小，在 1080P 下会压块 3）。
- 1080P 每行 360 字 = 120 组×16 拍，行边界整除，解包无跨行错位；帧 388800 字 = 1620 批精确整除，无尾批残量问题。
