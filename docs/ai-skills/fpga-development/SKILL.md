# FPGA 开发与项目分析

用户是 2026 嵌入式芯片与系统设计竞赛 FPGA 赛道选手（安路 PH1P35 图像处理、易灵思边缘检测两队）。思考与回复全中文（用户明确纠正过）；代码注释中文 Doxygen 风格。TD 编译耗时与编译方法见 anlogic-td-build 技能。深度参考（references/ 主题按需加载）：ddr-debug-bisection、video-out-fifo-underflow、sim-passes-board-fails、sc500-resolution-config、sim-debug-methodology、ram-inference-latency-trap、misalignment-compensation、chiplike-debug-tools、td-cli-build、competition-research-open-source、port-change-checklist、osd-chinese-font、foreground-overlay-chain、bg-capture-interaction、verilator-sim、scanline-fill-unit、parallel-branch-merge、image-algo-upgrades、adaptive-threshold-lessons、competition-defense-fact-check、fuse20-lessons（iverilog 位宽 bug XOR 规避、KEY4 长短按、阴影 v2 回退、字模 simhei 19px、BRAM 仿真相位链、高斯延迟账）、uart-serial-tx-design（字节流 UART 发送：ld_ack 握手、位计数、FIFO 语义对齐、tb 验证优先级）、hx1p35b-board-facts（HX1P35B 板载 CH340/H1-J1 串口引脚/官方 Uart_Plot 上位机）、competition-demo-script（演示视频脚本：评分点导向分镜表、动作必须从源码核实拨码语义、录制检查清单）、competition-technical-report（嵌赛技术报告模板：章节+字数限制、背景减除措辞、照片占位）、submit-release-cleanup（提交版工程整理：复制排除 Runs/.git、例化树判未用模块四种漏匹配坑、.al 条目删除双路径格式、GUI 编译准备）。

**背景减除架构（已定型）**：「DDR 读当前帧+读背景帧两路做差」是自创架构非主流，调试别拿片内 RAM 背景模型对照；掩码法「同地址读两帧天然对齐」已借鉴。作品文档/简介写「背景减除法」而非「帧差法」（帧差法 = 相邻帧相减、无背景采集步骤，与本系统原理不符；简介只有一次修改机会，措辞必须与演示动作 SW4 采背景严格对应）。简介/名称提交硬约束：名称 ≤15 字（汉字/字母/数字都算 1 字）；选题二基础要求 4 = OSD 必须叠加「安路」标识 Logo（写简介/验收前先 grep 工程 OSD 是否已有 Logo，没有必须加）；截止时若把「计划中的功能」写进简介（如外接框/质心坐标/区域填充）= 向评审承诺的硬任务，必须提交前下板验证，做不成的功能宁可不写。

**半帧撕裂（细线）**：重叠 N 行不根治（撕裂点 1 变 2），解法=非对称半帧（上1/4读184行/下3/4读544行+重叠4行）把撕裂点移到画面上部静止背景区；全帧读超消隐预算→画面错位。实施口径与写链帧复位三坑/排空批方案见 references/sim-debug-methodology.md「重叠半帧读实施口径」「写链帧复位三坑与排空批」两节。

**数码管诊断读数先核对信号定义（2026-10-25 教训）**：用户报「写计数 200~300 随机」——实际模式 3 显示的是 bg 读消隐期计数 S_fg_dbg_rd_cnt，不是写计数 S_dbg_wr_cnt（后者已不在数码管上），诊断方向差点被带偏（一度误判「写批每帧只写 1 批」）。下板诊断读数前必须 grep 数码管 case 确认每个模式显示的确切信号再解释读数。**诊断 LED 同理且更隐蔽**：先 grep 灯驱动条件里每个信号的驱动源——声明了但从未 assign 的 wire 被 TD 综合成 0，会把灯恒灭/恒亮毒化成假诊断（tvalid_act 判定 I_tvalid && O_tready，O_tready 悬空=0 → 灯恒灭，误判「摄像头不出流」一整晚）；修悬空（接 1'b1）后灯才恢复真实指示。

**诊断提问前先 session_search 回看历史对话（工作流铁律）**：拨码/按键「某个模式是干什么的」、某信号的既定门控约定，往往在此前会话里定过（调试期临时占用、二分门控等）。用户说「回看之前的对话」= 纠正：先查历史再提问，别把历史上已定的约定当新问题抛回去。下板现象分析前先 grep 该信号全部用途 + session_search 历史约定，再设计验证实验。


**编译时机由用户决定（工作流铁律）**：用户说「别编译/明天编译」时，只做静态分析 + 改好代码，不启动编译（已在跑的任务让它自然跑完即可）；把「改代码」和「编译」两个阶段分开，代码改完由用户挑时间统一编译。用户偏好「先找问题、改好代码，明天直接编译」的节奏，主动启动编译会被纠正。用户明确授权时（如「你去编译」「不节约时间，该仿真仿真」）连续执行仿真→改→再仿真→编译完整流程，离场（睡觉）期间不停工、不跳验证，把进度与仿真数据整理成结论等用户回来验收。**新模块/改模块必须先 iverilog 仿真跑通再启动编译（用户明确纠正过）**——杀编译重编浪费整轮时间。**新 .v 文件必须注册进工程文件列表（TD 不自动扫描）**——tcl 编译读 syn_1/phy_1 两个 .prj，只改 .al=black box 假跑，见 references/td-new-file-checklist.md。

**用户离场授权开工前先复述最终要求清单（用户原话「复述一下要求」）**：把 clarify 拍板结果逐条列成「改动范围+交互语义+验证流程」纯文本清单，覆盖用户反转过的选项，明确「先仿真再编译」顺序承诺；复述完再动手。离场（睡觉）期间干活属明确授权，但开工边界必须复述对齐。

**已启动的编译绝不擅自杀掉（用户两次强烈纠正，最高优先级）**：编译跑着的时候，任何方向决策（回退/重构/换方案/改架构）都必须等当前编译完成、用户下板报结果之后再动手——杀掉正在跑的编译 = 浪费整轮编译时间 + 打断用户验证计划。即使编译启动后发现源码还要改，也是等它跑完或先问用户；「把编译杀了直接推新方向」明确禁止。杀编译命令（仅用户同意后）：`taskkill.exe /F /IM td_commands_prompt.exe` 再 `ps aux | grep td_commands | grep -v grep | awk '{print $2}' | xargs kill -9`——pkill 的匹配串绝不能包含自己命令行的子串（匹配 DefaultFlow 会把自己也 SIGKILL）。

**TD 编译中改源文件不生效**：TD 在 SYN 启动后的 import 阶段读源文件，编译开始后再改 .v 不会进当前 bit。编译启动后若改了文件，必须主动告知用户「当前编译用的还是旧文件」并问是否杀掉重编，不要默默跑完一个已过时的版本。

**回复格式（用户纠正过）**：CLI 纯文本环境，正文不带任何 markdown 加粗/斜体，也绝不能让内部思考用的标记（`**`、`「」`、`——`）泄漏进回复——用户会看到满屏乱码并质疑。长分析用缩进 + 编号的纯文本重述；回复全程中文，不接受中英混杂的解释段落（代码块内标识符除外）。**thinking/内部推理也全程中文输出**（用户能看见思考过程并明确要求过）。

**PH1P35 器件资源（DS1301 系列概览表3-1，权威数据）**：LUT4s=38,189、DFFs=42,432、Dis-RAM(分布式)=507Kbit、**ERAM(嵌入块存储BRAM)=108个×20Kbit=2,160Kbit(2.16Mbit)**、DSP=40、PLL=6、MIPI DPHY=2。⚠️ 早期误记「BRAM约1Mbit/50块」是错的，实际 2.16Mbit/108 块。TD 报 `EMB exceeds limit 108` = ERAM 超 108 个。**存帧 BRAM 深度固定 65536（一个 IP 就占 25.6 个 ERAM），改 down_cnt 回绕不省 EMB（IP 深度不变），要省 EMB 只能减 BRAM 实例数或重新生成更浅的 IP**——RGB 减背景 3 块 65536 深 IP 必超（76.8+其他≈145>108），改用 B 单通道 1 块（25.6，≈93.8 不超）。

⚠️ **ERAM20K 位宽配置是离散的 1/2/5/10/20/40（没有 4bit/8bit，查 DS1300 数据手册表 2-1）**：4bit 数据只能塞「4K×5」配置（浪费 1bit = 20%），所以「按实际 bit 数」估算 ERAM 会偏乐观——实测 4bit×65535 深 = 16 个 ERAM（不是 12.8）、RGB 3 通道 4bit 65535 深 EMB=109 超 1 个，改 57600 深（4bit×57600=15 个 ERAM/块）EMB=106 不超。**单块 ERAM20K 最大深度 16K（仅 1bit 宽 = 16K×1 配置）**，位宽越宽单块深度越小（8K×2 / 4K×5 / 2K×10 / 1K×20 / 512×40），深度靠「多模块地址/数据级联」扩展。要省 ERAM：①减实例数 ②重新生成更浅/更窄的 IP ③数据改 reg 数组（LUT 实现，不占 ERAM，8bit×320 这种小 line buffer 适用，32bit×320×2 会爆 LUT）。ISP 坏点校正/白点诊断与视频链路图像质量 debug（详见 references/isp-bad-pixel-correction.md）。

## 分析一个 FPGA 项目的标准工作流（按序执行）

1. **clone 到 Windows 路径的 /mnt/d 等价路径**。用户 FPGA 资料统一放在 `D:\Users\user\Desktop\FPGA比赛\` 下（WSL 里是 `/mnt/d/Users/user/Desktop/FPGA比赛/`）。`git clone --depth 1` 即可，分析用不到完整历史。
2. **先读 README**：国一作品 README 通常写清了设备拓扑、IP 地址、工作模式、目录结构，能省掉大量猜测。
3. **定位工程入口和顶层**：安路工程入口是 `.al` 文件（用 TD 6.2 打开）；顶层模块在 `.al` 同级或 `src/`、`import/` 下的 `.v`。README 一般会点名「最终顶层文件」。
4. **读顶层 `.v`，按固定顺序扫**（这套顺序能快速抓架构，别从第 1 行死磕）：
   - 端口列表 → 了解外设（RGMII/HDMI/SD卡/摄像头/SDRAM 引脚）
   - `parameter` 定义 → IP/MAC/端口、分辨率、帧大小
   - 模式选择逻辑（`mode_sw` / `case`）→ 系统有几种工作模式
   - 时钟生成（PLL 例化）→ 几个时钟域，各干什么
   - 复位架构（POR + 手动复位 + 域复位 + 模式切换复位计数器）→ 这是国一作品的精华
   - 模块例化 + 信号线网 → 数据流走向
   - 最后的 Mux/Demux 仲裁段 → 共享资源如何分时复用
5. **分清原创 vs 官方 IP**：文件名带 `.enc.v` / `.enc.vhd` 的是加密 IP 核（源码不可见，通常是官方提供），如 `udp_ip_protocol_stack_merge.enc.v`、TEMAC。作者的原创集中在图像处理、分包协议、SDRAM 复用仲裁、上位机联调——分析时把重心放原创部分。

6. **加密 IP 比赛直接可用（用户反复确认过，别重复查证）**：安路赛题二（PH1P35 实时数字图像处理）的 MIPI PHY、片内 DDR 控制器、HDMI TMDS 编码这些官方加密 IP 都能用。依据（2026 选题指南 PDF，共 36 页）：第 8 页「提供参赛样例 lab_ex_1/2/3」（MIPI 采集→DDR→HDMI 显示，全用官方加密 IP 搭好）；第 16 页赛题正文「从 MIPI 视频流输入解码、视频数据缓存…到 HDMI 高清显示」——这三件事是芯片硬核，本身强制用官方 IP；第 35 页「参赛作品必须为原创」管的是算法/架构，不是平台 IP。注意：选题指南里「配套图像处理 IP 库、高速接口参考工程」那句在**赛题三**（第 20 页），别引错到赛题二。原创分落在图像处理算法、OSD 叠加、多算法切换、系统架构。
6. **对上位机协议**：读 PC 端 Python 的 `struct.unpack` 格式，和 FPGA 端包头拼接 `{...}` 逐字段核对。注意 Verilog 拼接 `{a,b,c}` 最左是最高位，小端 unpack 后 `header[0]` 是最低 32 位——别把字段顺序读反。

## 安路 TD 工具链要点
- **WSL 搜工程源码内容用 terminal `grep -rn`（search_files 内容模式在 /mnt 挂载上会漏报空结果）**：本次在 `/mnt/e/FPGA_Code/FPGACompetition` 搜 `IMAGE_BASE_ADDR_4`/`28000000` 时，search_files 内容搜索连返 0 结果、实际这些字符串明明在文件里，换 terminal `grep -rn` 立即命中。search_files 的 `target='files'`（列文件名）在 drvfs 上正常，只有 content 模式失效。搜地址/localparam/端口名/信号名一律 terminal grep，别信 search_files 返回 0 就以为没定义。
- 工程文件 `.al`，用 **Anlogic TD 6.2** 打开；`.qws` 是工作区，`.qdf` 是 assignment 默认值。
- **新建的 `.v` 文件必须手动 Add Source 才会进综合，TD 不自动扫目录**：工程 `.al` 是 XML，`<Verilog>` 段**逐个** `<File Path="...">` 列出源文件（每个带 UsedInSyn/UsedInP&R/BelongTo/CompileOrder 属性）。新建模块（如 algo_mode_sel.v/gray_convert.v）不加入就综合，报「cannot find module / cannot find port 'xxx'」。加法两种：①TD GUI 右键 Add Source；②直接编辑 `.al` 在 `<Verilog>` 段末尾加 `<File>` 条目（CompileOrder 接现有最大值 +1）。**直接编辑 `.al` 前必须关 TD**，否则 TD 保存工程会覆盖手工改动。一个 `<File>` 条目占 8 行（File 开 / FileInfo / 4 个 Attr / FileInfo 关 / File 关），改完 `.al` 总行数多 8 行可佐证生效。
- **「black box」错误（`ERROR: xxx is a black box in ...`）**：文件内容、模块名、实例化、`.al` 记录、编码（无 BOM）全部正确、iverilog 也编译通过，TD 综合仍报 black box——根因基本是 **TD 增量综合缓存没刷新**（新 Add Source 的文件没被重新综合，被当无实现的「黑盒」）。排查/解决顺序：①先确认 TD 源文件列表里能看到该文件（看不到 = Add Source 没真正生效，重新 Add Source）；②TD 里 Clean（清空上次综合结果）→ 重新 Run 综合（强制重读所有源文件）；③还不行就关闭 TD 重开工程再 Run。别急着怀疑代码——代码、路径、.al 都对时，十有八九是缓存问题。
- `.enc.v` / `.enc.vhd` = 加密 IP（源码不可见），`.qip` = IP 核引用清单。
- 换电脑打开工程常见报「找不到 IP 核 / .v 文件」：PLL、FIFO、SDRAM、行缓存等 IP 需在 TD 里重新生成（用 `Add Source` / `Add Existing File` 重导，路径残留原作者目录）。
- 常见器件：安路 EG4S20BG256（国一那套 HX4S20C 板子的主控）；用户图像处理赛道板主控 **PH1P35MDG324**（建工程 Device Family=PH1、Device Name=PH1P35MDG324）。
- **引脚约束坑（入门必踩）**：写完代码不做 Tools→IO Constraint 分配引脚，Bitgen 会报 `BIT-8123`（unconstrained io）拒绝生成位流。分配完引脚后必须重新编译一次再下板。注意康芯《安路软件使用完整流程》教程截图是 eagle_s20 板子录的，图里的引脚号别照抄，要查 PH1P35 自己的引脚分配表。详细流程、报错含义、TD 安装目录结构、新建工程目录布局、从 PDF/docx OCR 提代码的方法见 `references/anlogic-td-toolchain.md`。
- **.adc 约束文件不支持 `//` 注释**：TD 的 ADC 解析器不认 `//`，把 `//========== 注释 ==========` 当命令解析报 `ERROR: ... is not a valid ADC command`。约束文件只写纯 set_pin_assignment 语句（原工程 pin.adc 本来就是无注释的），别往里加注释行分组。
- **手动重建视频流工程**：用户想把官方 lab_ex1（摄像头→ISP→DDR→HDMI）搬进自己的工程。核心坑是 Add Directories 递归会把 IP 内部实现文件（ddr2/src/rtl/ 等）和旧版备用文件也加进来 → 语法错误；正确姿势是「干净源文件目录（42 个）+ 单独加 8 个 IP 核 + 约束 + 设顶层 design_top_wrapper」。IO Constraint 在第一次综合前是灰的（要先跑综合 Read Design）。完整流程、文件清单、日志诊断（SYN-6021/BIT-8123）见 `references/manual-video-project-rebuild.md`。从零建工程 + 手动搬官方视频流进自建工程的完整流程（Add Source 分类、9 个 IP 核清单、IO Constraint 灰色坑）见 `references/anlogic-td-from-scratch.md`。
- **TD 对「always 块外的 if/赋值」静默容忍且照样出 bit——编译成功≠代码生效**：patch 时若插入的 if/赋值落在 always 块外（块先 end 闭合、if 成模块级语句），TD 不报错、bit 照出，但该段逻辑被丢弃——板子表现为「功能完全没生效」（实例：数码管阈值覆盖 if 落在 always 块外 → 数码管永远显示 case 内容，整轮编译+下板白费）。铁律：**改动 always/case 后，用 read_file/sed 核对插入语句的确切 begin-end 层级，确认在目标块内再编译**；iverilog 报的 syntax error 行号要逐个确认是既有问题（如匿名例化）还是新引入的，别一概放过。

## 批改 Verilog 入门代码
用户学 FPGA 入门（流水灯/分频/testbench）时，优先扫这些高频错误：模块名以数字开头、端口名前后不一致（rest_n vs rst_n）、**分频时钟 clk_1hz 分频出来后第二个 always 还写 posedge clk（漏 _1hz）**、`timescale 反引号+1ns/1ps、仿真参数 T 太大跑不完（用 `#(.T(4))` 参数化覆盖）、testbench 缺 `$finish`。若用户「照文档编写」，先 OCR 文档原版代码对照，多半是抄漏几个字符。完整清单见 `references/verilog-common-errors.md`。

## HDL 练习闭环（iverilog 仿真 + TD 下板）

## 教用户从零写 HDL 模块
用户学 HDL 入门（已会流水灯，开始写比赛要用的模块）时：**不写孤立练习题**（用户原话「最好是我亲手敲出来的代码最后能用上」），每个练习都必须是比赛真实模块；给接口 + 功能要求 + 边界用例 + 各 always 块分工让用户自己敲，testbench 由我代写；用户会「一步一步来」喊停问单个概念，逐概念讲透。练习路线（按键消抖→灰度/二值化→多算法切换→帧差法）。**练习 vs 实现的区别（重要）**：练 HDL 是「用户亲手写模块、agent 给接口+思路+testbench」；但实现复杂模块时（如帧差法这种涉及 BRAM+降采样+放大回显的），用户会直接说「别给我思路，一口气全写完，我编译下板验证」——此时**直接代劳全部代码 + 配套改动（algo_mode_sel/isp_top/osd_cn_char/hdmi_mixer/.al）+ iverilog testbench 验证**，别再讲思路让用户自己敲。两种场景都合法，看用户当前意图，别机械套「用户亲手写」。、初学者核心混淆点（花括号 `{}` 不是代码块、`<=` 非阻塞 vs `=` 阻塞、打两拍消亚稳态、parameter vs localparam、always 并行非循环）、iverilog 验证闭环见 `references/hdl-basics-teaching.md`。按键处理推荐分层（用户已重构到位，别退回「key_debounce 塞边沿+电平两个输出」）：`debounce`（消抖，输出电平 debounced）→ 两个功能模块复用 debounced：`key_pulse`（读 debounced 做边沿检测，输出按下沿脉冲，按一下触发一次）+ `key_hold`（读 debounced 做长按检测，按住期间每 HOLD_MS 一个 tick、松开清零，实现「长按连续递增」）。消抖只写一次，别在两个模块里各抄一遍消抖逻辑。**多模式坑（长按误触发短按）**：key_pulse 检测的是「按下沿」，长按的开头也是一次按下沿，所以长按时 key_pulse 必然触发一次（长按=短按+持续）。若按键在不同模式干不同事（模式1短按切算法、模式2长按递增），只隔离「显示」不够，要用 mode 门控隔离「动作」：`wire key_pulse_en = key_pulse && (mode==2'd0); wire key_tick_en = key_tick && (mode==2'd1);` 再把 led_mode 接 key_pulse_en、num 递增接 key_tick_en。否则模式2长按会偷偷把模式1的计数器 +1，切回模式1才暴露。

## 板子引脚
HX1P35A 板（主控 PH1P35MDG324）引脚：clk=C4、LED1~4=D10/E10/C6/D6（高电平点亮）、KEY1~4=D5/A9/B9/C7（按下低）、SW1~4=A4/B4/E11/D11（**拨向板框侧=1/内侧=0**，实测，别信「拨上/拨下」这种方向词）、MIPI_CSI 摄像头、HDMI、千兆网、数码管（DIG0~7/SEL0~7，共阳）等全表见 `references/hx1p35a-board-pins.md`。做引脚约束时查这里，别信 TD 软件随机分配的引脚。原理图/手册/引脚 docx 的磁盘位置见 `references/hx1p35a-board-pins.md` 顶部。另：板上 100MHz 差分晶振 SIT9121 接 K5/L5（DDR I/O BANK，只支持 LVDS18 非 LVDS33），安路 LVDS 差分输入原语 = PH1P_LOGIC_IBUF_DIFF（TD 模板 template/verilog/Device-Primitive/PH1P/I,O/ph1p_i_o.v，端口 i_p/i_n/interm_disable/o/o_p/o_n + 参数 DIFF_TERM）。

**数码管极性（反直觉，写数码管前必读）**：段 DIG 共阳低电平点亮；位选 SEL 串 PNP9012 三极管反相，**也是低电平选中**（sel=0 亮，别信手册「SEL 高电平有效」）。共阳段码表 0~9 = C0/F9/A4/B0/99/92/82/F8/80/90。用数码管先把 SW6 拨上（拨上=数码管、拨下=双色LED）。详见 `references/hx1p35a-board-pins.md` 的「数码管」小节。

**动态扫描（8 位数码管「同时显示」的套路）**：8 个数码管共用段线、各独立位选，靠「1ms 轮扫 + 视觉暂留」实现。结构 5 个 always 块：①扫描分频（每 SCAN_MS 一个 scan_tick）②sel_idx[2:0] 0~7 循环（3 位计数器溢出自然回 0）③数据选择 MUX（`case(sel_idx)` 从 32 位 data 每 4 位取一个数 → cur_digit）④段码译码（复用 seg7 表）⑤位选译码（sel_idx→独热码取反，sel[sel_idx]=0 其余=1）。**data 位序**：data[3:0]=第 8 个（最右/个位）、data[31:28]=第 1 个（最左/最高位）——最高位在左，跟十进制书写一致（第一次写容易把 MUX 映射反，现象是数字左右颠倒）。要某位熄灭给 4'hF（走段码 default 全灭），别给 0（0 是合法数字会显示「0」）。模块组织：seg7 一个模块内聚「扫描+段码+位选」最简洁（顶层只例化一个），cur_digit 是内部信号别暴露成端口。

**数码管显示数值（二进制→BCD）**：曝光/增益这类数值是二进制（曝光 1990=0x07C6），数码管要的是十进制每一位（1/9/9/0），中间必须加「二进制转 BCD」模块。双 dabble（shift-and-add-3，16 次移位）模板见 `templates/bin2bcd.v`（16 位二进制 → 4 位 BCD，bcd[15:12]=千/[11:8]=百/[7:4]=十/[3:0]=个，输入须 ≤9999）。顶层级联两个实例 `bin2bcd(S_ae)`/`bin2bcd(S_ag)`，`seg7 .data({bcd_ag, bcd_ae})`——高16位=增益(数码管1~4)、低16位=曝光(数码管5~8)，正好拼 32 位 data。前导零：增益只有两位数，转 BCD 后千位百位是 0 → 显示「0080」；要熄灭前导零就把无意义高位 0 换成 4'hF（走段码 default 全灭）。

## SC500 摄像头增益/画面暗
SC500 增益寄存器 0x3e08（模拟增益档位 1x/2x/4x/8x）+ 0x3e09（FINE 微调），官方 lab_ex 默认 4x 室内偏暗，改 `uics500reg_720p60.v` 里 3e08=0x1f 即 8x 亮度翻倍（别设 0x2f「12x」——那是非法档会花屏，见「增益编码」那条）。画面暗排查：电脑相机对照排显示器、OSD Logo 亮度分摄像头 vs HDMI。完整编码表与排查法见 `references/sc500-camera-config.md`。

增益编码（⚠️ 查 SC500 数据手册 V1.8 表 2-4 后修正，别信「12x=0x2f」）：模拟增益 ANA GAIN（0x3e08）**只有 4 个合法档位** 0x03=1x / 0x07=2x / 0x0f=4x / 0x1f=8x；0x3e09 是 FINE 微调（0x20~0x3f），>8x 增益靠「0x1f 档 + FINE 微调」实现（最高 15.75x = 0x1F+0x3F，增益值 143，数据手册表 2-4 精确值；即数据手册标称的 16x 模拟增益）。**0x2f 不是合法档位，写入 0x3e08 直接花屏**——米联客 SC500GainTbl 里的「12x=0x2f」是错的（参考代码第 3 个 bug），增益上限必须压到 143（=8x 档最大），别设 175（144 起写 0x2f 非法）。增益值要先减 16 才是 SC500GainTbl 索引（uicfgcs500 例化 `.I(I_ag-16)`），增益值↔档位：16~47=1x、48~79=2x、80~111=4x、112~143=8x（**增益 128 是 8x 不是 12x**，用户曾误以为到顶）。SC500GainTbl 高 3 位选档、低 5 位微调，但档位字节只有 03/07/0F/1F 四个合法值，I[7:5] 取到 4（对应写 0x2f）就是非法档会花屏。增益「初始很亮、调回同值变暗」根因：初始化表硬编码增益（如 0x1f=8x）跟 ae_set 初始 80 经 SC500GainTbl 映射的 0x0f=4x 不一致——上电 O_ae_req 没触发、ae_set 的 80 没真正写入摄像头，画面用初始化表 8x（很亮），一按键才写 4x；修复把初始化表 0x1f/0x30 改成 0x0f/0x20 跟 ae_set 增益 80 对齐。

## SC500 摄像头传感器配置
SC500 官方数据手册（用户偏好官方一手文档，查曝光/增益/帧率寄存器先翻这里，别信商家 CSDN 链接）：`D:\Users\user\Desktop\FPGA比赛\板子资料\HX1P35A_Contest_202606\4_芯片手册\SC500摄像头\`，内有 `SC500CS_数据手册_V1.8.pdf`（曝光寄存器表 2-2、增益表 2-3、帧率计算 2.5 章节）、`SC500CS板原理图.pdf`、`6504镜头.pdf`。WSL 里用 `pdftotext` 提取文本后 grep 寄存器地址（如 `grep -n 3e00`）最省事。\n调画面亮度/增益/曝光查 `references/sc500-sensor-config.md`：模拟增益 0x3e08（0x03=1x / 0x07=2x / 0x0f=4x / 0x1f=8x，2 的幂翻倍）+ 0x3e09 微调档；官方 720p60 默认 4x 偏暗，把 0x3e08 从 0x0f→0x1f 即 8x、亮度翻倍（改 uics500reg_720p60.v，改完重新编译约 14 分钟再下载）。附「画面暗」排查路径：OSD 亮=HDMI 正常、强光直射变亮=配置偏暗。**完整排查结论（查 SC500 数据手册 V1.8 后确认，别再重复查证）**：①曝光语义正常——值越大曝光越长越亮（实测曝光 1100 比 1990 暗），确认法=调小曝光看画面变亮还是变暗，变暗=语义正常；②AWB 不压暗——awb.v 白平衡增益是「把 R/B 归一化到 G」（R 增益 = sum_g/sum_r × 2^16 定点、G 是基准不乘、中性灰时增益 = 0x10000 = 1.0 不缩放），画面整体暗不是 AWB 的锅；③**根因是曝光上限设错了（不是环境光/镜头膜！）**——SC500CS 数据手册 V1.8 明确：曝光时间寄存器 24 位 `{0x3e20[3:0],0x3e00[7:0],0x3e01[7:0],0x3e02[7:4]}`、步长 1/2 行、最小值 3、**最大值 = 2×帧长-10 = 2×2000-10 = 3990**（帧长 VTS 默认 0x07d0=2000 行），而 ae_set 的曝光上限写成 1990 恰好是最大曝光 3990 的一半——曝光被砍半、画面亮度被压一半，灰度 0~76 就是这么来的。修复：ae_set 曝光上限 1990→3990（`localparam AE_MAX=16'd3990`），曝光步进 1→100（粗调：4 位数范围 2~3990 步进 1 要按 3988 次、长按 13 分钟，步进 100 约 40 次 tick 长按 8 秒调全程，key_hold 是每 200ms 一个 tick）。数据手册还提「曝光第 N 帧写入、第 N+2 帧生效」，调曝光后画面过 2 帧才变，长按别急。**之前「环境光不足/镜头蓝膜」的结论被数据手册推翻，画面暗先查曝光上限（1990 是半档），别再走查镜头膜这条死路**。

## 复位链路 + 按键/SW 引脚（分析/重构按键逻辑前读）
HX1P35A 板**没有独立复位按键**：pin.adc 里 `I_rst_n=R10` 是米联客例程遗留的错误映射（R10 实为以太网 TXEN），工程能跑因为系统复位 `S_rst_n = S_pll_lock`（PLL 锁定标志），I_rst_n 只复位 PLL、接错也不致命——所有模块接 S_rst_n。按键现状 `I_button[0]=N2/[1]=J14`（扩展口，非板载 KEY），顶层补 `{I_button,2'b11}`。板载 KEY1~4=D5/A9/B9/C7（按下低）；拨码开关 SW1~4=A4/B4/E11/D11（**拨向板框侧=1/内侧=0** 实测，静态电平，做模式切换直接读电平别检测边沿）。ae_set 用 tick 脉冲做步进实现「按住连续调节」（不是长按检测）：r_ae_tick 每 ~4.17ms、r_ag_tick 每 ~133ms 一拍，减的是 tick 不是常量 1。细节见 references/video-project-ae-key-reset.md。官方 key_remove_shakes.v（hdmi_tx 内部例化，消抖 EDID 读取按键）在本工程是**死代码**：顶层 hdmi_tx 传 `.I_key_in(1'b0)`（输入恒0）+ 输出 S_key_edid_read_trig 声明后被赋值但无人引用（悬空）。机制跟自写 debounce 不同——它是「按下沿+延时判断」（检测下降沿→固定延时 100000 时钟→延时结束看按键还按着就输出脉冲），输出是**脉冲**；自写 debounce 是「连续稳定计数」（按下持续 20ms、中途松手清零重数），输出是**电平**。复用官方消抖注意它输出脉冲，接 key_hold（要电平）得用自写 debounce。消抖时钟域跟着目标模块走：key_remove_shakes 用 HDMI 像素时钟服务 hdmi_tx，搬去 ae_set 前端要接 S_24m_clk（24MHz）不是照抄 HDMI 时钟。

## 按键/SW 重构进主工程（用户已定稿，别重新推倒）
主工程按键重构的最终方案，动手前读这条对齐，别重头重新设计：
- **按键分工**：KEY1=复位（走 I_rst_n，引脚 D5，正好补「板子无复位键」的坑）、KEY2=加、KEY3=减、KEY4=算法切换（预留）。故 I_button 从 [3:0] 改成 **[2:0]**（KEY1 不占 I_button：I_button[0]=加/A9、[1]=减/B9、[2]=保留/C7）。
- **SW 模式决定「加/减调曝光还是增益」——这是「选目标」不是「选动作」**。别把验证工程的 mode 门控生搬硬套进主工程：验证工程门控是区分「短按切算法 vs 长按递增」两个不同动作；主工程 inc/dec tick 始终是「加/减」脉冲，SW 模式决定作用在曝光还是增益，判断放 **ae_set 内部**（I_mode），顶层不门控。
- **ae_set 重构方向**：删掉内部按键打拍 + tick 计时器，只接收「inc_tick/dec_tick + I_mode」，收到 tick 按 I_mode 调曝光/增益，值变了输出 O_ae_req。检测（debounce/key_hold）与计算（ae_set）彻底分离。
- **KEY2/KEY3 都是长按**（key_hold 连续调节），不需要 key_pulse（短按边沿）——key_pulse 只在以后 KEY4「按一下切算法」才用。
- **例化进主工程三注意**：①顶层 design_top_wrapper **没有 parameter**，debounce/key_hold 的 CLK_FREQ/DEBOUNCE_MS/HOLD_MS 直接写字面量 `.CLK_FREQ(24_000_000)`；②复位用 **S_rst_n**（=PLL 锁定）不是 I_rst_n（I_rst_n 只接 PLL reset）；③内部信号用 S_ 前缀（S_mode/debounced/inc_tick/dec_tick），跟主工程命名规范一致。
- **曝光快/增益慢差异会被抹平**：原 ae_set 内部曝光 tick 4.17ms 快、增益 133ms 慢；改用外部 key_hold 后若两个 key_hold 同 HOLD_MS，曝光和增益变同速。不要求差异就统一一个 HOLD_MS；要求就后续让 HOLD_MS 随 mode 动态选。
- **调试期占用原规划功能必须留恢复后路（用户会点名盘查「别把 SW 搞乱」）**：调试只许改「显示/指示层」（数码管 case、LED），按键/SW 的调节功能和门控一律不动；每轮占用把「原规划 vs 当前调试版」对照明细写进项目里的规划文档（表格式），恢复动作收敛到单一位置（如数码管 case 一处 + 诊断端口移除），写完明细再继续改，避免多轮调试后恢复路径散落。盘查时直接 grep 顶层把每个拨码/按键的全部用途列清单对照，逐一标注「未动 ✓」或「调试占用」，别凭印象。

**SW3/SW4 四模式语义（定稿，以 OSD 代码注释为准——作品文档拨码表把 10 写成背景检测是错的；文档与代码矛盾时以工程代码为准）**：00=原样+自动曝光（KEY4 短按切算法、长按切自动/手动）、01=背景检测涂白、10=外接框+质心、11=区域填充（KEY4 短按切显示三态）。SW3 只是模式位不再是手动/自动开关：SW34=00 时手动/自动由 KEY4 长按切的内部状态决定（复位默认自动），ae_set 的 I_auto_en = SW34=00 && 状态自动。

**KEY4 长短按分离（定稿交互，改按键语义前先对齐本条）**：短按=切算法（既有语义不动）、长按 200ms=切一次自动/手动（一次长按周期只切一次）。长短按分清根治=短按判定改「释放沿 + 按住未满 HOLD_MS」：按下沿起计数、满 HOLD_MS 置 held，释放沿 held=0 才发短按脉冲——长按开头那次按下沿被 held 吞掉（mode 门控只能隔离动作、消不掉触发本身）。给按键新增功能优先挂长按语义、短按既有功能不动（用户拍板 KEY4 语义时明确反转过「短按=自动/手动、长按=算法」的提议）。

## 下载成功但程序不跑
下载报成功（Downloading succeeded）但板上现象不对（LED 全亮/不动）时，先别改代码：验证 bit 内容（读 `*_Runs/best_result/*_phy.area` 引脚报告，确认 LOCATION 真编译进去了）、分析 `prj/log/td_*.log` 时间线（只 `import_db` 无 `Run phy_1 success` = 没重新编译、下的是旧 bit）；判断「编译成没成」读日志末尾的 `Run syn_1 success` / `Run phy_1 success`，别被日志中间的 ERROR 吓到——那些多是改代码过程中历史版本的残留报错，或官方加密 IP/例程自带的 `undeclared symbol 'open_nXXX'`、`'**'`、demosaic.v 嵌套注释 warning，都无害（TD 自己容忍）。定位用户代码语法错误可用 iverilog 单独编译新增模块（`iverilog -g2012 -Wall -o /tmp/t.vvp key/*.v ae_set.v`），比整工程重编快且能隔离出真错误。**验证「依赖还没写完的模块」的语法**：用 stub 占位缺的模块（如 gray_convert 还没写，就写 `module gray_convert(input [95:0] I_tdata, output [95:0] O_tdata); assign O_tdata=I_tdata; endmodule` 到 /tmp），编译后只看 `syntax error`——只报 `Unknown module type`（依赖未解析，说明自身语法 OK），报 `syntax error` 才是真语法错。改 CRLF/tab 混杂的 .v 文件多处插入时，用 execute_code 行级编辑（按检测到的换行 split，子串匹配定位插入点，join 写回）比 patch 工具可靠——patch 的模糊匹配在 CRLF 文件上会误匹配（如把 `.key_tick` 模糊成 `.key_pulse`）。但 execute_code 行级编辑的**定位锚点必须唯一**：用 `.I_ag`+`//增益值` 定位会同时命中 uicfgcs500（摄像头 I2C 配置）和 hdmi_mixer 两个例化（都有 `.I_ag` 和「增益值」注释），把端口误插两处 → 综合报 `cannot find port 'I_algo_mode' on this module`。改完 grep 该端口/信号出现次数核对（如 `.I_algo_mode` 应只出现在 isp_top + hdmi_mixer 两处），发现多插就按上下文定位删除（误插行往往下一行是别的端口如 `.O_cam_scl`）。、区分 JTAG SRAM（掉电丢失）vs Flash 固化（断电重启生效）。灯全亮 = FPGA 引脚默认高 = 配置没生效。完整排查路径 + WSL 调 PowerShell 查 Windows 设备命令见 `references/anlogic-download-debug.md`。

**下载后「OSD 正常 + 视频画面黑」→ 先按复位键 KEY1（DDR 校准偶发失败，不是代码问题）**：现象是 OSD 文字/Logo 正常（说明逻辑下板运行、HDMI 输出通路和时钟都对），但摄像头视频画面黑——视频数据走「摄像头→DDR 帧缓存→HDMI」，DDR 没数据。根因是**上电时片内 DDR 校准偶发失败**（下载成功 ≠ DDR 校准成功，下载只保证 bit 配进 FPGA，DDR 还要单独上电校准）。处理：按复位键 KEY1 触发完整复位（PLL 重锁 + DDR 重校准 + 摄像头重初始化）大概率直接恢复。注意「拔电源 10 秒」反而不如「按 KEY1 复位」立竿见影——复位键走的是干净的完整复位，断电重上电的时序未必每次都干净。三种黑屏要区分：持续黑屏（连 OSD 都没）= 下载/配置问题；OSD 在视频黑 = DDR 校准偶发失败（按复位）；偶发黑屏一下再恢复 = 时序违例（见 timing.sdc 那条）。跟「下载成功但功能不对」那条区别：那条是逻辑没跑，这条是逻辑跑了但 DDR 数据没起来。

## 下载成功但功能不对（灯不流水/不跑）诊断
位流下载成功（日志 "Chip validation success" + "Downloading succeeded"）≠ 功能正常。按此顺序排查，先确认代码本身没错再怀疑硬件：
1. 引脚约束对照官方例程 `2_Example/0_cnt1s/cnt1s.adc`（clk=C4、LED=D10/E10/C6/D6、rst_n=D5），别信 TD 随机分配。
2. LED 极性：HX1P35A 的 4 个独立 LED 是高电平点亮，双色 LED（复用数码管）才是低电平点亮——别混淆（见 `references/hx1p35a-board-pins.md`）。
3. 复位键：rst_n 低有效，KEY1 按下/被拉低会把 led 锁在复位值（如 4'b1000=LED4 常亮）不流动。先松开 KEY1，按一下给复位脉冲再松开看是否恢复。
4. 时钟源：C4 的 50M 晶振若不起，分频计数不跑（较少见，晶振一般好）。
诊断关键一步是问清「灯的具体现象」——哪个灯常亮/全灭/在闪——据此定位是复位锁死、时钟没起还是极性反了，别急着让用户改代码。

## OSD 叠加 Logo（基础任务第 4 条「必须含安路 Logo」）
官方 lab_ex3 的 `anlogic_logo_rom.v`（6400 行 case 表）就是安路 Logo 像素数据，直接复制进主工程 hdl_source_clean/ 用，别自己造。结构：`module anlogic_logo_rom(input [14:0] I_addr, output reg [24:0] O_pixel)`，**稀疏存储**（只存非透明像素约 6400 个，没存全透明），O_pixel[24]=有效标志、[23:0]=24 位 RGB；Logo 是 160×160 放画面左上角(0,0)。

叠加在 hdmi_mixer.v 的 DEBUG_MODE=0 else 分支，共 6 处改动：①信号声明（S_x_1d/S_x_2d/S_y_1d/S_y_2d 坐标打拍 + S_osd_hit/S_osd_color/S_logo_addr/S_logo_pixel）②localparam LOGO_X/Y/W/H=0/0/160/160 ③例化 anlogic_logo_rom ④坐标打拍（S_x/S_y 跟 S_video_data_2d 一起打两拍——**坐标也要打 2 拍跟像素数据对齐，否则 Logo 错位 2 像素**）⑤组合逻辑叠加 always @(*)（坐标在 Logo 区域→S_logo_addr=(S_y_2d-Y)*W+(S_x_2d-X)→查 ROM→S_logo_pixel[24] 则 hit+取 [23:0] 颜色）⑥输出 `S_osd_hit ? S_osd_color : S_video_data_2d`。文字叠加（人员名单/时间/署名）用 lab_ex3 的 osd_char_lib.v 字符库 + F_osd_char16_row 函数，但基础任务只要求 Logo，文字是可选加分。

**OSD 中文文字叠加（人员名单/时间/署名）**：字符库 osd_char_lib.v 结构是 `module osd_char_lib(input [7:0] I_char, input [3:0] I_row, output reg [15:0] O_row_bits)`——16×16 点阵，I_char 用 ASCII 码（0x41~0x5A=A~Z、0x30~0x39=0~9 七段数码管风格、0x3A=冒号），另有两个中文「安」0x80「路」0x81；**缺减号/空格/其他中文**。要显示中文名字（人员名单/署名）得自己造 16×16 中文字模：用 Python + PIL + **simhei 黑体**渲染二值化生成（主工程 osd_cn_char.v 的现有字模就是 simhei 黑体生成的——实测反推「李」字模匹配度 simhei 86.7% > Noto Sans CJK 82.8%，用 Noto 会导致新字和旧字风格/大小不一致；字体 `/mnt/c/Windows/Fonts/simhei.ttf`，渲染参数字号 16、y 偏移 0、阈值 128 直接渲染；WSL 里 `/usr/bin/python3` 跑脚本），写成独立模块 osd_cn_char.v（I_idx 索引 0~N → 16 行点阵），**别污染官方 osd_char_lib.v**。脚本见 `scripts/gen_cn_font.py`（比 PCtoLCD2002 省事，WSL 直接跑，改 chars 字符串即可加字）。

**字模字体可能「多批不统一」——加新字前先反推旧字字体，别假设全是同一种**：osd_cn_char.v 的现有字模是分多批生成的、字体未必一致（实测：名单「李」反推 simhei 86.7%，但「曝光值增益」那批「曝」反推 wqy-microhei 85.2% > simhei 79.3%——两批字体不同，是历史遗留）。新字和旧字并排显示（如顶部算法名「灰度」与右上角「曝光值」同处 Y=10 那一行）时字体/字号不一致会被放大暴露。加字前先硬编码旧字模 16 行 hex、逐位比对各字体各字号渲染结果算匹配度，确定旧字到底什么字体，再定新字字体。（补实测 2026-10-13：算法名批次「边」「缘」= simhei 100%；而「动」索引 37 属「自动/手动」批次、非 simhei 仅 55.9%。故「运动」算法名要新增「动」42、不复用 37，否则「运」(simhei) 与「动」(非simhei) 并排大小明显不一。判断哪批字模跟哪个字体对齐时，直接跑 gen_cn_font.py 对候选字逐位比匹配度最可靠。）

**「字不是一个大小」要分清三维度：字体 / 字号 / 笔画密度，别只纠结字体**（本次就栽在这——反复在 simhei/wqy-microhei/Noto 里打转，被用户提醒「你是不是忘记注意字体的大小了」）。量化三个指标：字形外框（高×宽=非空行列数）、字号（16px→外框 14×14、15px→13×13）、笔画像素数（密度）。复杂字（「曝」102 笔画）比简单字（「灰」58）即使同字体同字号也视觉上「胖一圈」，用户会感知成「大半个字」。强行视觉对齐的唯一办法是「降字号补偿笔画密度」：把笔画密的那批字用小一号字号渲染（曝光值 16px→15px），让视觉重量拉平。定位脚本：解析 osd_cn_char.v 各索引字模、量高/宽/笔画数分组对比（索引标签 4'd 和 5'd 都要匹配到；每个块会多解析一个 default 行的 16'h0000，量尺寸时取前 16 行忽略它）。

**复用已有字模索引会带入该字的历史字号**：加新算法名时若复用 osd_cn_char 里已有的字（如「二值」复用「值」=索引18），而该字之前在某批被降过字号（「曝光值」批降到 15px），复用时会和新加的字字号不一致（「二」16px vs「值」15px 差 1px）。要么新增独立字模（别为省一个字耗尽 5 位索引空间，最多 31 字），要么接受 1px 差异（笔画疏密会互相抵消、肉眼多半看不出，让用户下载后扫一眼再决定）。\n\n文字叠加逻辑跟 Logo 同套路（坐标判断→查字模→bit 判断→覆盖），关键计算：`(S_x_2d - TEXT_X) >> 4` 得第几个字符（÷16）、`(S_x_2d - TEXT_X) & 12'hF` 得字符内列（模16，**别用 `[3:0]` 位选，见陷阱**）、`S_y_2d - TEXT_Y` 得字符内行、`S_txt_bits[15 - S_txt_col]` 取点阵 bit（bit15 最左）。字符码用 case(S_txt_idx) 查。输出优先级 Logo > 文字 > 原图（`if(S_osd_hit) ... else if(S_txt_on) ... else 透传`）。右下角放文字：TEXT_X=1280-字数*16-边距、TEXT_Y=720-16-边距。

**多行文字（人员名单/完成时间/署名三行）扩展套路**：多行 = 「行号定位 + 字符索引 + 混合编码」三层。①行号由 S_y_2d 判断（三行 Y 坐标不同，如 640/664/688，每行 16 高 + 8 行距）②字符索引 `(S_x_2d - TEXT_X) >> 4`（该行第几个字符）③字符码用 `case(行号)` 嵌套 `case(字符索引)` 查（人员名单全中文、完成时间数字+中文混、署名中文）。字符码混合两类库：中文用 osd_cn_char 索引（0x00~0x0B：0=李 1=江 2=涛 3=陈 4=锐 5=张 6=展 7=鸣 8=年 9=月 10=日 11=、），数字用 osd_char_lib 的 ASCII（0x30~0x39）——叠字前先按字符码范围分流到对应字符库查点阵（字符码 <0x10 查 osd_cn_char、≥0x30 查 osd_char_lib）。S_txt_idx 位宽要容得下最长行（11 字符要 [3:0] 不是 [1:0]）。

**多行文字各行字符数不同 → X 范围必须按行区分 + 加区域使能（否则短行右边多一串「李」/竖线）**：多行文字各行字符数常不同（人员名单 15 字符、完成时间 10 字符、署名 3 字符），若 X 范围判断统一用最长行字符数（`15*CHAR_W`），短行超出的字符位置（完成时间第 10~14 字符）查字符码表落到 default=8'd0（「李」）→ 文字右边多一串「李」或竖线；且 S_txt_on 无区域使能时，坐标在文字范围外 S_txt_col 保持默认 0 也可能误点亮。修复：加 `S_txt_area` 使能信号，**每行单独判断自己的 X 字符数范围**（行0 `15*CHAR_W`、行1 `10*CHAR_W`），`S_txt_on = S_txt_area && S_char_bits[15-S_txt_col]`。S_txt_area 跟行定位放同一个 always @(*) 组合块算，S_txt_on 打拍时与 S_char_bits 同属第 N+2 拍组合结果、对齐无额外拍。另：这类「信号联动 + 机械改动 + 顺手删行/改注释」的 bug，用户偏好我**直接改**（原话「你检查出错误，直接帮我修改」），别让他自己一步步改（容易漏，见下一条「多信号/参数联动改动必漏改」）。

**OSD 显示动态数值（曝光/增益值实时显示，随按键变）**：跟固定文字不同，数值是动态变化的。套路：①顶层把 ae_set 的输出 S_ae/S_ag 传进 hdmi_mixer（加端口 `input [15:0] I_ae/I_ag`，顶层例化 `.I_ae(S_ae)/.I_ag(S_ag)`）②hdmi_mixer 里例化 2 个 bin2bcd（组合逻辑，S_bcd_ae/S_bcd_ag）把二进制转 4 位 BCD ③文字叠加里数字字符码用 `8'h30 + S_bcd_ae[15:12]` 这种「0x30 + BCD 的 4 位」直接得 ASCII 数字码（bcd[15:12]=千/[11:8]=百/[7:4]=十/[3:0]=个，值 0~9，+0x30 即 0x30~0x39）。**标签别用 osd_char_lib 的 ASCII 字母（A=0x41/E=0x45/G=0x47）**——osd_char_lib 里字母 A~Z 是「小点阵」（笔画只占中间几行、宽度窄），数字 0~9 却是「7 段数码管」风格占满 16×16 的大数字，字母和数字混排**大小明显不一致**（用户踩过：AE/AG 标签比数字小一圈，还被要求换中文）。标签用中文「曝光值」「增益值」：中文字模和数字都是 16×16 满格点阵、大小统一，也符合用户要中文标签的偏好。造「曝光值增益」5 个字（「值」字复用）加进 osd_cn_char 索引 16~20（16=曝 17=光 18=值 19=增 20=益）。显示位置用户要**右上角**（不是 Logo 下方）：8 字符 128 宽，`AE_AG_X=1280-128-20=1132`，曝光行 Y=10、增益行 Y=34（原方案 Y=170/194 放 Logo 下方被用户否了）。**osd_cn_char 索引超过 15 必须扩 I_idx 位宽**：I_idx 声明 [3:0]（4 位，最大 15）时，case 标签 `4'd16`~`4'd20` 会被截断（16=10000 是 5 位，4 位截掉最高位变 0~4）→ 查错字模 + iverilog 报 `Numeric constant truncated to 4 bits`。修复：I_idx 改 [4:0]、case 标签写 `5'd16`~`5'd20`、hdmi_mixer 例化 `.I_idx(S_txt_char[4:0])` 同步改（原来接 [3:0]）。这样长按 KEY 调曝光/增益时 OSD 数字实时变。跨时钟域：S_ae/S_ag 等配置信号是 24MHz 域，HDMI 像素时钟域（75MHz）读它们属于跨时钟域，**必须在 hdmi_mixer 入口打两拍同步**（`S_ae_1d <= I_ae; S_ae_2d <= S_ae_1d;` 后下游全用 S_ae_2d），不能裸读——裸读会被时序工具当跨域路径报 SWNS 违例（budget 只有相邻时钟沿差 ~0.65ns）。慢变化信号跨域不是「直接读没问题」，而是「必须打两拍再读」（见「时序违例诊断」条）。

**最终格式「曝光值(AE):1990」「增益值(AG):0080」——括号和 AE/AG 缩写也要大字模**：用户要中文标签后加括号英文缩写（原话「改成曝光值（AE）:1990」），且 AE/AG 也要跟中文一样大（原话「AE/AG 也跟中文一样大」）。两个追加动作：①**括号 () 也要造字模**（字符库里没有），用 simhei 渲染全角括号 U+FF08「（」/U+FF09「）」加进 osd_cn_char 索引 21=「(」22=「)」——**别用 DejaVuSansMono 渲染半角 ASCII 括号**（半角弧线会落在 16×16 格子左边列 3~6、开口朝右，导致「（自动）」里两个字不在括号正中，实测踩坑后改 simhei 全角、弧线正确落在列 10~13 右边、开口包住后面的字）；②**AE/AG 缩写不能再用 osd_char_lib 的小字母**（A~Z 是小点阵，跟中文/数字混排大小不一致），A/E/G 也要渲染成 16×16 大字模加进 osd_cn_char 索引 23=A/24=E/25=G，字符码查表里 AE 用 8'd23/8'd24、AG 用 8'd23/8'd25（不是 8'h41/8'h45/8'h47）。生成脚本仍是 `scripts/gen_cn_font.py`，改 chars 字符串即可（括号用 DejaVuSansMono 保证笔画撑满、中文用 simhei 黑体）。

**字符码分流判断的位宽坑（中文索引扩过 15 后必踩）**：字符码分流「中文 vs ASCII」用 `S_txt_char[7:4]==4'd0`（高 4 位为 0 判中文）——中文索引 0~15（0x00~0x0F）时高 4 位确实都是 0，但索引扩到 16~25（0x10~0x19）后高 4 位变成 1，这些新增中文（曝光值/括号/A/E/G）被误判成 ASCII 去查 osd_char_lib（没这些字符 → 显示空，现象「右上角只剩数字和冒号，中文和字母全没」）。修复：分流判断改成 `S_txt_char[7:5]==3'd0`（高 3 位为 0），因为中文 0~25 都 <0x20 高 3 位全 0，而 ASCII 0x30~0x3A 高 3 位是 001 能区分开。教训：**字符码分界位宽要按最大索引算，索引上限从 15 扩到 25 时分界位从 bit4 移到 bit5**，改索引范围时同步重核对分流判断的位宽。

**这条「高 3 位 == 0」判断在索引继续扩到 32（0x20）时也会失效，最终方案是 bit7 标志位**：索引加到 32/33（「帧」「号」，0x20/0x21）时高 3 位 = 001，跟 ASCII 数字区 0x30~0x39 的高 3 位（也是 001）撞车，「高 3 位 == 0」彻底无法区分。彻底解决：**中文字符码 = 0x80 + 索引（bit7=1 判中文），ASCII 直接用 ASCII 码（bit7=0）**，分流判断 `S_txt_char[7]`。配套改动三处：①osd_cn_char 的 I_idx 从 [4:0] 扩到 [5:0]（32 个索引用满，6 位最多 64 中文），case 标签新索引写 6'd32/6'd33；②hdmi_mixer 例化 `.I_idx(S_txt_char[5:0])`（原来 [4:0]）；③**所有现有中文 case 字符码 0~31 全部改成 8'h80+索引**（约 30 处，机械改动，改完重读一遍逐个核对，别漏——漏一处那个字就显示成空白/错字）。bit7 方案一劳永逸：以后加 Sobel/帧差法/跟踪的算法名和标签只动 osd_cn_char 加字模，别处零改动，比「每次加索引就移一位分界」可持续得多。

## 图像处理算法插入（灰度/二值化/Sobel，基础任务第 2 条）
ISP 数据流里 AWB 之后是算法插入点。关键数据格式和约束（写 gray_convert/二值化/Sobel 前必读）：

- **96 位 = 4 像素 × 24 位 RGB888**：`awb_O_tdata` 是 96 位，拆 4 像素，每像素 24 位 = `{R[7:0], G[7:0], B[7:0]}`（R 高 8 位、G 中 8 位、B 低 8 位）。像素 0 在 [23:0]（R=[23:16] G=[15:8] B=[7:0]）、像素 1 [47:24]、像素 2 [71:48]、像素 3 [95:72]。下游 data_96bit_to_128bit 转 128 位。

**96↔128 打包/解包格式（data_96bit_to_128bit / data_128bit_to_96bit，DDR 存帧/存背景要用，2026-10-18 补）**：96 位和 128 位最小公倍数 384，所以「4 个 96 位 = 3 个 128 位」滑动窗口打包（⚠️ 不是「5 拍拼 128 位」）。打包（cnt 每 valid +1、0~3 循环）：cnt=1 输出 `{上一拍96, 当前拍96[95:64]}`、cnt=2 `{上一拍96[63:0], 当前拍96[95:32]}`、cnt=3 `{上一拍96[31:0], 当前拍96}`、cnt=0 不输出 → 128 位流是 3/4 拍有效、有空洞。解包（data_128bit_to_96bit 逆运算，3 个 128 位拆 4 个 96 位，输出 4/4 拍连续、正好填补输入空洞）：A=128位1[127:32]、B={128位1[31:0],128位2[127:64]}、C={128位2[63:0],128位3[127:96]}、D=128位3[95:0]（D 缓存一拍、在输入空洞拍输出）。⚠️ **解包输入必须是「3/4 拍有效」——读侧 FIFO 的 re 绝不能直读 1'b1（2026-10-19 实战，横白线根因）**：背景读 bg_read 读侧原来 re=1'b1 直读，把「3/4 拍有效」读成「4/4 拍连续」，解包 S_cnt 每拍 +1、第 4 个 96 位 D 永远没机会在空洞拍输出 → 背景每 3 个 128 位只输出 3 个 96 位（缩水 1/4），和当前帧（230400 个 96 位）对不上 → 横白线约 18 根均匀分布。修复：读侧 re 接「当前帧 128 位 valid」（顶层 S_ISP_O_tvalid，本身就是 3/4 拍节奏），背景读跟当前帧同节奏、解包相位自动对齐。关键：DDR 存的是「连续 128 位」（打包空洞被 video_in 丢弃），所以读侧必须人为制造 3/4 节奏，不能直读。另见 `references/ddr-clock-resource-audit.md`（usr_clk 半速、资源账、soft_fifo 时序）。
- **灰度化接口约定**（gray_convert.v，纯组合逻辑）：`module gray_convert(input [95:0] I_tdata, output [95:0] O_tdata)`，灰度公式 `gray = (R>>2)+(G>>1)+(B>>2)`（= R/4+G/2+B/4，移位省乘法器，人眼对绿最敏感权重 1/2），4 像素各算各的，输出每像素 R=G=B=gray 拼回 96 位。边界：纯白 255,255,255 → 63+127+63=**253**（不是 255，移位除法舍小数，固有舍入不是 bug）。
- **二值化**（binary_convert.v，同款接口纯组合逻辑）：先算灰度 gray，再 `gray > THRESHOLD ? 255 : 0`（localparam THRESHOLD=8'd128，阈值先固定以后可调）。条件选择用 `always @(*)` 组合块 + if-else（符合用户「if-else 不用三元」偏好；这也是用户第一次接触「always 组合逻辑块」——要讲清 `reg` 声明 + 阻塞赋值 `=` 是组合逻辑、不是时序寄存器）。边界：`>` 严格大于，灰度恰好 128 判黑、129 判白；testbench 专门验证这个临界（构造灰度=128：R=4>>2=1、G=254>>1=127、B=0）。输出每像素 R=G=B=255 或 0 拼回 96 位，case MUX 加 3'd2 分支、algo_mode_sel 的 ALGO_NUM 改 3、OSD 算法名 case 加 3'd2（「二值」二字，需新增「二」字模、复用「值」索引18）。
- **二值化阈值可调（threshold_set + S_mode 第 3 种模式）**：固定阈值 128 对多数场景不合适（画面大面积黑/白，因为阈值切在灰度密集区），做成可调才有实用价值、也是加分点。完整链路：①新建 `key/threshold_set.v`（`module threshold_set(input clk, rst, inc_tick, dec_tick, enable, output reg [7:0] O_threshold)`，enable 时才调，初始 128、每 tick ±8 粗调、范围 0~255，localparam STEP=8'd8 方便改步进）；②复用 S_mode 的「选目标」机制——S_mode 从「0=曝光 1=增益」扩成「0=曝光 1=增益 2=阈值」（第 3 种 S_mode=2'd2，即 SW2=1 SW1=0），threshold_set 的 I_enable 接 `(S_mode==2'd2)`，KEY2/KEY3 长按 tick 在模式 2 下调阈值；③数码管按 S_mode 切换显示内容（`case(S_mode) 0→S_bcd_ae 1→S_bcd_ag 2→S_bcd_threshold`，不再固定显示曝光+增益）；④阈值 8 位转 BCD 前先 `{8'd0, threshold}` 扩成 16 位喂 bin2bcd；⑤OSD 右上角增益值下面加「阈值:xxx」行（Y=58），只在 `S_algo_mode_2d==2'd2`（二值化）时显示，6 字符 = 阈(索引31)+值(18)+冒号+百十个位；⑥字模「阈」新加进 osd_cn_char 索引31。binary_convert 阈值从 localparam 改成 input 端口 `I_threshold`（**端口不能声明成 reg，用 `input wire`**；别画蛇添足写 `reg THRESHOLD = I_threshold`——reg 声明时只能初始化常量，且直接拿输入端口比较即可，多绕一层还报错）。
- **算法模块 + MUX 必须纯组合逻辑、不打拍**：isp_top 里 AWB 之后插 gray_convert + `case(mode)` MUX 选原样/灰度。不打拍原因——tlast 从 AWB 直接透传到 O_tlast，data_96bit_to_128bit 内部已打拍；若算法/MUX 打拍数据而 tlast 不动，就错位一拍 → 黑屏（同「打拍后 de/vsync 必须补拍」的坑）。MUX 用 `case(mode)` 不用三元（用户偏好：加二值化/Sobel 只增 case 分支）。
- **算法模式控制信号跨时钟域打两拍**：mode 由 KEY4（24MHz 域）触发，isp_top/hdmi_mixer 在像素时钟域，读 I_algo_mode 前打两拍同步（`algo_mode_1d <= I_algo_mode; algo_mode_2d <= algo_mode_1d;`）再喂给 case MUX 和 OSD 字符码查表。慢变化控制信号跨域打两拍防亚稳态。
- **KEY4 切换框架**（algo_mode_sel.v，放 key/ 目录）：`module algo_mode_sel(input clk, rst_n, key_pulse, output reg [2:0] mode)`，每按一次 mode+1、到 `ALGO_NUM-1` 回绕（localparam ALGO_NUM=2，当前 0=原样 1=灰度；加二值化/Sobel 只增 ALGO_NUM + isp_top case 分支 + OSD 算法名 case 分支）。KEY4 用 key_pulse（按下沿脉冲，按一下切一次），不是 key_hold（长按）。OSD 顶部居中显示算法名：加第 5 行（S_row_idx 扩 [1:0]→[2:0]，ALGO_X=(1280-2*16)/2=624、ALGO_Y=10），字符码用嵌套 `case(mode)` 里再 `case(字符索引)` 选字模。

## 帧号显示 / 处理延迟可视化（高阶挑战(3)）
「处理延迟可视化」的最简实现 = **帧计数器 + OSD 帧号显示**（帧号一直跳，证明「采集→处理→显示」流水线逐帧实时跑、没卡死，比「帧号滚动」直观抓分，一天搞定凑及格线）。实现要点：
- **帧计数器零新增信号、零改顶层**：hdmi_mixer 已有 I_video_user（来自 VTC 的 O_vtc_user，每帧起始一个时钟周期的脉冲），直接用它在内部 `else if(I_video_user) S_frame_cnt <= S_frame_cnt + 1` 计数（坐标跟踪块早就在用它归零 S_x/S_y，别另找帧同步信号）。
- **帧号转 BCD 用现成 bin2bcd，但它是 16 位进 4 位 BCD 出、只支持 0~9999**：所以帧号计数器用 14 位、在 9999 处回绕（不是 65535——超 9999 显示错乱）。例化 `.bin({2'd0, S_frame_cnt})`（14 位补 0 凑 16 位）。
- **OSD 加「帧号:xxxx」行**：S_row_idx=6（[2:0] 三位够，现在用到 6），7 字符 = 帧(索引32)+号(33)+冒号+4 位数字。**帧号常显**（定位条件不加 S_algo_mode_2d 判断，任何模式都显示——它是「系统在跑」的证明，不是算法参数）。
- 帧号 4 位 @ 60fps 约 166 秒回绕，现场演示够用；要 5 位需把 bin2bcd 扩成 5 位 BCD（20 位输出）。真正进阶的「延迟可视化」是测输入 SOF→输出 SOF 的时钟周期差（跨时钟域），但先做帧号版凑及格线。
- **帧号与阈值的位置：帧号靠上、阈值靠下**（用户实测后要求调换）。右上角从上到下 Y=10 曝光 / 34 增益 / 58 帧号（常显）/ 82 阈值（二值化才显示）。原因：阈值只在二值化模式显示，若阈值在帧号上面，非二值化模式下中间空一行；帧号常显必须紧跟增益值。行定位块里 S_row_idx 逻辑行号不变（帧号仍=6、阈值仍=5），只换 Y 范围——行号和物理位置解耦，字符码查表 case(S_row_idx) 一处不用动。

## Sobel 边缘检测（第 4 个算法，基础扩展(1)，展示效果最好）

原理（用户问「原理」时按这个讲，逐层递进）：边缘 = 灰度值跳变最剧烈处（物体轮廓）；Sobel 用「梯度（变化率）」量化跳变，本质是对灰度图求导，两个 3×3 卷积核——Gx（左右差分，检测**竖直**边缘）、Gy（上下差分，检测**水平**边缘）。**卷积 = 拿 3×3 模板盖章、9 格逐格相乘再相加**；核的正负号做了「右边和−左边和」的抵消，抵消掉相同部分剩下的就是变化量（中间行/列权重 2 = 离中心近贡献加倍）。幅值 = |Gx|+|Gy|（硬件省资源的 sqrt 近似）> 阈值 → 白(255)=边缘，否则黑(0)=非边缘 → 黑底白线二值图（输出是纯黑白，不是「灰底」——用户容易把「输入是灰度图」和「输出」混一起，要纠正：没跳变是黑不是灰）。**先灰度化再做**：梯度只对标量（一个数）定义，RGB 是三个数；边缘=亮度突变、颜色对找边缘无用，先合成灰度省 3 倍算力且语义清晰（复用已有 gray_convert 输出，别重复灰度化）。

**Scharr 算子（Sobel 核的旋转不变升级，已实现 2026-10-17）**：Sobel 核 [1 2 1] 对横/竖边缘响应强、但对 45°/135° 斜方向偏弱（有方向偏差）；Scharr 核 [3 10 3] 各方向响应一致（旋转不变性）。硬件代价小——乘常数用移位加法（3x=2x+x、10x=8x+2x），不引入乘法器、不占 ERAM。**它只解决「斜线 vs 横竖线」的方向偏差，不解决「水平 vs 垂直」不对称（后者是 write-first bug，见上）；也不让横竖更清晰（横竖 Sobel 已稳）**。

**⚠️ Scharr 实现三件事（2026-10-17 实测）**：①**位宽整体 +1**——系数 [3 10 3] 使 gx/gy 幅值最大 4080（Sobel 的 4 倍），gx_pos/gx_neg 从 11bit→12bit、gx_s/gy_s 从 12bit→13bit、sobel_mag 从 11bit→13bit，quant_dir 的 ax/ax2/ay/ay2 同步 +1；②**mag8 右移从 >>3 改 >>5**——正好抵消 4 倍增益，mag8 量纲和 Sobel 完全一致（理想阶跃都=127 满量程），**所以阈值不用改**（原来 79 还是 79，噪声也不会更容易过阈值——噪声的 mag8 在 Scharr 下和 Sobel 下都是 Δ_noise/2）；③**⚠️ 溢出坑：|gx|+|gy| 最大 4080+4080=8160 超 12 位上限 4095，两个 12 位直接相加会溢出（强边缘爆掉变黑）**——必须显式扩 13 位：`sobel_mag = {1'b0,|gx|} + {1'b0,|gy|}`。原 Sobel 的 11 位相加碰巧不溢出（1020+1020=2040<2047），Scharr 必踩，改的时候先补这个再下板。

**⚠️「竖线比横线粗」是显示器面板物理特性，不是算法（2026-10-17 诊断铁律）**：数据上横竖都是严格 1 像素（Canny NMS 输出每像素 1bit），显示器上竖线显粗是面板物理——像素非正方形（横向比纵向宽）、LCD 子像素横向排列（竖线左右边界跨子像素间隙、显更宽）、非整数倍缩放（水平/垂直插值比例不同）。**判别铁律：旋转摄像头，若「粗」的方向跟着显示器物理方向变（不是图像内容方向变），就坐实是面板、不是代码**——别再往算法里找原因。答辩可主动说「数据是标准 1 像素细边缘，横竖粗细差是面板像素长宽比/子像素排列造成的，跟算法无关」，反而是理解物理显示的加分点。

**⚠️ 左边界伪竖线的屏蔽范围随阈值降低而扩大（2026-10-17）**：左边界伪竖线来自「高斯+Sobel 两层左邻居错位」（第 1 组 g0 左邻居读到上一行最右像素=垃圾值）。阈值高时只有第 1 组过阈值、`h_cnt_d6>=2` 够；**阈值降到 80 后弱伪边缘也过阈值、错位扩散到第 3 组（冒出 3 行断续竖线），要放宽到 `h_cnt_d6>=3`**。规律：阈值越低，左边界屏蔽组数要越多（别固守第一次调好的屏蔽值，改阈值后重看左边界）。

**⚠️「增益低 + 阈值低」是矛盾组合，别两头都不占（2026-10-17）**：用户想检测弱边缘（浅线），把增益从甜点 143 降到 111（降噪）又把阈值压到 80——结果增益低→弱边缘信号弱→需要低阈值，但低阈值又把「管道表面渐变」这类更弱的信号一起抓进来（一条管道画成好几行边缘）。**增益和阈值要同向走**：要么回甜点「增益 143 + 阈值 79」（增益高→弱边缘够强→阈值 79 稳定抓浅线、渐变到不了阈值），要么「增益 111 + 阈值 90~100」（保持低增益、阈值往上抬过滤渐变，代价是极浅的线漏检）。「想检测弱边缘必须 8x 增益 + 阈值卡噪声上沿」的甜点结论（见上）这里再次成立——**别降增益还想抓弱边缘，4x 放大不够、弱边缘掉阈值下**。

实现要点：
- **作为第 4 个算法塞进 KEY4 切换框架**：algo_mode_sel 的 ALGO_NUM 3→4；isp_top case MUX 加 `3'd3 : algo_data = sobel_data`（sobel_top 接 gray_convert 的 gray_data 输出）；OSD 算法名加「边」「缘」字模（索引 34/35，I_idx 已 [5:0] 够用）；mode 是 [2:0] 位宽不用动。一举两得：既交基础扩展(1)「边缘提取」，又把高阶(1)「多算法切换」从 3 个强化到 4 个。
- **Sobel 阈值独立、11 位（不能复用二值化阈值）**：梯度幅值 |Gx|+|Gy| 最大 = 1020+1020 = **2040**（每方向 max = 255+510+255），所以 Sobel 阈值范围 0~2040（11 位），二值化阈值是 0~255（8 位）语义范围都不同。参数：步进 **1**（精细调——用户实测要求：画面暗时 Sobel 有效阈值只在 24~72 这种小区间，步进 8 太粗一档跳 8 调不细、步进 1 才能一点点逼近；别按「0~2040 分 256 档」拍脑袋设步进 8，实际用的阈值区间很窄）、初始 256、S_mode==3（SW1=SW2=1 都拨向板框侧）调、数码管 4 位十进制显示（`{5'd0,thr}` 扩 16 位喂 bin2bcd）。新建独立 `sobel_threshold_set.v`（同 threshold_set 结构、位宽范围不同），别动已验证的二值化 threshold_set。**Sobel 的 OSD 阈值行和绿色文字跟二值化同款（用户要求）**：①hdmi_mixer 加 `I_sobel_threshold` 输入 + 例化 bin2bcd 转 BCD；②阈值行（Y=82）定位条件从 `==2'd2` 扩成 `==2'd2 || ==2'd3`、字符宽从 6 扩到 7；③阈值字符码按模式动态选 BCD 源——Sobel 显示 4 位（千~个位用 sobel_bcd）、二值化显示 3 位（百~个位用 binary_bcd、千位 S_txt_char=8'd0 走 osd_char_lib default 空字模补空），写法 `(S_algo_mode_2d==3'd3) ? 8'h30+S_bcd_sobel[15:12] : 8'h30+S_bcd_thr[11:8]`；④S_txt_color 绿色判断从 `==3'd2` 扩成 `==3'd2 || ==3'd3`。
- **line buffer 用「地址计数 + 读旧值」，别用移位寄存器（实测踩坑：移位寄存器导致边缘画面闪烁）**：2 条 × 320 深 × 32 位（1280 像素 ÷ 4 并行 = 320 组 × 4 像素 × 8 位灰度）。**移位寄存器方案的根本缺陷**：靠「固定深度 N，尾 = N 拍前 = 上一行」对齐，但 **ISP 数据流（demosaic→AWB→算法）行与行之间有消隐拍（tvalid=0）**，消隐期移位寄存器不动作，「N 拍前」对不上「上一行」→ 边缘图垂直错位，消隐拍数一抖动就闪烁（现象「边缘模式屏幕一闪一闪」）。**判断数据流有没有消隐的铁证：看官方参考模块的 line buffer 用什么**——demosaic 的 line_buffer_demosaic 用 BRAM + 读写地址计数器（addra/addrb 只在 valid 时 +1、消隐期地址冻结），这就是「数据流有消隐」的信号，照它做。**正确实现（reg 数组 + 地址计数 + 读旧值）**：`lb1[0:319]` 存当前行、`lb2[0:319]` 存上一行；写地址 waddr 只在 I_tvalid 时 +1（0~319 循环、tuser 归 0）、消隐期冻结；读地址 raddr 落后 waddr 一行（lock 在第一行结束 waddr==319 时才置位，之后 raddr 跟随 waddr 同步 +1）；每拍 `lb2[waddr] <= up; lb1[waddr] <= gray_4p;`（up = lb1[raddr] 读旧值——非阻塞赋值读本拍写之前的旧值，lb2 存 lb1 读出的上一行）。地址只在 valid 递增，天然对齐上一行、完全不受消隐影响。（顺带的 off-by-one：移位寄存器深度要 = 组数+1 即 321 才拿到「320 拍前」，但这条只对「无消隐连续流」成立，有消隐就彻底失效，别纠结深度，直接上地址计数。）两条 line buffer 串起来 → up/up2 分别是上一行/上上两行；垂直三行靠 line buffer、水平三列靠 r_prev_g3 缓存 + 打拍。前两行 up/up2 未填满，靠 cur_valid 屏蔽。

**⚠️ reg 数组 + 异步读 = distributed RAM = LUT 爆 slice（实测踩坑，综合直接失败）**：`wire up = lb1[raddr]`（组合逻辑异步读）只能综合成 distributed RAM（LUT 搭的），320×32×2 条 ≈ 2 万 bit 用掉约 1 万 LUT，加上原有逻辑直接 `ERROR: Design's slice number = 24737, exceeds the limit 21216`。**存一整行像素别用异步读 reg 数组。** 最终解法（实测通过）：**复用 demosaic 已验证的 `line_buffer_demosaic`（内部就是安路 BRAM IP `blk_mem_gen_demosaic` + 地址计数），级联 2 个 + 打拍对齐**——照搬 raw_matrix_3x3_buffer 的结构：`data0={I_tuser,gray_4p}`（33 位，line_buffer_demosaic 的 I_data 是 32 数据+1 tuser 位，灰度只 32 位就高位补 tuser）→ line_buffer_demosaic → data1（延迟一行）→ 再级联 → data2（延迟两行）→ 打拍对齐 `data_d0=data0 打 2 拍、data_d1=data1 打 1 拍、data_d2=data2 不拍`（因为每个 line_buffer_demosaic 有 1 拍流水延迟，靠补拍拉平）得到同拍三行。BRAM 是硬核不占 LUT，slice 立刻够。**BRAM 是同步读（读延迟 1 拍）→ sobel 数据整体延迟 2 拍**（写打 1 + 读打 1），所以 sobel_top 的 O_tvalid/O_tlast/O_tuser 要同步打 2 拍，且 isp_top 加 valid/tuser/tlast 的 MUX（`algo_mode_2d==3'd3 ? sobel_valid : awb_O_tvalid`，data_96bit_to_128bit 的 valid/frame_start、O_tlast 都改接 MUX 后的信号），否则 sobel 数据比 valid 晚 2 拍、画面错位。（BRAM 特性教学：同步读 vs 异步读、双端口、20Kb 块大小固定、read-before-write；distributed RAM=LUT 搭、异步读零延迟、小容量；一行像素必须上 BRAM——见 memory「FPGA 资源」或直接按这段讲。）
- **4 像素并行 3×3 的跨组边界（最绕的点）**：每像素的左右邻居会跨到相邻 4 像素组（P0 左邻居 = 上一组 P3、P3 右邻居 = 下一组 P0）。**实测采用的方案（不延迟、tvalid 天然对齐）**：P0 的左邻居打一拍缓存「上一组 g3」——三个寄存器 r_prev_g3_cur/up/up2 分别缓存当前行/上一行/上上行的「上一组 g3」；P3 的右邻居用「**复制 g3**」近似（下一组 g0 还没到，复制本组 g3 顶替）。⚠️ **这个「复制」让竖线（垂直边缘，靠 Gx 左右差分）的右边缘整列算出 Gx=像素3−像素3=0、检测不到 → 竖线变单边/断续，「上下（横线）比左右（竖线）清晰」**——横线靠 Gy（上下差分，用 line buffer 真实值）完全不受影响。之前误判「肉眼无感」，实际竖线断续肉眼可见，且加高斯滤波后阈值能压到 79，这个「凑合」就露馅了。**根治 = 「延迟 1 组 + 预取下一组」**：平滑灰度 3 行打 1 拍，g3 的右列改用「当前拍的下一组真实像素 0」（sm_cur[7:0] 等），其余像素用打 1 拍的 sm_cur_d1，数据延迟 1 拍 → tvalid/tlast/tuser 同步补 1 拍、h_cnt/v_cnt 打拍 +1、边界屏蔽顺延 1 拍。复杂度增，但这是竖线清晰的正解，别再用「复制」凑合。卷积结果是长组合路径（Gx/Gy ±1020、幅值 2040），打拍再比阈值，别让长组合链直接进比较。

⚠️ **「上下 vs 左右」方向性差异要先分清两种根因（2026-10-17 诊断教训）**：① **g3 右邻居复制 = 代码 bug**，只影响竖线（Gx 左右差分）的右边缘，延迟 1 组能修；② **横线（Gy 上下差分）上下边不对称（上边白线、下边白点）= 往往是物理现象**——手臂下缘背光、肤色和背景灰度差比受光的上缘小，Gy 幅值弱、落阈值下。③ **reg 数组 line buffer 的 read-before-write 在 TD 综合可能变 write-first → 上上行错位、Gy 跨度减半（2026-10-17 实测，本条推翻「代码对称改不动」的旧结论）**：见下面「⚠️ reg 数组 line buffer write-first」专条。**判别物理 vs 代码的终极铁律 = 让用户拿同一道线旋转 90°**：同一道墨水横放（靠 Gy 检测）测不到、竖放（靠 Gx 检测）测得到，就坐实代码方向性 bug（物理边缘不对称不会随旋转反转），别再用「本子/手臂边缘不对称」搪塞过去。**诊断铁律：先写 testbench 构造「标准横线」（水平边缘，灰度上下跳变）+「标准竖线」，验证代码上下/左右是否对称输出，再判断是 bug 还是物理现象**——别直接下板猜。**testbench 统计的分类边界必须精确对齐输出延迟**（canny 总延迟 8 行），否则「上边/下边」会被错误归类（如 `y<368` 把下边也算进上边），得出「下边没检测到」的假结论——本次就栽在这，代码其实对称、是统计 bug 误判成「Gy 有 bug」。

**⚠️ reg 数组 line buffer 的 read-before-write 在 TD 综合可能变 write-first（2026-10-17 实测，仿真对、下板错）**：reg 数组做「读旧写新」攒 3 行 line buffer（`d1 <= lb[addr]; lb[addr] <= d_in;`，非阻塞赋值右边读旧值），iverilog 仿真严格 read-first 测出横/竖线对称，但 **TD 综合可能把「同一地址同一拍读写」综合成 write-first（读新值）** → 「上上行」错位成「上行」→ Gy 上下差分跨度从「cur−up2（2 行）」缩到「cur−up（1 行）」、幅值减半 → 横线（靠 Gy 检测）消失/变细，竖线（靠 Gx，组内左右差分不经过 line buffer 的上下方向）完全正常。**证据链**：同一条线旋转 90° 横测不到竖测得到 = 代码方向性 bug，非物理。**为什么闭运算的 reg 数组下板没事**：闭运算对读新/读旧不敏感（填洞效果差不多），不能当「TD 是 read-first」的反例——只有「差分跨度」这类对行错位敏感的模块才暴露。**修复（唯一可靠）**：做差分的 line buffer 必须用 **BRAM（line_buffer_demosaic，内部 blk_mem_gen_demosaic 的 WRITEMODE_B=READBEFOREWRITE 硬件保证读旧值）**；+8 ERAM 用「强边缘 lb（4bit 标记）改 reg 数组」抵消（强边缘 lb 只做 8 邻域 OR 判断，对 read/write-first 不敏感，4bit×320 不占 ERAM）。

⚠️ **但「强边缘 lb 改 reg 数组抵消 +8 ERAM」实测失败（2026-10-17 下板，EMB 113>108 超 5）**：强边缘 lb 的数据只有 4bit（strong_4p 塞进 33bit BRAM，其余 28bit 是常量 0），**TD 综合时把常量 bit 优化掉了，那 2 个 BRAM 实际根本没占 8 ERAM**（只占 ~1 个）→ 改 reg 数组省不了 ERAM；而平滑 lb 的 8bit 数据是实打实的 +8 ERAM，净增 ~7。**通用教训：估算「某块数据改 reg 数组能省多少 ERAM」前，先确认那数据在 BRAM 里是不是真占位——只塞常量 0 / 只用低几 bit 的数据，TD 会优化掉，改 reg 数组省不了（本次就栽在这，误以为省 8 实际省 1）**。

⚠️ **真正省 ERAM 的大招：blk_mem_gen_demosaic IP 默认深度 2048 严重浪费，改成 512（2026-10-17 实测，一次省 18 个 ERAM）**——line_buffer 的地址只用 0~319（1280/4=320 组，IMG_WIDTH_4x=320），但米联客生成的 blk_mem_gen_demosaic 配成了 **2048 深度**（ADDR_WIDTH=11）。2048 深 × 33bit（映射 40bit 宽）= **4 块 ERAM/个**；改成 512 深（2^9，刚好装下 320）= 1 块 ERAM/个。6 个 line_buffer（灰度 2 + 平滑 2 + 幅值 2）从 24 块降到 6 块、**省 18 个 ERAM（113→95）**。改法（手动改 .v，不用 TD GUI 重新生成）：①blk_mem_gen_demosaic.v 的 `DATA_DEPTH_A/B 2048→512`、`ADDR_WIDTH_A/B 11→9`、`addra/addrb [10:0]→[8:0]`；②line_buffer_demosaic.v 的 `addra/addrb [10:0]→[8:0]`；③Design.xml + .m_params/.params 的深度/地址宽度同步改（防 TD 检测不一致重新生成覆盖）。⚠️ **改完别在 TD 里点「重新生成」这个 IP，否则按旧配置覆盖回 2048 深度**。ram_c36c2ca3b3a7 原语是参数化的（DATA_DEPTH_A 默认 1024），传参覆盖即可、不用改。通用结论：**米联客/官方给的 BRAM IP 深度常按「最大可能分辨率」配（2048/65536），实际用不到那么深，改浅 IP 深度是省 ERAM 最高性价比的一招——比「减实例数」「换更窄位宽」都省得多**。**对齐别搞错**：BRAM 版对齐跟灰度 lb 一致 = cur 打 2 拍 / up 打 1 拍 / up2 不拍（照抄 sobel_top 注释「data[0] 补 2 拍、data[1] 补 1 拍、data[2] 不补」），reg 版改 BRAM 后 sm_cur 仍打 2 拍、总延迟 8 拍不变，h_cnt/v_cnt 打拍和边界屏蔽都不用动。**强边缘 lb 反着改（BRAM→reg 数组）时 sup/sup2 要补拍对齐**：reg 数组「读旧写新」的延迟是 1 拍（非阻塞读），比 BRAM line_buffer_demosaic 的延迟（内部 data_d0 打 1 拍 + 同步读 1 拍 = 2 拍，再 +1 行）少 1 拍；所以强边缘 lb 从 BRAM 改成 reg 数组后，sup/sup2 要额外补拍才能对齐原 BRAM 版的流水线延迟——**scur +2 拍、sup +3 拍、sup2 +4 拍**（s_lb1_rd/s_lb2_rd 读旧值 1 拍后，再打 2/3 拍），否则滞后阈值的 8 邻域会水平错位 2~3 组（8~12 像素）。通用结论：**任何「reg 数组 ↔ BRAM line_buffer」切换实现，对齐拍数都要重推**——reg 读旧写新净 1 拍、BRAM line_buffer_demosaic 净 2 拍，两者差 1 拍，照搬旧对齐必错位。
- **边界处理：最外圈输出 0（黑）**。Sobel 处理不了最外一圈（无完整 3×3 邻域，第一行无上一行、第一列无左边），720p 下 1 像素损失看不见、黑又是「非边缘」默认色，不用折腾补零/复制/镜像。加有效区域使能（行号 1~H-2 且列号 1~W-2 才输出 Sobel 结果）。注意 C 伪代码 `for(y=1;y<H-1;y++)` 其实已隐含跳过边界。**输出延迟一行 → 行屏蔽要多加一行（cur_valid 要 row_cnt >= 2 不是 >= 1）**：窗口中心在「上一行」（卷积三行是 up2/up/cur，中心 e 是 up[7:0]），所以输出的是「上一行」的 Sobel、整体延迟一行；且「上上两行」要两行数据才填满。写 `row_cnt >= 1` 会让第二行输出用到未填满的 up2（出现假边缘）。行/组计数器用「组 319 回绕 +1」驱动行号（`grp_cnt==319 时 row_cnt+1`、tuser 归零），别依赖 tlast——这样消隐期 grp_cnt 冻结、行号天然对齐，跟地址计数 line buffer 同源抗消隐（demosaic 的 h_cnt/v_cnt 也是这么数的）。

**⚠️ 中值滤波用于「边缘检测前」是方向性错误，已撤掉（2026-10-12 实战反转）**：中值滤波靠「抹平」去噪，会同时抹掉运动模糊的弱边缘 → 移动快还是检测不到 + 边缘不清晰（一部分边缘没识别出来）+ 引入边界白线（line buffer 上电垃圾值透传）和近似中值的斜线伪影。最终结论：**边缘检测（Sobel）定位静止/慢速轮廓（阈值 128 清晰无噪点），运动目标交给帧差法**（帧差法对运动模糊不敏感——它比较前后帧差异，物体动得快差异大反而更好检测，不用硬让 Sobel 去抓快速运动）。正确去噪（若以后需要）是 Sobel 之后的**二值形态学（腐蚀+膨胀）**——去孤立白点、保留连续边缘线、不糊边缘，不是边缘前的灰度中值滤波。下面的 median_filter.v 实现留作反面教材 + 形态学可复用的 line buffer 框架：

## Canny 边缘检测（Sobel 升级，2026-10-14 实现）

Canny = 高斯滤波 + Sobel + 非极大值抑制(NMS) + 双阈值 + 滞后阈值。把 Sobel 的「粗边缘」细化成「1像素细边缘」、去弱噪声边缘、修复断链。**⚠️ 我们的 canny_top 从 Sobel 直接开始、缺了标准 Canny 第一步「高斯滤波去噪」→ 边缘噪声多（2026-10-17 参考别人 Canny RTL 确认）**。高斯滤波 ≠ 中值滤波：高斯是 3×3 加权平均（核 [1 2 1; 2 4 2; 1 2 1]，>>4 归一化，去噪保边缘梯度），中值滤波是取中值（糊边缘，之前踩过坑）。加高斯滤波要「平滑灰度 line buffer 攒 3 行」。⚠️ 平滑灰度是 4 像素并行 = **32bit 不是 8bit**，reg 数组是 32bit×320×2 ≈ 20480bit（LUT 实现、不占 ERAM，但占约 1 万 LUT）；用 33bit 的 line_buffer_demosaic（BRAM）则 +8 ERAM 超限。实测 canny 用 BRAM 攒灰度 3 行后 slice 余量够、32bit×320×2 reg 数组编译通过（slice 没爆）——之前 Sobel 爆 slice 是因为它 line buffer 本身也是 reg 数组 + 卷积逻辑一起超，canny 换 BRAM 后没这问题。别人 Canny 还用 CORDIC sqrt 算幅值 sqrt(Gx²+Gy²)，我们用 |Gx|+|Gy| 近似（误差约 10%，可接受不必换）。用户升级边缘检测时用这个（canny_top.v 替换 sobel_top，接口不变：I_tdata/I_threshold/O_tdata 全兼容，只是延迟 2 拍→6 拍）。

完整实现要点（都是踩坑总结）：
- **方向量化（免 atan2/除法）**：|Gy|>2|Gx|→垂直(dir2)、|Gx|>2|Gy|→水平(dir0)、否则 Gx/Gy 同号判 45°(dir1)/异号 135°(dir3)。2 倍近似 tan67.5°≈2.414，硬件用移位比较。
- **NMS（边缘细化核心）**：沿梯度方向比较中心幅值和 2 邻居幅值，中心非最大则抑制。4 方向邻居映射：dir0=左右、dir1=右上左下、dir2=上下、dir3=左上右下（3×3 窗口 a~i 中心 e）。4 像素并行的跨组边界同 Sobel：g3 右邻居复制 g3、g0 左邻居缓存上一组 g3。
- **幅值降位宽 8bit（mag>>3）**：NMS 只比较大小、8bit 精度够；4 像素 mag8=32bit 正好塞进 line_buffer_demosaic 的 32bit（11bit 幅值 4 像素=44bit 塞不下，必须降位宽）。幅值存 line buffer 攒 3 行；方向(2bit×4)用寄存器打拍缓存即可（NMS 只在中心用方向，不用存 line buffer）。
- **双阈值 + 滞后阈值（修复断链）**：强边缘(mag>高)直接保留；弱边缘(低<mag<高)若 8 邻域有强边缘才保留（连成线），孤立弱边缘丢弃。强边缘(4bit)存 line buffer 攒 3 行 + 8 邻居 OR。**断链根因 = 双阈值丢弃弱边缘**（边缘幅值不均匀，某些点幅值落阈值下被切掉），滞后阈值把连到强边缘的弱边缘接回来。
- **边界屏蔽（多层 line buffer 的垃圾值）**：Sobel 卷积边界 2 行 + 幅值 line buffer 2 行 + 强边缘 line buffer 2 行 = 前 6 行/后 5 行都是「上电垃圾值」产生的假边缘（现象：左边界竖白线 + 上边界白点连成线）。cur_valid 要 `v_cnt>=6 && v_cnt<=714`（不是 Sobel 的 2），损失边界 1.5% 肉眼不可见。
- **⚠️ 边界屏蔽的坐标要「打 4 拍对齐输出」，不能用第一级的 h_cnt/v_cnt（实测踩坑：左边竖线一直消不掉）**：输出比第一级 Sobel 延迟 4 拍（幅值 line buffer 2 + 强边缘 line buffer 2），直接用第一级 h_cnt/v_cnt 做边界屏蔽会「错位 4 组/4 行」——h_cnt>=1 对应输出组号 -3（还没输出），左边第一组根本没被屏蔽到。解法：h_cnt/v_cnt 打 4 拍得 h_cnt_d4/v_cnt_d4，cur_valid 用它们（`v_cnt_d4>=6 && <=714`、`h_cnt_d4>=1 && <=318`）精确对准输出的组号/行号。这是多层 line buffer 流水线的通用坑：任何「边界屏蔽/坐标判断」都要用「对齐输出的坐标」，不是第一级的坐标。**⚠️ 边界屏蔽必须用「打 4 拍的 h_cnt_d4/v_cnt_d4」对齐输出，别用第一级 Sobel 的 h_cnt/v_cnt**——输出比第一级 Sobel 延迟 4 拍（幅值 line buffer 2 + 强边缘 line buffer 2），直接用第一级 h_cnt 做边界屏蔽会「错位 4 组」，导致左边第一组根本屏蔽不到（现象：左边界竖线，用 h_cnt>=2 加强也消不掉——因为加强的是「第一级的组号」，错位 4 组后根本没对准输出的第一组）。正确做法：`reg [13:0] h_cnt_d1..d4, v_cnt_d1..d4` 打 4 拍，`cur_valid = (v_cnt_d4>=6) && (v_cnt_d4<=714) && (h_cnt_d4>=1) && (h_cnt_d4<=318)`。垂直边界（v_cnt）用加强值能凑合（错位 4 行后 v_cnt>=6 恰好盖住），水平边界（h_cnt）错位后左边彻底漏屏蔽、必须打拍对齐。
- 总延迟 6 拍（Sobel 2 + 幅值 line buffer 2 + 强边缘 line buffer 2），O_* 打 6 拍。
- 验证：iverilog testbench 构造垂直边缘（左半黑右半白），统计输出白像素（细边缘，约 1400~1600）。stub line_buffer_demosaic 用「地址计数 + 读旧写新」模拟「延迟一行」。



**⚠️ 形态学开运算（腐蚀+膨胀）不适合 Canny 细化后的 1 像素边缘（2026-10-14 实测，testbench 白像素 0）**：用户要「弱边缘清晰 + 无噪点」两全，想用「阈值 96 + 形态学开运算（腐蚀去噪 + 膨胀连接）」——但腐蚀（3×3 全白才白）会把 Canny 的 NMS 细化出的「1 像素细边缘」也腐蚀掉（一条竖线像素的 3×3 窗口是「上下白、左右黑」不全是白，被当成细结构去掉），testbench 垂直边缘白像素 = 0（边缘整个被腐蚀掉）。**本质矛盾：噪点（孤立点）和细边缘（1像素线）在「3×3 全白」判据下分不开**——腐蚀去噪点的同时必然去细边缘。开运算（腐蚀+膨胀）只适合「粗边缘」（Sobel 那种 2~3 像素宽，腐蚀后中间像素 3×3 仍全白、膨胀恢复），不适合「细化后的 1 像素边缘」。要「去噪点 + 保留细边缘」得方向感知形态学（保留「上下白」的竖线、去掉「全黑」的孤立点），复杂度高、竞赛不值得。**结论：Canny 细化后的边缘别上形态学开运算；弱边缘断续 + 噪点是渐变弱边缘的固有特性，阈值 128 干净收尾即可，别为「两全」上复杂形态学**。

**弱边缘 vs 噪点是同向权衡（增益/阈值/形态学都无解，别死磕）**：弱边缘（如承重柱阴影，灰度渐变、梯度小）和噪点（散点）在「增益/阈值」上同向——降阈值（128→96）或升增益（96→143 8x）弱边缘检测到了、噪点也一起进来；升阈值/降增益则反之。增益和阈值配套：增益放大信号（弱边缘+噪声一起放大），增益 143 + 阈值 128 能检测弱边缘（增益把弱边缘对比度放大 2 倍），但 8x 增益引入色度噪声（红蓝点）。三种组合都是「弱边缘 vs 噪点」权衡，没有免费午餐。**弱边缘检测甜点 = 增益 143（8x）+ 阈值 79**（2026-10-17 实测，推翻「增益 96 + 阈值 128」收尾）：高斯滤波去噪后，8x 把弱边缘（字）放大到 79+、噪声卡在 50~79，阈值 79 正好「字进来、噪声挡住」。**别降增益抓弱边缘**——增益 96（4x）时弱边缘信号被放大得不够、幅值掉到 50 以下，阈值设 50 也「啥都看不出来」（弱边缘根本没到阈值）。增益是放大镜：8x 把弱边缘和噪声一起放大，4x 放大不够、弱边缘跟噪声一起被挡掉。「想检测弱边缘」必须 8x 增益 + 阈值卡噪声上沿，没有「低增益还能看弱边缘」的选项。⚠️ **加高斯滤波去噪后，弱边缘甜点下移到「增益 143（8x）+ 阈值 79」（2026-10-17 实测）**：8x 把弱边缘（字）放大到 79+、噪声（高斯滤波后）卡在 50~79，阈值 79 正好「字进来、噪声挡住」。而增益 96（4x）弱边缘幅值 <50，阈值设 50 也「啥都看不出来」——**想检测弱边缘（字）必须 8x 增益 + 阈值 79，没有「低增益还能看弱边缘」的选项**（增益是放大器，4x 放大不够弱边缘掉阈值下）。

**⚠️ Canny 第一步是高斯滤波，我们之前漏了（2026-10-17 补，噪声多的根因）**：标准 Canny = 灰度 → **高斯滤波去噪** → Sobel → NMS → 双阈值。我们的 canny_top 直接从 Sobel 开始、跳过高斯滤波 → 噪声多、边缘不清晰。参考开源 Canny（Hardware-Implementation-of-the-Canny-Edge-Detection-Algorithm）和官方 lab_ex2 确认：**高斯滤波 ≠ 中值滤波**（中值滤波取 3×3 中值、抹平边缘 ❌；高斯是 3×3 加权平均核 [1 2 1;2 4 2;1 2 1]>>4、平滑噪声但保留边缘梯度 ✅）。加高斯滤波后噪声平均掉、真实边缘保留，可顺势把 Sobel 阈值 128 往下调抓弱边缘。实现：3×3 高斯卷积 function + 平滑灰度 line buffer（reg 数组 32bit×320×2=20480bit，不占 ERAM 占 LUT，本次未爆 slice）+ Sobel 输入从灰度改平滑灰度，总延迟 6→7 拍（h_cnt/v_cnt 打 5 拍、边界下限 8、O_* 打 7 拍）。官方 lab_ex2 的 edge_detect_96 是「2 像素配对降采样（1280→640 省 line buffer）+ 纯 Sobel」的省资源基础版；我们是「全分辨率 + Canny」完整增强版。



## 帧差法 / 运动目标检测（高阶挑战(4)，已实现 2026-10-13）

帧差 = |当前帧 − 上一帧| > 阈值 → 移动区域高亮。难点在「存上一帧」：整帧灰度 1280×720×8 = 7.37 Mbit，PH1P35 BRAM 约 1 Mbit 装不下。**最终方案：降采样 320×180 + 片内 BRAM 单缓冲 read-before-write**（绕开 DDR，旧方案复用 DDR 带宽顶 94% 被否）。

完整实现（motion_detect.v，插 isp_top 与 sobel_top 平行，输入 gray_data）：
- **降采样 1280×720 → 320×180**：水平 4 像素平均 `(g0+g1+g2+g3)>>2`（抗噪，别取第 1 个像素），垂直每 4 行取 1 行（`row_cnt[1:0]==0`）。1280/4=320 组、720/4=180 行。
- **存帧 BRAM（单缓冲，非双缓冲）**：read-before-write，A 口写当前帧 avg、B 口读同地址旧值。**安路 ERAM 的 A写B读同地址、B 读到旧值（写之前的值）——line_buffer_demosaic 的「延迟一行」就是靠这个，帧差存帧直接复用**。地址 down_cnt[15:0] 0~57599 每帧回绕（tuser 清零），天然「上一帧」对比，单缓冲 450Kbit 就够、不需要 900Kbit 双缓冲。BRAM 要 **65536 深 × 8bit**（57600 实际用）：现有 blk_mem_gen_demosaic 只有 2048 深不够用，**需 TD GUI 生成新 IP（blk_mem_gen_frame_diff，真双端口 8bit×65536，B 口 Read First）**。⚠️ 早期「单 primitive 深度上限 2048」误判：深度级联由 TD mapper 自动处理，非常规位宽/深度（如 40bit×23040）可直接例化 PH1P_LOGIC_ERAM 原语。端口名 TD 固定生成 dia/addra/wea/clka/addrb/dib/web/doa/dob。**⚠️ CLKMODE=SYNC（共时钟）生成的 IP 没有 clkb 端口**（wrapper 内部把 clkb 接 clka），例化时别写 .clkb——本次踩坑：motion_detect 照抄 demosaic 的端口写了 `.clkb(I_clk)`，但生成的是 SYNC 版没 clkb，编译报找不到端口，得删掉；ASYNC（独立时钟）才有 clka+clkb 两端口（blk_mem_gen_demosaic 就是 ASYNC 有 clkb）。**例化 BRAM 前先读生成的 .v 核对端口，别照抄别的 IP 的端口**。生成的 .xml 加到 IP files（不是 Design files，Design files 是 .v/.sv 源码）。

**TD GUI 生成这个 BRAM IP 的界面参数（2026-10-13 实测）**：IP Catalog 搜索框搜 **RAM**（别搜 ROM——存帧要读旧写新可写）；Primitive IP > Memory > RAM；双击后弹「Setup Exporting Options」改 Component Name 为 blk_mem_gen_frame_diff；参数页 Basic 选 **Memory Type = Dual Port RAM**（真双端口，Simple Dual Port 没有 web/dib 端口、会跟例化端口对不上）、**CLKMODE = SYNC**（A/B 接同时钟）；Port A/B Options 宽度 8 深度 65536（配完地址线变 [15:0]）；**B 口 Output Register 必须选 None**（否则读延迟变 2 拍、帧差时序错位）、Operating Mode 选 read_before_write、Operating Enable 选 Always Enable；ECC 灰色=该配置不可用、忽略。生成后 Add Source 把 .xml 加进工程（IP 走 .al 的 <IP_FILE> 段）。

**用户发 TD GUI 中文截图让我识别（OCR 工作流）**：WSL 有 tesseract（含 chi_sim 包），`tesseract 截图.png out -l chi_sim+eng --psm 6` OCR 出界面文字，据此逐步指导用户填 IP 参数。用户在 TD GUI 里操作、截图给我确认，是生成 IP/查界面这类任务的常态协作方式。
- **帧差**：`diff = |cur_d - prev|`（cur_d = avg 打 1 拍对齐 BRAM 读延迟），`motion = diff > 阈值`。阈值 localparam=32（第一版固定，后续按键可调再扩 S_mode）。
- **放大回显 320×180 → 1280×720**：水平 4× = 1 个 motion 标记复制 4 份填 96 位（同拍零延迟）；垂直 4× = line buffer 320 深×8bit 缓存一行 motion，降采样行边算边写 LB 直出、后续 3 行读 LB 重复输出（reg 数组异步读 = distributed RAM 2560bit 很小，不爆 LUT，跟 Sobel 的 320×32×2 爆 slice 不同）。
- **输出延迟 1 拍**（BRAM 同步读）：O_tvalid/tlast/tuser 打 1 拍；isp_top 的 valid/tlast/tuser MUX 加 `(algo_mode_2d==3'd4) ? motion_* : ...` 分支（motion 延迟 1 拍 vs Sobel 延迟 2 拍，别写反）。
- **资源风险**：存帧 450Kbit ≈ 22.5 块 20Kb，加 demosaic/Sobel/AWB 约 26 块，逼近 PH1P35 约 50 块上限，编译后看 BRAM 报告，超了就降采样 256×144（约 295Kbit 省 8 块）。
- **首帧花屏**：上电 BRAM 垃圾值，第一帧跟垃圾比差会花一下，1/60 秒后正常，属预期非 bug。
- 配套：algo_mode_sel ALGO_NUM 4→5；osd_cn_char 加「运」41+「动」42（simhei，**不复用索引 37 的「动」**——「自动/手动」那批字模非 simhei，并排会大小不一）；hdmi_mixer 算法名 case 加 3'd4「运动」。
- **验证**：iverilog testbench 用 stub 模拟 BRAM（reg 数组 + 非阻塞赋值 = read-before-write，initial 清零避免首帧跟 X 比），构造第1帧全黑第2帧运动块，统计输出白像素组数 == 期望 5000 即通过。运动块降采样后 25 行×50 组，垂直放大 4 倍 = 100 行×50 组 = 5000 组白。

**（2026-10-13 方案定稿）降采样 320×180 + 片内 BRAM 单缓冲，绕开 DDR**：重新算账——降采样后一整帧只要 320×180×8bit = 460800 bit ≈ 450 Kbit，正好塞进 PH1P35 约 1 Mbit 的 BRAM（原 1280×720×8=7.37Mbit 才装不下），彻底不用碰 DDR，带宽焦虑消失。方案要点（motion_detect.v，放 isp_top 里与 sobel_top 平行，吃 gray_data）：
- **降采样是 motion_detect 模块内部私有动作，其他算法无感**：gray_data 始终是全分辨率 96 位（4 像素）流，灰度/二值/Sobel/自动曝光全吃全分辨率；只有 motion_detect 内部降采样。水平 4:1 = 每拍 4 像素取平均 `(g0+g1+g2+g3)>>2`（抗噪，3 个加法器，帧差法对噪声敏感故别取第 1 个像素）；垂直 4:1 = 行计数器 `row_cnt[1:0]==0` 才处理（720÷4=180 行）。
- **存帧 BRAM 单缓冲 read-before-write 就够，不需要双缓冲**：地址 down_cnt 0~57599 每个降采样像素 +1、帧首 tuser 清零、每帧回绕；每个像素「先读 BRAM[addr] 得上一帧 prev，再写 cur」，读旧写新天然实现「上一帧对比」——单缓冲 450Kbit 而非文档早期写的双缓冲 900Kbit。帧差 `diff=|cur-prev|`、`motion=(diff>threshold)`。
- **放大回显 320×180 → 1280×720**：水平 4× = 1 个运动标记复制 4 份填满 96 位输出（同拍零额外延迟）；垂直 4× = 小 line buffer（320 深×8bit，reg 数组即可，distributed RAM 几十 LUT 不爆）缓存一行帧差结果，处理行(row%4==0)边算边写边直出、后续 3 行读 line buffer 重复输出，720 行连续输出。
- **输出延迟约 1~2 拍（BRAM 同步读），O_tvalid/tlast/tuser 对应打拍对齐**，isp_top 的 MUX 里给帧差法加 valid/tlast/tuser 分支（同 Sobel 套路，但链路比 Sobel 短：Sobel 是 2 条 line buffer 攒 3 行延迟 2 拍，帧差只有 1 块 BRAM 读延迟 + 1 行 line buffer）。
- **motion_detect 例化后一直并行跑（同 sobel_top）**：降采样/存帧/帧差全程在做，MUX 只在 KEY4 模式 4 才选中它输出——切模式即出图、无第一帧空白；代价是 450Kbit BRAM 上电即占用、全程占用（资源风险来源，需下板看报告，不够就降采样 256×144≈295Kbit 或存 6bit 灰度≈340Kbit）。
- **决策点：帧差阈值（0~255，初始建议 32）第一版做固定 localparam**，因为 S_mode[1:0] 四种已占满（0 曝光/1 增益/2 二值阈值/3 Sobel阈值），扩 3 位加第 5 种会牵动 sw_mode、数码管 case、各 I_enable 联动，且 SW3 已被自动曝光占用（重新分配开关现场易混淆）。配套改动：algo_mode_sel ALGO_NUM 4→5、isp_top 算法 MUX 加 3'd4 分支（阈值固定 localparam=32，无 I_motion_threshold 端口，后续做按键可调再加端口）、osd_cn_char 加「运」「动」索引 41/42、hdmi_mixer 算法名 case 加 3'd4 分支显示「运动」、新建 motion_detect.v 记得 TD Add Source。

**⚠️ 帧差法噪声问题是最大坑（暗光+高增益下噪声和运动帧差重叠，单阈值无法两全）**：下板实测阈值 32 静止天花板满屏白点、64 又把手运动一起滤掉（漏检），左右为难。根因：增益越高传感器噪声越大（8x 档噪声帧差可到 50~80），和真实运动帧差（40~100）重叠——用户一度怀疑「摄像头太垃圾」，其实是算法没抗噪。**⚠️ 下面 1/2/3 三条（4×4 平均、run_length、阈值 40）是试过的弯路，最终被「4×1 + 时间滤波」取代，见下一条「已解决」**。有效解法（业界标准思路，不是单纯调阈值）：
1. **降采样升级成 4×4 块 16 像素平均（水平 4 像素平均 + 垂直 4 行平均，不是「水平平均+垂直取1行」）**：噪声幅度降约 4 倍（±50→±12），运动是成片的、平均后基本保留，把噪声和运动拉开距离。垂直 4 行平均 = 3 个 reg 数组 lb0/lb1/lb2 缓存前 3 行水平平均、第 4 行（row_cnt[1:0]==3）做 `(lb0+lb1+lb2+当前行avg_h)>>2`。
2. **空间连通性过滤（run_length >3）**：一行内连续 >3 个运动像素才保留，滤孤立噪声白点（噪声「孤立」、运动「连续」）。run_len 饱和计数到 4、行边界/消隐清零。只滤「水平」孤立点，垂直孤立残留需 3×3 形态学腐蚀补。
3. **阈值 40**（业界开源项目 kiranalur45/FPGA-Real-Time-Motion-Detection 用 75，配无降采样全分辨率帧差；它还用时间滤波 hist_sum 连续 3 帧 + object_filter run_length>3，是去噪标准套路，可作为后续参考）。
- 更彻底去噪（若还飘白点）：3×3 形态学腐蚀（去孤立白点，复用 Sobel 的 line buffer 结构，AND/OR 比 Sobel 卷积还简单）+ 时间滤波（连续 N 帧运动才算，去单帧噪声，需额外存运动结果一帧）。
- **帧差法原理性限制：只能画运动「轮廓」**（手内部两帧都有、帧差≈0 就空）。要「整块手」得**背景减除**：|当前帧 − 背景模型| 检测整块物体（含内部无空洞），工业界检测完整物体的标准方案。**简单背景减除 = 存固定背景 B（初始化后不更新）+ 减背景**，跟帧差法（存上一帧+减上一帧）结构几乎一样、改动量小（只需加「背景采集触发」拍一张空背景 + 光照不能大变，不像 GMM/ViBe 那样复杂）。关键洞察：**背景减除阈值卡「前景背景灰度差」（手 vs 天花板几十上百）>> 噪声，顺便解决帧差法的阈值两难**（帧差法阈值卡「运动速度」，慢速挥手帧差 16~40 跟噪声 ±20 重叠 → 16 白点/40 漏检）。所以「手轮廓不完整」和「阈值两难」两个帧差法痛点，背景减除一起解决——竞赛冲「运动目标检测」分时优先考虑。跟用户解释时点明手轮廓不完整是帧差法原理不是 bug，别反复调参硬扛。
- 加 run_length 过滤后总延迟变 2 拍（帧差 1 + 连通性 1），O_tvalid/tlast/tuser 打 2 拍。

**✅ 已解决（2026-10-14）：4×4 平均稀释慢速运动 → 降采样退回 4×1 + 时间滤波（最终方案，iverilog 验证 5000 白组通过）**——4×4 块平均（16 像素）把手边缘帧差从像素级 100+ 稀释到块级 30~40，阈值 40 卡掉、降到 16 仍检测不到。**教训：降采样空间平均是双刃剑——平均越多噪声越小、但慢速运动边缘帧差也被稀释越狠，去噪该靠时间维而非空间维**。最终方案（motion_detect.v 重写）：① 降采样退回 4×1（水平 4 像素平均 + 垂直取 1 行 `row_cnt[1:0]==0`），恢复运动灵敏度；② **时间滤波** `motion_t = motion && motion_hist[down_cnt_d1]`——motion_hist 存上一帧 motion（57600×1bit 分布式 RAM 约 3600 LUT，读旧写新同帧差存帧套路），连续 2 帧都判运动（噪声时间随机单帧、运动时间持续多帧）；③ **去掉 run_length**（时间滤波已去噪声，且 run_length 会误伤运动边缘）。总延迟回到 1 拍（BRAM 读 1 拍，时间滤波是组合零延迟）。
- **帧差法 testbench 设计坑（重要，测半天白组数=0 的根因）**：帧差法检测「变化」不是「静止」，testbench 里运动块若两帧同灰度（都 255）则帧差=0 测不出 motion——要让运动块**帧间灰度变化**（第2帧255、第3帧100，帧差155）或移动位置。时间滤波要「连续 2 帧运动」才检测到，testbench 至少 3 帧（第1帧黑、第2/3帧运动块且灰度变化），统计第 3 帧。调试内部信号用**层次引用** `u_md.motion`、`u_md.cur_d` 等 $display 打印，别只看最终输出。
- 配套：增益降 4x（值 96，8x 噪声大）、曝光拉 3990（初始 1990 半帧偏暗，画面暗先查曝光不是光照）。

**⚠️ 三帧差分（时间滤波 3 帧）也会过度去噪，手轮廓没了（2026-10-14 实测）**：连续 3 帧运动 AND 看似去噪更彻底（白点几乎清零），但手的运动边缘在每个像素位置只有 1~2 帧的帧差（手经过瞬间有变化、之后重叠区帧差≈0），连续 3 帧要求把「手的运动边缘」也当短时噪声滤掉了 → 挥手只剩几个白点、看不到手轮廓。**最终收敛方案：二帧差分（时间滤波 2 帧）+ run_length(>2) + 阈值 16 + 降采样 4×1（水平4像素平均+垂直取1行）**——白点解决 + 挥手能检测。**去噪别上三帧差分，那跟「检测手」矛盾**：帧差法检测「变化」、手边缘的变化本质是「短时」（1~2 帧），时间滤波 N 帧越狠越把真运动也滤掉。要「整块手」（含内部、无空洞）得靠背景减除（存固定背景+减背景），不是帧差/时间滤波能解决的。

**⚠️ 时间滤波 2帧 vs 3帧（2026-10-14 实战，去噪别过头）**：试过升级成「三帧差分」（连续 3 帧都判运动），结果白点几乎没了但**手的轮廓也没了**——因为慢速挥手时「手边缘」在每个像素位置只有 1~2 帧的帧差（手经过的瞬间有变化、之后内部重叠区帧差≈0），三帧差分把它当「短时噪声」滤掉了。**最终定版：时间滤波 2 帧（连续 2 帧运动）+ run_length(>2) + 阈值 16**，是「去噪」和「保留运动」的平衡点。教训：时间滤波/连通性加码到一定程度会误伤慢速运动，别无限加码。

**⚠️ motion_hist（运动历史）必须用 BRAM，别用 reg 数组**：存 57600 个 1bit 运动标记，用 reg 数组（分布式 RAM/LUTRAM）爆 MSlice（`Design's mslice number = 8664, exceeds the limit 8112`）。必须用 BRAM（blk_mem_gen_motion_hist，65535×1 双端口 read-before-write，约 3 块 20Kb）。生成时 CLKMODE 若选 ASYNC（独立时钟）会有 clkb+cea 端口（SYNC 则无 clkb），例化前读生成的 .v 核对端口，别照抄别的 IP。

**帧差法检测不到「整块物体」→ 背景减除（工业界标准，2026-10-14 搜索确认）**：帧差法 = |当前帧−上一帧|，只检测「运动边缘」（手内部两帧都有、帧差≈0 是空的），这是原理性缺陷不是 bug；要「整块手高亮」得背景减除 = |当前帧−背景模型|，检测与背景不同的物体整体。简单背景减除改动量小（现帧差法是「存上一帧+减上一帧」，改成「存固定背景+减背景」），但要加「背景采集触发」+ 光照不能大变。**阈值关系（关键洞察）**：帧差法阈值卡「运动速度」（慢速挥手帧差 16~40 跟噪声 ±20 重叠→两难）；背景减除阈值卡「前景背景灰度差」（手 vs 天花板几十上百 >> 噪声→阈值 50 就噪声全滤+整块检测），背景减除顺便解决了帧差法的阈值两难。帧差在摄像头时钟域（写 DDR 前），OSD 文字在 HDMI 端（读 DDR 后），所以 OSD/帧号不影响帧差——之前误判「帧号滚动导致白点」是错的，白点纯是传感器噪声（光子散粒噪声，亮度越高噪声越大，白点集中在亮部/灯附近）。8x 增益还会产生「色度噪声」（红蓝点），跟帧差法无关（帧差用灰度/亮度），降增益即消。

**✅ 背景减除已实现（2026-10-14，motion_detect.v 从帧差法改造成背景减除，iverilog 验证 4800 白组通过）**：核心改动——存帧 BRAM 从「每帧存上一帧」改成「存固定背景」（`wea = avg_en && bg_capture`，采集帧写、之后不更新），减背景 `|cur_d - bg| > 50`（bg 是 BRAM 读出的背景，替代帧差法的 prev）。**SW4（I_sw[3]，引脚 D11）控制采集：0=等待采集、1=已采集、0→1 上升沿触发采集**。采集状态机（bg_state 三段：空闲→等帧首→采集完整一帧）——保证采集的是「完整一帧」（从帧首到帧尾），不是「从上升沿到下一帧首的半帧」（半帧背景会前后不一致、产生假前景）。已采集标志 = SW4 电平（bg_captured = sw4_d2）。输出门控：bg_captured 打 3 拍对齐输出，未采集（SW4=0）输出全黑、已采集输出前景。OSD 运动模式下帧号行换成「已采/未采」（字模 已43/未44/采45，字符码 `S_sw4_2d ? 8'h80+43 : 8'h80+44` + 采）。演示流程：KEY4 切运动模式 → 画面空着 → 拨 SW4 0→1 采背景 → 手伸进整块变白。阈值 50 固定 localparam（前景背景差几十上百，好设）；光照敏感（采完背景别大动光照）。⚠️ **背景减除检测「跟背景不同的前景目标」，静止的手也一直标记——严格说不是「运动检测」是「前景/目标检测」**。用户会质疑「这真的是运动识别吗」，答辩话术：「我实现的是背景减除（帧差法的升级），检测画面中相对背景出现的前景目标，目标运动进入时立即标记、之后持续跟踪不丢失——比帧差法只画轮廓、目标一停就消失更完整」。⚠️ 简介写「帧差法标记运动区域」但实际是背景减除，答辩主动说「升级到背景减除」圆过去（或改简介，但简介只有一次修改机会，策略=先做功能、下板验证、最后按实际效果定稿）。**SW4 复用空闲引脚 I_sw[3]（引脚约束已接好 D11，代码里原本没用到）——加新控制信号先查 I_sw 里有没有空闲位，别急着新增引脚约束**。时间滤波（连续 2 帧）对背景减除保留去噪声（前景持续、噪声单帧），run_length 保留去孤立白点。

**⚠️ RGB 减背景会超 EMB（2026-10-14 实测 145>108），最终收敛到 B 单通道**：RGB 三通道减背景要存 3 块背景 BRAM，但 blk_mem_gen_frame_diff 是 65536 深（每块 = 25.6 EMB/块，PH1P35 上限 108），3 块 = 76.8 EMB 直接爆（`emb number=145 exceeds 108`）。**关键坑：BRAM IP 深度是生成时固定的 65536，改 down_cnt 回绕范围（如降到 28799）不省 EMB——IP 还是 65536 深，占满 25.6 EMB**。降采样救不了 EMB，只有「换更小的 BRAM IP」或「减少 BRAM 块数」才行。最终方案：**B 单通道减背景**（1 块 BRAM）——手是肤色（偏红黄，B 分量低）vs 背景灰白（B 分量中），**B 通道差最明显**（50~70），用 B 通道就能区分手和背景，同时只要 1 块 BRAM（跟灰度一样，EMB 不超）。改动：输入 RGB 里只提取 B 通道（`b0=I_tdata[7:0]` 等，跟灰度提取同代码、只是语义从 gray 变 B）、降采样 B、1 块背景 BRAM、减背景 `|ΔB|>阈值40`。⚠️ **B 单通道实测效果不好、别停这（2026-10-16 迭代）**：AWB 白平衡把整帧 R/B 归一化到 G，画面肤色多时把肤色「降 R 升 B」拉向中性，B 单通道差实际只有约 30（不够、边缘不稳定），R-B 色差更是被 AWB 压到阈值下（全黑）。**最终定版 = RGB 3 通道 4bit + 57600 深 BRAM**（3 块 4bit×57600 = 15×3=45 ERAM，不超 108）：三通道 OR 互补（手内部 R 弱时 B/G 兜住，解决内部变黑）+ 320×180 全垂直分辨率（4:1 锯齿减半）。4bit=取高 4 位（1 级=16 原始量纲，阈值 2 级≈32）。**通道迭代完整链（都踩坑）：灰度（丢颜色）→ B 单通道（差30不够）→ RGB 3ch 8bit 320×90（锯齿）→ R-B 色差（AWB 压缩全黑）→ R 单通道（内部变黑）→ RGB 3ch 4bit 57600（定版）**。验证 testbench：前景背景灰度都是150但颜色不同（R差60/B差60），RGB 减背景检测 4800 白组。

**（2026-10-16 更新）背景减除通道选择的最终完整迭代链（踩坑全记录）**：灰度（丢颜色，R/4+G/2+B/4 把 R 权重压到 1/4）→ B 单通道（差 30 不够）→ **R-B 色差（全黑！根因 AWB 白平衡把整帧 R/B 归一化到 G，肤色被「降 R 升 B」拉向中性，R-B 差压到阈值以下）**→ R 单通道（内部弱处黑，无互补）→ **最终 RGB 3 通道 4bit + 320×180 + 深度 57600**（三通道 OR 互补解决内部变黑，4bit 压缩 + 57600 深省 ERAM 刚好装下）。⚠️ **关键教训：AWB 会压缩「色差类特征」（R-B 这种相对量），但保留「绝对值差」（手 R 高 vs 背景 R 中）。选通道特征时先想「这个特征在 AWB 后还保留吗」——R-B 色差被 AWB 补偿掉、R 绝对值差保留。** 最终资源：3 块 4bit×57600=45 ERAM（每块 15 个，4K×5 配置），加其他共 106/108 不超。



**⚠️ AWB 白平衡压缩 R-B 色差（最反直觉的坑，2026-10-16 实测全黑）**：AWB 把整帧 R/B 归一化到 G（R 增益=sum_g/sum_r、B 增益=sum_g/sum_b），画面肤色多时把肤色「降 R 升 B」拉向中性 → 手肤色 R-B 差被压到阈值以下（全黑）。但「R 的绝对值差」（手 R 高 vs 背景 R 中）在 AWB 后依然大，是肤色最稳定的特征。教训：**减背景别用「R-B 色差」这类相对量（会被 AWB 压缩），用单通道绝对值差或三通道 OR**。

**⚠️ 安路 ERAM20K 位宽配置只有 1/2/5/10/20/40，没有 4bit/8bit**（DS1300 数据手册 2.2 节，权威）：4bit 数据塞进「4K×5」配置（浪费 1bit=20%）、8bit 塞「2K×10」（浪费 2bit=20%）。**按「配置粒度」算 ERAM，别按「实际 bit 数」算**（后者偏乐观，之前 EMB=109 超 1 个就是这么来的）。ERAM20K 单块 20Kbit，配置离散 16K×1 / 8K×2 / 4K×5 / 2K×10 / 1K×20 / 512×40，单块最大深度 16K（仅 1bit 宽），靠「多模块地址/数据级联」扩深度。4bit×57600 深 = 15 个 ERAM（57600/4096 级联），4bit×65535 深 = 16 个 → 深度 57600 每块省 1 个（3 块省 3，109→106 刚好不超）。**深度 57600 是「刚好装下 320×180」的最优值，再小不够、再大白占 ERAM**。

**✅ 闭运算填洞 + 修圆**（加在 motion_filt 后，膨胀 3×3 OR + 腐蚀 3×3 AND）：填手内部 <3×3 降采样像素的阴影黑洞（>80° 手掌阴影）、修圆 4×4 块状锯齿，总延迟 +2 拍。**⚠️ 两层顶部边界都要屏蔽**：①闭运算 line buffer 前 2 个降采样行是上电垃圾（down_cnt<640 时透传 motion_filt 不膨胀/腐蚀）；②放大回显 line buffer 顶部 3 行（垂直 4 行平均结果第 3 行才输出、整体下移 3 行，row_cnt<3 时输出 0）。reg 数组 line buffer 用「非阻塞赋值右边读旧值」实现读旧写新（避免组合异步读「读新值」的毛刺），不占 ERAM（占少量 LUT）。

**✅ 动态目标跟踪（高阶挑战 2）不占 ERAM，外接框优于质心（2026-10-16 规划）**：跟踪 = 每帧算目标外接框（min_x/max_x/min_y/max_y 四个 9 位寄存器 + 比较器）+ OSD 坐标显示 + 画跟踪框（当前像素坐标 vs 框边界比较），全程不存整帧 → **0 ERAM**（这是它跟运动检测/边缘检测「要存整帧」的本质区别）。**外接框（min/max）比质心好**：外接框只要比较器（无除法器），质心要 Σx/N 需要除法器（占 DSP/一堆 LUT）。在运动检测（背景减除）基础上加跟踪 = 检测 → 定位（外接框）→ 叠加（框 + 坐标），展示「手在彩色画面里被白色标记 + 矩形框框住 + 右上角实时坐标」，动感十足、是全场最有记忆点的展示。运动检测结果叠加到原样画面（前景白 + 背景原样彩色）比纯黑白更直观，可用 SW4 在原样模式控制「运动检测开/关」（拨开采背景 + 叠加，拨回纯原样）。

**✅ 背景减除颜色通道最终定版：RGB 3 通道 + 320×180 + 4bit 压缩（2026-10-16，历经六轮迭代）**。上面「B 单通道」最终被证明不够（B 差仅 30），完整迭代链（每个都是踩坑，别重走）：①灰度（R/4+G/2+B/4 把 R 权重压到 1/4，丢颜色，手内部变黑）②B 单通道（B 差 30 不够）③RGB 3 通道 8bit + 320×90（内部变白，但垂直 8:1 降采样锯齿严重 + 旋转 45° 不完整）④R-B 色差 + 320×180（**全黑**，见下条 AWB 坑）⑤R 单通道 8bit + 320×180（能检测但内部 R 差弱处变黑，单通道无互补）⑥**RGB 3 通道 + 320×180 + 4bit（定版，三通道 OR 互补 + 全垂直分辨率 + 4bit 省 ERAM）**。

**⚠️ R-B 色差被 AWB 白平衡压成中性 → 全黑（2026-10-16 实战，关键非直觉坑）**：手肤色原始「R 高 B 低」→ R-B 差大，但 AWB（白平衡）把整帧 R/B 归一化到 G，画面肤色占比高时会把肤色「降 R 升 B」拉向中性，手的 R-B 差被压到阈值以下 → R-B 色差方案全黑。**AWB 补偿不掉「R 绝对值高」这个特征，只能补偿掉「R 和 B 的相对差」**——所以减背景用「R 差（绝对值差）」比「R-B 色差（相对差）」稳。判断通道特征前先想「AWB 会不会把这个特征补偿掉」；颜色通道依赖 AWB 后数据时天然不稳定（AWB 随画面内容动态变增益）。

**✅ 4bit 压缩是「3 通道 + 320×180」唯一可行路径（ERAM 硬约束，2026-10-16 算清）**：PH1P35 ERAM=108。RGB 3 通道 8bit×65536=76.8 ERAM，加视频流必经的 demosaic(~8，blk_mem_gen_demosaic 2048×33)+AWB delay(9.6，blk_mem_gen_awb_delay_signal 2048×96)+FIFO/zhenghe(~11)+motion_hist(3.2)≈108.6 已经顶到上限——**demosaic/AWB 抛不掉（RAW→RGB→显示必经），所以 8bit 版物理塞不下（抛 canny 也卡线）**。4bit 版：3 块 4bit×65535=38.4。⚠️ **实测下板 EMB=109 超 108 一个**（其他模块实测占 70 不是估的 68，38.4+70=108.4——估算偏乐观，务必下板看报告为准）。**最终解法：BRAM IP 深度填成 57600（刚好=320×180 降采样像素总数）省 ERAM**——安路 ERAM 按「实际 bit 数向上取整到 20Kbit」分配：4bit×65535=262140bit→13 ERAM/块，而 4bit×57600=230400bit→12 ERAM/块（每块省 1 个），3 块 36 ERAM、总 106 不超。**关键技巧：TD 的 RAM IP 深度可填非 2 的幂（65535、57600 都实测能生成），且深度直接影响 ERAM 数——生成存帧/背景 BRAM IP 时直接把深度填成「降采样像素总数」别用默认 65535/65536**。若安路仍按 2 的幂深度打包（待下板验证），兜底方案：G 通道半分辨率 32768 深再省 6 个。4bit = 取高 4 位（>>4），1 级=16 原始量纲，阈值 2 级≈原始 32（比 8bit 阈值 40 略灵敏，手内部弱差 20~30 也能被 3 通道 OR 兜住）。生成 4bit IP 参数：位宽 4、深度 57600、Dual Port RAM/SYNC/read_before_write/NOREG。

**单通道 vs 3 通道互补（「内部变黑」根因）**：单通道（R 或 B）检测时，手内部某处该通道差弱就变黑；3 通道 OR（`R差||G差||B差>阈值`）互补——手内部 R 弱时 B/G 兜住，内部不易变黑。testbench 用「R 差弱(10) B 差强(50)」的手肤色可验证 3 通道 OR 价值（R 单通道会全黑、3 通道 12320 白组整块检测）。4bit 版本垂直 4 行累加平均的位宽：4bit 输入 → 水平 4 像素和 6bit → 垂直 4 行累加器 reg[5:0]（不是 8bit 版的 reg[9:0]）→ >>2 回 4bit。

**动态目标跟踪 + 坐标叠加（高阶挑战(2)）实现路径（2026-10-16 用户提出，标准做法，复用现有模块）**：运动 mask 已能「整块手变白」，升级成「框出手 + 显示坐标」走这条链：①**软边缘**（motion 输出从硬 0/255 改成「差÷阈值×255」渐变灰度，边缘圆滑——锯齿是降采样固有，提分辨率到不了圆滑，软边缘是唯一解）②**边缘检测提轮廓**（在软边缘 mask 上做 Sobel/Canny，复用 line_buffer_demosaic 框架，提出手外轮廓线）③**质心/外接框**（累加器统计运动像素 Σx/Σy/Σn，帧尾除得质心坐标；或 min/max 得外接框）④**叠加显示**（轮廓线 + 坐标 OSD 叠加原样/灰度画面，bin2bcd + osd_cn_char 显示「X:xxx Y:xxx」）。效果 = 原样/灰度画面 + 手外轮廓线 + 坐标数字，比「整块白」直观、直接补上高阶(2)。

**⚠️⚠️ AWB 白平衡压缩色差 → 背景减除选通道的血泪结论（2026-10-16 三轮迭代，推翻上面「B 通道最明显」的旧结论）**：motion_detect 的输入是 **AWB 之后** 的 `awb_O_tdata`，不是 AWB 前。AWB 白平衡把整帧 R/B 归一化到 G（R 增益=sum_g/sum_r、B 增益=sum_g/sum_b，全局同乘），画面肤色多时会把肤色「降 R 升 B」拉向中性——**R-B 色差被压到阈值以下，全黑**；但「R 绝对值差」（手 R 高 vs 背景 R 中）在 AWB 后依然大，是肤色最稳定的特征。颜色通道五轮演进（全试过）：①灰度 R/4+G/2+B/4 把 R 权重压到 1/4→丢颜色、手内部变黑；②B 单通道 B 差仅 ~30（早期误记 50~70）、阈值 40 检测不到；③RGB 3 通道能检测（靠 R 差）但为省 ERAM 砍到 320×90→锯齿严重+旋转45°不完整；④**R-B 色差被 AWB 压缩→全黑**（且「正部分截断」`(r>b)?(r-b):0` 还把背景偏蓝信息丢了）；⑤**R 单通道 R 绝对值差 survives AWB→能检测**。**结论：竞赛背景减除选通道优先 R 单通道（手 R 高），别用 R-B 色差（AWB 会压缩）；要「内部完整不变黑」用 3 通道 OR 互补，但 8bit×65536×3 超 ERAM（76.8+其他68≈145>108），只能 4bit 压缩（3×65536×4bit=38.4 ERAM 不超，4bit 的「1级=16」等效阈值更细、配合 3 通道 OR + 时间滤波反而能兜住差 20~30 的内部弱处）或砍到 320×90。**testbench 验证通道选择的方法**：模拟 AWB 后肤色「R 差大但 R-B 差小」（如手 R=200 G=160 B=170、背景 R=140 G=140 B=140，R 差 60、R-B 差仅 30），R 单通道能检测（12320 白组）、R-B 色差会全黑，一次验证就锁定正确通道。**锯齿（块状边缘）是降采样的固有代价，光靠提分辨率到不了圆滑，得加软边缘（输出差÷阈值渐变灰度）或形态学膨胀后处理**——这是独立的第三件事，跟通道/分辨率方案解耦。

**⚠️ B 单通道下板后仍漏检 → 升级 RGB 3 通道 + 320×90 降采样（方案①，2026-10-16 最终定稿）**：B 单通道（阈值40）下板后手「内部变黑 + 旋转45°只剩一半」——根因还是丢颜色：实际肤色 B 差只有 30~40 卡在阈值边界（没想象中「50~70 那么明显」），灰度更把肤色平均掉（手肤色灰度 165 vs 背景 149 只差 16）。「哪个单通道差最明显」的思路对 B 差 50~70 的场景成立，实际肤色 B 差不够稳，单通道扛不住。方案① = **RGB 三通道分别减背景、任一通道差>阈值 OR 判前景**（手 R 差 70 明显超阈值，颜色不丢，手完整含内部）。实现要点（motion_detect.v 重写，延迟仍 3 拍，isp_top 不用改）：
- **垂直 8 行累加平均降采样 320×90**：核心目的不是抗噪，是把降采样 320×180→320×90，让 32768 深 IP 装下 3 通道。用 3 个累加器 reg 数组（`reg [10:0] acc_r[0:319]` ×3，异步读旧写新）：第 0 行 `acc<=avg` 初始化、第 1~6 行 `acc<=acc_rd+avg` 累加、第 7 行 `sum8=acc_rd+avg`、`avg8=sum8>>3`（`acc_rd=acc[grp_cnt]` 组合读，读的是上一行同 grp 的旧值，天然 read-before-write 累加）。**累加器比 7 个 line buffer 省 5 倍**（3×320×11bit=10560bit vs 21×320×8bit），但 8 行平均结果在第 7 行才输出 → 画面整体下移约 7 行（1%，肉眼无感，别纠结回溯对齐）。
- **3 块 32768 深 BRAM**（blk_mem_gen_frame_diff_32k，R/G/B 各一块）：新 IP 是 **ASYNC（有 clkb、无 cea）**——跟 motion_hist（ASYNC 有 clkb+cea）又不完全一样，例化前必读生成 .v 核对端口（老教训第 N 次踩）。资源账：3×13 ERAM=39 + 其他 68 ≈ 107，紧贴 108 上限（剩 1 个），编译后必看 BRAM 报告，超了降 256×72 或存 6bit。
- **down_cnt 改 15 位 [14:0]（0~28799）**：32768 深 IP 地址 15 位；但 motion_hist 是 65535 深地址 16 位，15 位接 16 位端口零扩展（iverilog 报 padding warning，无害）。两个不同深度 IP 地址位宽不匹配是常态，别硬对齐，零扩展/截高位都无害（down_cnt 最大 28799 高位恒 0）。
- **减背景 OR 判前景**：`motion = (|ΔR|>40) || (|ΔG|>40) || (|ΔB|>40)`，阈值 40 三通道通用（手 R/B 差超、背景灰白差小不超）。
- **放大回显垂直 4×→8×**：LB 仍 320 深×8bit，只改重复行数 4→8。

**验证 testbench 套路（关键，用「灰度几乎相同、仅某通道差明显」证明 RGB 必要性）**：背景 R150/G150/B150（灰度149），手肤色 R220/G160/B120（灰度165 只差16，B差30<阈值40，R差70>40）——灰度丢、B 单通道也漏，只有 RGB 三通道（R 差 70）能测。若还停留灰度/B 单通道，testbench 白拍数会是 0；RGB 三通道白拍数 12320（手 80组×20行×8垂直，扣 run_length 边界损失 2 组/行）。比「随机颜色」有说服力——它精确复现「手内部变黑」的根因。

**（2026-10-13 全天调试后的最终结论，冲帧差法前必读）**：
- **白点解决链**：降采样 4×1（撤销 4×4，恢复运动灵敏度）+ 时间滤波 2 帧（连续 2 帧运动）+ run_length>2 + 阈值 16。⚠️ **三帧差分（连续 3 帧）去噪过头**——手的运动边缘每个位置只有 1~2 帧帧差，3 帧相与会把手的轮廓也滤掉（只剩零星白点、看不到手），所以时间滤波用 2 帧不用 3 帧。
- **帧差在摄像头时钟域（S_csi_rx_clk），OSD 文字在 HDMI 端（hdmi_mixer）才叠加，帧差根本看不到 OSD**——「帧号滚动导致白点」是误诊（帧差在 OSD 叠加之前就完成了），除非摄像头对着显示器形成回授。别把 OSD 文字当帧差噪声源；帧号常显是「处理延迟可视化」展示点，别为此隐藏它。
- **帧差法「手轮廓不完整」是固有缺陷**（只检测「运动边缘」，手内部两帧都有、帧差≈0 是空的），工业界检测整块物体用「背景减除」。阈值关系（关键）：帧差法阈值卡「运动速度」（慢速挥手帧差 16~40 跟噪声 ±20 重叠→两难）；背景减除阈值卡「前景背景灰度差」（手 vs 背景差几十上百 >> 噪声→阈值 50 就噪声全滤+整块检测），**背景减除顺便解决帧差法的阈值两难**。简单背景减除改动量小（帧差法「存上一帧+减上一帧」改成「存固定背景+减背景」，存帧/减法/阈值全现成），但要加「背景采集触发」+ 光照不能大变。色度噪声（红蓝点）是高增益下 R/G/B 通道噪声不相关，8x 档才有、降到 4x 就没了，跟帧差法（用灰度）无关。

**解决落地（2026-10-14）：降采样退回 4×1 + 时间滤波（连续2帧运动）+ run_length 去孤立白点**——挥手终于检测出来了。关键坑：
- **存「上一帧 motion」必须用 BRAM，别用 reg 数组（分布式 RAM）**：1bit×57600 的 reg 数组综合成 distributed RAM，爆 MSlice（8664 > 8112 上限）。改成 BRAM（blk_mem_gen_motion_hist，1bit×65535，约 3 块 20Kb）。存一整帧数据（哪怕 1bit）都要 BRAM，这是硬道理。
- **时间滤波 BRAM 读延迟 1 拍，motion 要打 1 拍（motion_d1）对齐**：motion_t = motion_d1 && prev_motion，总延迟从 1 拍变 2 拍；再加 run_length 变 3 拍，O_tvalid/tlast/tuser 同步打对应拍。
- **⚠️ 新生成的 BRAM IP 可能是独立时钟（ASYNC）**：有 clkb + cea 端口，跟之前 SYNC 共时钟的 IP（无 clkb）端口不同。**每次生成新 BRAM IP，例化前必须读生成的 .v 核对端口**，别照抄上一个 IP 的端口（本次 motion_hist 是 ASYNC，例化要接 .clkb(I_clk) 和 .cea(1'b1)，照抄 frame_diff 的 SYNC 端口会缺这两个）。深度也可能是 65535 不是 65536（填深度的界面显示），57600 以下够用不影响。
- **run_length 补时间滤波的漏**：时间滤波（连续2帧）去掉「单帧噪声」，但「连续2帧都超阈值的孤立噪声点」还残留成几个小白点。噪声空间上是孤立单点、运动是成片，run_length（连续>1个运动像素，run_len 饱和到2）去孤立点、保留成片运动。别用 run_length>3（太严会误伤运动边缘）。
- **增益 84（4x 档中间值）白点最少**，往两边走白点变多（增益低信号弱、增益高噪声放大），是传感器物理特性。手「静止」时白点略多是肌肉微抖（真实微小运动），非噪声，别硬调阈值（会漏掉慢速挥手）。
- **testbench 坑**：帧差法检测「变化」不是「静止」，运动块必须帧间灰度变化（如第2帧255、第3帧100）或移动才产生帧差；让第2/3帧运动块都是255（静止）帧差=0，会误判「检测不到」。时间滤波需运动持续2帧，testbench 要 3 帧（第1帧黑、第2/3帧变化）第3帧才检测到。

**最终版（2026-10-14 后段）：时间滤波 2帧 → 三帧差分（连续 3 帧 motion 相与）+ run_length >2**——为压掉「连续2帧都超阈值的噪声簇」再上三帧差分。实现：**复用同一个 motion_hist IP（1bit×65535）例化 2 个实例级联**（u_hist1 A写motion/B读prev1=上一帧、u_hist2 A写prev1/B读prev2=上上帧，都是读旧写新），**不用重新生成 IP——同一 IP 例化多实例**。motion_t3 = motion_d2 && prev1_d1 && prev2（motion打2拍、prev1打1拍对齐 BRAM 读延迟）。总延迟 4 拍（帧差1 + 三帧差分2 + run_length1），O_* 打 4 拍。

**⚠️ 帧差看不到 OSD（架构认知，我误诊过「帧号导致白点」）**：帧差在**摄像头时钟域**（写 DDR 之前，motion_detect 在 isp_top 里）完成，OSD 在 **HDMI 端**（读 DDR 之后，hdmi_mixer）才叠加——帧差看到的画面根本没有 OSD 文字。用户问「帧差在摄像头域为什么被帧号影响」→ 我一度误诊让用户改 hdmi_mixer 隐藏帧号，是错的（白改，还损失「处理延迟可视化」展示点）。**唯一例外：摄像头对着显示器拍（视频回授，显示器画面含滚动的 OSD 帧号）**，帧号才会通过「显示器显示→摄像头拍回」绕一圈进入帧差。诊断运动检测白点前，先问清摄像头对着真实场景还是显示器——回授会引入画面闪烁 + OSD 帧号，是另一类问题。

**帧差法白点本质 = 光子散粒噪声（亮度相关，不是均匀噪声）**：白点集中在画面亮部（天花板灯附近），因为噪声 ∝ √亮度，亮度越高噪声绝对值越大、帧差越大越易超阈值。增益越高越严重（8x 档噪声放大）。所以白点分布是「哪里亮哪里多」，用户会描述「白点集中在正上方/中间」——这是亮部噪声，不是算法 bug。

**红蓝点 = 色度噪声（chroma noise），跟帧差无关**：高增益下 R/G/B 通道噪声不相关，产生彩色斑点（红蓝点），只在彩色画面可见；帧差用灰度（亮度通道），色度噪声不影响运动检测白点。解法就是**别用 8x 增益**（降到 4x 档 80~111 红蓝点消失），不是滤波问题、也不是摄像头坏。区分两类噪声：亮度噪声（黑白颗粒，影响帧差/灰度算法）vs 色度噪声（红蓝斑点，影响彩色画面观感）。

**背景减除颜色通道完整迭代链（2026-10-16 定版，别再走弯路）**：灰度（R/4+G/2+B/4 把 R 权重压到 1/4，丢颜色内部变黑）→ B 单通道（B 差仅 30 不够）→ ~~R-B 色差~~（被 AWB 压缩，全黑）→ R 单通道（内部 R 弱处变黑，无互补）→ **RGB 3 通道 4bit + 57600 深（定版）**。
- **R-B 色差全黑的根因**：AWB 白平衡把整帧 R/B 归一化到 G（R 增益=sum_g/sum_r、B 增益=sum_g/sum_b），画面肤色多时把肤色「降 R 升 B」拉向中性，R-B 差被压到阈值以下。**依赖 AWB 后数据的「色差」特征（R-B）都不稳定**；「绝对值差」（手 R 高 vs 背景 R 中）在 AWB 后依然大，是最稳的颜色特征。→ 结论：背景减除用「绝对通道差」，别用「色差（R-B/R-G）」。
- **定版 RGB 3 通道 4bit**：三通道 OR 互补（手内部 R 弱时 B/G 兜住，解决内部变黑）+ 4bit 压缩省 ERAM（离散位宽配置）+ 57600 深（比 65535 每块省 1 ERAM，见器件资源段）。取高 4 位 >>4，阈值 2 级≈32。8bit 版 3 块 65536 深必超 EMB。
- **闭运算（膨胀+腐蚀）填洞+修圆**：手不是平面，>45° 手掌凹凸产生阴影、阴影处颜色接近背景 → 内部小黑点；块状锯齿是 4×4 降采样粒度。膨胀（3×3 OR，填 <3×3 黑洞）+ 腐蚀（3×3 AND，修圆凸角、不改变外形）。加在 motion_filt 之后，两级各 +1 拍。
- **原样 SW4 叠加（比纯黑白直观）**：运动检测集成到「原样」模式（算法模式 0），SW4 拨 0→1 采背景+叠加白色前景、拨回 0 纯原样，algo_mode_sel ALGO_NUM 精简回 4（原样/灰度/二值/边缘）。叠加 = 原样数据打 5 拍对齐运动检测延迟 + 每像素 `motion标记 ? 白 : 原样`。
- **顶部屏蔽**：垂直 4 行累加平均结果在第 3 行（row_m==3）才输出，放大回显时顶部 3 行读 line buffer 垃圾值 → 加 `row_cnt_d5<3` 屏蔽（输出 0）。这是「下移 3 行」的固有边界。

## 运动检测收尾关键发现（2026-10-16，背景减除迭代定版）

**最终定版**：RGB 3 通道 4bit + 320×180 降采样 + 深度 57600 BRAM + 闭运算（膨胀+腐蚀）。完整迭代链（都是踩坑，别重走）：灰度（丢颜色）→ B 单通道（B 差 30 不够）→ RGB 3 通道 8bit 320×90（锯齿）→ R-B 色差（AWB 压缩全黑）→ R 单通道（内部弱处变黑）→ RGB 3 通道 4bit 65535 深（EMB 超 1）→ 57600 深 + 闭运算 ✅。

**⚠️ 安路 ERAM20K 位宽配置只有 1/2/5/10/20/40，没有 4bit/8bit**（DS1300 数据手册 2.2 章节，配置表：16K×1/8K×2/4K×5/2K×10/1K×20/512×40）：4bit 数据塞「4K×5」配置（5bit 宽，浪费 1bit=20%），所以「按实际 bit 数估算 ERAM」必然偏乐观。实测：4bit×65535 深 = ceil(65535/4096)=16 个 ERAM（不是 13），4bit×57600 = 15 个。**深度 57600 刚好装下 320×180（=57600），每块省 1 个 ERAM**。减 ERAM 只能「重新生成更浅深度的 IP」，改 down_cnt 回绕不省（IP 深度生成时固定）。

**⚠️ R-B 色差在 AWB 后失效（全黑）**：AWB 把整帧 R/B 归一化到 G（R 增益=sum_g/sum_r），画面肤色多时把肤色「降 R 升 B」拉向中性，R-B 差被压到阈值下。正确方向是「R/B 绝对值差」（R 单通道 或 RGB 3 通道 OR），不是「R-B 相对色差」——AWB 补偿不掉「R 绝对值高」，只能补偿「R/B 相对差」。手肤色特征「R 高」是 AWB 后最稳定的（比 B 差、R-B 差都稳）。

**背景减除 vs 帧差法（答辩概念，用户会质疑「静止也能识别是不是运动识别」）**：背景减除检测「跟背景不同的前景目标」（静止也在标记），帧差法检测「变化」（静止消失）。赛题「运动目标检测」用背景减除是标准做法（标记完整目标 vs 帧差法只画轮廓且一停就消失）。答辩话术：「我实现的是背景减除（帧差法的升级），检测相对背景出现的前景目标，运动进入立即标记、持续跟踪不丢失」。简介若写「帧差法」要主动说「升级到背景减除」圆过去。

**闭运算填洞 + 修圆（4×4 降采样的锯齿 + 手内部阴影小黑点）**：膨胀（3×3 OR 填 <3×3 降采样像素的黑洞）+ 腐蚀（3×3 AND 修圆角），加在 motion_filt 之后，两级各 1 拍延迟（总延迟 +2 拍，O_* 从 3 拍变 5 拍）。line buffer 用 reg 数组「读旧写新」的时序坑：组合逻辑异步读会读到「写之后的新值」（不是上一行的旧值），必须「在 always 块内非阻塞赋值右边读旧值」或「打 1 拍」保证读旧值。闭运算只能修「1 像素圆角」、填「<3×3 洞」，4×4 降采样是天花板（要更圆滑得提高分辨率，但 BRAM 不够/DDR 带宽顶 94%）。阴影小黑点若 >3×3 降采样像素（>12 原始像素）3×3 填不掉，要 5×5 窗口。

**叠加显示模式（原样 + 运动标记，2026-10-16，检测结果叠回真实画面更直观）**：运动检测纯黑白（前景白、背景黑）不够直观，用户要「背景检测和原样结合」→ 加一个算法模式「叠加」：前景（motion 标记=1）显示白色、背景显示原样彩色，评委一眼看懂「真实场景里手被标出来」。实现（通用套路，任何「检测结果叠加回原图」都照这个）：①algo_mode_sel `ALGO_NUM +1`；②isp_top 里原样 `awb_O_tdata` **打 N 拍对齐检测链的延迟**（motion 闭运算后延迟 5 拍，就打 5 拍 `awb_data_d1..d5`），每像素 `motion_data[bit] ? 24'hFFFFFF : awb_data_dN[23:0]` 叠加——motion_data 是 4 像素×24 位、每像素 R=G=B=motion_px（0 或 255），取 [23]/[47]/[71]/[95] 最高位当「标记 bit」；③算法 MUX 加 `3'dN : algo_data = motion_overlay`；④valid/tlast/tuser MUX 复用检测链的（叠加数据延迟 = 检测延迟，同步信号照搬）；⑤OSD 算法名加字模。叠加模式能让「检测是否准确」直接可见（手轮廓 vs 真实物体对得上），是演示/答辩加分项，比纯黑白值得优先做。

**顶部边界效应（两处都要屏蔽，2026-10-16 实测踩坑）**：① 垂直 4 行累加平均结果在第 3 行（row_m==3）才输出，放大回显「第 3 行直出 + 后续 3 行读 line buffer 重复」，顶部 row 0~2 读的是 line buffer 垃圾值/上一帧值（画面整体下移 3 行）→ 屏蔽 `row_cnt_d5 < 3` 输出 0（row_cnt 打 5 拍对齐输出）；② 闭运算的膨胀/腐蚀 line buffer 前 2 个降采样行是上电垃圾 → 屏蔽 `down_cnt_d3/d4 < 640`（前 2 行透传不膨胀/腐蚀）。两处边界是「垂直降采样平均」和「形态学 line buffer」各自的固有边界，分开屏蔽别混——用户会先报「顶部前几行不对」，屏蔽完还会报「第一行不对」，就是漏了第二处。

**SW4 集成到原样模式做开关（交互简化，2026-10-16）**：不要单独的「纯黑白运动模式」和「叠加模式」两个算法模式，而是把运动检测叠加做成「原样模式 + SW4 开关」——SW4 拨 0→1 采背景 + 在原样画面上叠加运动标记（手变白），拨回 0 纯原样。算法模式精简回 4 个（原样/灰度/二值/边缘）。isp_top 模式 0 改成 `sw4_2d ? motion_overlay : awb_data_d5`（SW4 跨时钟域打 2 拍），valid/tlast/tuser 复用 motion 的（模式 0 数据延迟 = 检测延迟，同步信号照搬，所以「原样」也延迟 5 拍但肉眼无感）。OSD「已采/未采」提示触发条件改成「原样模式 + SW4=1」。用户会更喜欢这种「运动检测内嵌默认模式」的交互，别默认堆模式数量。⚠️ **铁律（用户两次纠正）**：算法模式恒 4 档（原样/灰度/二值/边缘），OSD 只显示 4 个模式名——任何新检测功能只能内嵌模式 0 + 开关（SW4），绝不新增第 5 档（algo_mode_sel 的 ALGO_NUM 别随手 +1）。叠加实现 = 逐 24bit 掩码 MUX：motion 输出每像素全 FF(前景)/全 00(背景)，`ov0 = motion_data[23:16] ? 24'hFFFFFF : awb_d1[23:0]` 四段拼 96bit，无需 ERAM 涂白链。

详细迭代链 + 全部踩坑见 `references/motion-detect-background-subtraction.md`。

## 背景减除定版（2026-10-16/17：RGB 3 通道 4bit + 深度 57600 + 闭运算 + 叠加）

**通道迭代链（都是踩坑，最终 RGB 3 通道 4bit）**：灰度（丢颜色）→ B 单通道（B 差 30 不够）→ RGB 3 通道 8bit 320×90（锯齿严重）→ **R-B 色差（全黑！AWB 坑）**→ R 单通道 8bit（内部变黑）→ **✅ RGB 3 通道 4bit 65535 深（EMB=109 超 1）→ ✅ 57600 深（106 不超，最终定版）**。

**⚠️ AWB 压缩 R-B 色差（关键坑，2026-10-16）**：AWB 白平衡把整帧 R/B 归一化到 G，画面肤色多时把肤色「降 R 升 B」拉向中性，手的 R-B 差被压到阈值以下 → R-B 色差减背景全黑。而 R 的「绝对值差」（手 R 高 vs 背景 R 中）在 AWB 后依然大，是肤色最稳定特征。所以**背景减除别用「色差类」特征（R-B/R-G），用「绝对值差」特征（R 单通道）或「RGB 3 通道 OR」**（三通道 OR 互补：手内部 R 弱时 B/G 兜住，解决内部变黑）。

**RGB 3 通道 4bit 方案（最终）**：提取 R/G/B 高 4 位 → 水平 4 像素平均 → 垂直 4 行累加平均（320×180）→ 3 块 4bit 背景 BRAM → 减背景任一通道差>阈值判前景 → 时间滤波(2帧) → run_length(>2) → **闭运算** → 放大回显。4bit 语义：取高 4 位(>>4)，1 级=16 原始量纲，阈值 2 级≈32。

**闭运算（膨胀+腐蚀）填洞+修圆**：3×3 膨胀（OR，有前景就前景，填 <3×3 黑洞）+ 3×3 腐蚀（AND，全前景才前景，修圆块状锯齿）。line buffer 用 reg 数组 + **非阻塞赋值右边读旧值**（读旧写新），右邻居复制近似、左邻居 r_prev 缓存。总延迟 3→5 拍。

**顶部两层边界屏蔽（2026-10-17，别只屏一层）**：① 闭运算 line buffer 前 2 个降采样行垃圾 → down_cnt<640 透传；② 放大回显 line buffer 前 3 个原始行垃圾（垂直 4 行平均结果第 3 行才输出，下移 3 行）→ row_cnt<3 输出 0。两层独立，都屏。

**叠加模式（原样+运动标记，2026-10-16）**：不要纯黑白模式，运动检测集成到「原样」模式用 SW4 开关——模式 0 = `SW4 ? 叠加 : 原样打5拍`，SW4 拨 0→1 采背景+叠加（手变白），SW4=0 纯原样。原样画面打 5 拍对齐 motion 延迟，valid 用 motion_valid（5 拍），切换无错位。OSD「已采/未采」在「原样+SW4开」时显示。算法模式精简回 4 个（原样/灰度/二值/边缘）。

**4×4 降采样是硬约束（答辩要圆）**：全分辨率 1280×720 存一整帧 4bit=180 ERAM 超上限 108，降采样到 320×180 是「片内 ERAM 方案」的唯一出路。所以「边缘偏差 4~8 像素」「块状锯齿」「暗背景检测弱」都是降采样/背景减除的物理天花板，不是 bug。但「唯一出路」这个说法见下条 DDR 重新评估修正——DDR 是第二条路。

**⚠️「DDR 带宽顶 94% 被否」2026-10-17 重新评估后修正：DDR 存背景其实够用，是之前算太满**——板子 PH1P35MDG324 合封了 **DDR3 SDRAM 512Mb（64MB）/16bit/1.5V/1066Mbps，带宽 ~17Gbit/s**（权威判据：DS1300 datasheet 表 3-11 Integrated Memory I/O=1.5V=DDR3 标准电压、SDR SDRAM 是 3.3V；且 DS1300 正文「PH1P35MDG324 内部合封高速存储器，支持 SDRAM 数据位宽 16-bit 容量 512Mb」。**判「合封存储是 SDR 还是 DDR」看三点：①供电电压 1.5V=DDR3 / 1.35V=DDR3L / 3.3V=SDR SDRAM；②原理图差分时钟 FPGA_DDR_100MHZ_LVDS_P/N = DDR（SDR 用单端）；③有 DDR_VREF 参考电压 = DDR3**）。当前视频显示帧缓存（video_in 写 + video_out 读 ≈2.6Gbit/s）只占 17Gbit/s 的 ~15%。之前「94% 超限」是拿「灰度整帧读 + 整帧写回」算的（帧差法要每帧读上一帧 + 写回结果），但**背景减除只需「读背景」（写背景是采背景时一次性）**——全分辨率 RGB 4bit 背景读 = 11Mbit×60fps = 0.66Gbit/s ≈ 4%，显示 15% + 背景 4% = **19% < 100%，带宽和容量（512Mb=64MB）都充裕**。**收益：运动检测从 320×180 提到 1280×720 全分辨率（4 倍线性/16 倍面积、前景边界从 4×4 块状锯齿变 1 像素精确）+ 释放 45 ERAM（3 块背景存储，片内余量 13→58）**。方案：复用现有 DDR 控制器加一路「读背景」+ DDR 仲裁 + 跨时钟域 FIFO（改动中高）；进阶 = 显示改直通（异步 FIFO 不用 DDR 整帧缓存）把 DDR 带宽 100% 解放。⚠️ 但「边缘偏差/块状锯齿是降采样固有」的答辩话术仍成立，只是「唯一出路」被修正——DDR 是第二条路，代价是 DDR 仲裁复杂度。评估文档在工程根目录 `资源清单.md`（芯片/板级资源 + ERAM 瓶颈）、`资源全用评估.md`（DDR 全用方案 + 性能量化）。

**⚠️ DDR 存背景（第三个整帧访问）导致「闪烁」——瓶颈是「切换频率」不是「带宽」，占空比/防抖都无效（2026-10-18 实战）**：DDR 存背景的坑不是带宽（合封 DDR3 17Gbit/s 够），而是「第三个整帧访问」——video_in 写一帧 + video_out 读一帧 + 背景读一帧，三个访问抢一个 DDR 口，背景读把原本稳定的「写→读」节奏打乱，DDR 读写指针在周期点错位一下 → 现象「横白线约 18 根、分布均匀、切换到其他算法也闪烁」（错位是 DDR 底层周期，跟算法无关，所以切算法也闪）。**「帧同步读」「空闲防抖」「占空比 25%（突发 60 停 180）」都无效**——因为「读的总量」（每帧读一整帧）没变、切换次数没减，只是延后了触发。**正解两步：①模式使能——背景读只在运动检测（原样+SW4）模式读，切其他算法关掉背景读，其他算法回到两路节奏不闪；②降分辨率——背景降采样 640×360（2:1），背景读数据 1/4、切换 1/4，运动检测模式节奏也稳。** 教训：DDR 单口 + 多路访问的瓶颈是「切换频率」不是「带宽」，减少「读的总量」（降分辨率）才减切换；调「读的节奏」（防抖/占空比）不减总量、没用。⚠️ 背景读的「每帧读一整帧」是「必要」的（减背景用，且背景片内 ERAM 存不下、不能缓存），所以「隔帧读」也不行——只能降分辨率或模式使能。

**⚠️ 闪烁更深层根因 = 背景流与当前帧缺帧同步对齐（2026-10-19 补，比「切换频率」更深一层）**：地址验证（IMAGE_BASE_ADDR_4 28000000→0）下板结果「白线没消、闪烁频率降低」——坐实「跨 bank 切换」只是开销之一、非根因。真根因在时钟域 + 对齐缺失。**权威时钟频率（读 `prj/FPGACompetition_Runs/phy_1/final_timing.rpt` 的 Clock Summary 表，别手算 DDR PLL 分频——IP 参数 PLL0_REFCLK_FREQ=100 但 ref_clk 实为 50M、PLL1_REFCLK_FREQ=133.3 也非实际，参数语义会误导）**：摄像头 S_csi_rx_clk=**60MHz**（MIPI 240M÷4，`o_fabric_div4_8_clk` 直通 BUFG 成 O_hs_rx_clk）、DDR 用户接口 usr_clk（=S_ddr_clk=dhi_clk）=**66.667MHz**、ddr_clk=**266.667MHz**、HDMI 像素=**75MHz**/串行=**375MHz**。⚠️ 之前记忆里「摄像头 74.25M」「usr_clk 133.3M」都是错的；**60M vs 66.667M 只差 11% 的异步边界，是三个整帧访问里最容易错位的跨域**。**闪烁三处代码硬证据**：①bg_read 的 data_128bit_to_96bit `I_128b_frame_start` 接 `1'b0`（帧对齐「留阶段2」没做）②motion_detect 减背景直接 absdiff、**不看 `I_bg_valid` 门控**（背景 FIFO 读空时减的是旧/错位数据）③DELAY=55 拍脑袋硬凑。bg_read FIFO 读侧 `re=1'b1` 直读 60M、写侧被仲裁+防抖卡到低有效速率 → FIFO 频繁读空 → 背景 valid 断续 → 减背景错位 → 白线。**这解释了为什么「占空比/防抖/地址」都只能降频率不根治——它们动的是「读的节奏」，没动「读出的背景跟当前帧对齐」这件事**。治本（优于降分辨率）：背景解包 I_128b_frame_start 接真实背景帧开始（跨时钟域同步过去）+ motion_detect 减背景用 I_bg_valid 门控 + 对齐拍数下板调；降分辨率 640×360 是治标（错位频率降到 1/4）。

**⚠️ 改模块延迟后，所有对齐它的地方要连锁改（2026-10-18 实战，motion_detect 5→57 拍导致右边黑屏）**：motion_detect 重写（加 DDR 背景读 + 延迟对齐 DELAY=55 拍）后延迟从 5 拍变 57 拍，但 isp_top 里「原样数据打 5 拍」和「同步信号 MUX（用 motion_valid）」没改，导致原样模式数据（5 拍）和同步信号（57 拍）错位 52 拍 → video_in 写 DDR 时数据比 valid 早到、尾部数据没写进 → 「右边黑屏」。**改任何模块的流水线延迟，必须 grep 所有「对齐它的延迟」的地方（数据打拍、valid/tlast/tuser 的 MUX 选择）一起改**，别只改模块内部。且「数据延迟」和「valid 延迟」要精确相等（motion_detect 里数据 58 拍、valid 57 拍曾差 1 拍，也要对齐——去掉多余的 dilate_d1 打拍才对齐）。

**DDR 帧缓存多路仲裁（运动检测 DDR 存全分辨率背景，2026-10-17/18 踩坑）**：
- **DDR 是单路 AXI 接口**：ph1p35_324_ddr_wrapper 只有一组 `I_mc_app_addr/cmd/en/wdf_*` + `O_mc_app_rd_*`，video_in（写）+ video_out（读）靠顶层「busy 互斥」共享这一路（`S_ddr_user_addr = 写使能?写地址 : 读使能?读地址 : 0`，写优先；mc_to_user_interface 把用户接口转 AXI）。加第 3 路（背景读）要把这个互斥扩成 3 路。
- **背景写复用 video_in、不新建写模块**：采背景帧（bg_capture 覆盖完整一帧，motion_detect 的 bg 状态机生成、跨时钟域打 3 拍到 DDR 域）时，写地址切到背景缓冲区 `IMAGE_BASE_ADDR_4=28000000`（第 5 块；前 4 块乒乓是 0/7000000/14000000/21000000），写指针不动（采背景帧不写正常乒乓，显示读上一帧）。背景写数据 = video_in 的打包 128 位，直接复用现成写突发。
- **⚠️ 踩坑 1：背景读「自由循环持续读」会饿死显示 → 画面闪烁**。bg_read 若读完一帧又读一帧持续抢 DDR，video_out 读被饿死、FIFO 读空 → 画面一闪一闪（时序/仲裁竞争）。**背景读必须「帧同步受控读」**：I_frame_start（DDR 域帧开始，从 video_in 的 S_frame_start 引出）触发读一帧、读完（S_rd_total==FRAME_CNT-1）停、等下一帧再读。调试时给 bg_read 加 I_bg_en 使能开关：阶段 1 接 0 禁用（只验证「背景写 + 仲裁」不破坏显示），阶段 2 接 1 启用。
- **⚠️ 踩坑 2：3 路仲裁「同时触发」竞态**。video_in 写和 bg_read 读若上一拍都空闲、这一拍同时满足触发，写优先会让 bg_read 的地址被写地址覆盖、整个 240 拍突发读错。**bg_read 读使能要「当前拍避让」**：`O_rd_en = S_rd_valid & ready & !video_in_wr_busy & !video_out_rd_busy`，不能只靠触发条件的 busy 判断（那是上一拍的值）。
- **96↔128 打包/解包**：data_96bit_to_128bit 是「4 个 96 位拼 3 个 128 位」的滑动窗口（96/128 最小公倍数 384，cnt=1/2/3 输出 3 个 128 位、cnt=0 空洞）。解包（data_128bit_to_96bit）是逆运算：3 个 128 位拆 4 个 96 位，**输出节奏 3:4 不均匀**——cnt=2 时要输出 C 和 D 两个 96 位，D 缓存到下一拍（输入空洞拍）输出。解包后的 96 位背景给 motion_detect 减背景。
- **延迟对齐（待下板调）**：背景读延迟 = DDR 读（video_out 注释「约 40 拍」）+ 跨时钟域 FIFO + 解包 1 拍 ≈ 45~55 拍。motion_detect 当前帧打 DELAY 拍（localparam DELAY=55 拍脑袋、下板调）对齐背景。帧对齐（解包 I_128b_frame_start）暂接 0，若前景整帧错位再补帧同步。
- **全分辨率减背景**：删掉 320×180 降采样 + 3 块 4bit 背景 BRAM，改「96 位当前帧 − 96 位背景，任一通道 |Δ|>40 判前景」（8bit 阈值，手肤色 R 差约 70），前景边界 1 像素精确、不再 4×4 块状锯齿。闭运算先简化为水平 3 邻域 OR（去孤立点），完整 3×3 后续可加。减背景阈值 8bit（不是旧 4bit 的「1 级=16 量纲」），别照搬旧阈值。

**运动检测 DDR 改造（2026-10-18 阶段 1：背景写 + bg_read + 3 路仲裁）**：背景写**复用 video_in 写通道**（不新建背景写模块——采背景帧 bg_capture 写地址重定向到第 5 块缓冲区 `IMAGE_BASE_ADDR_4=28000000`、写指针不动，0 额外 ERAM）；新建 bg_read 自由循环读背景（低优先级，读地址读完一帧回起始）。⚠️ **DDR 单路接口多路访问的仲裁竞态（关键坑）**：3 路互斥（video_in 写 + video_out 读 + bg_read 读）的 busy 信号是组合判断对方 busy，会「同时触发」竞态——video_in 写和 bg_read 读同时触发时，合并逻辑写优先、bg_read 读的地址被写地址覆盖、读错一整个突发。**修复：bg_read 读使能加「当前拍避让」`O_ddr_user_rd_en = S_rd_valid & ready & !I_video_in_wr_busy & !I_video_out_rd_busy`，读在 video_in 写/video_out 读忙时暂停（读计数不递增）、空闲再继续**。通用教训：DDR 单路接口加多路访问别只靠 busy 互斥（组合判断会同时触发竞态），读使能要当前拍避让写。完整架构 + 阶段 2 待做见 `references/motion-detect-ddr-migration.md`。

**（已废弃：并行+门控三路仲裁整体失败，最终解 = 串行状态机仲裁 ser_arbiter.v，详见 references/ddr-video-framebuffer-arbiter.md §18.21）——DDR 帧缓存加第 3 路访问（背景读写）的仲裁模式（2026-10-17 实施，运动检测 DDR 改造阶段 1）**：给单路 DDR 接口（video_in 写 + video_out 读，原本 2 路 busy 互斥，顶层 `S_ddr_user_addr = 写?写地址:读?读地址:0` 写优先）加第 3 路「背景读写」，落地要点：①**背景写复用 video_in**——采背景帧（bg_capture 覆盖完整一帧，从 motion_detect 经 isp_top 透传引出）时写地址切换到背景缓冲区（第 5 块 `IMAGE_BASE_ADDR_4=28000000`，每帧数据 230400 个 128 位），写指针不动，不另建写通道；②**背景读独立模块 bg_read**——读地址自由循环（背景固定、无需帧同步对齐，帧对齐留阶段 2），跨时钟域 FIFO（DDR→摄像头）输出 128 位背景；③**3 路仲裁**：video_in 写/video_out 读的 busy 互斥各自加 `|| bg_rd_busy`，bg_read 低优先级（`!video_in_wr_busy && !video_out_rd_busy` 才触发）；④**⚠️ 竞态修复（关键，否则背景读错整个突发）**：bg_read 读使能要「当前拍」避让 `O_ddr_user_rd_en = S_rd_valid & ready & !I_video_in_wr_busy & !I_video_out_rd_busy`——否则 bg_read 和 video_in 写「同时触发」（上一拍都空闲，两个 S_rd_valid/S_ddr_wr_valid 同一拍置位）时，合并逻辑写优先会把背景读地址覆盖成写地址，读错整个 240 拍突发、减背景错位几十像素。底层合并扩展：`S_ddr_user_rd_en = vo_rd_en || bg_rd_en`、地址 `写?写地址:vo读?vo读地址:bg读?bg读地址:0`（写优先不变）。

## 运动检测 DDR 改造（2026-10-18，全分辨率背景减除的尝试与两个架构级教训）

目标：背景减除从「片内 ERAM 320×180 降采样」升级到「合封 DDR 全分辨率 1280×720」。架构：背景写复用 video_in（采背景帧写第 5 块缓冲区 28000000、写指针不动）；背景读独立 bg_read 模块（帧同步受控读 + 128→96 解包 + 跨时钟域 FIFO）；3 路 busy 互斥仲裁（bg_read 低优先级，只在 video_in 写 + video_out 读都空闲时读，读使能当前拍避让）。

**⚠️ 核心教训 1：DDR 单端口三整帧访问必打架**（同「DDR 存背景导致闪烁」条：~23% 带宽非瓶颈，是仲裁时序竞争）。**⚠️ 核心教训 2：改模块延迟必须同步改下游对齐**（同「改模块延迟后连锁改」条：motion_detect 5→57 拍错位 52 拍→右边黑屏）。

**⚠️ DDR 半速根因 + 时钟树 + 调时钟方向（2026-10-19，重大修正）**：米联客把 DDR ref_clk 接 50M 晶振(C4) 而非板上的 100M 差分晶振(SIT9121, 引脚 K5/L5)，导致**整个 DDR 半速**（内存 533Mbps + usr_clk 66.667，带宽 8.53G 而非标称 17G）——这才是背景读写侧速率不足、白线上下漂移的真根因。调满速正解=ref_clk 换 100M 差分晶振；⚠️ 改 `CLK0_DIV ×4→×2` 是错的（usr_clk 翻倍但内存半速，速率不匹配 MC 饿死）。bg_read 读侧 re=1'b1 直读会丢解包 D 错位出白线，re 应接当前帧 128 位 valid。详见 references/ddr-clock-tree-half-speed.md。

**128↔96 打包/解包**：data_96bit_to_128bit 是「4 个 96 位拼 3 个 128 位」的滑动窗口打包（96/128 最小公倍数 384，S_cnt 0~3 循环）；data_128bit_to_96bit 是逆运算（3 个 128 位拆 4 个 96 位，输出比输入多 1 拍需缓存第 4 个 96 位到 S_pending）。背景存 DDR 是打包后的 128 位，减背景要解包回 96 位对齐当前帧的 96 位域。

## 自动曝光 AEC（高阶挑战(5)）

闭环负反馈：统计一帧平均亮度 → 比目标亮度 → 亮减曝光/暗加曝光，直到稳定。**比帧差法简单得多**——帧差法要存一整帧（DDR 带宽顶到 94%），自动曝光只要「统计一个数」（累加器），完全不用碰 DDR。这是用户嫌「帧差法麻烦、对硬件要求高」后选的替代高阶项（同分、更简单、还能解决手动曝光的过曝问题）。

- **两个新模块**：`brightness_stat.v`（亮度统计，放 isp/ 接 gray_data 像素域；28 位累加器累加一帧灰度、帧尾 `O_avg = r_sum[27:20]` 右移 20 求平均≈除以像素数 921600，14% 偏低可接受；帧计数每 10 帧输出一个 `O_adjust` 调节脉冲）+ `ae_auto.v`（放 key/，24MHz 域复用 ae_set 写寄存器通道；比较目标 128 ± 死区 16、亮减暗加曝光、`localparam STEP=100/AE_MAX=3990/AE_MIN=2`；O_avg/O_adjust 内部跨时钟域打两拍同步）。isp_top 加 O_brightness_avg/O_brightness_adjust 输出端口。
- **调节频率不能太快**：数据手册「曝光第 N 帧写入、第 N+2 帧生效」有 2 帧延迟，每帧调会过冲振荡，故每 10 帧调一次（帧计数放 brightness_stat 像素域，别放 ae_auto——那要帧结束信号跨时钟域，麻烦）。
- **SW3 切换自动/手动**：SW3 低电平=自动（`~I_sw[2]`）、高电平=手动。顶层 MUX：`S_ae = I_sw[2] ? ae_set.O_ae : ae_auto.O_ae`、`S_ae_req` 同理；**ae_set 的 I_enable 改成 `~S_mode[1] && I_sw[2]`**（手动模式才允许按键调曝光/增益，否则自动模式下 S_mode 0/1 跟 ae_auto 抢写曝光寄存器）。ae_set 的 O_ae/O_ae_req 改接中间信号 S_ae_manual/S_ae_req_manual，S_ae/S_ae_req 变 assign（MUX 后）。
- **OSD 显示「自动」标记 + 「目标」行**：曝光行括号里 AE 换成「自动」（「曝光值(AE)」→「曝光值(自动)」，AE 2 字符↔自动 2 字符，字符数不变布局不动，`S_txt_char = S_auto_mode_2d ? 8'h80+8'd36 : 8'h80+8'd23`）；目标行「目标:xxx」（Y=106，6 字符，只在 S_auto_mode_2d==1 时显示）。新增字模 36~40=自/动/手/目/标（「手动」复用「手」+「动」）。hdmi_mixer 加 I_auto_mode/I_target 输入 + bin2bcd_target。
- **最终方案（演进后，别退回第一版）**：**手动/自动共享同一个曝光值寄存器**；**增益也加入自动调节（完整 AEC+AGC，曝光优先增益兜底）**；**目标亮度可调**（不是写死 128）。增益值 128 是 8x 不是 12x（要减 16 再查 SC500GainTbl）。
- **目标亮度可调（已实现，target_set.v，复用自动模式下的 S_mode 0）**：自动模式曝光自动了、S_mode 0 空出来改调目标亮度；手动模式 S_mode 0 仍是调曝光，不用扩 S_mode 位宽。`key/target_set.v`（同 threshold_set 结构：S_mode==0 且 SW3 低时使能、初始 **60** 不是 128、步进 8、范围 0~255）。ae_set 的 TARGET localparam 改成 input 端口 `I_target`，比较用**饱和上下界**：`target_upper = (I_target>239)?255:(I_target+DEADBAND)`、`target_lower = (I_target<DEADBAND)?0:(I_target-DEADBAND)`——别直接写 `I_target ± DEADBAND`（目标调大后 8 位加减会溢出/下溢，边界处比较错乱）。数码管 S_mode 0 分支按 SW3 选显示：`seg_data = I_sw[2] ? {FFFF,S_bcd_ae} : {FFFF,S_bcd_target}`（手动=曝光、自动=目标亮度）；hdmi_mixer 的 I_target 接 S_target（不再写死 8'd128）；新增 bin2bcd_target。
- **目标值别设 128，按环境光实测调（实战教训）**：目标 128 = 平均灰度要稳在 128（中间灰），但房间光下即使曝光拉到 3990 + 增益 143（8x 档最大 15.75x），画面平均亮度也只有 60~80，**够不着 128 对应的平衡区间 [112,144]** → 自动曝光永远卡在「太暗→加曝光/加增益」分支、一路顶到上限（3890/143）平衡不了。表现就是用户问「自动只能调到 3890 143，是目标值太高了吗」——是的。目标值要设成「当前光线下最大曝光+增益能达到的平均亮度」附近，房间光约 50~70，初始设 60。做成可调后现场边看画面边调（调的目标是「曝光/增益不顶到上限、画面亮度合适」），别写死一个拍脑袋的值。

  **目标亮度 + 二值化/Sobel 阈值初始值必须配套（实战，别各自拍脑袋）**：三个初始值同一套量纲，否则上电后自动曝光画面（平均亮度≈目标）下二值化/Sobel 效果不对。用户实测：目标 100 时二值化阈值 60、Sobel 阈值 128 最清晰。规律：二值化阈值≈目标亮度（「灰度>目标就白」=让比平均亮的前景变白）；Sobel 阈值≈目标的一半左右（画面暗则边缘梯度小，阈值跟着降，256 是按较亮画面设计的）。之前目标 60 + 二值化 128 + Sobel 256 三套不配套，上电切二值化全黑、切 Sobel 检测不到边。改法：target_set 初始 60→100、threshold_set 初始 128→60、sobel_threshold_set 初始 256→128。「平衡」的算法 = 平均亮度落在 [目标-死区, 目标+死区] 内就停，死区是防振荡的滞环容差（类比空调恒温「低于 25 制热、高于 27 制冷、中间停机」）；每 10 帧统计一次（曝光第 N+2 帧生效，留足余量防过冲）。

**阈值联动自动调节（定稿方案）**：SW34=00 且自动状态时二值化阈值=avg、Sobel 阈值=avg×4（11bit 域），auto_en=1 时阈值直接跟随联动值、按键忽略；手动状态按键调、自动不覆盖。系数依据（用户要求「自动模式下算法显示不随曝光/增益剧烈变化」）：阈值跟亮度走、画面占比稳定；增益抬噪声同时抬 avg 有自稳性，系数下板不满意再调。实现坑：TD 带 initializer 的 wire 先声明后用（联动块放例化前）；avg 像素域进 24M 域打两拍。

- **手动/自动必须操作同一个参数寄存器，别分两个模块再 MUX（实测踩坑：切换跳变回初值）**：第一版是 ae_set（手动，r_ae 初始 1990）+ ae_auto（自动，r_ae 初始 1990）两个独立模块 + 顶层 MUX 选输出。用户实测：自动模式把曝光调到 3990，切回手动变回 1990——因为两个模块各有一个 r_ae，MUX 切换时从自动的 3990 跳到手动的 1990（不共享）。修复：**把自动调节逻辑合并进 ae_set**（ae_set 加 I_auto_en/I_avg/I_adjust 输入，内部 `if(I_auto_en) 自动亮度闭环调 r_ae_set / else if(I_enable) 手动按键调 r_ae_set`，I_auto_en=~I_sw[2] 与 I_enable=~S_mode[1]&&I_sw[2] 天然互斥），r_ae_set 是唯一寄存器、手动自动共用，切换不跳变；ae_auto.v 废弃、顶层删 MUX、S_ae/S_ae_req 直接接 ae_set 输出。教训：调节类参数（曝光/增益/阈值）的「手动」和「自动」是同一变量的两种驱动方式，应该共用一个寄存器，别拆成两模块再 MUX（MUX 会跳回各自初值）。

- **完整 AEC+AGC（曝光优先、增益兜底）**：数据手册「曝光时间优先，曝光到顶再调增益」。自动模式一个 if-else 同时管曝光和增益：太暗 → 先加曝光（AE_STEP=100），曝光到 3990 再加增益（AG_STEP=16）；太亮 → 先减增益（AG_STEP=16），增益到 16 再减曝光（AE_STEP=100）。增益参数 AG_MIN=16/AG_MAX=143（8x 档最大，0x2f 非法会花屏）/AG_STEP=16（约半档）。增益变化走同一个「r_ae/r_ag 变化就触发 O_ae_req」的写寄存器逻辑，不用额外改触发（那个 `(r_ae!=r_ae_set)||(r_ag!=r_ag_set)` 判断天然覆盖增益）。

  **演进：曝光优先增益兜底会「曝光一路顶到 3890 才动增益」（用户不满，要权重分批次）**：改成「曝光/增益按权重交替」——太暗时曝光调 AE_WEIGHT 次、增益调 1 次（加曝光不增噪故曝光权重高），太亮时增益调 AG_WEIGHT 次、曝光调 1 次（减增益降噪故增益权重高）。用两个计数器 r_dark_cnt/r_bright_cnt 实现交替：`if(cnt>=WEIGHT) 调另一参数并清 cnt，else 调主参数并 cnt++`，权重做成 localparam AE_WEIGHT/AG_WEIGHT（默认 3）可调，值越大增益参与越晚。好处：增益从调节一开始就同步参与，不再等曝光顶满；顺带修了「曝光最多只能到 3890 碰不到 3990 真上限」的 off-by-one（原 `else if` 串行使曝光到 3890 就转去调增益，改交替后曝光分支走 else 能到 AE_MAX=3990）。

- **滚动快门摄像头曝光/增益切换瞬间输出异常帧（帧撕裂/花屏），用「丢弃切换帧」解决**：SC500 是滚动快门（逐行曝光），自动曝光触发后 I2C 要 ~2ms 连写 5 个寄存器（曝光 3+增益 2），写入落在某一帧中间 → 同一帧里上半屏已按旧曝光采完、下半屏用了新曝光 → 「上下撕裂」（上半个屏幕改了、下面没来得及，**不是**数据错位的花屏，画面结构还在）。手电筒强光下更严重：曝光被减到接近下限（极短曝光）、增益档位剧烈切换，切换瞬间摄像头输出一整帧异常数据，写进 DDR 显示出来就是「花一下」。铁证 = 帧号「每隔 N（=调节周期）花一下」——花屏跟调节强相关。根治要把曝光写入对齐帧消隐期，但 I2C 100kHz 写 5 寄存器 2ms > 帧消隐期 0.67ms，塞不下。**实用解法「丢弃切换帧」**：把 ae_set 的调节请求 S_ae_req（24M 域）跨时钟域同步到 video_in（DDR 域），检测上升沿后跳过下一帧——`r_skip_next` 置位 → 下一帧 S_frame_start 时写指针不变 + `r_frame_masked` 屏蔽这一帧 DDR 写（FIFO 攒的异常数据不写进 DDR，下一帧 S_fifo_rst 清空），缓冲区保留上一帧正常画面，异常帧永远不显示。改法：①video_in 加 `input I_ae_req` 端口 + 3 拍同步 + 上升沿检测（`ae_req_s2 & ~ae_req_s3`，别用电平直连——S_ae_req 是 24M 一拍脉冲）+ r_skip_next/r_frame_masked 两个标志；②写指针判断加 `|| r_skip_next`；③写突发条件加 `&& (!r_frame_masked)`；④顶层 video_in 例化 `.I_ae_req(S_ae_req)`（跟 uicfgcs500 的 I_ae_req 同信号）。副作用：每次调节丢 1 帧（重复上一帧，自动曝光调整期间帧率约 54fps 轻微卡顿，亮度进死区后不调节不丢帧），但异常帧不显示了 → **调节频率可放心加快**（30 帧改回 10 帧，用户原话「有问题的不显示」）。若丢 1 帧还偶尔花，异常帧可能在「再下一帧」，改成连跳 2 帧罩住。**⚠️ 跳帧触发信号别用 I_ae_req（调节请求），要用 I_ae_cfg_done（I2C 写完）——实战迭代后确认的修正**：I_ae_req 发生在 I2C 写寄存器「之前」，从它触发到摄像头真正切换之间隔着 ~2ms 的 I2C 写入（5 个寄存器），时序有抖动，跳帧总是「偏早」罩不准——即使连跳 2 帧，异常帧仍偶发落在跳帧窗口之后（用户实测「一次花屏 2 次、一次花屏 3 次」）。正确做法：跳帧触发改用 `I_ae_cfg_done`（uicfgcs500 的 O_ae_cfg_done，曝光表写完成 = I2C 刚写完），它的上升沿精确对齐「摄像头即将切换」时刻，连跳 3 帧（异常帧可能持续 2~3 帧）才稳定罩住。O_ae_cfg_done 生命周期：初始化完成=1、收到 I_ae_req 时=0、曝光表写完=1，上升沿即「I2C 写完」——注意初始化完成时也有一个上升沿（会跳过流刚起来的前 3 帧，无害）。顶层 video_in 例化改 `.I_ae_cfg_done(S_ae_cfg_done)`，跳帧逻辑用 `[2:0]` 计数器 `r_skip_cnt`（触发置 3、每帧 S_frame_start 减 1、>0 时屏蔽写 + 写指针不动）替代单 bit r_skip_next（连跳 N 帧比「跳 1 帧」更通用、可调）。

**潜在坑（待观察，未根治）：「切算法瞬间画面撕裂成多段（一分为 3）」**：Sobel 的 line buffer 让数据整体延迟 2 拍，isp_top 的 valid/tuser/tlast MUX 在 `algo_mode_2d` 从非 Sobel 切到 Sobel 时，同步信号会「从 0 拍延迟跳到 2 拍延迟」。若这个切换正好落在跳帧窗口或帧边界附近（强光下自动曝光频繁触发跳帧、写指针节奏被打乱），帧开始信号可能错位一下 → video_in 写指针多走/少走一格 → DDR 乒乓读写指针错位 → 画面横切多段。复位后读写指针重新对齐就恢复，是偶发的时序竞争。根治方向（未做）：给「算法切换」也加跟曝光切换一样的帧对齐/跳帧保护。现象与「花屏」区分：花屏 = 单帧异常数据（调节触发、每 N 帧花一下）；一分为 3 = 持续撕裂成段（读写指针错位、复位才恢复）。与此区分：之前的「帧撕裂」描述是上下亮度不一致（滚动快门固有，降频率缓解），「花屏」才是数据错位（异常帧，丢帧根治）——两者用户会先后报告，别混成一个问题。⚠️ **「1 分为 3」还有一个物理触发（2026-10-18 实测：膝盖碰桌子震动就触发）**——震动导致摄像头排线/电源接触不良→帧同步丢失→写指针错位，跟「切算法」的逻辑触发是两码事。判别：震动/碰一下就花 = 先查物理连接（摄像头排线最细最松、HDMI 线、电源），插紧再复位，别急着改代码；逻辑触发（切算法+跳帧）才走「算法切换加帧对齐保护」的根治。

**⚠️「帧撕裂=滚动快门固有、只能降频率缓解」的结论被官方数据手册推翻（2026-10-11 查到 SC500CS 数据手册 V1.8 后修正）——撕裂根因是增益没设 `0x3e03=0xb`，可根治，别再用「放慢调节频率」的权宜之计**：SC500CS 的曝光/增益本来就是帧同步的（数据手册 2.2.2 明确「第 N 帧写入、第 N+2 帧生效」，切换发生在帧边界、不该撕裂）。撕裂的真正根因是**增益没进「手动控制模式」**——数据手册 2.2.3 要求 AGC 手动控制必须先写 `0x3e03` 的 Bit[3:0]=0xb，而米联客驱动整个没写 0x3e03（grep uics500_cfg 目录只有 3e00/01/02/08/09），导致模拟增益寄存器 0x3e08/0x3e09 写入「立即生效」（模拟增益是模拟电路、切换立即作用到当前帧）→ 滚动快门撕裂。根治是 **Group Hold 帧同步**，不是单写 0x3e03（⚠️ 实测只写 `0x3e03=0x0b` 仍有撕裂，别停这步）：①曝光表写增益前写 `0x3e03=0x0b`（AGC 手动控制使能，只是**必要前提**）；②曝光表改用 **Group Hold 打包**成 9 个寄存器——`0:3800=0x00`(开始打包 group0)→写 3e00/01/02+3e03=0xb+3e08/09→`7:3800=0x10`(结束打包)→`8:3800=0x60`(group0 在帧内特定时刻统一生效)，REG_SIZE 5→9。`0x60` 让整组寄存器在「下一个帧内生效时刻」统一生效，才是撕裂的真根治。数据手册还提供 **Group Hold** 机制（`0x3800` 写 0x0X=开始打包/0x1X=结束/0x6X=立刻生效/0x4X=延迟 N 帧生效，`0x3817[3:0]` 控帧延迟 N），可做「原子+帧同步」更新一组寄存器的更精细控制。曝光寄存器是 20 位 `{0x3e20[3:0],0x3e00[7:0],0x3e01[7:0],0x3e02[7:4]}`、最大 2×帧长-10=3990。完整寄存器要点见 `references/sc500-frame-sync-registers.md`。

- **OSD 曝光/增益的标记从 AE/AG 改成「手动/自动」（用户要求，别保留 AE/AG）**：用户原话「AGAE 不要了，改为手动和自动」。曝光行「曝光值(手动/自动):xxxx」、增益行「增益值(手动/自动):xxxx」，两行都用 S_auto_mode_2d 决定第一个字 `8'h80+8'd36(自) 或 8'h80+8'd38(手)`，第二个字固定「动」8'd37（手动/自动第二个字都是「动」，所以只变第一个字、字符数不变布局不动，跟「AE↔自动」的字符数一致的道理）。AE/AG 这两个缩写标记彻底废弃。

## 竞赛项目参考架构（重点抄的对象）
一个可复用、能塞进单颗芯片跑「采集 + 显示」两套大工程的顶层范式：
- **A/B 双工程合并 + 单 SDRAM + 单 UDP 协议栈 + Mux 分时复用**，用 2 位拨码开关选模式。
- 复位分「域复位」（A 域只在采集模式活、B 域只在显示模式活），模式切换用 2048 周期计数器给 SDRAM/UDP 做重配置复位，防总线挂死。
- 图像处理用「逐像素流水线先算好所有通道结果、再按模式 case 选输出」，省面积。

详见 `references/guoyi-reference-architecture.md`（2025 安路国一开源作品完整剖析，含 UDP 分包协议字段表和 16 种图像处理模式）。

**DDR 控制器架构（单路 AXI + busy 互斥 + 加一路访问的仲裁套路）**：PH1P35 视频流「摄像头→video_in 写 DDR→video_out 读 DDR→HDMI」里，DDR 控制器是**单路 AXI 接口**（ph1p35_324_ddr_wrapper.v 的 `I_mc_app_*`），video_in/video_out 靠 busy 信号互相避让（2 路互斥、无调度器），4 块乒乓缓冲区地址 0/7000000/14000000/21000000。要加第三路访问（背景读写、帧缓存）＝加第 5 块缓冲区 + 新建读/写模块 + 扩成 3 路互斥（背景读写低优先级、只在两路都不 busy 时做）。完整接口、突发、带宽账见 `references/ddr-controller-architecture.md`。

**⚠️ DDR usr_clk 8:1 铁律（2026-10-23 下板坐实，「4:1 标准」不适用本 IP）**：官方 lab_ex1 和米联客给的 DDR IP 都跑 **usr_clk 66.667M（8:1）**——IPUG035「只支持 4:1」的说法对这个 MIS DDR IP 版本无效，4:1（改 CLK0_DIV ×4→×2）实测两版都**校准失败→黑屏+写帧计数0**：MC↔PHY 的 DFI 接口是同步接口（MC 在 dhi_clk/usr_clk 域、PHY 在 ctl_clk 域），改比例把 1:1 打成 2:1 → 命令/数据采样错位。**dhi_clk=ctl_clk=内存 CK 三者 1:1 锁死；要 usr_clk 快只有整体等比超频（VCO 缩放、所有时钟同比），1600Mbps 参数集见 references/ddr-video-framebuffer-arbiter.md §17.18**。IPUG035/Soft FIFO/ERAM 文档在板子资料 `6_PH1P35数据手册/参考IP设计资料文档.zip`。

## 陷阱
- 错位类 bug 排查：references/bug-misalignment-debug.md
- 变量命名可能「反了」：国一作品里 `IMG_PICSEQ` 实际存帧号、`IMG_FRAMSEQ` 实际存包号，但拼接顺序与上位机解析顺序恰好对上，功能正常——读代码时别被变量名带偏，以实际递增位置为准。
- 上位机 UI 名可能骗人（如「运动检测」页实际没实现，复用视频显示逻辑）。
- 图像发送顺序是 G-R-B，上位机 numpy reshape 成 BGR 给 OpenCV 正好对上——这是刻意的，别当成 bug「修」回去。
- 写「数 N 个时钟 = X ms」时序/tick/分频注释前，先 grep 例化处 `.I_clk(...)` 确认实际时钟频率再算周期，别套「100MHz 数 10 万 = 1ms」常识值。踩坑：ae_set 的 I_clk 接 S_24m_clk（24MHz），数 100000 周期 ≈ 4.17ms 不是 1ms，注释错写「约 1ms」被用户抓到。复位链路（S_rst_n=PLL 锁定）与 ae_set tick 连续调节见 references/video-project-ae-key-reset.md。
- **localparam 算 `CLK_FREQ*时间参数` 中间结果溢出**：`50_000_000*500 = 250亿` 超过 32 位有符号上限 2^31≈21 亿会溢出成负数/错值——HOLD_MS=500 溢出成 -769804（hold_cnt 无符号永远数不到 → 长按「没反应」）、100/200ms 溢出后碰巧还是正数但间隔缩约 7 倍。改「先除后乘」`(CLK_FREQ/1000)*ms`（前提 CLK_FREQ 能被 1000 整除，50M/1000=50000 无精度损失；不能整除则用 64 位）。临界点 HOLD_MS≥43 即溢出（50M×43≈21.5 亿）。debounce 的 50M×20=10 亿没溢出所以没暴露，但 DEBOUNCE_MS 改大一样踩。定位法：写 iverilog testbench 缩短参数（#(.HOLD_MS(2))）隔离验证链路逻辑，先确认是「逻辑错」还是「参数溢出」。
- **计数器位宽要容得下计数上限（改时钟频率后必须重核对）**：分频/扫描计数器位宽必须 > 计数上限，且计数上限随时钟频率变。踩坑：seg7 动态扫描 scan_cnt 声明 [15:0]（最大 65535），验证工程 50MHz 时 SCAN_MAX=(50M/1000)*1-1=49999 够用；搬进主工程改 100MHz 后 SCAN_MAX=(100M/1000)*1-1=99999 > 65535，scan_cnt 永远数不到、scan_tick 永不产生、sel_idx 卡 0，数码管只显示第 1 个数字（data 最高 4 位）。修复：scan_cnt 加宽 [16:0]。跟 localparam 溢出同类——改频率/参数后，所有计数器位宽连同 localparam 上限一起重核对。
- **多模式按键调节必须给每个调节模块独立使能，别只靠 I_mode 的某一位「选目标」**：ae_set 的 I_mode 接 `S_mode[0]`（0=调曝光 1=调增益），但没有独立使能信号 → S_mode==2（调二值化阈值）时 S_mode[0]=0，ae_set 仍停在「调曝光」分支，KEY2/KEY3 会**同时改曝光和阈值**（曝光变化小、用户没察觉）；S_mode==3（调 Sobel 阈值）时 S_mode[0]=1，会同时改增益（增益变化影响画面亮度，更明显）。修复：ae_set 加 I_enable 输入，接 `~S_mode[1]`（只有 S_mode 0/1 才使能调曝光/增益）。教训：SW 模式扩到 2 位以上后，「用 S_mode[0] 选曝光/增益目标」和「用 S_mode 整体门控是否调节」是两回事——每加一个调节模块（曝光/增益/二值化阈值/Sobel 阈值）都要精确门控使能，否则相邻模式串台（多个调节模块同时响应同一个 KEY2/KEY3）。
- **重构带复位赋值的模块，别删 reg 声明里的初始值（= xxx）**：`reg [15:0] r_ae = 1990;` 的初始值会综合成 bitstream 上电默认值，是「复位可能执行不到」时的兜底。踩坑：ae_set 复位 I_rst=~S_pll_lock、时钟 S_24m_clk 又是同一 PLL 生成的——PLL 未锁定期间时钟不稳定、复位赋值执行不了，PLL 锁定后 I_rst 已释放，复位根本没跑；官方靠 reg 初始值 =1990/80 兜底，重构时删了它上电就变 0（数码管显示 0 而非 1990/80）。修复：目标值寄存器 r_ae_set/r_ag_set 和输出寄存器 r_ae/r_ag 都加回初始值（=1990/=80）。凡复位信号依赖 PLL 锁定、时钟又来自同一 PLL 的模块，务必保留 reg 初始值。
- **数字常量位数规则**：`28'hF` 是「24 个 0 + 4 位 F」（高位补 0，不重复填充），不是「28 位全 F」。要 28 位全 F 用复制语法 `{7{4'hF}}`（或 `{28{1'b1}}`）。踩坑：`data={28'hF,num}` 前 6 个数码管显示 0 而非熄灭，因为前 6 组是 0000（合法数字 0）不是 F。
- **位选/部分选择不能直接作用于表达式**：`(S_x - 12'd100)[3:0]` 是语法错误（位选只能作用于 net/reg 信号名，不能作用于算术表达式结果），iverilog/TD 都报 `syntax error / Malformed statement`。取表达式低 N 位用「与掩码」：`(S_x - 12'd100) & 12'hF`（低 4 位 = 模 16，效果等同 [3:0]）。踩坑：OSD 文字叠加里 `S_txt_col = (S_x_2d - TEXT_X)[3:0]` 报 syntax error，改成 `& 12'hF` 才过。
- **iverilog 不支持「无实例名例化」，TD 支持（顶层语法检查必踩）**：`key_pulse (...)`（模块例化不带实例名，直接 `模块名(端口连接);` 缺 `实例名`）这种写法 TD 能综合、但 iverilog 报 `syntax error` + `Invalid module instantiation`——不是代码错，是工具差异。同理米联客参考代码 demosaic.v 里的 `/*//input`（块注释内再套行注释）iverilog 报 `Possible nested comment`，TD 容忍。**用 iverilog 检查顶层时，报 `syntax error` 先怀疑这两类工具差异，别急着怀疑自己改的代码**：给无实例名例化临时补实例名（`key_pulse u_key_pulse (...)`）再编译，demosaic/awb 这类米联客模块用 stub 替换（awb 还依赖 divider/signal_delay 两个米联客子模块，也要桩）。判断标准：iverilog 报 `Unknown module type`（模块未定义 = 自身语法 OK，如 PLL/MIPI/DDR/FIFO 等安路硬核 IP）vs `syntax error`（真语法错）——过滤掉 `.enc.v` 加密文件报错和 `Unknown module type` 后，还冒 `syntax error` 才是真问题。
- **时序约束缺失（timing.sdc 空 + 没被 .al 引用）→ STA coverage 低 → 时序违例查不到**：用户主工程 `src/constraints_source/timing.sdc` 原本是空的（0 字节），**而且根本没被工程引用**——`.al` 里只有 `<ADC_FILE>`（pin.adc）没有 `<SDC_FILE>` 标签，所以 TD 只加载 DDR IP 自带的 ddr2.sdc，STA coverage 仅 ~25%。后果：时序报告「没有违例」（SWNS 正数）是**假象**——Clock Summary 里只列 DDR 时钟（133/533MHz），OSD 所在的 HDMI 像素时钟域（74.25MHz）根本没被时序检查。踩坑：加 anlogic_logo_rom（6400 行大 case 表，综合成几千 LUT 级联的大组合逻辑）后偶发黑屏——输出路径「坐标→算地址(乘法)→查 6400 行 case→颜色选择→O_hdmi_data」组合链延迟超像素时钟周期，时序违例随温度/电压波动，表现为偶发黑屏一下再恢复。特征：重新插拔 HDMI 线只暂时缓解、过会儿又黑屏（跟「持续黑屏」=下载配置问题区分）。诊断：读 `prj/FPGACompetition_Runs/phy_1/final_timing.rpt` 看 STA coverage 和 Clock Summary——coverage 极低且没有用户时钟 = 时序根本没查；真正确认靠**隔离验证**。
  - **补约束（已做完，照搬官方 lab_ex3 即可，别手写）**：官方 `lab_ex3_osd_SC500_720P/lab_ex3_osd/td_project/camera_to_dsi_display.sdc` 就是现成 17 行完整约束，**直接照搬**——因为用户工程的 PLL/MIPI/DDR 三个硬核 IP 例化层次跟官方 lab_ex3 完全一致（PLL 内部 wrapper hash `ph1p_phy_pll_wrapper_25a56e5ce2f9` 都相同，DDR 时钟名 ddr_clk/usr_clk 由 ddr2.sdc 的 rename_clock 生成）。约束结构 5 步：①`create_clock` 主时钟 50M（`get_ports I_sys_clk`，周期 20ns）+ MIPI 高速时钟 240M（`get_nets IO_rx_clk_pad_p`，周期 4.167ns）②`derive_clocks`（TD 特有，自动从 PLL/MIPI/DDR 硬核派生输出时钟，100M/24M/74.25M/371.25M 不用手写频率）③`rename_clock` 给派生时钟起别名（PLL 的 clkc[0]=100M/clkc[1]=24M/clkc[4]=HDMI像素74.25M/clkc[5]=HDMI串行371.25M、MIPI 的 o_fabric_div4_8_clk）④`set_clock_groups -asynchronous` 把 MIPI 域 / PLL 域 / DDR 域三组分开（跨域靠 FIFO/打拍，本就不查时序）⑤`.al` 里 `<ADC_FILE>` 后加 `<SDC_FILE>` 标签引用 `../src/constraints_source/timing.sdc`（CompileOrder=2，跟 pin.adc 同目录；**改 .al 前先关 TD**）。补完约束重跑布局布线，coverage 从 25% 涨到覆盖全逻辑域，同时**第一次冒出真违例**（大 case 表/Sobel 组合链），逐个打拍/BRAM 化修。约束只影响「检查」不影响功能——报违例画面照常出，只是工具告诉你「时序紧、长期可能不稳」。⚠️ **sdc 约束文件禁用中文注释（用户实测报错过一次，别再写）**：TD 的 sdc 解析器对中文（非 ASCII）注释会报错。约束文件（.sdc/.adc）注释一律用英文或纯 ASCII，官方 camera_to_dsi_display.sdc 就是纯无注释的。中文注释只在 .v 源文件里写（hdmi_mixer.v 大量中文注释从未报错，安全）。
- **隔离验证法（临时注释某块功能，定性定位时序/功能问题）**：注释要处理干净**三处**——①目标模块的例化 ②驱动它的 always 块 ③输出逻辑里对它的引用（三处一起改，别留半截引用，否则产生「未驱动信号」warning 干扰判断；输出逻辑直接改纯透传 `O_hdmi_data <= S_video_data_2d`）。改完用 `iverilog -g2012 -Wall -o /tmp/t.vvp hdmi_mixer.v` 单独编译验证语法（注释掉例化后 iverilog 不再需要被注释模块的源文件，报 Unknown module type 说明注释没生效或没保存）。重新综合下载看现象变化，能定性定位问题来源——黑屏消失=OSD 时序问题，还在=更底层。
- **`end else if` 链中间插入新分支，末尾不要写独立 `end`**：Verilog 的 if-else 链靠「下一个 `else if` 前的 `end`」闭合上一个分支，只有最后一个分支才用独立 `end`。在链中间插入分支（如 OSD 行定位加第 5 行「算法名」）时，新分支写成 `end else if(新条件) begin ... 内容`，**末尾不写 `end`**，让原有的 `end else if(下一行)` 的 `end` 来闭合它。踩坑：多写一个 `end` 导致后面的 `end else if` 找不到对应 begin，iverilog 报 `syntax error` + 一串 `Invalid module item / Invalid module instantiation`（连锁报错淹没真错误位置）。定位：看第一个 `syntax error` 行号，数该 always 块的 begin/end 是否配平。（execute_code 行级编辑插分支时，定位锚点要用**语义唯一**的内容——如某行特有的 `S_txt_row = S_y_2d - 12'd34;`，别用「缩进 N 空格 + end」这种结构特征，因为坐标跟踪/时序打拍/行定位多个 always 块里都有相同缩进的 end，会误插到别的块；往「当前最后一个分支」后插时，要**替换**它的独立 end、让新分支的 `end else if` 里的 end 去闭合它，别在独立 end 之后再插入，否则多一个 end 双重闭合，同样炸一串 syntax error。本次就是「缩进锚点」误插了 3 次才用 `S_y_2d - 12'd34` 这种语义锚点修对。）

## OSD 打拍流水线（确认是 OSD 时序问题后，拆关键路径）
**分级隔离**（纯透传 → 只 Logo → Logo+文字，逐级加回）能精确定位是哪个叠加块引入的问题：纯透传不黑屏 + 只 Logo 不黑屏 + 加文字才黑屏 = 输出 MUX 从「2选1」变「3选1」多了一层，把本就接近临界的 Logo 链推过临界（anlogic_logo_rom 的 6400 行 case 表本身时序够，是输出 else-if 链加层后超了）。此时**不必 BRAM 化**，先打拍流水线拆关键路径：把 Logo 叠加拆成两个块——①地址计算保持组合逻辑（`always @(*)` 算 S_logo_addr）②命中结果打拍（`always @(posedge)` 寄存 S_osd_hit/S_osd_color），数据多打一拍 S_video_data_3d，输出改用打拍后的 S_osd_hit + S_video_data_3d。对齐：第 N 拍数据 → 第 N+2 拍坐标 S_x_2d 算 Logo → 第 N+3 拍 S_osd_hit 与 S_video_data_3d 同属「第 N 拍那个像素」。**多驱动坑（重构/拆块必踩）**：拆块时旧的组合逻辑 always @(*) 块必须删掉，否则 S_logo_addr/S_osd_hit/S_osd_color 被旧块+新块同时驱动（多驱动，TD 报错/行为不确定）；iverilog 对多驱动很宽松（退出码 0 不报错），别拿 iverilog 编译通过当「没多驱动」的依据，要肉眼确认每个信号只有一个 always 块驱动。

**打拍后 de/vsync/hsync 必须跟数据一起补拍（错位 1 拍 → 黑屏）**：打拍流水线把数据打到 3 拍（S_video_data_3d，为跟 S_osd_hit 对齐），但 de/vsync/hsync 只打了 2 拍没跟着补 → 同步信号和数据错位 1 拍，HDMI 输出时 de 有效但数据是错位值，画面黑屏（现象「没有摄像头画面了，只剩 Logo 和文字」）。修复：de/vsync/hsync 也补到 3 拍（加 S_video_de_3d/S_video_vsync_3d/S_video_hsync_3d，O_hdmi_de/vsync/hsync 改接 3 拍），让 vsync/hsync/de/data 全部同拍。这个错位在打拍当天就埋下，之前「只有 Logo」「单行文字」时影响小没暴露（横向错位 1 像素肉眼难辨），后面才炸成黑屏——**改任何打拍流水线都要同步核对「数据多打几拍，同步信号（de/vsync/hsync）就多打几拍」**，不能只补数据不补同步。
- **多信号/参数联动改动必漏改（改名/改位宽/改参数时，改完 grep 核对所有引用点）**：一处改动牵动多处时，用户反复出现「改了一半没改全」。典型：①信号位宽改了（S_txt_char [3:0]→[7:0]）但旧的 [3:0] 声明没删 → 重复定义；②信号改名（S_txt_bits→S_cn_bits/S_char_bits）删了声明但例化端口、打拍赋值还引用旧名 → 未定义信号；③例化端口没同步更新（osd_cn_char 的 .I_idx 还接 8 位 S_txt_char 而非 S_txt_char[3:0]、.O_row_bits 还接已删的 S_txt_bits）；④case 内容改了（11 字符→15 字符）但字符数判断 `11*CHAR_W`、TEXT_X 没跟着改。改完别只看「编译过了」，iverilog 报的 syntax error / 重复定义 / 未定义信号就是漏改清单逐个修；或 grep 该信号名把所有引用点过一遍。这类笔误还有 `f(` 少打 `i`（if 写错）、`end` 数错（实际是别的语法错，先看报错行号定位）。

## 时序违例诊断（读 final_timing.rpt + 跨时钟域打两拍修复）

补完 timing.sdc 后重跑布局布线，coverage 涨到 ~96%，同时**第一次冒出真违例**。读报告 `prj/FPGACompetition_Runs/phy_1/final_timing.rpt` 判断：

- **SWNS = Setup Worst Negative Slack（最坏建立时间负余量），负值 = 数据「迟到」不是「早到」**。setup 检查数据必须在时钟采样沿前稳定；SWNS 负 = 数据到达时间 > 要求时间（报告里 Arrival − Required = 负 slack，如 557.128 − 548.321 = −8.807ns）。用户会问「是不是数据早到了」，纠正：是迟到。报告顶部 `Timing Status` 有 SWNS/STNS/HWNS/HTNS（S=setup、H=hold、W=worst、T=total）；`Clock Summary` 每个时钟一行，哪行 SWNS 负值 = 哪个时钟域违例（本工程只有 clk2 HDMI_PIXEL_CLK 负）。
- **两类违例分开看**（报告按 `Path Group: X -> Y` 分组）：
  - **跨域违例（伪违例）**：Begin Point 和 End Point 时钟不同（如 `pll_clk_24m -> HDMI_PIXEL_CLK`）。根因 = 慢时钟域信号跨到快时钟域没打拍同步。工具按最坏情况（两个非整数倍频时钟相邻边沿差，budget 极小，如 24M vs 75M 最坏 0.653ns）检查，数据路径 9.2ns 远超预算 → 报 −8.8ns。**修复不是改约束，是接收模块入口打两拍**：打拍后路径起点变成本域寄存器、budget 恢复周期值（13.333ns），违例消失、设计真正健壮。
  - **同域违例（真违例）**：Begin/End 同一时钟域，组合逻辑太深（如 15 级、数据路径 13.468ns 略超 13.333ns 周期、含 DSP 乘法器 mult0）。修复 = 打拍流水线拆关键路径（见「OSD 打拍流水线」条）。
- **打两拍修复套路**：接收模块（75M 域）给跨域输入声明 `_1d/_2d` 寄存器 + always 打两拍 + 下游全部改用 `_2d`。先确认哪些输入已打过拍（本工程 hdmi_mixer 的 I_algo_mode/I_auto_mode 早已打，I_ae/I_ag/I_threshold/I_sobel_threshold/I_target 五个漏了——都在 bin2bcd 裸用），只补漏的。多 bit 慢速配置信号（曝光/增益/阈值，按键级变化）打两拍即可（显示用途，采错最多一帧 OSD 数字闪一下，不致命但影响答辩/现场稳定性）。补完用 `iverilog -g2012 -o /tmp/check hdmi_mixer.v anlogic_logo_rom.v osd_cn_char.v osd_char_lib.v key/bin2bcd.v` 单独语法检查，再让用户重编译看 SWNS 转正。
